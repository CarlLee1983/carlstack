Netflix 在 2023 年第四季股東信公布的付費會員數是約 2.6 億（[Q4 2023 股東信](https://www.sec.gov/Archives/edgar/data/1065280/000106528024000029/ex991_q423.htm)），這些人的電視、串流棒、手機與瀏覽器都需要及時收到狀態更新。Netflix 公開過的做法有兩條線：

1. **Zuul Push（後來稱 Pushy）**：在邊緣維護 WebSocket / SSE 長連線，取代定時輪詢（Polling）。2018 年的演講說是數百萬條常駐連線（[QCon New York 2018](https://www.infoq.com/presentations/neflix-push-messaging-scale/)），2024 年的文章說已成長到數億條（[Pushy to the Limit](https://netflixtechblog.com/pushy-to-the-limit-evolving-netflixs-websocket-proxy-for-the-future-b468bc0ff658)）。
2. **EVCache**：以 Memcached 為基礎、跨 AWS 可用區（AZ）的分散式記憶體快取（[EVCache 官方 Wiki](https://github.com/Netflix/EVCache/wiki)）。

下面的內容以這些一手來源為準，每項說法都標明來源與年份。XFetch 不是 Netflix 公開過的做法，第三節把它當成可以搭配快取使用的通用技巧來講。

## 一、Zuul Push：為電視與串流裝置維護持久連線

iOS 與 Android 走 APNs 與 FCM；電視、串流裝置與瀏覽器則改用 Netflix 自建的 Zuul Push（[RENO 文章](https://netflixtechblog.com/rapid-event-notification-system-at-netflix-6deb1d2b57d1)，2022）。Netflix 的說法是，早期電視端 UI 會每隔數秒輪詢一次後端服務，長連線讓它不必再輪詢（[Pushy to the Limit](https://netflixtechblog.com/pushy-to-the-limit-evolving-netflixs-websocket-proxy-for-the-future-b468bc0ff658)，2024）。

### 1. 消除輪詢的常駐連線

裝置建立 **WebSocket** 或 **Server-Sent Events（SSE）** 長連線。2018 年投影片的架構圖標的就是 WebSockets / SSE（[投影片](https://archive.qconnewyork.com/system/files/presentation-slides/final_qcon_ny_-_zuul_push_presentation.pdf)），Zuul 原始碼的推播協定也只有這兩種。連線建立後，伺服器可以在事件發生時主動推資料給裝置。

### 2. Push Registry 與派送流程

後端要通知某個裝置，得先知道它連在哪一台 Zuul Push 節點上。2018 年的演講說明了這條路：

- **註冊**：裝置連上後，連線資訊寫入 Push Registry，當時的後端儲存是 Redis（透過 Dynomite，[投影片](https://archive.qconnewyork.com/system/files/presentation-slides/final_qcon_ny_-_zuul_push_presentation.pdf)）。2024 年的[文章](https://netflixtechblog.com/pushy-to-the-limit-evolving-netflixs-websocket-proxy-for-the-future-b468bc0ff658)提到後來遷移到 KeyValue。
- **派送**：發送端透過 Push Library 把訊息丟進 Kafka 佇列，由 Message Processor 查 Registry 找到目標節點，再把訊息投遞過去。Kafka 讓發送端與接收端解耦，發送端是 fire and forget。
- **2024 年新增的 direct push**（[Pushy 文章](https://netflixtechblog.com/pushy-to-the-limit-evolving-netflixs-websocket-proxy-for-the-future-b468bc0ff658)）：Push Library 直接查 Registry 後送出，不經佇列。

RENO（Rapid Event Notification System）是另一層：它接收各種事件，只把通知送給目前在線的裝置，判斷在線與否靠的是 Zuul 維護的 registry。RENO 文章列出的事件類型包括 Viewing Activity、Personalized Recommendation Refresh、Membership Plan Changes、Member "My List" Updates、Member Profile Changes 與 System Diagnostic Signals。RENO 也有依事件優先級排序的佇列，重複的事件會合併（[RENO 文章](https://netflixtechblog.com/rapid-event-notification-system-at-netflix-6deb1d2b57d1)，2022）。

### 3. Goldilocks 擴展策略

單機維持 100 萬條連線有個風險：該機崩潰時，100 萬台裝置會同時重連，形成驚群（Thundering Herd）。Netflix 的原話是「We could have a million connections per instance, but a down node would lead to a thundering herd of a million devices reconnecting at the same time」（[Pushy to the Limit](https://netflixtechblog.com/pushy-to-the-limit-evolving-netflixs-websocket-proxy-for-the-future-b468bc0ff658)，2024）。

- 2018 年的 **Goldilocks strategy** 投影片寫的是「Optimize for cost, NOT instance count」與「More number of smaller servers >> few BIG servers」。Goldilocks 要的是大小剛好、成本最佳，不是越小越好。2024 年的[文章](https://netflixtechblog.com/pushy-to-the-limit-evolving-netflixs-websocket-proxy-for-the-future-b468bc0ff658)也說，Netflix 後來把每個節點的目標連線數從約 60,000 提高到約 200,000。
- **依連線數縮放**：Auto-Scaling 不看 CPU 或 RPS，而是看每台機器的開放連線數。2018 年投影片的說法是「Auto-scale on number of open connections per box」；2024 年的文章說，目前連線數超出目標越多，一次擴增的實例越多。

## 二、EVCache：跨可用區的記憶體快取

**EVCache（Ephemeral Volatile Cache）** 是以 Memcached 與 spymemcached 為基礎的快取方案（[EVCache README](https://github.com/Netflix/EVCache)）。依官方 Wiki，它的跨 AZ 做法是：

- **寫入所有 AZ，只讀本地 AZ**：同一個 Region 的每個 AZ 都有一份資料，寫入送到各個 AZ，用戶端的讀取固定送到同一個 zone，Wiki 說這樣可以改善延遲。Wiki 沒有說寫入是同步還是非同步，也沒有給出延遲數字。
- **客戶端路由與容錯**：同一個 zone 內以 Ketama 一致性雜湊分片。啟用 zone fallback 時，本地節點無法回應就改讀其他 zone。

## 三、通用技巧：用 XFetch 降低快取擊穿

這一節不是 Netflix 公開過的做法。我查過 Netflix 的部落格、2018 年的演講與 EVCache 原始碼，都沒有提到 XFetch。它出自 Vattani、Chierichetti 與 Lowenstein 的論文〈[Optimal Probabilistic Cache Stampede Prevention](https://www.vldb.org/pvldb/vol8/p886-vattani.pdf)〉（VLDB，2015），可以和 EVCache 這類快取搭配使用。

快取擊穿（Cache Stampede）發生在熱門項目過期的那一刻：假設大量請求同時發現快取是空的，一起去後端重新計算，資料庫就會被壓垮。傳統做法是加分散式互斥鎖（Mutex），但鎖會增加延遲。

XFetch 的做法是讓每個讀取者在快取過期前，各自用機率決定要不要提早重算。論文的判斷式如下：

```text
now - delta * beta * ln(rand()) >= expiry
```

- `delta`：重新計算該快取資料所需的耗時。
- `beta`：調整提早程度的係數，大於 0。
- `expiry`：快取的過期時間點。
- `rand()`：每次讀取各自抽一個 (0, 1] 的隨機數。

條件成立的讀取者就去重算並寫回。離過期越近，條件成立的機率越高，所以通常在過期前就有人重算完。這個做法降低同時重算的機率，不保證只有一個請求重算，也不能徹底消除擊穿。

## 四、Slow-Fast 訊息策略

Slow-Fast 出自 Netflix 的個人化通知系統，介紹文章發表於 2026 年 6 月（[Thinking Fast & Slow for a Personalized Notification System](https://medium.com/netflix-techblog/thinking-fast-slow-for-a-personalized-notification-system-4d89b26525cd)）。它管的是 push、email 等通知，和第一節的 RENO 的跨裝置事件同步是不同的系統，我沒有找到任何來源把兩者串在一起。

- **Slow Policy**：為每位會員規劃一段期間（文章以每週為例）內的訊息節奏，包括 push 與 email 的頻率，並考慮會員疲勞或選擇退訂的可能性。
- **Fast Policy**：每天出現通知時機時，負責挑出當下最相關的訊息。

## 五、系統架構維度對比

| 架構面向         | 傳統輪詢 / 單一快取方案         | Netflix 公開過的做法                                |
| :--------------- | :------------------------------ | :-------------------------------------------------- |
| **推播通訊機制** | 定時 HTTP Polling（資源浪費大） | **Zuul Push (WebSocket/SSE)** 長連線                |
| **連線故障防護** | 大節點斷線引發重連雪崩          | **Goldilocks 策略**（大量較小的實例，依連線數縮放） |
| **跨可用區容災** | 單一快取節點故障穿透資料庫      | **EVCache 寫入各 AZ、讀取本地 AZ**，可 fallback     |
