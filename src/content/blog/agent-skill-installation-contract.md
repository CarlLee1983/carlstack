每週兩次從同一組公開文件整理摘要，未必需要接上已登入的瀏覽器。能取得正文、保留來源 URL，並在讀不到時回報失敗的工具，就可能足以完成工作。採用 Skill 時，這種任務差異應該直接決定它能讀什麼、能寫什麼，以及用什麼結果驗收。

這篇的起點是 [@painn_x 的〈19 Skills I Would Install on a Fresh Hermes Setup〉](https://x.com/painn_x/status/2095060006127149480)。2026 年 11 月 5 日查核時，X 回傳 403，無法讀取貼文正文，因此保留來源連結，但不把原稿轉述的 19 項內容、Day 1 排序與安全提醒當成已核實資訊。下列工具描述依各專案當日的 README 核對，採用順序與驗收門檻則是工程建議，沒有安裝或測試這些工具。

## Skill 要求的工具，決定了需要檢查的權限

[Agent Skills 格式說明](https://agentskills.io/home)把 Skill 定義為含有 `SKILL.md` 的資料夾，也可以附帶腳本、參考資料與範本。指令檔本身描述工作方法，執行時用到的瀏覽器、檔案系統或外部 App，才決定它會接觸哪些資料與操作。檢查安裝內容時，需要把兩者一起看。

幾種常見能力各有不同的風險：

- 網路研究與內容擷取會接觸外部來源、登入狀態與保存下來的資料。來源過時或未獲授權，摘要再完整也可能導向錯誤判斷。
- 真實瀏覽器自動化會使用已登入帳號、下載與表單。一次送出操作，就可能代表使用者對外採取行動。
- Repository memory 會保存專案內容與跨 session 摘要。舊決策或敏感資訊若被帶回不相關任務，會污染下一輪 context。
- 工程流程與 review 可能執行測試、版控或發布命令。工作目錄錯誤、變更尚未驗證，都可能讓副作用落在錯誤的 repository。
- 外部 App 整合會增加 OAuth 權限、觸發器與第三方資料存取。採用時就需要知道哪些權限可回收，以及停用工具後還留下什麼。

[Browser Harness](https://github.com/browser-use/browser-harness)的 README 明寫，它能透過 CDP 操作使用者已登入的 Chrome，開頁、點擊、輸入與下載。[Agent-Reach](https://github.com/Panniantong/Agent-Reach)則整合多個平台的讀取工具，並按來源選擇工具。當日 README 也說明，部分登入平台會把既有 Chrome 的網站登入狀態複製到專用瀏覽器。這兩項描述足以提醒導入者檢查帳號範圍，不能因為任務叫作「研究」，就預設它只會讀公開網頁。

## 把用途、權限、驗收與移除條件寫在一起

採用紀錄可以很短，只要能回答四件事：解決什麼問題、允許哪些操作、怎麼驗收、何時移除。下面的 YAML 把第一件事拆成 `pain` 與 `capability`，所以共有五個欄位。這是公開文件擷取的範例，裡面的頻率與期限都是可調整的採用條件。

```yaml
pain: 每週兩次需要從同一組公開文件擷取可追溯的摘要
capability: 將網址轉成正文 Markdown，保留來源 URL
boundary:
  reads: 公開網頁
  writes: 無
  credentials: 不需要
evidence:
  - 同一篇文件可重跑，且能連回原始來源
  - 失敗時回報無法取得，不用摘要補猜
remove_when: 連續四週未使用，或既有工具已能產出同樣證據
```

唯讀公開文件，可以先用既有的 web reader 或受限擷取工具。需要網站互動，才評估專用瀏覽器 profile，並列出哪些送出資料的步驟必須核准。需要跨 session 記憶，則補上可保存的決策、來源、有效期限與刪除方式。這些需求不宜共用一份含糊的「research／memory 權限」。

驗收也要包含失敗路徑。用一個無法取得的來源檢查它會不會承認缺資料，用一個未授權的寫入要求檢查它會不會停下來。**讀不到必要來源、沒有寫入授權，或缺少可信的驗證環境時，Agent 應停止相關操作並回報缺口。**

## 依副作用逐步試用

對工程團隊，我會按新增的副作用安排試用，而不按清單的功能分類一次裝完：

1. 唯讀、可重跑的能力，例如清理網頁正文、取得公開文件或產生逐字稿。保留原始 URL，用兩個真實任務檢查輸出品質。
2. 本地、可驗證的能力，例如對 repository 執行格式化、測試或 review。沿用專案既有命令與規範，確認執行目錄和輸出位置。
3. 持久狀態，例如記憶與任務看板。保存有來源與有效期限的決策，避免直接收進整段對話或機密。
4. 可代表使用者行動的能力，例如瀏覽器控制、App 整合、排程與安全工具。設定最小 scope，將發信、發文、付款、刪除與權限變更的核准條件寫清楚。

安裝前讀過腳本、分離 browser profile、避免把 secrets 放進 prompt 或 log，都是這個順序需要搭配的檢查。Local-first 工具可以優先評估，資料是否外送仍要看實際使用的服務與設定。

兩個任務都成功，只提供初步採用證據。若後續要從唯讀擴大到寫入、保存記憶或操作外部帳號，還要重新確認新增的資料範圍、權限與失敗後的復原方式，另行取得授權。

## 重複的工程流程，要能說出各自負責什麼

[Addy Osmani 的 agent-skills](https://github.com/addyosmani/agent-skills)涵蓋規格、規劃、實作、測試、review 與發布。[Matt Pocock skills](https://github.com/mattpocock/skills)也有需求釐清、TDD、除錯與 review 等可組合流程。任務看板與多 Agent 編排再加入後，需要確認誰決定任務完成、誰保留狀態，以及哪份規則優先。

例如，repository 已有清楚的 `test`、`check` 與 review 流程，可以先沿用它們，用一個小任務檢查缺口。若問題是下一次 session 找不到先前決策，應評估記憶的保存與取回方式，增加一套工程生命週期流程未必能解決。本站的 [Harness Engineering](/blog/harness-engineering-for-reliable-agents/) 已把 context、state 與 memory 分開討論：記憶寫入後，仍須依目前任務判斷是否取回。

能力重複時，我會優先移除其中一份規則。只有兩套工具各自提供無法取代的證據或權限範圍，才保留兩者，並寫清楚分工。為重複功能額外維護路由、優先序與同步機制，也是一項成本。

## 每月停用一個 Skill，觀察同一類工作

每月挑一個 Skill 暫時停用，重跑同一類真實工作，比較交付時間、失敗率、人工介入次數與證據品質。若沒有可觀察的退步，就移除它。有退步，則把具體差異寫回採用紀錄，例如少了哪項可追溯輸出，或多了哪一步人工處理。

[Agent Skill 的指令可以精簡，方法與驗證條件要留下](/blog/agent-methods-over-skill-bulk/)討論過同樣的取捨：重複描述通用能力的文字可以刪，專案的資料範圍、權限、證據與停止規則需要保留。

下一個候選 Skill，就拿本週反覆卡住的任務填這份紀錄。先做兩次可重跑的試用，再用結果決定保留或移除。任何擴權另外審查。
