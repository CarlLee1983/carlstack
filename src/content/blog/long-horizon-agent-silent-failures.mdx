Agent 回報還在工作，檔案卻停在昨天，背景記憶沒有寫入，API 帳單還在增加。這幾種失敗未必會讓主程序拋出例外；只看最後一段回覆，很難判斷任務究竟完成了多少。

原稿從 [Google Cloud Tech 的 Long Horizon 貼文](https://x.com/googlecloudtech/status/2090248297214525569)與 [ADK Long Horizon sample](https://github.com/google/adk-samples/tree/main/core/python/long-horizon-harness)整理出五個檢查方向。2026-11-05 修訂時，這兩個頁面未能重新取得完整內容，因此不沿用原稿中的命中率、prompt 字元數與實作預設參數。以下是依官方 API、Python 與雲端文件修正的工程檢查方法；故障注入與停止規則是這裡提出的設計建議。

## Stable prefix：量測快取，也量測整個任務的花費

把固定的 instructions 與工具定義放前面、會變動的記憶與計數器放後面，有助於保留可重用的 prompt 前綴。[Gemini caching 文件](https://ai.google.dev/gemini-api/docs/caching)建議共用內容放在前段，並在短時間內送出相似前綴的請求。實際能否命中仍受模型、API、最低 token 數與快取機制影響，無法用「第二輪必須命中」當通用斷言。

測試時固定模型、API 版本、工具定義與共同內容，連續送出一組請求，再改變前綴做對照。逐次記錄輸入、輸出與快取 token，連同延遲和估算費用一起比較。命中為零時，先檢查測試是否符合該模型的條件，再檢查 prompt 排列。

欄位也要跟呼叫的 API 對上。Interactions API 文件使用 `usage.total_cached_tokens`；Python 的 `generate_content` 回應則在 `usage_metadata.cached_content_token_count` 提供快取 token 數，可對照 [token 文件](https://ai.google.dev/gemini-api/docs/generate-content/tokens)。不要把其中一種結構寫成所有 SDK 都適用的讀法。

快取命中率只能解釋部分成本。長任務還需要記錄重試、工具與背景 worker 的花費，並由模型外的控制程式執行預算限制。下一次呼叫前先保留預估額度，再以實際用量結算，能降低多個 worker 同時超支的風險。若供應商延後回報用量，預算報表也要標示尚未結算的部分。

## Background learning：強參考保不住已經關閉的行程

把記憶整理放到背景，可以縮短使用者等待回覆的時間，但會多出一項需要追蹤的工作。[Python asyncio 文件](https://docs.python.org/3/library/asyncio-task.html#asyncio.create_task)要求保留 task 的強參考，避免 task 在完成前被垃圾回收。這只處理行程內的生命週期；行程被終止時，強參考與 shutdown drain 都無法保證寫入完成。

需要跨重啟恢復的工作，應先持久記錄 job ID、輸入版本、狀態與可重試條件，再交給 worker。工作完成後寫入結果版本；重跑同一個 job ID 時，避免把同一筆記憶重複加入。記憶可能過期或寫入失敗，讀取端也要看得見版本與最後成功時間。

可做兩種故障注入：

- 正常取消 worker，檢查是否留下取消原因，以及尚未完成的寫入。
- 直接終止行程，重新啟動後檢查過期的 lease 或 heartbeat。系統應能把它辨識為失聯、重新排程或交由人工處理，不能要求已死掉的 worker 自己補寫 `failed`。

背景 worker 只取得該任務需要的記憶讀寫權限。使用者範圍可以沿用，權限範圍不必照搬主 agent。

## Persistent workspace：恢復檔案之後，還要核對外部副作用

重啟後找得到檔案，不代表整個任務已恢復。工具版本、checkpoint、資料格式與未完成步驟都可能不一致。[Google Developers 的 ADK 教程](https://developers.googleblog.com/build-long-running-ai-agents-that-pause-resume-and-never-lose-context-with-adk/)把持久狀態與暫停、恢復放進長任務設計；檔案保存與任務狀態仍需要各自驗證。

一個小型恢復測試可以先寫入產物雜湊、環境版本與 checkpoint，重啟後重新連接同一個使用者的工作區，再比對三者。另一個使用者必須無法讀到這些檔案。若環境是重新建置，也要驗證依賴能依版本清單還原，而非假設安裝過的工具會永遠留著。

最容易漏掉的是外部副作用。worker 可能已送出請求，卻在寫入 checkpoint 前失聯。恢復後不能直接再送一次；先以操作 ID 查詢外部結果，或在支援的服務使用 idempotency key。若無法確認，將結果標成 `unknown`，保留核對所需的識別碼。這個狀態必須阻擋自動重做有風險的操作。

## Explicit failure：等待批准與執行結束要分開

子任務的文字摘要可以幫人閱讀，父任務的控制流程則需要結構化狀態。`pending`、`running`、`waiting_approval` 是尚未結束的狀態；`completed`、`failed`、`cancelled`、`timed_out` 才表示該次執行已結束。任務是否達成驗收條件，還要另行判斷。

下面是結果格式示意，並非特定框架的 schema：

```json
{
  "job_id": "child-17",
  "attempt": 2,
  "execution_state": "timed_out",
  "acceptance_state": "not_verified",
  "tests_run": false,
  "external_effect_state": "unknown",
  "next_action": "reconcile_before_retry"
}
```

控制程式應依欄位判斷能否繼續，摘要再補上「子任務逾時，尚未執行測試」。單靠在 prompt 寫 `INCOMPLETE`，仍無法保證父 agent 不會誤報成功。即使子任務填了 `completed`，也要核對對應的產物版本與驗收結果。

故障注入至少涵蓋逾時、步數耗盡、等待批准與結果遺失。測試要確認父任務沒有產生完成紀錄，也沒有在批准到達前執行受限動作。每次嘗試的步數上限之外，還需要整個任務的累計預算，否則反覆開新 session 就能繼續消耗資源。

## Guard chain：觀察政策決策，也驗證實際連線

只比對 `169.254.169.254` 字串，不能可靠限制網路目的地。不同 URL 解析器接受的地址表示法不同，DNS、redirect 與 proxy 也會改變實際連線位置。輸入檢查可以提早拒絕明確風險，執行時仍要由 sandbox、host firewall 或 egress proxy 限制實際流量。

[GCP metadata 文件](https://docs.cloud.google.com/compute/docs/metadata/overview)列出 metadata DNS 名稱、IPv4，以及適用於 IPv6-only VM 的原生 IPv6 端點；文件也要求隔離不應取得 metadata 的程序。因此，測試清單要涵蓋平台實際使用的端點，不能只測 IPv4 的字串變形。

安全的 probe 應在受控測試環境，用假的 metadata 服務與無敏感資料的請求驗證拒絕結果。測試地址變形、redirect、DNS 回覆改變，以及檢查後到連線前目的地變動的情況。測試成功的證據應包括連線確實被拒絕，而不只有 agent 說「不允許」。

批准紀錄則要對上使用者、動作、目的地、資料範圍與有效期限。重啟或重試時重新核對，目標改變就不能沿用原批准。模型提出的 allow／ask／deny 建議可以進入政策流程，但不能自行放寬模型外的限制。

Audit 保留規則版本、決策、操作 ID 與必要的目的地資訊。完整 argv、URL query、request body、環境變數與憑證不應直接寫入一般紀錄。先縮減欄位，再遮罩敏感值，同時限制紀錄的讀取權限與保留時間。

## 從一個已經遇過的失敗開始

挑一個可在測試環境重現的問題，寫清楚觸發條件、應觀察到的狀態與停止規則。例如子任務逾時後，父任務只能回報未完成；若外部操作結果未知，恢復流程必須先核對結果，不能直接重送。

讓 probe 讀取模型之外的紀錄，再把失敗案例留進回歸測試。只有當觀測結果顯示缺少控制時，才補上對應的限制。
