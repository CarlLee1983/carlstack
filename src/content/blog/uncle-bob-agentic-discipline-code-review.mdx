Agent 寫完功能，單元測試與驗收測試都通過，維護者仍可能答不出資料在哪裡被修改、權限在哪裡檢查。這時候再加一個 review agent，未必能補上對系統的理解。

Robert C. Martin 的 Agentic Discipline 值得討論，因為它嘗試把更多審查放在規格與可重跑的證據上。2026-11-05 修訂依據是 Clean Coders 的公開課程介紹與 Warrant 規則，未把付費影片視為已觀看，也不以二手轉述證明 Martin 完全停止閱讀程式碼。原稿引用的社群回覆、日期與票數，不再用來支撐技術結論。

## 高層規格增加了一個可審查的對象

[Agentic Discipline Part 2](https://cleancoders.com/episode/agentic-discipline-2)的公開介紹把 source 定義成足以據之建構系統的高層文件，並描述以同一份文件建立五種語言與平台實作的示範。這是課程對開發方式的主張，公開介紹沒有提供可量化的證據，證明所有專案都能因此省去人工程式審查。

這個方向可以用在需求審查：功能開始前，先確認業務規則、錯誤情境與不能改變的限制；完成後，逐條對照外部可觀察結果。我的判斷是，這能改善審查順序，但高風險變更仍需要有人讀懂實作。規格未提到跨租戶存取時，忠實實作規格的程式仍可能有權限漏洞。

## 六種角色分別留下什麼證據

[Part 6](https://cleancoders.com/episode/agentic-discipline-6)公開介紹列出 Swarm Forge 的六種角色，並說明各自在隔離的 Git worktree 工作。流程依序涵蓋：

1. Specifier 把任務整理成 Gherkin 驗收情境及手動 UI QA 程序。
2. Coder 實作功能、單元測試與驗收測試框架，通過 Gherkin 情境後交接。
3. Cleaner 依 DRY 與 CRAP 等品質檢查重構程式與測試。
4. Architect 檢查模組與依賴，補上 property-based tests。
5. Hardener 執行語言層與 Gherkin 層的 mutation testing。
6. QA 將原先的 UI 程序轉成自動操作並驗證結果。

公開介紹支持這些角色與順序，沒有交代每一種合併衝突或測試失敗的處理方式。實際採用時，我會要求每份交接紀錄帶上 commit、執行環境、命令、結果與未解問題，接手者在相同版本上重跑必要檢查。這是對工作流的補充設計。

隔離的 worktree 可以分開檔案修改，卻不會自動讓六個角色得到不同的判斷依據。若它們都沿用同一份有缺漏的規格或同一組錯誤 mock，六次通過仍可能漏掉同一個問題。

## 獨立審查要有不同的證據來源

review agent 可以先讀核准的需求與 diff，再自行選擇要檢查的反例，避免只跟著作者的完成摘要走。驗收條件應由人確認，測試結果應由工具產生，review 的問題則要能回到程式與執行結果核對。

例如一個訂單 API 改動，正常使用者成功更新訂單的測試通過後，仍要檢查另一個租戶是否能用訂單 ID 存取同一筆資料。這需要追查身份、查詢條件與授權邏輯，不能只看覆蓋率。再增加一種模型或一個角色，可以多找反例，但無法單憑角色數量證明審查已獨立。

人工 review 的深度可以依風險調整。文案、局部樣式與既有模式的簡單變更，通常能用較小的審查範圍處理。授權、資料遷移、併發控制與不可逆操作，則需要熟悉系統的人讀相關實作、失敗路徑與回復方式。若 PR 大到無法合理檢查，拆成可獨立驗證的變更，比單純增加 reviewer 更直接。

## Coverage 與 mutation score 各自回答有限的問題

覆蓋率顯示哪些程式在測試中被執行，無法單獨證明斷言正確。mutation testing 則修改程式中的某些行為，再觀察測試能否偵測。依 [PIT 的基本概念文件](https://pitest.org/quickstart/basic_concepts/)，結果還包含存活、未覆蓋、逾時與執行錯誤等情況，而且有些 mutation 與原程式行為等價。

因此，mutation score 需要連同工具、operator、排除規則與測試範圍閱讀。存活的 mutant 應逐項分類，不能一律解讀成測試缺陷，也不能為了達標直接排除。沒有生成的錯誤、沒寫進規格的業務限制，以及測試環境沒有模擬的競態，都可能不在分數涵蓋的範圍內。

CRAP 或其他品質指標可以協助挑出需要追查的區域。分數變好之後，仍要確認重構有沒有改變介面、資料流與操作成本。**若關鍵路徑沒有人能解釋，或驗收證據對不上目前版本，就先停止合併。**

## 用 Warrant 約束一個 Story 的範圍

原稿在 2026-10-02 已將採用工具改為 [Warrant](https://github.com/CarlLee1983/Warrant)。它的[規則區塊](https://github.com/CarlLee1983/Warrant/blob/main/plugin/skills/warrant/agents-block.md)要求以人類核准的 Story 限定工作，執行儲存庫宣告的驗證命令，並逐條對照驗收證據。若命令沒有通過或任一條件缺少通過觀察，只能回報部分完成。這套規則本身不指定六角色流程。

下面是搭配角色分工的工作流示意，並非 Warrant 的可執行設定檔：

```yaml
story: "specs/stories/<slug>.md：Goal、Out of Scope、Acceptance Criteria"
source: "人類核准的 Story、業務規則與限制"
roles:
  specifier: "補齊可重跑情境與 QA 程序"
  coder: "實作功能與測試"
  cleaner: "依具體品質問題重構"
  architect: "檢查邊界、依賴與不變條件"
  hardener: "執行 repository 支援的 mutation/property checks"
  qa: "依原始程序驗證可觀察行為"
canonical_gate: "AGENTS.md 宣告的唯一驗證命令，例如 make verify"
completion_report: "逐條驗收證據、跳過或受阻的檢查、殘餘風險"
human_gate: "確認產品意圖與高風險實作，決定是否合併"
```

角色可以合併或省略，驗收證據必須保留。agent 不得為了過關放寬需求、跳過失敗測試或擴大範圍。驗證命令若尚未宣告，應停止並請維護者補上，不能自行挑幾個比較容易通過的檢查代替。

規則文字的執行仍依賴採用端。讓 CI 跑相同命令、限制誰能修改驗收條件，並檢查完成回報與實際產物，才能知道規則有沒有落實。

## 從一個能回復的 Story 試做

選一個範圍小、失敗後能回復的變更，先留下人類核准的規則、錯誤情境與驗證命令。完成後，要求回報逐條驗收結果、目前 commit、跳過的檢查與殘餘風險，再請 reviewer 沿一條關鍵路徑追查實作。

如果 reviewer 發現規格漏了權限情境，就回到需求與測試補足它；如果只是重複做機械檢查，再考慮交給工具或 specialist。下一輪增加什麼檢查，應由這次漏掉的問題決定。
