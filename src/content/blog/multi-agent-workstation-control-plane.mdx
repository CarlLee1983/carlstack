當五個 Coding Agents 同時完成工作，注意力很容易成為新的瓶頸：哪一個結果要先看？哪一個只是 process 結束，哪一個真的通過驗收？如果兩個 Agent 同時改到同一個 checkout，又由誰處理衝突？

原稿以 [David Ondrej 的〈Agentic Engineering Setup (after 2,000+ hours)〉](https://x.com/davidondrej1/status/2094424967345496191)為起點，整理 bb、cmux、Ghostty、Herdr、優先級工具、遠端 VPS、skills、worktrees 與 production database 讀取等做法。2026-11-05 重查時，X 原文回傳 403，無法重新核對全文；這份工具清單與下文對 Corral 的描述保留為原稿的歷史摘要，不作為目前產品能力的依據。

可操作的建議改以官方文件查核：Herdr TUI repository master `ee5bfb5`、bb main `5758b8c`，以及 Git、OpenAI、PostgreSQL 文件。沒有實測這套完整工作台的效能，也不以「2,000 小時」推導工具排名。接下來要處理的是 review 排序、平行寫入、session 復原與執行權限。

## 看得到 Agent，不等於擁有控制平面

終端分頁解決的是畫面配置。多 Agent 工作台還需要回答工作目前在哪裡，以及什麼事件值得打斷人。

[Herdr](https://github.com/herdrdev/herdr) TUI 提供 workspace、detach、reattach 與遠端連接。[原生回報狀態](https://herdr.dev/tui/docs/agents/)是 `idle`、`working`、`blocked`；整合有回報狀態時採用該回報，否則對支援的 agent 讀取畫面。resume 整合不等於 state report，安裝 integration 也不保證原生狀態回報。sidebar 的 `done` 是待查看的完成提示，會留到使用者查看，不能拿來判定 process 已退出。

[bb](https://github.com/get-bb/bb)提供 desktop、web、CLI 與 HTTP API 等操作介面。選擇遠端配置時要讀 README 的安全限制：development server API 沒有驗證，且能執行命令、讀取檔案。應只放在可信任網路，並以防火牆限制存取；不能直接把它當成可公開連線的遠端工作台。

工作流可以另設以下狀態，不必模仿某個 runtime 的欄位：

- `running`：任務仍在執行，附 session 與最近一次觀察時間。
- `blocked`：寫明缺少的輸入、權限或決策，由負責人解除阻塞。
- `needs-review`：交付固定 base/head commit 的 diff、測試命令、exit code、log 與剩餘風險。
- `changes-needed`：reviewer 或 CI 指出失敗條件，交回修改。
- `accepted`：同一 head commit 的必要 checks、review 與風險核准均通過。

**審查後又改了 head，就重開受影響的檢查與 review。**狀態不能沿用到未被驗證的新版本。

本站先前整理的 [Grok Bot 工程控制平面](/blog/grok-bot-engineering-control-plane/)處理的是大量 Cloud Agents 的持久任務帳本、巡檢與 proof bundle；個人工作台可以更小，但同樣不能把 process state 當成 product state。

## 優先級排的是人類注意力，不是 Agent 完成順序

原稿將 Ondrej 的 Corral 描述為依 P1 到 P4 排序完成工作的自製工具。這裡不推定它目前的公開狀態或實作，採用的是可以獨立檢驗的設計：讓 review queue 按需求的重要性排序。

優先級不應只看誰先完成，也不該讓 Agent 單方面決定。最小排序可用四個欄位：

1. **使用者影響**：production 事故高於內部整理。
2. **阻塞關係**：會解鎖其他工作者優先。
3. **風險**：資料、權限、付款、部署與大範圍刪除需要較早取得人類判斷。
4. **注意力成本**：五分鐘能解除的阻塞，可能比需要一小時深度 review 的低風險功能更適合先處理。

這是一條給人類的 review queue，不是替每個 Agent 建立複雜排程器。只有同時完成的工作真的開始互相搶注意力，才需要專用介面；兩條工作線用一張 issue board 或清楚的終端名稱就夠了。

## Worktree 隔離檔案，沒有隔離整個世界

[Git worktree](https://git-scm.com/docs/git-worktree)讓同一個 repository 同時擁有多個 linked working trees，各自 checkout 不同 branch。每個 linked worktree 有自己的 HEAD 與 index。即使兩個 Agent 修改不同檔案，共用 checkout 的 `git add`、commit 與 branch 切換仍會互相影響，建置也可能覆寫相同產物。平行寫入者應使用獨立 worktree；若維持共用 checkout，就指定單一寫入者並序列化 Git 操作。

但 worktree 不是 sandbox。worktree 共用 object database、部分 refs 與設定，也可能共用：

- 相同 port、database、cache 與外部測試帳號；
- 使用者層級的 credentials 與設定；
- CPU、記憶體、磁碟與網路頻寬；
- 最後仍需合併的 branch 與相同 CI queue。

reviewer 則應在另一個 checkout 檢查固定 commit，避免讀到作者持續修改中的檔案。合併衝突留在整合階段處理，不把另一個 agent 的 staged changes 順便提交。

隔離要依失敗面分層：檔案衝突用 worktree，process 與 dependency 用 container 或獨立 worker，filesystem 與 network 用 sandbox，外部系統則用專用帳號與最小權限。多開目錄不能替代這些邊界。

## 遠端持久執行換來的是營運責任

把 Agent 放進 VPS，再透過 SSH 與可 reattach 的 runtime 連回去，確實能避免筆電睡眠、斷線或關機直接終止 session。前提是遠端 server 仍存活。[Herdr session-state 文件](https://herdr.dev/tui/docs/session-state/)說明，一般 server 停止再啟動或主機重啟後，只能恢復 layout 等保存狀態，原 process 不會復活；conversation resume 依賴 agent 本身支援。terminal history 預設不保存，以免留下 secrets。另有實驗性 live handoff 可在支援的 server 替換流程中嘗試保留 process，但不保證成功，也不能跨主機斷電復原。

遠端主機至少增加以下責任：

- SSH key、service account 與權限撤銷；
- secrets 注入、rotation 與 audit；
- system package 與 Agent runtime 更新；
- network allowlist、備份、監測與異常處理；
- 多 session 同時執行測試時的資源限制。

遇到中斷時，先確認遠端 process 是否仍在，再決定 attach 或重建 session。重建前核對最後 commit、未提交差異與外部副作用，避免把已送出的部署或付款重做一次。遠端更新若需要重啟 server，就安排工作保存與中斷時段。

選擇遠端配置也等於接下這些維運工作。只有任務需要跨裝置接續、執行時間長於本機可用時間，或本機資源已成為量測到的瓶頸時，遠端 worker 才有必要。

## Skill 描述流程，平台才強制邊界

原稿整理的做法是把單步重複文字做成 snippet，把多步工作流做成 skill。可採用的判準是：先重複、確認流程穩定，再封裝；不要為尚未發生的第二次工作建立抽象。

但 skill、ADR 與操作指南都只是可讀知識。完整的治理需要把「建議」與「不能越過」分開：

- skill 說明怎麼做 review、發布或研究；
- ADR 記錄程式碼無法表達的核心決策與背景；
- tests 與 CI 驗證可機械判斷的行為；
- branch protection 強制必要 checks 與 review；
- sandbox 限制 filesystem 與 network；
- approval policy 決定哪些動作需要核准，以及由哪個 reviewer 處理。

[OpenAI 的 Codex 安全實務](https://openai.com/index/running-codex-safely/)也把 sandbox 與 approval policy 視為獨立控制：模型可以提出工具呼叫，環境仍決定它實際能碰什麼、何時需要核准。核准的處理方式依配置而定，可能涉及人工或自動 reviewer，不能把所有 approval 都寫成人工按鈕。停用 permission checks 前，必須先確認剩下的 sandbox 與外部權限能限制哪些行為。

若 Agent 需要查 production database，只授予 `SELECT` 是起點。[PostgreSQL 權限文件](https://www.postgresql.org/docs/current/ddl-priv.html)還要求檢查角色繼承與 `PUBLIC` 權限：該帳號是否能繼承其他角色，或透過可執行的函式取得超出預期的能力？`SELECT` 可以呼叫函式，不能只看 table grants 就宣稱帳號完全無副作用。

特別要盤點 [functions](https://www.postgresql.org/docs/current/sql-createfunction.html) 的 `EXECUTE` 權限與 `SECURITY DEFINER`。後者以函式擁有者權限執行；新函式預設可能授予 `PUBLIC` 執行權，應按需求撤銷，並檢查安全的 `search_path`。避免讓診斷帳號透過函式寫入或取得敏感內容。

採用 [row-level security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) 時，superuser 與 `BYPASSRLS` 角色可繞過政策，table owner 通常也會繞過，除非適用 `FORCE ROW LEVEL SECURITY`。以 agent 實際登入角色驗證可讀資料範圍，搭配敏感資料遮罩、查詢逾時、獨立 credentials 與 audit。這些檢查都應先在測試環境完成，再決定是否開放 production 診斷。

更完整的任務契約、持久狀態、驗證、權限與 trace，可參考本站的 [Harness Engineering 七個控制面](/blog/harness-engineering-for-reliable-agents/)。個人工作台只是在這些控制面上加了一層注意力管理，不會取代它們。

## 從兩條工作線開始

不用先安裝一整套 Agent cockpit。最小導入只要一個 repository、兩項低風險工作與既有 CI：

1. 為每項工作寫下目標、限制、接受條件與必要證據。
2. 兩個平行寫入者使用各自的 worktree，分開測試產物、port 與測試資料；否則採單一寫入者。
3. 統一使用 `running`、`blocked`、`needs-review`、`accepted`，把 sidebar 提示、process 是否存活與交付驗收分開記錄。
4. 把 review queue 依影響、阻塞、風險與處理成本排序。
5. 保留每項工作的人工介入次數、返工原因、CI failure 與 review 等待時間。

這些數字比 pane、prompt、commit 或 Agent session 數量更接近真正瓶頸。[Vectal Labs 的 `agentic-productivity`](https://github.com/vectal-labs/agentic-productivity)會記錄 commits、sessions 與 prompts；這類活動量仍要和交付品質、返工與人工注意力一起解讀，不能單獨當成 productivity。

## 下一次 review 固定版本與證據

選兩項低風險工作試跑，要求每項交付都附 base/head、測試結果與風險。reviewer 在固定 commit 上重現失敗或確認通過，再決定合併。如果還要逐一追問「測的是哪個版本、log 在哪裡」，先補齊這段交接，再增加第三個 agent。
