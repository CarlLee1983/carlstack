session 結束、context 被壓縮，或工作轉交給另一個 Agent 時，先前談過的偏好、限制與決策可能沒有被帶過去。下一輪便得重新問使用者，或冒著沿用錯誤假設的風險繼續。

保存歷史紀錄時，需要一起決定用途、保留期限與更新權限。未結案的 bug 可能只需要保留兩天，卻比三個月後仍成立的飲食偏好更急迫。保存錯誤摘要也有代價，下一輪可能把昨天的猜測當成已驗證的設定。

[Anthropic 在 2026 年 11 月 6 日發布的〈The components of agent memory〉](https://www.anthropic.com/research/components-of-agent-memory)補上了錯誤修正的實驗：讓模型在背景回查原始對話，修正記憶筆記，再供後續 session 使用。我會把這類整理視為一個需要驗收的資料更新工作，留下來源、差異與可回復版本。

舊版文章引用 [@0xWast3 的 Memory Engineering 貼文](https://x.com/0xwast3/status/2084625810112032849)，先前查核未取得正文，不能確認其框架或程式碼細節。以下五階段、欄位與發布流程是設計建議，尚未實作驗證。這次更新核對 Anthropic 原文、官方 cookbook 與 Claude Code 文件，沒有重跑廠商評測。MemGPT 與 LongMemEval 的研究結果另附來源，資料治理仍需依產品與法規落實。

## 完整歷史仍需要篩選與版本管理

把完整對話反覆交給模型，至少有三個結構性問題：

1. 成本需要預算：歷史愈長，需要放入請求的材料通常愈多；快取可能降低部分成本，但不會替你判斷內容是否仍有效；
2. 資訊沒有輕重之分：隨口提到的午餐，可能與安全限制占據相同篇幅；
3. 舊事實不會自動失效：當使用者改變偏好，舊答案與新答案可能同時留在 context 裡。

context window 容納這次請求要讀的材料。材料如何保存、判斷有效版本與取回，還需要由系統處理。

- Prompt Engineering：指定這次回答的目標與約束。
- Context Engineering：選擇這次請求或任務要看見的材料，包含取回的記憶。
- Memory Engineering：管理跨 session 的任務狀態、事實與偏好如何保存、更新與退出。

這些工作會重疊。[MemGPT（2024-02-12 修訂版）](https://arxiv.org/abs/2310.08560v2)研究的是以分層儲存與資料移動管理有限 context。這種分層設計可以和較長的 context 一起使用。

## 原始紀錄與整理筆記要能互相核對

來源保存到哪裡，會決定錯誤能不能改回來。我建議把每一層的責任寫清楚：

- 原始紀錄保留使用者說了什麼、工具實際回傳什麼，以及當時的任務版本。查核時仍要區分發言者與內容來源。
- 記憶筆記保存整理後的事實與適用範圍，附上能回查的紀錄位置。
- wiki 或主題索引連接不同筆記，讓 Agent 找得到相關材料。頁面仍應能追到來源。
- 每次 session 自動載入的內容只放常用線索與索引，細節按任務取回。

這樣分開後，修正可以沿著來源往上找。假設筆記把測試環境寫成正式環境，查核端要能找到原始工具回應，修正筆記，再檢查引用它的 wiki 與自動載入內容。只改其中一份摘要，另一份衍生資料仍可能把舊值帶回來。

原始紀錄也有信任邊界。工具輸出中的網頁文字可能帶有錯誤資訊或惡意指令，逐字保存只能證明當時收到這段文字，不能保證內容為真。事實核對要檢查資料來源，操作授權則要回到使用者與系統的權限規則。

## 用五項責任管理記憶生命週期

Capture、Consolidate、Retrieve、Reconcile 與 Decay，分別處理記憶的擷取、合併、檢索、更新與退場。每一項都需要留下可檢查的結果。

### 1. Capture：先決定用途與保留期

Capture 決定哪些資訊值得保存，以及應放在哪種狀態裡。不要用「三個月後還有用嗎」作為唯一門檻。待回覆的問題、明天到期的工作、目前排查到哪一步，都可能在下一次 session 前遺失，卻又不該變成永久偏好。

例如「我現在被這個 bug 搞得很煩」不適合直接推論為人格特質；但 bug 尚未解決、已試過哪個修正與下一步需要誰協助，值得存成有到期或完成條件的任務狀態。「Code Review 請直接指出問題」則可存成限定於 review 情境的偏好。

我的做法是分開管理任務狀態、可重用偏好與參考知識，為各自指定來源、範圍及保留政策。只保存完成用途所需的資料，不把完整敏感原文複製到每份摘要。

### 2. Consolidate：把重複訊號合成一條可信記憶

相同偏好可能在不同對話中以不同句子出現。若每次都新增一筆，不只浪費空間，也會讓檢索結果充滿近似內容。

Consolidate 要做的是把重複、近似或零碎的訊號合併，並保留來源與強度。例如三次出現「回覆請簡潔」，可以合併為同一筆偏好的補充證據。同一訊息被複製三次時，則應視為重複來源，不能增加證據強度。

但合併不能只看文字相似度。「我偏好簡潔的 Code Review」與「架構提案需要完整說明」並不衝突；它們的適用情境不同。生產系統至少還要比較主體、範圍與時間，不能只靠單一相似度閾值判斷。

### 3. Retrieve：只取回這次需要的部分

記憶只有在正確時機被取回，才會產生價值。每次把整個記憶庫注入 prompt，只是把 context window 的問題搬到另一個地方。

較合理的檢索會同時考慮：

- 與目前任務的語意相關性；
- 記憶的新鮮度與有效期限；
- 過去被確認或使用的次數；
- 記憶本身的可信度；
- 這次請求允許使用的 token 預算。

排序之前，先以租戶、使用者、專案範圍、存取權限與有效狀態過濾；不能先向量搜尋所有租戶，再期待模型忽略不該看見的結果。`confidence` 是對事實的估計，不是操作授權；被取回的文件與舊摘要也不能自行授權部署、寄信或揭露資料。

最後回傳預算內與任務相關、附帶來源的記憶，避免無關內容占用 context。

### 4. Reconcile：新舊事實衝突時，不要默默猜答案

假設記憶庫原本寫著「部署區域是東京」，新訊息卻說「已遷移到新加坡」。系統至少需要三種處理結果：

- Supersede：新事實明確取代舊事實；
- Coexist：兩者適用於不同專案、環境或時間；
- Flag conflict：證據不足，保留衝突並要求確認。

證據不足時，將衝突留在輸出裡並要求確認。對部署設定、法規要求或客戶資料這類高風險資訊，衝突狀態本身就是必須被看見的資料。

### 5. Decay：降低權重、失效與刪除要分開

資訊久未使用可以降低檢索權重，但不能只靠使用次數決定有效性。安全限制可能很少被查詢，仍然必須生效；未完成任務也不能因冷門而消失。

- 降權：內容仍有效，只是一般檢索排序較低。
- 失效：超過 `valid_until` 或已被新版本取代，不再作為目前事實；查歷史時可在授權範圍內引用。
- 封存：移出日常檢索，但仍保有資料，必須有保留期限與存取控制。
- 刪除：依政策移除原始紀錄及可識別的衍生副本，包含索引、摘要與快取；備份則依既定保留與復原政策處理，不能宣稱改一個 status 就已清除所有副本。

因此，封存不是履行刪除請求的同義詞。若存在依法必須保留的資料，應明確列出例外、權限與期限，而不是以「方便恢復」無限保存。

## 背景修正要有候選版本與發布條件

Anthropic 的[背景整理 cookbook](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)先讓 analyzer 讀取各份 transcript，再由 organizer 整理筆記與連結。範例將原始紀錄視為資料，限制寫入範圍，並讓後續 Agent 以唯讀方式使用記憶。它提供了可參考的分工；若正式任務會依記憶採取外部動作，我還會加上候選版本與發布檢查。

我建議多做五項檢查：

1. 固定本次輸入的紀錄清單與目前記憶版本，在獨立候選版本整理。
2. 每筆修改保留舊值、新值、依據與受影響的衍生筆記。缺少支持資料時標記待查，不直接補成確定敘述。
3. 用固定問題檢查候選版本。至少包含一筆明確更正、一筆證據不足的衝突，以及一筆不應改動的既有事實。
4. 發布前確認目前版本未被其他工作修改。若版本已變，重新合併與驗收，避免後寫者覆蓋剛完成的修正。
5. 發布後記錄新 session 使用哪個版本。若答案退步，能切回前一版並追查差異。

唯讀掛載能限制這個 session 修改記憶，卻不會讓它讀到的內容自動可信。被污染的筆記仍可能影響回答或工具選擇，因此還需要執行端的權限檢查。

更新時機也要隨資料而變。使用者明確撤回的要求應立即影響目前任務，不能等夜間整理完成。重複筆記合併、補連結或跨 session 比對可以排到背景，降低互動時的等待。查詢量很低的專案則可以在下次讀取前按需整理，避免每天重掃大量未變動的材料。

## wiki 的整理成本要按使用量計算

Anthropic 在[同一篇研究文章](https://www.anthropic.com/research/components-of-agent-memory)報告，對約 35 萬份內部檔案設計的 25 題測試，搜尋單獨使用的分數是 53%，搜尋加整理後 wiki 最高為 61%，每題約少用 20,000 tokens。分數指符合評分條件的比例，不能解讀成一般任務成功率。這組內部題目也不足以推定其他公司的語料會有相同收益。

我會用自己的查詢分布評估是否值得建立 wiki。跨文件問題多、相同背景反覆被查詢時，整理成果比較有機會重用。若多數問題只需定位一份文件，直接搜尋可以先作為成本基線。

比較時固定模型、工具、問題與判定方式，分別記下建置、更新、查詢三筆成本。下面的式子只是估算記帳方式，尚未填入實測數字：

```text
總成本 = 初次整理成本 + 期間更新成本 + 查詢次數 × 平均每次查詢成本
```

查詢端省下的 tokens，必須連同整理時使用的 tokens、模型單價及快取條件換算。若每天改動很多文件，維護支出可能比查詢節省更多。除了答案正確率，也要量測舊資訊被引用的次數、來源可追溯率與更新後多久才生效。

自動載入的記憶則應另外計算。依 [Claude Code 文件](https://code.claude.com/docs/en/memory#how-it-works)，`MEMORY.md` 在 session 開始時只自動載入前 200 行或 25 KB，以先達到的限制為準，其餘主題檔案按需讀取。這是產品的載入規則，不能直接當成其他 Agent 的最佳預算。我會先量出常駐內容占多少輸入，再刪除任務很少用到的細節，保留可追查的連結。

## 最小可用的記憶資料模型

向量索引能找相似內容，更新與退場則需要可查詢的欄位：

- `id`、`version`、`content`：穩定識別、版本與整理後的內容。
- `tenant_id`、`subject_id`、`scope`：擁有者與適用的使用者、專案、環境或任務。
- `source`、`observed_at`：原始證據位置與記錄時間；來源的權限仍須檢查。
- `confidence`、`evidence_kind`：區分明確陳述與推論，不作為授權憑證。
- `valid_from`、`valid_until`：事實適用期間，與記錄時間分開。
- `supersedes`、`status`：取代關係與啟用、衝突、失效或封存狀態。
- `retention_until`、`deletion_requested_at`：保留政策與刪除流程的追蹤點，不代表已完成刪除。

例如部署區域的目前值改成新加坡時，東京的紀錄可以成為有結束時間的歷史版本；若不知道遷移日期，記錄未知而非補造時間。兩個 Agent 同時更新同一筆記憶時，應用版本檢查或交易防止後寫者無聲覆蓋前者，再由明確規則決定合併或標記衝突。

來源、範圍、版本與狀態應能獨立查詢，方便追查某筆記憶為何被採用或排除。

## 從原型走向正式系統，應該驗證什麼

正式系統需要持久化儲存、可追溯的更新紀錄及失敗復原；若選用向量檢索，再加入 embedding 與索引。衰減率與合併閾值應由實際資料校準，不能抄一組參數就宣稱可靠。

最小的評估集合可以先回答六個問題：

1. Capture 是否把一次性情緒誤當永久偏好，或漏掉只有兩天有效的未完成任務？
2. Consolidate 是否把不同情境的資訊錯誤合併？
3. Retrieve 的前幾筆結果，是否真的足以支持目前任務？
4. Reconcile 是否能辨識知識更新，並在不確定時停止猜測？
5. Decay 是否誤封存仍有效的限制？刪除後能否從一般檢索、衍生摘要與快取再次找到該資料？
6. 跨租戶查詢、撤銷權限與並行更新，是否仍遵守隔離與版本規則？

[LongMemEval](https://arxiv.org/abs/2410.10813v2) 將長期對話記憶拆成資訊擷取、跨 session 推理、時間推理、知識更新與拒答等能力；2025-03-04 修訂版報告中的受測 long-context 系統仍有長期互動記憶落差。這是該基準與受測系統的結果，不能外推為所有模型的固定失誤率；它的 indexing、retrieval、reading 三階段也不同於前述五項設計責任。評估時可以記錄答案是否正確、能否指出來源，以及證據不足時是否拒答。

若任務涉及帳務、醫療、法規或基礎設施設定，還應加入人工覆核、租戶隔離、敏感資料刪除與可追溯且受保留政策約束的 audit log。

## 下一步：用更新、修正與刪除案例驗收

下一次實作先建立一筆兩天後到期的任務、一筆會被新事實取代的設定、一筆與原始工具結果矛盾的摘要，以及一筆要求刪除的資料。跨 session 讀回它們，驗證任務未漏失、目前答案不再引用舊值、錯誤摘要已修正，且刪除資料不會從摘要或索引復活。

再讓兩個整理工作同時修改同一筆記，檢查是否出現遺失更新。這些案例通過後，再擴大資料量與檢索策略。若要測試長任務中途改變要求，可以接著使用[記憶失效與中途改單的驗收案例](/blog/muse-wonder-memory-revision-contract/)。
