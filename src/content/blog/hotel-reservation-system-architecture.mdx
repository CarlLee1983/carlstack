一筆住宿預訂必須涵蓋每一晚的庫存。12 月 31 日入住、1 月 2 日退房，需要保留 12 月 31 日與 1 月 1 日兩晚；其中一晚不足，整筆預訂就要回滾。

房型配額讓飯店保留入住時分配房號的彈性。特定房號、無障礙客房或不可換房的需求仍需額外約束。商業超賣則應由飯店明確設定，預設不超過可售實體庫存。

這裡使用教學模型與 SQL 片段，使用單一 MySQL InnoDB 資料庫。SQL 的命名參數由應用綁定，應用負責檢查列數、提交及有限次重試。交易與鎖語意依據 [MySQL 8.4 文件](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)，不是已壓測的 OTA 系統。

## 1. 核心需求與容量規模估算（Back-of-the-Envelope）

在進入架構設計前，必須先與面試官對齊業務邊界與非功能性約束：

### 核心業務邊界

- **規模範圍**：全球連鎖體系，涵蓋 5,000 間飯店、共計 1,000,000 間客房。
- **付費模式**：線上預訂時需全額付款，支援彈性取消退款。
- **超賣政策**：以整數 `sell_limit` 設定每日可售上限；10% 僅供說明，須經營運核准。
- **房價動態性**：各房型每日價格動態浮動（與入住率動態掛鉤）。

### 儲存與併發估算

1. **每日預訂量**：假設平均客房入住率為 70%，旅客平均連續入住 3 晚。
   `每日訂單數 = 1,000,000 × 70% ÷ 3 ≈ 233,333 筆/天`
2. **預訂峰值 TPS**：
   `平均預訂 TPS = 233,333 ÷ 86,400 秒 ≈ 2.7 TPS`
   假設峰值為平均的 10 倍，約 27 TPS，取整約 30 TPS。這也假設穩態、一筆訂單一間房，忽略取消與重訂。
3. **查詢 QPS（讀多寫極少）**：
   假設每 10 個瀏覽工作階段完成 1 筆預訂，且每個工作階段查詢房態 10 次：
   `房態查詢 QPS = 30 ÷ 10% × 10 ≈ 3,000 QPS`。只有 10% 轉換率時，無法單獨推導 100 倍查詢量。

> [!NOTE]
> 在這組假設下，優先驗證跨日期交易與熱門房型的鎖競爭。全站平均 TPS 低，也可能有單一日期集中搶購。

## 2. 資料模型重構：從「房間實體」到「房型日期矩陣」

`room` 表仍可管理實體客房；對外可售配額另以房型與日期儲存。

### 反模式：以特定房間綁定預訂

如果資料表設計為：

- `room_id`: 201（具體房號）
- `status`: AVAILABLE / RESERVED

當使用者預訂 5/1 ~ 5/4 的豪華套房時，系統必須搜尋「哪一間特定房號在這 3 天都是空的」。這需要查詢日期範圍重疊，並提早固定房號。查詢成本取決於索引與資料量；是否要固定房號則是產品約束。

### 正確解法：房型日期庫存表（`room_type_inventory`）

將庫存維度收斂至「**（飯店 ID + 房型 ID + 具體日期）**」的最小粒度單元：

```sql
CREATE TABLE room_type_inventory (
    hotel_id INT NOT NULL,
    room_type_id INT NOT NULL,
    date DATE NOT NULL,
    total_inventory INT NOT NULL,    -- 實體房間總數（扣除維修中）
    total_reserved INT NOT NULL DEFAULT 0, -- PENDING 與 PAID 合計
    sell_limit INT NOT NULL,         -- 核准的整數可售上限，通常等於 total_inventory
    version INT NOT NULL DEFAULT 0,  -- 樂觀鎖版本號（可選）
    PRIMARY KEY (hotel_id, room_type_id, date)
);
```

#### 資料量試算

若為 5,000 間飯店、每間平均 20 種房型、預先預載未來 2 年（730 天）的房態：
`5,000 × 20 × 730 ≈ 7,300 萬列`

實際空間還有列格式、索引與頁面開銷。應以代表性資料量測表與索引大小、Buffer Pool 命中率及查詢延遲，再決定機器規格。

## 3. 防超賣鎖機制之深度權衡

當兩名旅客同時在搶購跨年夜同一間五星級飯店的最後一間海景房時，系統如何避免兩筆訂單同時成功？

### 策略 1：悲觀行鎖（`SELECT ... FOR UPDATE`）

在交易開始時，直接鎖定連續日期的庫存列：

```sql
BEGIN;

-- 鎖定目標日期區間的所有庫存行
SELECT date, total_inventory, sell_limit, total_reserved
FROM room_type_inventory
WHERE hotel_id = ? AND room_type_id = ?
  AND date >= '2026-12-31' AND date < '2027-01-02'
ORDER BY date
FOR UPDATE;

-- 應用層檢驗：須讀到兩晚；任一天 total_reserved + 1 > sell_limit 則 ROLLBACK
-- 庫存更新與 PENDING 訂單寫入必須同一交易，任何失敗均回滾

UPDATE room_type_inventory
SET total_reserved = total_reserved + 1
WHERE hotel_id = ? AND room_type_id = ?
  AND date >= '2026-12-31' AND date < '2027-01-02';

COMMIT;
```

- **優點**：同一交易內鎖定、檢查與更新，容易對照庫存不變量。
- **代價**：
  1. **鎖等待阻塞**：當該房型熱門時，需要相同排他鎖的交易會等待，長交易可能耗盡連線池；一般一致性讀取不等同鎖定讀取。
  2. **死鎖風險（Deadlock）**：若交易 A 預訂 12/31 到 1/2，交易 B 預訂 1/1 到 1/3，兩者鎖定不同日期的順序若非全域嚴格排序，仍可能在 InnoDB 內部觸發死鎖偵測與強制回滾。

### 策略 2：樂觀版本號鎖（Optimistic CAS）

讀取時不加鎖，提交時比對版本號：

```sql
-- 1. 讀取版本號
SELECT date, total_inventory, sell_limit, total_reserved, version
FROM room_type_inventory
WHERE hotel_id = ? AND room_type_id = ?
  AND date >= '2026-12-31' AND date < '2027-01-02';

-- 2. 應用層檢驗通過後更新（需同時比對多列版本）
UPDATE room_type_inventory
SET total_reserved = total_reserved + 1, version = version + 1
WHERE hotel_id = ? AND room_type_id = ? AND date = '2026-12-31' AND version = ?;
```

- **優點**：讀取可用一致性快照，是否較快需量測。
- **代價**：在跨 N 晚預訂場景中，只要其中 1 天的版本被其他人先修改，整筆多晚交易就必須回滾重試。熱門日期可能產生大量衝突，應設定退避與重試上限。

### 策略 3：資料庫原子條件更新約束（Atomic Constraint，業界推薦）

利用關聯式資料庫單行更新自帶行鎖與 ACID 特性，將業務判定直接推入 SQL `WHERE` 條件：

```sql
START TRANSACTION;
-- num_rooms 必須是正整數，start_date < end_date；end_date 是退房日
UPDATE room_type_inventory
SET total_reserved = total_reserved + :num_rooms
WHERE hotel_id = :hotel_id
  AND room_type_id = :room_type_id
  AND date >= :start_date AND date < :end_date
  AND total_reserved + :num_rooms <= sell_limit;
-- 應用立即取得這條 UPDATE 的 affected rows。
-- 等於 DATEDIFF(end_date, start_date) 才能建立 PENDING 訂單並 COMMIT。
-- 不足、缺日期、訂單唯一鍵衝突或任何例外：ROLLBACK，禁止保留部分日期扣減。
```

#### 工程判定邏輯

同一連線、同一明確交易內完成列數檢查與訂單寫入。日期列的複合主鍵防止重複；應事先建立每一晚庫存。`num_rooms` 為正整數時，符合條件的列都會實際變動。

原子條件更新仍會取得 InnoDB 鎖，並持有到提交或回滾。它減少應用來回讀改寫的步驟，沒有「無鎖」或微秒鎖定保證。死鎖與鎖等待逾時須回滾整筆交易，再依冪等鍵有限次重試。CAS 版本寫法也必須把每晚更新與訂單寫入包在同一交易，逐晚檢查成功。

## 4. 兩階段房態預扣生命週期與延遲釋放狀態機

在電商或飯店流程中，旅客從按下「預約」到完成信用卡扣款通常需要數分鐘。這段時間房態處於**「已預扣但尚未支付」**的中間態。

系統必須落實完整的兩階段預扣流程，防止旅客卡住庫存不結帳：

### 流程步驟拆解

1. **防止重複下單（Idempotency Key）**：
   前端在旅客進入結帳填單頁面時，由後端簽發全域唯一的 `reservation_id`（UUIDv7）。後續提交請求無論點擊幾次，後端皆依此 ID 去重，底層以 `reservation_id` 的唯一索引（Unique Constraint）阻擋併發重複插入。
2. **建立 PENDING 預扣訂單**：
   使用上述原子更新語句預扣目標日期的配額，並在 `reservation` 主表中建立狀態為 `PENDING` 的訂單記錄。
3. **安排 15 分鐘逾時檢查**：
   在建立訂單的交易內寫入 outbox，提交後由 Worker 派送到期任務，並定期掃描已到期的 `PENDING` 訂單補漏。Kafka 本身不提供任意延遲訊息，需另外實作排程。
4. **處理付款與取消競爭**：
   付款回呼與逾時 Worker 都先在交易內對同一 `reservation` 列 `SELECT ... FOR UPDATE`，再檢查目前狀態。讀取訂單原本保存的飯店、房型、日期與房數，不使用回呼帶來的任意扣減參數。
   - 支付成功且仍為 `PENDING`：改為 `PAID`，保留庫存並提交。重複付款事件不再修改庫存。
   - 逾時且仍為 `PENDING`：改為 `CANCELLED`，同一交易釋放每晚庫存。狀態已改變就跳過。

```sql
-- 已在同一交易中鎖定訂單，確認 PENDING 且 expires_at <= CURRENT_TIMESTAMP
UPDATE room_type_inventory
SET total_reserved = total_reserved - :num_rooms
WHERE hotel_id = :hotel_id AND room_type_id = :room_type_id
  AND date >= :start_date AND date < :end_date
  AND total_reserved >= :num_rooms;
-- 檢查 affected rows 等於住宿夜數，否則 ROLLBACK 並告警。
-- 同一交易把訂單改成 CANCELLED，全部成功才 COMMIT。
```

外部付款不在資料庫交易內。若取消先提交而付款稍後成功，應記錄支付收據與補償任務，再走冪等退款或人工處理，不能直接把 `CANCELLED` 改回 `PAID`。已付款旅客取消是另一條退款流程。

## 5. 面試官進階追問與架構擴展（Deep Dive）

在白板面試最後 10 分鐘，資深面試官通常會提出以下進階擴展場景：

### Q1：如果流量規模擴大 100 倍（如 Booking.com 全球等級），單庫撐不住怎麼辦？

- **Sharding 策略**：以 `hotel_id` 為分片鍵（Shard Key），透過 `hash(hotel_id) % N` 進行水平分庫。因為所有房態查詢與預約下單都嚴格限定在單一飯店內，單一飯店的庫存與訂單可留在同分片；跨飯店訂單、全域付款與報表仍需另外設計。
- **快取架構與非同步同步**：以 Redis 快取熱門飯店的房態日曆。為了避免 Cache 與 DB 雙寫不一致，底層以 Debezium 監聽 MySQL Binlog（CDC 機制），非同步將資料庫變更串流回寫 Redis。即使快取有延遲，最終預約依然會穿透到資料庫進行原子條件更新，以資料庫交易中的可售上限為準。

### Q2：飯店允許超賣 10%，如果當天真的 100% 旅客都抵達 Check-in，該如何收尾？

這是一個非常考察候選人「真實工程經驗」的業務問題：

- **架構降級與補償政策**：超賣是商業決策而非系統缺陷。當超賣真正爆發（所有人都來了且無人取消），飯店有一套標準 SOP：
  1. 免費將客戶升等至高階套房（利用套房庫存消化標準房超賣）；
  2. 若全館客滿，主動將客人安排至同集團鄰近星級飯店，並提供免單補償與點數。
- 在系統設計層面，`sell_limit` 只限制系統接受的預訂量。取消率、到店率及轉館成本仍可能超出預估；飯店要能調低上限並安排補償，10% 沒有普遍安全性。

## 6. 架構決策清單與下一步

在實施高併發預訂與預扣系統時，建議團隊依循以下工程清單驗收：

- [ ] **維度解耦**：資料庫核心模型按「房型 + 日期」設計，不與具體實體房號提前綁定。
- [ ] **交易原子性**：條件更新、列數檢查與訂單寫入同一交易，失敗時完整回滾。
- [ ] **端到端冪等性**：結帳入口全面強制要求客戶端傳遞唯一 `reservation_id`，防止網路抖動重試造成的重疊扣減。
- [ ] **兩階段超時防禦**：建立以延時佇列或分級時間輪為基礎的自動過期解鎖管線，避免未付款訂單長期佔死房態。

驗收至少涵蓋最後一間房雙請求、缺一晚庫存、退房日不扣、重複取消、付款與逾時競爭，以及提交後派送失敗。每次都核對訂單狀態與每晚預留合計。
