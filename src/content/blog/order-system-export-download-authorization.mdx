假設營運人員在 09:00 送出訂單報表，09:01 被移除匯出權限。報表 09:02 才完成，系統照著建立工作時留下的信箱，寄出一個可下載一天的網址。這位人員沒有再登入，仍然拿到了訂單資料。

[前一篇](/blog/order-system-export-admission/)限制報表可以排幾份、同時做幾份。這次處理檔案交付。**每次開始下載前，都以目前權限重新判斷；建立工作時通過的檢查，不沿用成下載許可。**

虛構商店採用模組化單體、MySQL 與私有物件儲存。數字、時限和人員情境都是教學假設，尚未部署下載服務或執行整合與負載測試。官方資料查核於 2026-11-01。

## 資料快照固定，讀取資格仍會改變

首版只允許提出報表的營運人員下載自己的工作，不開放共用連結。每份工作保存提出者、所屬商店、篩選條件、完成狀態、檔案識別值與到期時間。身分來自伺服器驗證後的登入資訊，不能相信請求自行填入的提出者 ID。

下載要同時符合四個條件：帳號仍啟用、目前仍有該商店的匯出權限、工作屬於這個人與商店、檔案已完整完成且未過期。工作狀態查詢也受同樣的身分與範圍限制，避免透過檔名、筆數或篩選條件洩漏資訊。

[訂單明細授權篇](/blog/order-system-detail-authorization/)已處理「A 不能拿 B 的訂單」。這裡多了一條時間軸：同一個 A，在送出工作和領取檔案時，可能擁有不同權限。

報表內容仍依[匯出快照篇](/blog/order-system-export-snapshot/)固定資料版本。權限檢查卻不能讀那份舊快照，也不能只看登入時寫入 Session 的角色。OWASP 建議每次請求都驗證權限，靜態資源也要受到保護；下載檔案同樣是一次資料存取。[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)

## 小報表先由應用程式把關並串流

我會先保留一個登入後的下載端點，例如 `GET /exports/{jobId}/download`。通知只放這個端點的連結，不包含可直接取得物件的網址。

端點先驗證身分，再從主庫讀取最新帳號、商店權限與工作資料，完成上述條件判斷。查核使用新的短查詢，不重用早已開始的長交易或有延遲的讀取副本。權限資料庫無法回應時，回傳暫時無法下載，不退回建立工作時的舊授權。

通過後才由伺服器讀取私有物件並串流回應。物件位置由工作紀錄決定，不接受使用者提供任意儲存路徑。下載期間不持有授權查詢的資料庫交易或連線。檔案缺失或讀取中斷就讓這次下載失敗，重新下載仍走相同端點。

檔案完整產生與工作完成狀態，沿用前篇的規則。背景工作即使在撤權後才完成，也只留下私有成品，不因此取得公開權限。首版容許這部分已受理的運算完成，靠到期清理回收檔案；若要撤權時連生成工作也取消，另外定義取消流程，不讓它取代下載檢查。

設定下載回應為 `Cache-Control: private, no-store`，並核對反向代理沒有另一條可快取或繞過授權的檔案路徑。`no-store` 規範限制符合規範的 HTTP 快取保存與重用回應，不會追回使用者已另存的檔案。[RFC 9111 §5.2.2.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5)

## 「撤權生效」要有可測的判定點

規則可以寫成：撤權交易提交後才開始的主庫授權查詢，必須拒絕新下載。授權查詢先讀到有效權限，接著才發生撤權的競態，視為已獲准的這次下載，允許完成。

這個選擇保護的是新下載的受理。已在傳輸的資料不會自動停止，已落在對方電腦上的檔案也收不回來。若產品要求撤權後中斷所有既有傳輸，就得追蹤進行中的串流並處理取消，承諾也要寫成可量測的延遲，而不是「立即收回」。

同樣地，檔案有效期假設是完成後二十四小時。端點依工作紀錄的到期時間拒絕新的下載，即使清理程序晚了十分鐘，檔案仍留在儲存空間，也不應繼續供應。授權期限與物理刪除分開驗收，才不會把清理排程的延遲變成額外存取時間。

## 短效簽名網址省傳輸，也留下有效期

另一個方案是在下載端點重新授權後，發出短效 S3 presigned URL，讓瀏覽器直接向 S3 取檔。應用程式省下檔案串流與長連線，適合較大的成品或較高下載量。

AWS 文件說明，這類網址使用簽署者的 IAM 憑證，持有者可在有效期間多次使用。它不是一次性票券。臨時憑證到期或被撤銷等情況可能讓網址提早失效。[S3 presigned URL 文件](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

假設應用程式在 09:00:00 核准並簽出六十秒網址，09:00:10 撤除員工角色。若簽署憑證與 S3 政策未改，單改應用程式的角色資料，不會自動通知 S3 拒絕這個網址。這是依兩套授權機制做出的工程推論。產品必須接受網址剩餘有效期內，持有者仍可能發起新下載，也要避免把完整網址寫進分析紀錄或轉寄通知。

AWS 也明確指出，到期檢查發生在 HTTP 請求開始時。到期前開始的下載可以繼續，斷線後若已到期，重新開始會失敗。因此六十秒限制的是新請求的受理時間，不能寫成「六十秒後所有位元組都停止流出」。

這間商店先選應用程式串流，理由是報表小、下載少，而且不接受撤權後還憑舊網址開始下載。若改用簽名網址，這項產品契約必須一起改，不能只把它當成效能最佳化。

## 算傳輸成本，再決定要不要卸載

沿用前篇每份最多兩萬列的範圍，新增完整檔案上限 5 MiB，超過就失敗而非交付截斷檔案。假設一天產生六十份，平均每份 3 MiB，保留二十四小時，穩定每日用量下成品約需 `60 × 3 = 180 MiB`。暫存、版本保留與刪除延遲另計。

再假設尖峰同時四人下載，每人有效傳輸率 1 MiB／秒，應用程式對外約需 4 MiB／秒，約 33.6 Mbit／秒。如果檔案從物件儲存經過應用程式，同時還有約 4 MiB／秒的讀入流量。這些都未含協定開銷、重試與其他 API。

首版另限制全站最多四條下載串流及每條三十秒的傳輸期限，滿額拒絕新下載，超時取消讀取並關閉串流。這些是待測預算，與前篇「兩份同時生成報表」是不同額度。需要驗證框架、代理與儲存 SDK 的緩衝和背壓，不能看到 `stream` 就宣稱記憶體不會成長。

量測下載併發、傳輸時間、程序記憶體與下單延遲。如果四條下載已讓下單超過既有 SLO，先降低下載額度或把串流放到有獨立資源預算的路徑。檔案變大、網路成本或長連線成為可重現瓶頸時，再評估短效簽名網址；若產品仍要求逐次即時授權，就保留可查當下權限的交付層。

## 驗收要把撤權插進不同時刻

這是一組待執行的整合測試計畫，需要走實際登入、主庫、下載端點、代理與儲存設定：

1. 工作仍在等待時撤權，讓它完成，再用原 Session 下載。必須拒絕，不能因建立時成功而放行。
2. 檔案完成後撤權，再開始下載。回應不能包含檔案資料，工作狀態入口也要符合相同範圍限制。
3. 暫停一個已通過授權的下載，撤權後再放行。依這版契約，既有傳輸可完成，但下一次請求必須拒絕。
4. 拿另一名營運人員的有效工作 ID 請求下載，並嘗試匿名直取儲存物件。兩條路徑都不得取得檔案。
5. 延遲到期清理、模擬權限查詢故障，確認不會以「檔案還在」或舊角色快取作為放行理由。
6. 讓四個慢下載占滿名額，再送第五個；同時觀察下單及記憶體。取消一條後，確認實際讀取已停止才回收額度。

若試作簽名網址方案，另測同一網址重複使用、簽出後撤權，以及到期前開始、到期後重新連線。這些結果應與產品接受的剩餘有效期一致。

## 練習：把網址縮成十秒，就能立即撤權嗎？

團隊把原本一天有效的下載網址改成十秒，並宣稱「離職撤權立即生效」。請給出一個仍可下載的時間順序，再寫出你願意接受的產品契約。
