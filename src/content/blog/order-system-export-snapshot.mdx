營運人員下載一百筆尚未取消的訂單。程式先讀前五十筆，接著已讀到的其中一筆被取消，程式按最後的訂單 ID 續讀後五十筆，最後另外查總數。檔案留下了一百列，頁尾卻寫九十九筆。每次查詢都成功，合在一起卻無法回答「這是哪個時間點的訂單」。

**同一份報表的明細與合計，共用一筆有時限的唯讀快照交易。** 分批只改變每次取得多少資料，不更換讀取時點。

以下延續虛構商店，固定討論 MySQL 8.4 的 InnoDB，數量與時限都是教學假設。尚未執行資料庫整合測試或匯出壓測，後面的驗收是實作前要準備的測試計畫。

## 報表承諾一個時點，不追著下載進度更新

這份報表依指定的下單日期範圍，列出快照中尚未取消的訂單、成立金額及狀態，附相同篩選條件的筆數與金額合計。日期範圍採已換算完成的起點包含、終點不包含條件，匯出途中不重新解讀「今天」。只有受授權的營運人員能下載，查詢及檔案存取沿用既有權限檢查。

成立金額是訂單約定的金額，不代表銀行已入帳或扣除退款後的營收。需要對帳時，還得另定收款與退款的口徑，不能拿這份營運報表代替。

快照建立後才提交的取消，不應只影響後半份檔案。重新產生的報表可以不同，已完成的同一份檔案則保持不變。檔案紀錄篩選條件、產生時間與報表識別值，讓讀者知道它有時間邊界。產生時間是操作紀錄，不宣稱是可以用來恢復資料庫的精確快照識別碼。

[退款查詢的讀取契約](/blog/order-system-cache-read-contract/)關心顧客能否看到已確認的新狀態。這裡接受稍舊的狀態，換取整份資料的一致閱讀時點，兩種需求不必使用相同讀取方式。

## 同一個連線池，不代表同一份快照

首版維持模組化單體與主庫，使用一條匯出期間專用的連線，明確設定 `REPEATABLE READ`，開始唯讀交易並建立一致快照。所有明細批次與合計，都在這條連線、這筆交易內執行一般 `SELECT`。中間不提交、不切換副本，也不以重新借連線代替失去的連線。

MySQL 官方說明，InnoDB 在 `REPEATABLE READ` 下，同一交易的一致讀沿用第一個一致讀建立的快照。`READ COMMITTED` 則讓各次讀取取得新快照，因此只加上 transaction 包裝仍可能出現開頭的情況。[Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

`WITH CONSISTENT SNAPSHOT` 不會自行切換隔離層級；在非 `REPEATABLE READ` 下會被忽略並產生警告。`READ ONLY` 限制修改，也不能單獨保證跨頁讀到同一版本。[START TRANSACTION](https://dev.mysql.com/doc/refman/8.4/en/commit.html)

明細按不可變且唯一的訂單 ID 排序，每批從上一批最後的 ID 繼續。這讓遍歷順序明確，但版本一致性仍由交易維持。若每批提交再開始，即使 ID 沒重複，也可能混入不同時間的狀態。

範圍只涵蓋同一 InnoDB 交易內的一般讀取。匯出不修改訂單、不混用 `FOR UPDATE`，也不在交易中逐筆呼叫金流或物流 API。那些外部結果沒有參加這份資料庫快照。

## 三百萬 bytes 的檔案，也要設定停止條件

假設單次最多一萬筆、每批五百筆，需要二十個明細批次。若每列序列化後平均三百 bytes，資料列約三百萬 bytes，也就是十進位的 3 MB。這還沒算標題、格式、驅動緩衝與應用物件，不能拿來當程序記憶體上限。

先設每次最多三十秒、同時一份匯出，並限制日期範圍與筆數。超過一萬筆就拒絕匯出，請操作人員縮小範圍，不能截斷結果後仍標成完整報表。這些是待驗證的保護預算，不是宣稱三十秒一定足夠。合計查詢使用同一快照與相同條件，不能拿交易外的列表總數填入頁尾。

讀出的資料寫入受保護的暫存檔，不直接向瀏覽器串流。所有批次完成、筆數與合計核對通過、交易正常結束後，才標記檔案可下載。若超時、連線中斷或寫檔失敗，關閉交易並丟棄暫存結果；重試重新產生完整一份。

這會增加暫存空間與等待時間，卻避免下載到一半才發現後段失敗。接收者慢慢下載，也不會一直占著資料庫快照。逾時處理還要確認查詢和連線真的結束，不能只有 HTTP 回錯誤，背景程序仍然讀下去。

## 唯讀交易仍然要付舊版本的成本

InnoDB 必須保留活躍快照可能讀到的舊版本。官方文件指出，長時間唯讀交易也可能讓 `History list length` 增加，因為相關 undo 資料尚不能清除。[Purge Configuration](https://dev.mysql.com/doc/refman/8.4/en/innodb-purge-configuration.html)

因此驗收除了完成秒數，也要量匯出期間的下單延遲、資料庫負載與舊版本保留情形。批次縮小主要減少一次處理的資料量，如果反而拉長整筆交易，未必更適合主庫。

若一萬筆的正常範圍也經常超過時限，或量到匯出影響下單，就重新評估方案。先檢查查詢計畫、篩選索引與輸出欄位，再考慮受控的持久報表資料集或獨立報表來源。保存報表時，仍得交代那份資料如何取得一致版本；換成另一台資料庫不會自動補上這個契約。

## 逐批讀最新資料，適合另一種用途

若營運只想巡覽目前有哪些訂單待處理，可以讓每批各自讀最新資料，避免維持長交易。畫面明確標示資料持續變動，不提供宣稱同一時點的整份合計，也不把結果當作核對憑據。

這個方案省下快照持有時間，代價是讀到的集合可能隨操作改變。即使加上「訂單 ID 不超過匯出開始時最大值」，既有訂單仍可能取消或更新，欄位版本沒有因此凍結。

對現在的小型下載需求，保留有上限的一致快照比較容易驗收。若需求改成長時間巡覽，則應改寫使用承諾，而不是默默把每頁提交當成效能修正。

## 測試時，讓取消插在兩個批次之間

準備一組可核對筆數與金額的訂單，使用兩條獨立連線安排交錯：

1. 匯出讀完第一批後暫停，另一條連線取消一筆已讀到的訂單並提交。恢復匯出，確認明細、筆數與合計仍符合原快照。
2. 改為取消尚未讀到的訂單，再新增一筆符合日期條件的訂單。原報表維持原集合，重新產生的報表才反映變更。
3. 故意把某個批次移到新連線，或改成逐批提交，確認測試能抓到版本混用，而非只檢查 ID 是否重複。
4. 在最後一批之前斷線、超時或讓暫存空間不足。不可出現可下載的半份檔案，重新執行也不可接續舊的半份內容。

再於代表性寫入負載下量成本，才決定筆數與三十秒預算是否可用。下一步可從現有匯出找出「明細、總數、合計」三個查詢，確認它們究竟用了幾條連線、幾筆交易。

## 練習

有人建議每五百筆提交一次，並保存開始時的最大訂單 ID，這樣就能降低長交易成本。若匯出期間，一筆已讀訂單被取消，這份檔案還能保證明細與最後查到的合計一致嗎？你會保留哪個契約，調整哪個方案？

### 參考思路

最大 ID 限制不了既有訂單的狀態變更。每批重開交易後，前段明細可能留下取消前的資料，最後合計卻排除了它。若仍要同一時點，就保留同一讀視圖並限制規模，或設計可證明一致的持久報表資料集。若願意改成逐批巡覽最新狀態，則要明確取消整份同時點核對的承諾。
