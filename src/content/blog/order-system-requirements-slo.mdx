假設下單 API 已經回了 `201`，前端顯示「訂單成立」。顧客重新整理，明細卻查不到訂單。後端追到一半才發現：程式先回成功，接著才寫庫存預留；那次寫入失敗了，畫面上的成功沒有對應的完整訂單。

把 HTTP 回覆加快，解決不了這個問題。本例的做法很直接：訂單、成交價快照與庫存預留，在同一筆 MySQL 交易確認提交後才能回 `201`。逾時則顯示「結果待確認」，保留原操作鍵查詢或重試，不能把沒有收到答案解讀成沒有成立。

這是「系統設計每日實戰」的第一篇。商店與事故都是虛構的；流量、期限與目標數字是教學假設，尚未用訂單服務壓測。先把成功、缺貨與逾時各自代表什麼說清楚，後面的容量與架構選擇才有可驗收的對象。

## 按下結帳之後，哪些資料必須已經存在？

案例只做單倉、單幣別、每張訂單一種商品。首版不處理付款、優惠券、預購與跨倉調撥。「成立」表示價格快照與庫存預留完成，還沒有收款。假設促銷尖峰每秒 20 次下單嘗試、持續 10 分鐘；這些輸入還不足以決定買幾台機器。

本例把 `201` 的發送位置放在 COMMIT 確認成功之後，回覆必須帶訂單 ID。此時到主庫查詢，應能找到訂單、當次的品項價格快照與有效預留。HTTP 的 `201` 只定義資源已建立；上述幾份資料要一起提交，是我們額外訂的業務契約。[RFC 9110 §15.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.2)

價格從伺服器取得，以整數最小貨幣單位保存。訂單記下當次成交價，不接受客戶端傳來的總價當權威，也不在顧客查舊訂單時重新套用目前價格。

接著要決定的，是顧客看不到回覆、再按一次時怎麼辦：

- 同一使用者、同一冪等鍵、同一正規化內容：找回原結果。若已成立，回原訂單 ID，不再預留一次。
- 同鍵卻換商品或數量：回明確衝突，不覆寫第一次的操作內容。
- 已判定缺貨：保存並重放缺貨結果。補貨後要再買，顧客必須發起新操作、使用新鍵。
- 回覆逾時：顯示待確認，以原鍵查詢或重試。前端不得自動換鍵，否則後端會把它當成另一次購買。

為什麼連缺貨都要記住？假設第一次已告訴顧客缺貨，回應卻丟了；幾秒後庫存補進來，同一鍵重送若突然成立，重試就改變了第一次已作出的決定。本例選擇讓原鍵固定代表原意圖與原終局結果，代價是要多存拒絕紀錄。

還有一條容易被藏在錯誤處理裡：查不到庫存，不等於缺貨。資料庫故障要回報未能確認，不能 catch 所有例外後一律回缺貨；缺貨也不能直接包成 `500`。

完整回覆快取暫定保留 7 天，自動重試限 24 小時；精簡去重索引首版不自動刪除，保留使用者／鍵、請求摘要、終局結果與訂單 ID。快取到期後由這些資料重建回覆，不能把舊鍵重新當成新操作。這些保留期限是案例政策；[AWS 的冪等 API 設計](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)提供的是識別操作、參數衝突與晚到重試的問題分析，沒有替本店決定要保留幾天。

## 偶爾回得慢，和偶爾多扣一份庫存，能算在同一個預算裡嗎？

如果這次回覆晚了，顧客可以拿原鍵確認結果。如果同一次操作已經扣了兩份庫存，重試再順利也不會自動把多扣的那份修回來。

因此本例把下面四條當成每次操作都要守住的不變量：

1. 同一使用者與冪等鍵最多對應一張訂單，請求摘要不可被後來的內容換掉。
2. 可售庫存不得小於零，一次成立只產生一次預留效果。
3. 訂單金額等於伺服器價格快照乘以數量，零或負數數量必須拒絕。
4. 訂單、快照與預留共同提交，不能留下其中一半卻回覆成立。

MySQL InnoDB 的交易與唯一索引能支撐這些規則，但業務判斷仍要寫進程式。兩個請求都先 SELECT、都沒找到收據，仍可能一起 INSERT；`(customer_id, idempotency_key)` 必須有非空唯一約束。庫存更新帶上 `available >= quantity`，確認改到一列才繼續，鎖定／更新順序也要一致。[InnoDB ACID](https://dev.mysql.com/doc/refman/8.4/en/mysql-acid.html)、[CREATE INDEX](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)

遇到錯誤時，不能只寫「有 transaction，所以會回滾」。MySQL 的 deadlock 會回滾整筆交易，lock timeout 預設只回滾當前敘述。本例在應用邊界明確結束並回滾整筆交易，再以原鍵有限次重試。只有指定冪等唯一鍵的衝突才能進入原操作查詢；也要先回滾這次交易，避免把不該留下的變更提交。[InnoDB 錯誤處理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)

假設 99.5% 的請求及時完成，剩下的少數卻重複預留，能不能說還在錯誤預算裡？本例的發布規則是不行：驗收發現一次不變量失敗，就停止發布查原因。錯誤事件仍要計入可靠性報表，但剩餘預算不能當成放行已知資料錯誤的理由。

## 99.5% 要除以誰？沒有訂單 ID 的請求也要算

Google SRE Workbook 用「好的事件／有效事件」來定義 SLI，也區分想量的使用者結果與實際量測方式。[Implementing SLOs](https://sre.google/workbook/implementing-slos/) 對這個下單入口，我會先提這份待業務確認的目標：

> 過去滾動 28 天，至少 99.5% 的合格下單 HTTP 嘗試，在可信任入口收完請求後 1,000 ms 內，送完符合契約的終局回覆。

這句話還不夠拿去寫報表，要再回答三個問題。

### 下單失敗，會不會連分母都沒有留下？

若只從 `orders` 表數成功訂單，就永遠看不到連 DB 都進不去的請求。因此入口收到請求時，先留下 attempt ID、操作鍵的安全摘要與起始時間，再和完成事件對接。

通過身分與靜態輸入檢查、屬於支援商品／數量格式的嘗試，算入分母。缺貨也是合格嘗試。`5xx`、容量不足的 `429`、上游逾時，以及沒有留下完成紀錄的請求，都不能因為沒有訂單 ID 就被刪掉。

若故障導致資格無法判定，保守留在分母、視為未成功，另外追蹤資格不明數量。只有已確認的格式錯誤與未授權請求排除；排除量突然增加也要查，避免事故被錯誤分類成使用者問題。

顧客重試一次，就多一次 HTTP 嘗試。另一方面，同一業務操作成立幾張訂單，要用冪等鍵另外彙整。前者量每次請求的體驗，後者抓重複與未決操作，不能把兩個分母混用。

### 回了 200，是否就算好事件？

本例只接受成立、原單重放、缺貨或正確的同鍵內容衝突，而且要同時符合契約、在 1,000 ms 內送完。回應碼本身不夠；若回 `202` 表示仍在處理，也沒有交付這份目標要求的終局結果。

計時採入口同一觀測端的單調時鐘，避免拿兩台機器的 wall clock 相減。入口沒有量到 DNS、TLS 建連與消費者網路，也無法證明手機畫面收到結果；上線時另外用瀏覽器遙測與外部合成探測補足，不能把這份報表叫作所有使用者的端到端成功率。

### 500 次失敗，可以換算成幾分鐘停機？

假設某個 28 天視窗有 100,000 次合格嘗試，99.5% 目標對應最多 500 次不良事件。不能直接換成「允許停機 201.6 分鐘」：促銷時的一分鐘可能用掉遠多於凌晨一分鐘的請求預算。

過慢與錯誤都會使事件落出分子，原因仍要分開記錄，才能追到鎖等待、入口限流或應用失敗。空視窗回報資料不足，不顯示 100%。預算耗盡時，本例選擇暫停非必要功能發布，先處理主要原因；連分母都收不齊時，先修量測。這是案例的治理提案，不是來源替所有團隊訂的門檻。

## 回 201 之前完成，會讓哪些架構選擇變貴？

訂單與庫存先留在同一個 Laravel 或 Node.js 應用，使用同一筆 MySQL InnoDB 交易。訂單模組處理用例與冪等結果，庫存模組處理預留規則；程式內的分工，不必立即變成跨網路呼叫。

<OrderContractDiagram />

這樣可以在一個交易邊界內檢查「訂單和預留一起存在」。代價是共用故障域、熱門 SKU 可能鎖競爭，成立後的主庫查詢也增加負擔。每秒 20 次是否能達標，仍要拿指定資料量、熱點分布與部署規格壓測。

Redis 可以之後用來快取非權威資料，Elasticsearch 可以之後做搜尋投影；兩者都不替首版裁決成立與否。若加入寄信，先把待通知工作與訂單一起存下來，提交後再寄，避免郵件故障把已成立訂單拖回失敗。

提交後的資料能承受哪些故障，還取決於 InnoDB 刷盤、binlog 與儲存設定；備份及故障切換也要驗收。本例沒有承諾任何事故下零資料損失，上線前仍須定義 RPO／RTO。[InnoDB 提交刷盤設定](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_flush_log_at_trx_commit)

那可不可以先回 `202`，把預留放到背景？可以，但顧客此刻只拿到「已受理」，還不知道有沒有買到。RFC 9110 的 [202 語意](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)也沒有承諾最終一定執行成功。

若採這條路，入口先持久化操作紀錄，回查詢 ID 與位置，畫面顯示 pending。接著得另訂完成 SLO，追蹤已受理的唯一操作多久進入成立或缺貨；佇列積壓、worker 中止、重複投遞與恢復，都成為需要實作的行為。它仍可以留在單體裡，同步／非同步和單體／微服務是兩個選擇。

目前保留同步，是因為這份需求要在下單回覆知道成立或缺貨，還沒有壓測證據迫使它讓步。若尖峰無法在合理成本下達標，且產品願意接受稍後確認，才改這份承諾。只把狀態碼改成 `202`，不能拿來宣稱原本的終局回覆 SLO 變好了。

## 在送出成功回覆前暫停，會看見什麼？

驗收時要能控制執行順序。把程式停在「COMMIT 已確認、HTTP 還沒送出」的位置，丟棄這次回覆，再讓顧客以原鍵重試。應找回同一張訂單與同一份預留；timeout 不得觸發新鍵或第二次扣減。

另一個暫停點放在預留已寫入、交易還沒提交時。恢復執行後注入例外，等 rollback 完成，再從另一條連線查詢：訂單、預留與成功收據都不能留下。這兩個測試分別回答「提交前失敗」與「提交後答案遺失」，不能只用殺掉程序的一種測試代替。

其餘必須驗收的反例包括：

- 同鍵同內容同時送入，只成立一張訂單；同鍵不同內容衝突，原摘要不被覆寫。
- 只剩一件庫存，兩個不同鍵競爭，恰好一筆成立、一筆缺貨，可售數為零。
- 缺貨後補貨，原鍵仍回原缺貨結果；新鍵才重新嘗試購買。
- `201` 後的新明細查詢能讀到主庫的正確快照；日後改成讀副本，要重驗這條契約。
- 額定負載下記錄所有入口嘗試、錯誤與尾延遲；短期壓測通過，不能宣稱已觀察滿 28 天 SLO。

本文尚未建置訂單服務，上面是待執行的整合驗收。下面則是一份可以執行的合成測試，只驗 SLI 計算，不會啟動 HTTP 或資料庫，也沒有產生實際延遲。

`contractOK` 在實務上要由回應與主庫／對帳證據核對，不能讓服務隨手寫 `true`。測資都是已結束或已滿 1,000 ms 觀察期的嘗試；期限未到且仍在處理的另列 pending，不提前算失敗。

儲存為 `slo-contract.mjs`，執行 `node slo-contract.mjs`：

```js
import assert from "node:assert/strict";

function measure(attempts) {
  // eligibility 未知仍計入；只有已證明不合格才能排除。
  const eligible = attempts.filter((x) => x.eligible !== false);
  const good = eligible.filter(
    (x) =>
      x.eligible === true &&
      x.contractOK === true &&
      ["created", "replayed", "sold_out", "key_conflict"].includes(x.outcome) &&
      Number.isFinite(x.elapsedMs) &&
      x.elapsedMs >= 0 &&
      x.elapsedMs <= 1000,
  ).length;
  return {
    total: eligible.length,
    good,
    ratio: eligible.length ? good / eligible.length : null,
  };
}

const created = {
  eligible: true,
  outcome: "created",
  contractOK: true,
  elapsedMs: 250,
};
const soldOut = { ...created, outcome: "sold_out", elapsedMs: 80 };
const healthy = measure([created, soldOut]);
assert.deepEqual(healthy, { total: 2, good: 2, ratio: 1 });

const degraded = measure([
  created,
  soldOut,
  { eligible: true, outcome: "timeout" },
  { ...created, elapsedMs: 1400 },
  { eligible: false, outcome: "invalid_input" },
]);
assert.deepEqual(degraded, { total: 4, good: 2, ratio: 0.5 });
assert.equal(degraded.ratio >= 0.995, false);
assert.equal(measure([{ outcome: "gateway_error" }]).ratio, 0);
assert.equal(measure([{ ...created, eligible: undefined }]).good, 0);
assert.equal(measure([{ ...created, contractOK: false }]).good, 0);
assert.equal(measure([{ ...created, outcome: "accepted" }]).good, 0);
assert.equal(measure([{ ...created, outcome: "key_conflict" }]).good, 1);
assert.equal(measure([]).ratio, null);
console.log("PASS: SLI 分母、終局回覆、延遲與空視窗反例");
```

這份合成檢查於 2026-10-11 執行通過；它只證明固定測資下的計算規則，不證明庫存併發安全、時鐘儀表或正式環境 SLO。接到真實服務時，要以獨立觀測資料取代 fixture，並保留逾期當下的結果，不能等重試成功後把原失敗擦掉。

## 練習：產品願意等 30 秒，SLO 要怎麼改？

同一商店的促銷尖峰從每秒 20 次變成 200 次。產品說：「先收到就好，30 秒內告訴我結果。」你決定改成 `202`，還要補哪幾件事？

請寫出受理時持久化什麼、入口 SLO 如何修改、完成 SLO 的分母與時鐘、30 秒後仍 pending 的處置，以及哪個測試失敗會讓你拒絕切換。

### 參考思路

`202` 只承諾操作紀錄已持久受理，回覆穩定查詢 ID。入口仍計入所有合格嘗試，受理失敗不能消失。完成目標可提案為「28 天內 99.5% 的已受理唯一操作，從受理起 30 秒內到達可查詢的成立或缺貨終態」，數字仍須業務批准與壓測。

若報表時間為 T，取受理時間在 `[T − 28 天 − 30 秒, T − 30 秒)` 的操作，判斷各自第 30 秒時是否已有可查詢終態。未滿 30 秒的另列 pending；超期未完成、查詢不可用或 worker 卡住，都留下不良事件。後來補成功不能抹掉當時逾期，重試也不能重設起點。

超期案件要進待調查清單，前端與客服繼續用原操作 ID 查詢。若允許取消，還要定義取消與 worker 的競態。切換前至少測「持久受理後 worker 中止再啟動，只完成一次」與「提交後回覆遺失，重送仍指同一單」。

回到現有下單程式，可以先找出回 `201` 的那一行，確認它前面到底等到了哪個 COMMIT；再找入口報表，確認沒有訂單 ID 的失敗請求是否仍在分母。這兩處對不起來，就算 p99 很漂亮，也還沒量到顧客以為自己買到的結果。
