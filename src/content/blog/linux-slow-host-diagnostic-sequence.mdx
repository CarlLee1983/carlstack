一個 API 開始變慢，登入主機後看到 load 是 8、記憶體 free 很少、根目錄使用率 94%。該加 CPU、清快取，還是刪日誌？現在都還不能決定。這三個數字描述的不是同一件事，也沒有證明誰讓請求等待。

本文採用虛構的 4 個邏輯 CPU 主機與背景報表工作；所有情境數字都是教學假設，沒有壓測或正式事故資料。目標是選出下一個低風險觀察，形成能被推翻的假設，而不是發明適用所有系統的警報門檻。若尚不熟悉路徑、程序與權限，先做[基本指令的隔離練習](/blog/linux-basic-commands-safe-workspace/)。

## 先對齊慢的是什麼，以及你站在哪裡

記下受影響 API、時間範圍、延遲分布、錯誤率與完成量，並核對同期部署、批次工作與流量變化。平均延遲正常不代表尾端正常；單一使用者說慢，也不等於整台主機資源不足。

登入後確認目前是宿主機、VM 還是容器。容器能看到的 CPU 數、主機總記憶體與它實際獲得的 cgroup 配額可能不同。先沿現有監控和部署紀錄核對，不在事故中盲目安裝一整套工具。

```bash
date -Is
uptime
free -h
vmstat 1 6
```

這組命令以 Linux、procps 為範圍，已在隔離環境執行讀取測試；輸出不代表本文假設的事故。下面的 `iostat` 與 PSI 路徑在該環境未提供，沒有實跑，使用前需核對安裝套件、核心及掛載範圍。

## load 高，先分清可執行工作和不可中斷等待

[uptime](https://man7.org/linux/man-pages/man1/uptime.1.html)的 load average 是 1、5、15 分鐘平均，不是 CPU 百分比。[proc_loadavg](https://man7.org/linux/man-pages/man5/proc_loadavg.5.html)說明其涵蓋可執行工作（包含正在執行與等待執行）和不可中斷等待的工作。後者經常與 I/O 有關，但不能一律等同磁碟故障。

4 個邏輯 CPU、load 8 只是提示需要拆解，不能直接寫成「CPU 使用率 200%」。讀 `vmstat` 的 `r`、`b`，再看 `us`、`sy`、`id` 等 CPU 時間比例及它們是否持續。若可執行工作堆積、CPU 閒置少，才更支持 CPU 競爭；若等待增加但 CPU 仍有閒置，就應追查等待來源。

[vmstat](https://man7.org/linux/man-pages/man8/vmstat.8.html)第一份報表的速率通常是開機以來平均；後續才是取樣間隔。程序與記憶體欄位仍是當下狀態，不能把整行都稱為開機平均。`vmstat 1 6` 讓你有後續五個一秒區間可比較，但這仍只是一段短觀察。

```bash
ps -eo pid,comm,stat,%cpu,%mem --sort=-%cpu | head -n 11
```

這裡只看程序名稱，避免把可能帶有憑證的完整參數貼進工單。[ps](https://man7.org/linux/man-pages/man1/ps.1.html)的 CPU 百分比是程序生命週期的平均比例；[top](https://man7.org/linux/man-pages/man1/top.1.html)的顯示也受模式與多核心計算方式影響。兩者不能不看時間範圍就直接相比，更不能看到第一名就立刻結束它。

## free 少，先查可用量和換頁活動

[free](https://man7.org/linux/man-pages/man1/free.1.html)的 `available` 是不需交換就可供新應用使用的記憶體估計，包含可回收部分。`free` 少可能只是 RAM 被有效利用，並不自動表示記憶體耗盡。

接著看 `vmstat` 的 `si`、`so` 是否在觀察期間持續出現，不能只看 `swpd` 的既有交換空間用量。換頁活動、應用延遲與容器記憶體限制需要放在同一時間軸上。容器被限額或發生 OOM，不能單憑宿主機還有 available 就排除。

此時不要把清除快取當成通用修復。它可能讓後續讀取重新走較慢的路徑，也沒有解決應用保留過多資料的原因。更有價值的下一步，是確認哪個工作增加了常駐需求，以及是否能依既有流程暫停新增背景工作。

## df 接近滿，和磁碟等待久分開查

先對準應用實際寫入的掛載點，而不是只看根目錄。下方路徑是佔位符，需換成你有權限讀取、已存在的應用資料目錄：

```bash
df -h /path/to/application-data
df -i /path/to/application-data
# 若已安裝 sysstat，才執行；本文環境未提供此工具
iostat -xz 1 6
```

[df](https://man7.org/linux/man-pages/man1/df.1.html)分別提供檔案系統區塊及 inode 使用情況。容量接近滿可能影響後續寫入，inode 不足也可能使新檔案建立失敗；兩者都不直接等於目前 I/O 延遲過高。必要時核對保留空間與權限，但不要在不知道資料用途時批次刪除日誌。

[iostat](https://man7.org/linux/man-pages/man1/iostat.1.html)的 `await` 包含排隊和處理時間。`%util` 不能對平行處理的 RAID 或現代 SSD 一概解讀為已達吞吐上限。第一份累積報表和後續區間也要分開看。應用可能受遠端儲存、資料庫或網路等待影響，本機裝置指標正常不能替整條請求路徑背書。

## PSI 補充等待，不取代原因調查

若核心與環境提供，可以讀取：

```bash
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

[核心 PSI 文件](https://docs.kernel.org/accounting/psi.html)用 `some` 表示至少部分工作因資源短缺停滯的時間比例，`full` 描述所有非閒置工作同時停滯的情況。`avg10`、`avg60`、`avg300` 是不同時間窗，`total` 是累積微秒；不要把累積值當成瞬間百分比。系統層級 CPU `full` 未定義，為相容性回報零，不能據此認定 CPU 沒壓力。

`/proc/pressure` 的系統範圍與 cgroup 內的觀察不同。若應用受容器限制，應核對對應群組的壓力與限額。PSI 顯示等待的影響，但不會直接告訴你應該終止哪個程序。

## 用一個假設決定一次處置

假設背景報表開始後 API 延遲升高；同時觀察到儲存等待和 I/O 壓力增加，CPU 仍有閒置。這比較支持「兩個工作競爭儲存」的假設，但仍不是證明。

最小處置可透過應用既有開關，暫停接收新的非必要報表工作，保留已在途工作與復原方式。它比直接重啟主機或強制終止程序更容易比較影響。若工作量下降後延遲改善，也要排除外部流量同時減少；若沒有改善，就撤回假設，沿追蹤查下游，而不是繼續加大同一種處置。

替代方案是增加資源或把背景工作移到獨立主機。這可能改善隔離性，卻增加成本與維運範圍；在沒有持續競爭的證據前，不必把擴機當成第一步。確認長期壓力來自無界併發後，再考慮併發上限、排程時段、佇列與背壓，而不是只把主機規格拉大。

## 恢復要看服務，而不只看圖變綠

處置前後比較相近工作量的 API 延遲分布、錯誤率和完成量，也檢查背景工作是否累積到無法消化。CPU 下降可能只是請求都失敗了；延遲下降也可能只是停止服務。記下這次改動、可復原方式及仍未排除的原因，才算留下可用的排障紀錄。

練習：4 個邏輯 CPU 的主機 load 偏高，但 CPU 閒置時間仍多。你會先要求哪兩類觀察？為什麼不能直接增加 CPU？

參考思路：先分辨可執行與不可中斷等待工作，再把裝置或下游等待、PSI 與應用請求時間對齊。CPU 有閒置讓「純 CPU 飽和」較不吻合，但仍需核對容器配額與觀測範圍。下一步是縮小等待來源，不是把另一個單一指標當答案。
