一張訂單列表要依金額由小到大排列。只有三筆時，任何寫法看起來都很快；增加到數萬筆，又要求同金額維持建立順序，就得決定資料怎麼比較，以及排序過程能花多少資源。

[Code Crack 的排序 Reel](https://www.facebook.com/reel/1395782485411974) 把多種演算法放在一起播放。動畫適合觀察資料如何移動，畫面上的秒數卻不能直接當成選型結論。以下用自訂訂單資料練習選擇，沒有做效能壓測。

## 先寫出「排對」的條件

排序會改變元素順序，不應把訂單漏掉或複製一份。還要回答三件事：

1. 金額是數字還是字串？`"100"` 和 `"20"` 的文字順序不等於金額大小。
2. 同金額如何處理？維持原清單順序，還是按建立時間、訂單 ID 排列？
3. 能否修改原陣列？同一份資料若還被其他畫面使用，原地修改可能讓另一個畫面一起變動。

**穩定排序會保留比較結果相等的元素原始相對順序。** 例如輸入 A、B 都是 100 元，穩定排序後 A 仍在 B 前面。它不保證資料庫每次回傳的原始順序相同；跨次查詢若要一致，仍應指定完整排序條件。[Python 排序指南](https://docs.python.org/3/howto/sorting.html#sort-stability-and-complex-sorts) 說明穩定性與多欄位排序；[PostgreSQL 查詢教材](https://www.postgresql.org/docs/current/tutorial-select.html) 也示範了相同第一排序欄位下，再加第二欄位消除不確定順序。

## 插入排序：每次把一筆放進已排好的部分

把 `[4, 1, 3]` 想成三筆金額：先視 4 為已排好，再把 1 插到 4 前面，最後把 3 插進 1 與 4 中間。每一輪只處理一筆新資料，適合用來理解「前面這段已經有序」這個不變條件。

資料幾乎排好時，需要移動的元素較少。反過來，若輸入完全逆序，每筆都可能往前移很多格，典型插入排序的最差時間會成長為 `O(n²)`。這裡的 `n` 是元素筆數，不是秒數。不能看見 `O(n²)` 就斷言十筆資料一定慢，但筆數大幅增加時要留意它的成長速度。

## 合併排序：先排小段，再合成一段

同一組資料也可以拆成 `[4]` 和 `[1, 3]`。左右各自排好後，只比較兩邊尚未取出的第一筆：先取 1，再取 3，最後取 4。

標準合併排序的時間是 `O(n log n)`；常見陣列實作需要額外空間保存合併結果。這是拿暫存空間換取規則清楚的合併流程。若希望維持穩定性，兩邊元素比較相等時，先取原先位於左邊的元素。插入與合併的推導可對照 [MIT 6.006 第 3 講投影片](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-fall-2011/90a37c49b07b105ea7a027abc67eddc6_MIT6_006F11_lec03.pdf)。

`log n` 可以先理解為反覆對半切分需要的層數。這個分析只描述工作量的成長；物件大小、比較函式成本與執行環境仍會影響實際耗時。

## 計數排序：先確認數值範圍真的小

假設資料只有整數評分 0 到 5，可以先數各分數出現幾次，再依分數輸出。處理成本與筆數 `n`、可用值的範圍 `k` 有關，常見計數排序為 `O(n + k)`。

若輸入是三個分散在 0 到十億的整數，為每個可能值配置計數格就不划算。它利用了「值可以對應有限整數位置」這項額外資訊。

基數排序再把整數或字串按位分批處理；最低有效位優先的典型做法，每輪須保留相同位值的相對順序，前一輪的結果才不會被破壞。輪數、每輪可用值範圍及鍵的長度都要算進成本。[MIT 第 7 講講義](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-fall-2011/bf7d79105762bf79bbc0925438e1468a_MIT6_006F11_lec07.pdf) 說明了比較模型的限制與整數排序使用的假設。

先掌握這三種機制，再看其他排序，才容易理解它們省掉什麼工作。日常產品程式通常先用標準函式庫，不必為了影片出現八種名稱，就在專案維護八套實作。

## 用內建排序，仍要測自己的比較規則

下面這段完整 JavaScript 示例，資料都是教學用整數元。可存成 `sorting.mjs`，執行 `node sorting.mjs`：

```js
import assert from "node:assert/strict";

const orders = [
  { id: 3, amount: 100 },
  { id: 1, amount: 20 },
  { id: 2, amount: 100 },
];
const byAmount = [...orders].sort((a, b) => a.amount - b.amount);
assert.deepEqual(
  byAmount.map((x) => x.id),
  [1, 3, 2],
);

const fixedOrder = [...orders].sort(
  (a, b) => a.amount - b.amount || a.id - b.id,
);
assert.deepEqual(
  fixedOrder.map((x) => x.id),
  [1, 2, 3],
);
assert.deepEqual(
  orders.map((x) => x.id),
  [3, 1, 2],
);
assert.deepEqual([100, 20].sort(), [100, 20]);
assert.deepEqual(
  [100, 20].sort((a, b) => a - b),
  [20, 100],
);
```

第一個排序保留同金額的原順序，第二個額外指定 ID。複製陣列可避免 `sort()` 改動原陣列順序，但這只是淺複製，裡面的物件仍共用。[ECMAScript 的排序規格](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.sort) 要求穩定排序，未要求所有實作採用某個指定演算法。預設比較會轉成字串，數值排序因此應提供比較函式。

上述斷言已在 Node.js 24.22.1 執行通過；這只驗證示例輸出，沒有證明速度。實務上還應測空陣列、重複值、負數，以及業務是否允許缺值或 `NaN`，不能把不合法金額默默塞進比較式。

## 需要所有資料有序嗎？

只找最小值，掃描一次即可，不必先把全部資料排序。只取少量最小項目，可以評估堆積或標準函式庫提供的 top-k 操作；[Python heapq](https://docs.python.org/3/library/heapq.html#heapq.nsmallest) 就區分小量選取與完整排序的適用情況。資料原本在資料庫時，也先想清楚是否應讓查詢完成排序與分頁，避免整批載入應用程式。

## 練習：相同金額的訂單應該誰先？

輸入依序是 A（100 元，建立時間 10）、B（20 元，建立時間 12）、C（100 元，建立時間 9）。需求是金額小的先，同金額則較早建立的先。只按金額做穩定排序，能滿足需求嗎？請寫出期待順序，以及比較時需要的欄位。

### 參考思路

期待順序是 B、C、A。只按金額的穩定排序會保留 A 在 C 前面，因此不符需求；應再比較建立時間。若時間也可能相同且需要跨次結果一致，最後再加唯一 ID。下一步先把這些相同值案例寫成測試，再考慮是否需要更換排序實作。
