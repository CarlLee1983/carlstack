下單程式直接更新庫存表，後台補單也直接更新，退款功能再抄一份。即使三處 SQL 今天都正確，下次「可售庫存」多了一條規則，也得記得改三個地方。

這一篇要決定誰有權寫入資料，以及誰負責把幾次寫入一起提交。案例先維持一個應用與一個 MySQL：庫存模組管理庫存規則，訂單模組管理訂單與成交快照，下單用例協調共同交易。

這是「系統設計每日實戰」第 3 篇，不需要先完成前兩篇的練習。沿用[需求契約](/blog/order-system-requirements-slo/)：單倉、單幣別、每張訂單一種商品，尚未付款。回覆 `201` 前，訂單、價格快照與庫存預留必須一起提交；同鍵重送不能再扣庫存。成立後查詢讀主庫。

所有資料表名稱、流量與時間均為教學假設。本文沒有實作或壓測訂單服務；下列介面和測試是待實作的設計規格。

## 寫入責任跟著規則走

最小方案分成三個資料擁有者，以及一個下單用例。這裡的模組是程式內部邊界，允許本地交易協作；不宣稱它們已經是能獨立部署、完全自治的限界上下文。

### 訂單模組保存當時成立了什麼

它寫入 `orders`、`order_items` 的成交快照，以及下單冪等結果。公開入口接受已確認的價格值與預留識別值，檢查訂單規則後保存。其他模組不能取得它的可寫 ORM entity，也不能藉通用 repository 任意更新訂單狀態。

商品現在的價格與歷史成交價格有不同用途。這個案例選擇保存本次下單讀到的伺服器價格與版本；商品日後改價，不重算舊訂單。這是本文的業務政策，不是 MySQL 交易自動替我們決定的結果。

### 庫存模組掌管可售數與預留

它寫入 `stock` 與 `reservations`，提供 `reserve` 這類具名操作。條件更新、數量檢查及預留紀錄都留在模組內。呼叫端只拿到預留成功的值或缺貨結果，不拿到可以自行改庫存的查詢建構器。

這個入口仍須處理併發，不能只有「先查再扣」而沒有條件更新或鎖定。具體鎖策略留給後續篇章；今天先把它放在唯一需要負責的地方。

### 商品模組提供目前可用的價格值

它擁有商品與價目資料，回傳商品識別值、金額、幣別及版本等不可變的回傳資料。訂單保存這份值的快照，商品模組不回頭修改歷史訂單。

讀到價格後、交易提交前，另一筆交易可能已經改價。因此這份政策只承諾採用本次讀到的價格，沒有承諾「提交瞬間最新價」。若業務要求顧客確認後才能接受新價格，就必須另定報價有效期或版本衝突行為。

Fowler 在 [Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)（2014-01-15）討論模型與語言的邊界。同一個「商品」在不同模型有不同意義；本文把目前價目和成交快照分開，是沿著這個問題做出的案例選擇，不是每張表都要變成一個 context。

## 交易交給下單用例，SQL 留在資料擁有者

下單用例決定先後順序、缺貨時回什麼，以及哪些結果一起提交。它呼叫公開介面，不親自更新庫存表。交易執行器則借用一條 MySQL 連線，把需要參與交易的模組介面綁在這條連線上。

下面是介面契約示意，不是可直接執行的 TypeScript。省略 HTTP 驗證、金額型別、鎖順序及完整冪等實作：

```text
transactionRunner.run(scope => {
  previous = scope.orders.findOrClaimOperation(key, payloadFingerprint)
  if previous is terminal: return previous

  price = scope.catalog.readPrice(sku)
  reservation = scope.inventory.reserve(sku, quantity)
  if reservation is outOfStock:
    return scope.orders.saveRejection(key, "out_of_stock")

  order = scope.orders.create(price, reservation)
  return scope.orders.saveSuccess(key, order)
})
// run 成功提交後，HTTP 層才傳回終局結果。
```

這裡的 key 指 `(customer_id, idempotency_key)`，沿用第一篇的使用者範圍。`reserve` 回傳缺貨時，必須保證本次沒有庫存或預留變更；`saveRejection` 隨正常交易提交保存終局結果。補貨後重送原鍵仍重放缺貨，新的購買意圖要用新鍵。

`findOrClaimOperation` 代表一份必須另外實作與驗收的併發契約：同鍵不同內容要拒絕、同鍵同內容要重放，同時首次請求不能都取得新操作資格。這段示意沒有解決 unique-key 競爭與重試演算法，也不能當作可上線實作。

MySQL 8.4 官方文件說明，autocommit 預設開啟；多敘述交易由同一 session 的 `START TRANSACTION`、`COMMIT` 或 `ROLLBACK` 管理。[InnoDB autocommit、commit 與 rollback](https://dev.mysql.com/doc/refman/8.4/en/innodb-autocommit-commit-rollback.html)

所以「同一個資料庫網址」或「共用同一個 pool」都不夠。若庫存 adapter 從 pool 另借連線，自行提交成功，下單外層的 rollback 不會撤銷那條連線上的提交。Laravel 或 Node.js 的 transaction callback，也要確認所有參與者實際使用了它綁定的連線。

**模組不得自行提交共同交易。** 庫存模組內再執行 `START TRANSACTION`，不能當成巢狀交易使用：MySQL 會隱式提交既有交易。某些框架以 savepoint 模擬巢狀 scope，那是另一層語意；不能靠函式名稱猜測行為。多種 DDL 也會造成隱式提交，schema migration 不應混進下單流程。[MySQL 隱式提交規則](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)

## 共用連線是一項刻意留下的耦合

這個方案讓資料規則集中，卻沒有得到獨立資料庫、獨立故障隔離或獨立部署。程式若仍使用同一組 DB 權限，封裝主要靠模組 API、相依檢查與審查；它不是惡意程式也無法穿越的安全邊界。

Shopify 在 2019-02-21 的 [Deconstructing the Monolith](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) 中，描述元件的公開 API 與資料專屬 ownership。那是單體內建立資料邊界的案例；文章也承認隔離仍在推進，不能引用成已完成百分之百隔離的證明。

沿用[容量篇](/blog/order-system-capacity-budget/)的假設：尖峰每秒 20 次嘗試，每次累計借用 DB 連線平均 0.08 連線秒，平均占用是 `20 × 0.08 = 1.6 條`。這次把寫入藏進模組，不會自動降低這個預算。若每個模組另開 pool，反而需要重算所有連線占用。

實作時應量測借用總時間、交易時間與鎖等待。若模組入口在持鎖期間呼叫外部 API，網路延遲也會拖長交易。此案例沒有付款呼叫；未來加入金流時，不能把遠端扣款塞進這份本地交易，就宣稱兩邊能一起 rollback。

## 兩個替代方案，各自省下什麼

### 讓下單用例直接寫所有表

初期檔案更少，追一條流程也比較直觀。如果系統只有很小的單一用例、沒有第二個寫入入口，這是可以考慮的起點。

代價在第二個入口出現時變明顯：後台補單、庫存調整或取消訂單各自複製 SQL，規則容易分散。本案例選擇資料 ownership，是因為預期會出現這些入口；不是因為多幾層介面本身就比較好。

### 把庫存移成獨立服務

獨立服務可以帶來不同的部署與擴縮方式，但原本的 MySQL 本地交易無法直接跨過 HTTP。庫存已預留、訂單沒成立時，必須重新設計預留期限、補償、重試與對帳，並重新檢討 `201` 的承諾。

當庫存確實需要獨立團隊與發布週期、不同安全或資料責任，或量測顯示有可由隔離解除的瓶頸，再提出拆分方案。只有檔案變多、或入口每秒 20 次，還不足以證明需要遠端服務。

## 驗收要故意破壞連線與寫入邊界

寫好目錄結構只能證明檔案被搬過。至少安排以下整合驗收，使用實際 MySQL InnoDB，而不是只用記憶體 fake：

- 庫存預留成功後、訂單建立前注入例外。交易結束後以另一條連線查詢，確認庫存恢復、預留及新訂單都不存在；成功冪等結果也不能留下。
- 故意把庫存 adapter 改成另一條 autocommit 連線。上一個測試應該失敗，證明測試抓得到漏回滾，而非永遠通過。
- 商品價格更新後查舊訂單，成交快照保持原值。另測本次讀價後才改價，確認行為符合選定的價格政策。
- 讓兩個請求同時使用相同鍵，檢查最多一張訂單、一次庫存預留，並測同鍵不同內容與缺貨結果重放。
- 搜尋跨模組 repository import，以及 raw SQL 對他人表的寫入。import lint 無法單獨保證 SQL 沒越界；需搭配 adapter 所有權、變更審查及反例測試。

以上是驗收計畫，本文沒有執行這些資料庫測試。效能也仍須回到容量篇的負載條件驗證，不能把封裝完成等同 SLO 通過。

## 練習：取消訂單由誰釋放庫存？

沿用尚未付款的案例。新增取消功能：只有已成立且未取消的訂單可以取消，取消與釋放預留必須一起提交；重送取消請求不能釋放兩次。

請寫出誰驗證訂單狀態、誰修改預留，以及誰負責 commit。再挑一個中途失敗點，說明交易後應查到什麼。不要先增加訊息佇列。

### 參考思路

取消用例協調共同交易，訂單模組驗證並轉換訂單狀態，庫存模組執行一次性的預留釋放。兩邊使用交易執行器提供的同一連線；誰先取鎖要有一致規則，不能每個入口各排一套。

可以在釋放預留後、保存取消狀態前注入失敗。若採本篇原子契約，交易後訂單仍成立、預留仍有效，可售數不能增加。重送成功取消請求時應重放結果或辨識已取消，不再次釋放。這份答案還需要併發與鎖策略才能實作，下一步先把它寫成可失敗的整合測試。
