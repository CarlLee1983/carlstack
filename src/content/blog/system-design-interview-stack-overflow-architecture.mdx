微服務（Microservices）與 Kubernetes 流行之後，很多工程師直覺認為：一個每天要接兩三億次 HTTP 請求的平台，一定需要大量微服務實例和複雜的分散式架構。

**Stack Overflow** 在自建機房時期走的是另一條路。根據 Nick Craver 2016 年的[架構文章](https://nickcraver.com/blog/2016/02/17/stack-overflow-the-architecture-2016-edition/)與 2019 年底的 [stackexchange.com/performance 存檔](http://web.archive.org/web/20191231070423/https://stackexchange.com/performance)，整個 Q&A 網路靠的是 **9 台 Web 伺服器**（2016 年的清單上有 11 台 IIS）、**4 台 SQL Server（分成 2 組叢集）**、**2 台 Redis** 與 **3 台 Tag Engine 伺服器**。Craver 在 [2013 年](https://nickcraver.com/blog/2013/11/22/what-it-takes-to-run-stack-overflow/)寫過，Web 伺服器平均 CPU 使用率在 5～15%，SQL Server 約 5～10%。2019 年的效能頁上，首頁平均渲染 12.2 毫秒、問題頁 18.3 毫秒。

這是 2013～2019 年的架構。2025 年 7 月 31 日機房合約到期，Stack Overflow 以這天為期限把公開站台搬到 Google Cloud，應用程式跑在 Kubernetes 上，前面是 Cloudflare 與 nginx，HAProxy 跟著機房一起退役（[Stack Overflow Blog，2025-08-28](https://stackoverflow.blog/2025/08/28/moving-the-public-stack-overflow-sites-to-the-cloud-part-1/)）。下面講的元件與數字，都以自建機房時期的公開資料為準。stackexchange.com/performance 現在已經是 404，只能看 Wayback Machine 的存檔；文中的每秒請求數是我用每日總數除以 86,400 換算的平均值，官方沒有直接公布。

「如何設計 Stack Overflow」是系統設計面試的經典題，考的是候選人懂不懂「讀多寫少業務特徵」、「快取階層」與「單體 vs. 微服務架構權衡」。下面先整理 Stack Overflow 公開過的數字與架構，最後再回到面試時怎麼答。

---

## 1. 業務特徵與容量估算（Capacity Estimation）

動手設計前，先估出系統的容量規模與核心限制。

- **讀多寫少（Read-Heavy）**：
  - 問答網站的流量大多是讀者從搜尋引擎進來看問題，提問、回答的人少得多，面試時通常就這樣假設。Stack Overflow 沒有公布前端的讀寫比；Craver 在 2013 年提過一個相關數字：資料庫放在記憶體裡、前面又有兩層快取，所以資料庫的磁碟存取反而是寫入居多，讀寫比 40:60。
- **流量指標**：
  - 2016-02-09 這一天，負載平衡器收到 209,420,973 次 HTTP 請求，其中 66,294,789 次是頁面載入，平均約每秒 2,400 次請求。
  - 2019-07-30 這一天是 308,065,226 次 HTTP 請求（[Craver，2019](https://nickcraver.com/blog/2019/08/06/stack-overflow-how-we-do-app-caching/)），平均約每秒 3,600 次。
  - 2019 年底的效能頁寫的是每月 13 億次頁面瀏覽。
- **儲存量**：
  - 2019 年兩組 SQL Server 叢集，一組記憶體 1.5 TB、資料庫 2.8 TB，另一組記憶體 768 GB、資料庫 3.9 TB。2025 年規劃上雲時，團隊估算要約 1.5 TB 記憶體才能把資料庫放進記憶體。

## 3. 撐起效能的幾個做法

### 3.1 快取：不做輸出快取，靠兩層資料快取

1. **CDN 不快取問答頁**：
   - Craver 在 [2019 年的快取文章](https://nickcraver.com/blog/2019/08/06/stack-overflow-how-we-do-app-caching/)寫明：「For the past several years, Stack Overflow (and all Q&A sites) output cache nothing.」
   - [2017 年的 HTTPS 文章](https://nickcraver.com/blog/2017/05/22/https-on-stack-overflow/)公開了 Fastly 上的 VCL：只有 `/users/flair/` 快取 180 秒，其他回應一律改成 `Cache-Control: private`，用他的話說是「bypass everything else」。
2. **L1：Web 伺服器的本機記憶體快取**：
   - 2019 年的快取文章把它分成 Global、Site、Local 三種，都放在各台 Web 伺服器的記憶體裡。Global 與 Site Cache 沒命中時會去 Redis 找；Local Cache 不經過 Redis，放的是取得成本低、但大到不值得來回 Redis 的資料。
3. **L2：Redis**：
   - 2016 年的架構文章說，L1 沒命中就從 Redis 取值；下一台需要這筆資料的伺服器就算 L1 沒命中，也能在 Redis 找到。Redis 同時負責 pub/sub，用來通知各台清掉 L1、推送 websocket 即時更新。2019 年每個資料中心只有 2 台實體 Redis 伺服器。

### 3.2 自行開發的 Dapper 微型 ORM

Stack Overflow 換掉的是 LINQ to SQL。Sam Saffron 在 [2011 年](https://samsaffron.com/archive/2011/03/30/How+I+learned+to+stop+worrying+and+write+my+own+ORM)寫道：「Much of our work at Stack Overflow depended on the assumption that LINQ-2-SQL is fast enough. Turns out it was not fast enough for us.」2016 年時，程式碼裡還留著一些 LINQ to SQL，新開發都用 **Dapper**。Dapper 的 [README](https://github.com/DapperLib/Dapper) 寫明它「originally developed for and by Stack Overflow」，是開源專案。

- 直接寫原生 SQL。
- Dapper 在執行期用 `DynamicMethod` 產生物件對應的 IL 程式碼（Emit IL），README 的基準測試裡，速度接近手寫的 `SqlCommand`。

### 3.3 標籤（Tag）檢索：獨立的 Tag Engine

Stack Overflow 的使用者常用標籤（例如 `[kubernetes]`、`[go]`）篩選問題。這件事交給獨立的 Tag Engine 服務，不走 Redis：

- 2016 年的架構文章說，Tag Engine 跑在一個以 http.sys 為基礎的「Stack Server」上，造訪 `/questions/tagged/java` 這類頁面就會打到它。2013 年與 2019 年它都跑在 3 台專用伺服器上。
- 2016-02-09 一天有 3,661,134 次 Tag Engine 請求，總共花了 147,018,571 毫秒（40.8 小時），平均每次約 40 毫秒（換算）。

### 3.4 SQL Server：兩組叢集，master 扛下幾乎所有負載

- 2016 年有 4 台 SQL Server，組成 2 組 AlwaysOn Availability Groups 叢集。每組有 1 台 master「taking almost all of the load」，讀寫都在它上面，另有 1 台在紐約的非同步副本。
- 2013 年 Craver 提到，備援機開始承接唯讀負載，主要是 Stack Exchange API。

## 4. 垂直擴展（Vertical Scaling）：何時不需要微服務？

- **單台硬體的極限比想像中高**：一台現代伺服器可以配 128 核心 CPU、2TB RAM 與高速 PCIe NVMe SSD。程式碼寫得夠精簡（沒有記憶體洩漏、沒有多餘抽象、沒有無效的網路跳轉），單台機器就能扛住數萬 QPS。Stack Overflow 2013 年的 Web 伺服器平均 CPU 只用到 5～15%。
- **沒有分散式網路開銷**：單體架構省掉了微服務之間的 RPC 序列化、網路延遲、分散式交易與服務發現開銷，維運也簡單得多。

## 5. 系統設計面試總結矩陣

下表是面試時的通用解法，不全是 Stack Overflow 的做法：它的標籤篩選用自建的 Tag Engine，問答頁也不放在 CDN 快取。

| 面試維度          | 推薦架構解答方案                                                               |
| :---------------- | :----------------------------------------------------------------------------- |
| 資料儲存選型      | RDBMS (PostgreSQL / MySQL) 儲存問題與解答實體，搭配全文索引                    |
| 快取階層架構      | CDN（靜態資源）-> Web 本地記憶體 -> Redis 分散式快取                           |
| 標籤多維度搜尋    | 獨立的標籤索引服務（如 Stack Overflow 的 Tag Engine）或 Elasticsearch 倒排索引 |
| 高併發投票與按讚  | Redis 記憶體計數 + Write-Behind 非同步批次回寫資料庫                           |
| 即時通知 (新回答) | WebSocket / SSE 長連線推播給線上的提問者                                       |
