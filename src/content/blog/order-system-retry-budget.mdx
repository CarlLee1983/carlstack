退款供應商變慢了。原本一秒內回來的請求，開始等到逾時。值班工程師把 worker 從兩個加到八個，想把待辦清掉；幾分鐘後，逾時更多，最早那筆退款還躺在佇列裡。

監控上的八個 worker 都很忙，客人卻沒有比較快拿到結果。

這是訂單系列的虛構案例。前幾篇已經處理[付款晚到後的退款處理](/blog/order-system-late-payment/)、[待辦索引](/blog/order-system-due-work-index/)與[畫面新鮮度](/blog/order-system-cache-read-contract/)。今天補上外呼出口：首次嘗試、重試與結果核對，都必須算進同一份供應商呼叫額度。多開 worker 不能憑空增加這份額度。

## 每次退款只試三次，仍可能一起塞住出口

「每筆最多三次」限制單筆花費，沒有約束同一秒有多少筆一起發送。假設每秒新進十筆退款，每筆最多三次嘗試，最壞情況每秒會形成約三十次外呼需求；這是持續流入下的粗估，不是任何單一秒的精確上限。再遇到整批工作同時醒來，瞬間尖峰還會更高。

若 HTTP SDK、worker 與外層排程各自重試，連「三次」是在哪一層算的都會失真。[AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)說明重試會加重已經過載的服務，也建議避免多層各自放大重試，並以退避與 jitter 分散呼叫時間。

本案例把重試決策集中在退款派送器。SDK 的自動重試必須納入同一計數，或在這個呼叫路徑關閉後由派送器負責。不能只看工作執行了幾次，要能數出實際送到供應商的嘗試。

## 限速與在途數，守的是兩種資源

系統仍是模組化單體、MySQL 持久待辦與少量 worker。第一版只安排一個供應商派送程序，停機時待辦留在資料庫；不為了做限速就先部署一套分散式協調服務。部署時不讓新舊程序重疊派送；重啟後先保守等待上一輪本地呼叫時限，再恢復平滑發送，不把停機期間當成可累積的額度。這仍不證明遠端已停止，未決案件要繼續核對。它有單點可用性的代價，但外呼額度的所有權清楚。

以下數字都是教學假設，未經壓測，也不是任何金流業者的限制：

- 每秒最多開始五次外呼，平滑發送，相鄰啟動至少間隔二百毫秒，不累積閒置額度來爆量補送。
- 最多十個本地在途呼叫。即使到了下一個發送時點，只要十個位置都被占用，也先不送。
- 每筆呼叫設連線與整體時限，範例整體時限三秒；實作需確認 DNS、TLS 與讀取是否都被涵蓋。

每秒五次控制啟動速率，十個在途位置控制本地同時等待的資源。若平均每次耗時零點五秒，五次／秒約占二點五個在途位置；若每次都等滿三秒，十個位置最多只能支撐約 `10 ÷ 3 = 3.33` 次／秒。取平均作這種估算只適合穩態理解，尖峰與尾延遲仍要另外量測。

本地逾時只代表我們不再等待，不保證供應商停止執行。所以十個位置不是「供應商最多同時執行十筆退款」的證明；遠端取消與查詢能力必須依實際契約確認。

首次呼叫、可安全重試的呼叫、結果核對，都要經過這個出口。若供應商各端點有不同配額，可再分子額度，但不能漏算共同的帳號總限制。增加第二個派送程序前，也必須決定額度如何分配；各自拿五次／秒，總數就已翻倍。

## 逾時的退款，先留下「不知道」

派送器拿到錯誤後，要先判斷它告訴了我們多少事。

欄位驗證失敗等明確拒絕，修正資料以前不重送。供應商明確回覆暫時無法接受，而且契約允許重試，才安排下一次嘗試。不能只憑所有 4xx 或所有 5xx 就做同一個決定。

送出後斷線、逾時或程序中斷，可能已經退款，只是答案沒回來。這類工作保留為結果待確認，沿用原業務操作識別值，優先利用供應商查詢、通知或對帳資料收斂結果。若契約明確提供仍有效的冪等重送能力，也可以照該契約重送；不能換一個新鍵來碰碰運氣。

[Stripe 的 API v1 冪等文件](https://docs.stripe.com/api/idempotent_requests)是具體例子：同鍵會回傳已保存的第一次回應，包括部分 500 結果；鍵被清除後再次使用可能被視為新請求。這說明「有冪等鍵」仍需要閱讀保存期限與錯誤語義，不能假定無限期安全。本篇的虛構供應商沒有被假定成 Stripe。

等待中的工作只保存下次可執行時間，不占住資料庫交易或連線睡覺。領取工作時用短交易建立處理權，交易結束後才外呼。程序在送出與記錄結果之間崩潰，接手者仍要依上述未知結果流程處理，不能把租約到期當成遠端未執行。

## 等待拉開了，總量還是要限制

對已確認可以重試的工作，範例使用帶隨機性的指數退避：第二次嘗試等一至二秒，第三次等一至四秒。這只是本案例的排程方式；供應商若給了有效的 Retry-After，至少等到該時點，再受共用出口限制。工作到期可執行，不代表立刻取得發送權。

本案例設定每個業務操作最多三次自動退款嘗試，並在受理後十五分鐘仍無終局時轉人工核對。核對查詢另有有限次數及間隔，仍計入五次／秒總額度，避免退款重送少了、查詢風暴卻來了。這些值都要與實際退款時效、冪等有效期間及維運能力一起調整；**超過自動處理預算，保留案件與責任人，不刪除未完成的退款。**

如果所有工作共用 FIFO，一批重試可能讓新工作長時間排不到。第一版可在首次嘗試與重試／核對兩組待辦間交替取件，各組按最早受理時間排序；某組空了才讓另一組使用空位。這會讓新工作有進展，也讓舊案不被永久餓死。分組不增加總額度，人工補送也必須走同一出口。

[Google SRE 的過載處理章節](https://sre.google/sre-book/handling-overload/)提醒，光看 QPS 不能完整描述資源成本，也討論在客戶端限制發送。對退款系統，這些原則的落點是同時觀察外呼速率、在途量、成功結案率與最老待辦年齡；worker 忙碌率不是完成率。

## 佇列能延後壓力，不能兌現無限等待

假設故障期間兩分鐘完全無法結案，每秒仍受理兩筆，就累積二百四十筆。恢復後若每秒確實能結案五筆，而新進仍是兩筆，淨消化速度是三筆／秒，理想上約八十秒清完。

這裡用的是「成功結案五筆／秒」，不是「發出五次／秒」。如果每筆平均耗兩次外呼，五次／秒只夠約二點五筆／秒，扣除新進兩筆後，二百四十筆要約四百八十秒才能清完；核對查詢也會再消耗額度。這些都是簡化推算，未模擬排程、失敗與延遲分布。

持續流入大於成功結案能力時，任何佇列最後都會滿。對尚未承諾受理的新申請，可以在接近容量或時效上限時明確拒絕並提供查詢方式；已受理、或業務上必須履行的退款，則保留並告警、擴大人工處理能力，不能靜默丟棄，也不能回報已完成。

另一個方案是讓客人的 HTTP 請求同步等退款結果。它少一段背景派送流程，低流量時容易理解；代價是供應商變慢會直接占用應用資源，客人斷線後仍需要未知結果核對。這個案例已有持久退款待辦，因此選擇背景處理，並承擔排程與可觀測性的成本。

若恢復後最老案件仍無法在承諾期限內結案，才討論協調更高供應商配額、縮減非必要查詢，或依供應商／帳號隔離派送。單純多開 worker，只在本地執行能力確實是瓶頸、且外部額度與資料庫容量都有餘裕時才有幫助。

## 驗收要看供應商變慢的那十分鐘

本文沒有執行金流 API 或壓測。以下是實作驗證計畫，不能當成通過結果。

在隔離環境用可控制的替身服務，依序注入快速成功、延遲三秒、先完成再中斷回應、明確拒絕與恢復正常。記錄每次實際外呼的啟動時刻、類型、操作識別值與本地在途數。核對平滑五次／秒與十個位置同時生效；把 SDK 隱藏重試也算進去。

讓一批工作同時到期，確認 jitter 與出口限制不會被重啟或人工補送繞過。再於外呼後、落庫前中止程序，驗證接手者保留未知結果並核對，同一業務操作不被換鍵重做。超過次數與時間上限的案件，要能在人工清單找到，並有可追溯的處理紀錄。

最後持續送入新工作，量故障解除後的最老待辦年齡是否下降。只有呼叫成功率恢復、積壓卻繼續增加，仍未恢復服務承諾。

這次的設計決定是：由同一個派送出口管理所有供應商呼叫，讓重試也付出額度；未決退款留在可核對的待辦裡。回到那八個忙碌的 worker，下一步應先把每秒外呼與成功結案畫在同一條時間軸上，找出究竟是工作做不完，還是同一件事做了太多次。

### 練習

故障後累積六百筆退款，每秒新進三筆；供應商允許每秒十次外呼，每筆平均需要兩次外呼才能結案。忽略其他瓶頸時，多久才能清完積壓？若產品要求兩分鐘內清完，你會先確認哪個假設，並調整哪項承諾或容量？

### 參考思路

十次外呼約支撐五筆結案，扣除三筆新進，淨消化兩筆／秒，需要三百秒。兩分鐘清六百筆需要每秒額外結案五筆，加上新進共八筆，按每筆兩次需要每秒十六次外呼。先確認「平均兩次」有沒有漏算核對、重試與長尾；配額未增加前，不能靠加 worker 承諾兩分鐘。也可以協商受理速度或結案期限，但已受理案件的責任要保留。
