一封客服來信寫著「付款完成了，但查不到訂單」。後端可以請語言模型協助把它分類成付款問題，再交給人處理。這個小功能已經會碰到 AI 開發最常見的問題：送了什麼資料、回答能不能用、錯誤怎麼發現，以及模型究竟可以做哪些事。

這份目錄以這個虛構練習貫穿學習順序。目標是把模型接進應用程式，不要求先訓練模型，也不要求為了入門改用另一種程式語言。[Itsrohitdev 的 AI 學習路線 Reel](https://www.facebook.com/reel/1421684673366162)提供了選題起點；以下依官方文件整理必要觀念，再連到本站適合的正文。文件查核日期為 2026 年 10 月 31 日，案例與練習數量是教學安排，沒有呼叫付費模型或宣稱準確率實測。

## 閱讀目錄：每一步只多接一項責任

1. [把模型當成有輸入輸出的 API](#把模型當成有輸入輸出的-api)：能區分 HTTP 成功與分類正確。
2. [知道模型看得到哪些資料](#知道模型看得到哪些資料)：分清模型回答、資料查詢與事實依據。
3. [用固定題目檢查提示修改](#用固定題目檢查提示修改)：能留下正常、含糊及惡意輸入案例。
4. [有文件缺口才加入檢索](#有文件缺口才加入檢索)：能判斷 SQL、關鍵字搜尋與向量檢索各處理什麼問題。
5. [工具權限與部署仍由程式負責](#工具權限與部署仍由程式負責)：知道何處限制讀取範圍、費用與副作用。

如果你要學的是「請 AI 幫忙寫程式」，可先讀另一條[AI Coding 入門路線](/blog/ai-coding-beginner-learning-route/)。兩者可以一起學，但寫得出功能與判斷模型回答是否可靠，是不同的練習。

## 把模型當成有輸入輸出的 API

一般 API 可以輸入訂單 ID，回傳資料庫裡的訂單。語言模型 API 接受指令與內容，再產生回應。例如 Anthropic 的 Messages API 接收結構化訊息，生成下一則訊息；這仍是一個需要驗證輸入、處理回應與錯誤的介面。[Messages API 官方參考](https://platform.claude.com/docs/en/api/messages)

第一個版本只做分類。輸入一段來信，輸出分類及是否交給人判讀，不允許它退款或修改訂單。這個應用層契約示意只描述輸入與驗收，不能直接當成供應商 API 請求：

```json
{
  "input": "付款完成了，但查不到訂單",
  "expected_output": {
    "category": "payment",
    "needs_review": true
  },
  "allowed_categories": ["payment", "delivery", "other"]
}
```

應用程式收到回應後，要檢查 JSON 是否能解析、欄位型別是否正確、分類是否在允許清單內。模型回傳 HTTP 200，只表示那次請求成功回應，不能代替分類正確性的判斷。格式不合約時可以交給人工，不應把原始文字直接塞進後續業務流程。

先讀[REST 與 GraphQL 的請求／回應基礎](/blog/rest-graphql-request-response-foundations/)，把「一次請求」「回應格式」「內部實際做了哪些工作」分開。這一步的小練習是拿三份假回應測接收端：合法分類、未知分類、缺少欄位。即使還沒接模型，也能先驗證自己的程式。

## 知道模型看得到哪些資料

分類器只收到來信，沒有收到付款紀錄。它可以判斷來信在談付款，卻沒有證據說「這筆款項已入帳」。模型產生的內容也可能與事實或提供的資料不一致。Anthropic 的降低幻覺指南建議允許不確定的回答，並要求可核對的來源依據。[降低幻覺官方指南](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)

這裡先記住三個詞就夠了。Prompt 是這次交給模型的指令與內容；context 是這次生成可使用的上下文；token 是模型處理文字等內容的單位，不等於固定一個中文字或一個英文單字。供應商會規定可接受的上下文與輸出長度，實際限制要查所選模型的文件。[模型術語官方說明](https://platform.claude.com/docs/en/about-claude/glossary)

工程上的第一個選擇是少送資料。客服分類練習可以使用自行編寫的來信，不需要姓名、電話、卡號或真實交易紀錄。如果之後要回答訂單狀態，應由後端查詢已授權的訂單，再把必要欄位提供給模型。

小練習是把「分類付款問題」與「確認付款成功」分成兩條驗收句。前者檢查文字分類，後者需要可信交易資料。這個區分可延伸讀[AI 與需求契約：保留成功、失敗和結果未知的差異](/blog/ai-abstraction-contracts-and-acceptance/)，但不必先完成整篇架構討論才能動手。

## 用固定題目檢查提示修改

提示可以直接寫成：「依來信內容分類為 payment、delivery 或 other；資訊不足時標示 needs_review；不要回答訂單狀態。」這已經交代任務、選項與限制。繼續加角色或形容詞之前，應先確認現有提示在哪些輸入上失敗。

評估（evaluation）就是用事先定義的案例和判準檢查結果。Anthropic 的評估文件要求成功條件具體、可測量，且與應用目標相關；除了任務表現，也可納入一致性、延遲及成本。[定義成功條件與評估](https://platform.claude.com/docs/en/test-and-evaluate/define-success)

練習時可自行編寫 12 封信：四封內容明確、四封同時提到付款與物流、四封資訊不足或夾帶「忽略規則」等指令。這個數量只是便於開始，不是品質保證。每封先由人寫下期望分類、可接受的模糊範圍，以及必須交給人處理的情況。

改提示後用同一批資料比較，把錯誤留下來；再準備未用來調提示的新題目檢查是否只迎合舊案例。如果格式合法率提高，卻把含糊來信都硬分成付款，修改仍有問題。也不要把模型自己輸出的「信心 99%」直接當成已校準的正確率。

## 有文件缺口才加入檢索

分類穩定之後，下一個練習可以是「根據店家的退貨說明，找出相關段落供客服閱讀」。這時才需要檢索：先找資料，再把相關內容交給模型，常稱為 retrieval-augmented generation，簡稱 RAG。[RAG 的資料與生成流程](https://www.anthropic.com/research/contextual-retrieval)

選什麼查詢方式，要看問題。訂單 ID 精確查狀態，用既有資料庫查詢即可；搜尋某個規則名稱，可以先試關鍵字。當使用者的說法和文件用詞不同，才評估語意檢索。Embedding 會把文字轉成數值表示，用來衡量語意相似程度；相似度高仍不代表文件正確、最新或對該使用者有權限。[Embeddings 官方說明](https://platform.claude.com/docs/en/build-with-claude/embeddings)

最小版本可先用少量公開練習文件，記錄每份文件的標題、版本與段落位置。驗收分兩次：搜尋是否找到正確段落，生成的答案是否真的受到段落支持。查錯文件時，換一個更會寫答案的模型也不能補回缺失的證據。

完成這個小版本後，才把[企業開源 AI 技術棧](/blog/open-source-ai-stack-blueprint-architecture/)當成進階比較資料。向量資料庫、自架推理與編排框架各有維護成本，不是第一堂課的安裝清單。

## 工具權限與部署仍由程式負責

工具呼叫讓模型要求外部能力。例如它可以提出 `lookup_order` 及訂單 ID，由應用程式執行查詢再回傳結果。以 Anthropic 的 client tools 為例，模型回傳結構化工具呼叫，實際執行發生在你的應用程式。[工具呼叫官方說明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

因此，查詢前仍要由後端確認登入者有權讀該筆訂單。模型提供的 ID 和來信內容都不能取代授權。第一個練習只開唯讀查詢，拒絕任意 SQL，也不讓分類功能順便退款。外部文件還可能夾帶誘導模型改變任務的指令，稱為 prompt injection；需要以最小權限、輸出驗證及高風險操作的人為確認限制影響。[OWASP Prompt Injection 防護指引](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

部署前可沿用熟悉的後端服務，補上單次逾時、使用量上限、有限重試與人工接手。記錄模型與提示版本、請求耗時、用量及失敗原因，但不要把原始敏感來信無限制寫進 log。是否要轉背景工作，取決於使用者能否等待與你的延遲量測，無須一開始就加佇列。

延伸閱讀可選[Agent 資料庫授權邊界](/blog/agent-database-authorization-boundary/)與[Trace Engineering](/blog/trace-engineering-for-agents/)。前者進一步討論授權路徑，後者處理多步工作追蹤，都超出第一版分類器的必要範圍。

## 練習：先決定一項不交給模型的工作

替這個客服分類功能寫下三件事：允許的輸入、必須交給人處理的輸出，以及模型不能直接執行的操作。再選一封同時提到「未收到商品」和「想退款」的來信，說明分類結果為什麼不能直接觸發退款。

### 參考思路

分類是對文字的判讀，退款還牽涉訂單歸屬、付款狀態、金額與業務規則。第一版可以只輸出分類與人工處理旗標，讓現有後端和人處理退款。先把這條界線寫進驗收案例，再考慮是否增加模型、檢索或工具。
