退款 worker A 送出請求後停住了。三十秒過去，接手的 B 向供應商核對，查到退款已完成，便把工作結案。這時 A 恢復執行，拿著先前的逾時錯誤，把同一筆工作改回「等待重試」。

客人的錢已經退了，後台卻又準備做一次。

這是虛構案例。即使平常只有一個派送程序，重啟交接也可能讓舊執行流程晚到。今天的決策是：每次取得工作都拿到新的 `attempt`，所有修改工作狀態的路徑都必須帶著它。資料庫只接受目前這一代的寫入。

這項保護有明確邊界：它能擋住 A 覆寫本地紀錄，不能收回已經送到金流的請求。退款是否發生，仍要靠供應商的證據確認。

## 同一筆退款，需要兩種不同的身分

沿用前篇的 MySQL 持久待辦與單一供應商派送出口。[待辦索引](/blog/order-system-due-work-index/)負責找到工作，[外呼預算](/blog/order-system-retry-budget/)負責限制發送；本篇補上工作交接後誰能寫回結果。增加接管機制不會增加供應商額度，核對與補送仍走同一出口。

工作表至少要分清楚這些欄位：

- `operation_key`：這筆業務退款的固定識別值，綁定付款、金額與幣別。A、B 接手的是同一筆退款，這個值不變。
- `attempt`：本地處理權的世代，例如 A 拿到 7，B 接手後拿到 8。每次領取或接管，在同一列鎖保護下遞增，不重設、不循環使用。
- `state`：排程狀態，例如 ready、running、succeeded、manual_review。供應商已受理但尚未完成時，不能直接寫 succeeded。
- `lease_until`：允許其他流程嘗試接管的時間，以資料庫的 UTC 時間判斷。
- `next_action`：下一步是首次送出，還是核對未知結果。接管 running 工作時，設定為核對。

若把 attempt 拼進供應商冪等鍵，A 用 `refund-123-7`、B 用 `refund-123-8`，供應商可能把它們當成兩筆退款。**attempt 用來撤換本地寫入者；operation_key 用來辨認同一筆業務操作。** 兩者不能互換。

欄位拆開也讓維運紀錄有用：看到同一 operation_key 出現三個 attempt，表示換過三次處理者，不等於已退款三次。

## 三十秒到了，代表可以接管

本案例選擇一個容易檢查的契約：租約期限到了，其他流程可以競爭接管；真正撤換寫入權的時點，是接管交易成功把 attempt 從 7 改成 8。

因此，若期限已過但尚未有人接管，A 仍可提交已確認的結果。若 B 先完成接管，A 的 attempt 就失效。這是刻意的設計選擇，不宣稱「時間一到，舊程序立刻停止」。

[AWS Builders' Library 的 leader election 說明](https://aws.amazon.com/builders-library/leader-election-in-distributed-systems/)提醒，程序可能在檢查租約後暫停；它恢復時，先前的判斷已經過期。把「呼叫前查一下還是不是我」當成唯一保護，無法處理這個空隙。

本地資料的裁決要放在實際寫入處。完成與接管都鎖住同一筆工作：A 先完成，B 就不能再接管 succeeded；B 先換代，A 的條件更新就不能成功。鎖的範圍只涵蓋短交易，等待金流時不持有資料庫列鎖或交易。

## 領取與回寫，必須遵守同一套條件

以下是 MySQL 8.4／InnoDB 的設計片段，尚未在資料庫執行；參數綁定、錯誤處理與完整 schema 省略，不能直接當成生產 worker。

首次領取時，在同一連線的短交易中以主鍵做 `SELECT ... FOR UPDATE`，確認仍是 ready 且已到期，再將 attempt 加一、state 改成 running、填入 lease_until，讀回新 attempt 後提交。只有提交成功，worker 才取得這次處理權；候選 SELECT 讀到 id 還不算領到。

接管也走同一條主鍵鎖定路徑，只是條件改成「仍為 running 且已到接管期限」。鎖住後重新確認狀態，將 attempt 加一、更新期限，並把 next_action 設為 reconcile。領取提交結果不明時，這個執行流程不進行外呼，交由後續排程檢查持久狀態；若已是 running，就等到符合接管條件再核對。不能因為沒收到 commit 回覆就再加一次世代，也不能只看到自己預期的 attempt 數字就認定那次提交屬於自己。

[MySQL 的鎖定讀文件](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)說明 `FOR UPDATE` 的交易與列鎖行為。這裡用它序列化單筆工作的交接，不需要為這個案例先引入 Redis 分散式鎖。日後若使用 `SKIP LOCKED` 增加領取並行度，也只是略過被鎖的候選，不能省掉回寫檢查。

取得可信的退款完成證據後，完成路徑使用下列條件更新：

```sql
UPDATE refund_jobs
SET state = 'succeeded',
    provider_refund_id = :verified_refund_id,
    lease_until = NULL
WHERE id = :job_id
  AND state = 'running'
  AND attempt = :my_attempt;
```

這條 UPDATE 和本地退款紀錄的完成變更，要放在同一筆交易。只在工作列確實轉移一筆時，才更新對應退款紀錄並提交；零筆就回滾這次狀態變更，讀回目前結果。使用相同資料庫連線，也不要讓 ORM 的另一個 repository 偷開獨立交易。

零筆可能是已被接管，也可能是同一完成操作先前已提交、回覆卻遺失。後者可以核對現有的終局與供應商退款識別值，確認是否已完成；兩種情況都不能移除 WHERE 條件強行補寫。[MySQL UPDATE 文件](https://dev.mysql.com/doc/refman/8.4/en/update.html)區分 matched 與實際 changed rows，實作時要核對 driver 回傳語義；本例成功會把 running 改成 succeeded，不依賴「同值更新」判斷。

同樣的 id、state、attempt 防線，也要套在重排、標記錯誤與轉人工的更新。只保護成功路徑，仍擋不住開頭那個遲到的逾時錯誤。

這裡沒有加入 `lease_until > NOW()`。寫入資格由目前 attempt 決定，時間只影響接管資格；[MySQL 日期函式文件](https://dev.mysql.com/doc/refman/8.4/en/date-and-time-functions.html)也說明 NOW() 取 statement 開始時的時間，不能把它當成精密的提交時刻檢查。所有接管時間統一由主庫取得，時鐘跳動仍會影響接管快慢，但不會讓舊 attempt 通過新一代的條件。

## 被擋下的結果，仍可能包含真的退款

B 接手後先核對原 operation_key 對應的退款證據。查詢方式必須依實際供應商能力設計，例如已保存的 provider_refund_id、商戶參考號或付款下的退款清單；不能假設每家都有「用冪等鍵查退款」的 API。若供應商確認退款已完成，B 可以依目前 attempt 提交結果；若查詢仍待處理，就繼續安排核對。查無紀錄時，還要確認查詢的可見性與原請求是否仍可能執行，不能立刻推論「沒有退款」。

只有供應商契約允許以同鍵、同參數安全重送，且仍在其保證範圍內，才安排重送。以 [Stripe API v1 的冪等文件](https://docs.stripe.com/api/idempotent_requests)為例，鍵的保存與清除會影響重送語義；不能拿一次建立的 key，假定半年後仍安全。本文的供應商是虛構的，沒有假定它提供 Stripe 的保證。

如果 A 在失去處理權後才收到可信的退款成功回覆，也不能把這份外部事實當垃圾丟掉。可以留下獨立的、可去重的回應觀察紀錄，交由目前處理者或對帳流程核實；觀察紀錄本身不授權 A 覆寫工作狀態。驗證過的 webhook 也應走統一的退款事實處理入口，避免另一條路徑把已完成狀態退回待辦。

**供應商無法提供可靠核對，也沒有仍有效的冪等保證時，未知退款停止自動重送，轉人工處理。** 多一個租約欄位不會讓這筆退款變得可判斷。

## 租約長度，付的是接管等待成本

沿用前篇每次本地外呼三秒的教學時限，這裡暫設三十秒接管期限、每五秒檢查一次過期工作。這些是待驗證參數，沒有壓測，也不代表任何金流產品的建議值。

在排程器正常、資料庫可用且忽略鎖等待的簡化模型下，程序剛領到工作就中止，接手者約需等三十至三十五秒才開始核對。這是接管開始的等待時間，還要加上供應商查詢與排隊時間，才接近客人看到終局的時間。

把期限縮成五秒，可以更早接管，但正常的排程延遲或程序暫停也更容易觸發交接，增加核對外呼。延長成五分鐘則減少交接，卻讓當機案件多等數分鐘。選值應對照單次處理時間分布、部署交接與產品允許的未決時間。

第一版不做持續續約：一次只領取能立即進入既有出口的工作，不預先領一大批再排隊等。需要下一次核對時，持久化排程後釋放本地處理流程。若未來出現確實需要長時間持有的工作，再加入帶 attempt 條件的續約，並驗證接管與續約競爭；心跳活著仍不能證明遠端操作完成。

另一個方案是讓資料庫交易跨越整次 HTTP 呼叫，靠列鎖阻止 B 接手。它少了一段世代判斷，代價是金流變慢就長時間占住交易與連線；程序在遠端成功後中止，本地交易照樣可能回滾，未知結果仍然存在。這個案例選短交易與顯式交接，承擔核對流程的成本。

## 驗收要讓舊程序真的回來

只把 A 殺掉、看到 B 成功接手，沒有驗到這次防線。以下是隔離環境的驗證計畫，本文未執行 MySQL 競爭測試或真實退款。

先讓 A 取得 attempt 7，暫停在外呼之後、回寫之前。推進到可接管時間，讓 B 取得 8，核對並結案；再恢復 A。A 的完成、錯誤重排與轉人工三種寫回都必須影響零筆，已完成的退款紀錄不得回退。

再交換順序：期限已到，A 先成功完成，B 隨後嘗試接管。B 應看到終局而退出。這一項專門驗證「期限只允許接管」的契約，避免維護者誤把它改成另一套到期失效語義。

最後用替身供應商模擬「已退款，但斷掉回應」。確認 B 沿用原 operation_key，接管本身不觸發新的業務退款；A 遲到的成功證據可被記錄與核對。另在本地完成交易提交後切斷連線，驗證重查終局能辨認已完成，不會為了零筆更新再退一次。

觀察接管次數、舊 attempt 拒絕次數、最老未決退款年齡與核對外呼占比。若正常運作也頻繁接管，先找程序暫停、期限過短或預領太多；若未決年齡超出承諾，才評估續約、排程分工或專用佇列。換佇列後，這些業務身分與舊結果檢查仍要保留。

開頭那筆工作需要的修正很具體：把所有 `UPDATE refund_jobs` 找出來，確認每條 worker 寫回都帶目前 attempt，再補一個「B 結案後 A 才回來」的固定測試。能接手只是恢復的一半，另一半是讓過期的處理者無法改寫接手者的決定。

### 練習

A 取得 attempt 12，期限已過，B 尚未接管。A 此時收到已驗證的退款完成回覆。依本文契約，A 能否結案？若 B 已把 attempt 改成 13，但尚未查到退款結果，A 又該如何處理這份回覆？請分開寫出工作狀態與外部證據的去向。

### 參考思路

尚未接管時，A 可用 running 與 attempt 12 的條件完成交易；若它先提交，B 就不能接管已結案工作。B 已取得 13 時，A 的狀態更新必須失敗，但可信回覆可作為獨立觀察留存，由目前處理者核實後結案。兩種順序都沿用同一 operation_key；期限與 attempt 不會產生第二筆退款的業務授權。
