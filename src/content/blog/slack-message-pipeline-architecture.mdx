在 Slack 頻道按下 Enter 之後，訊息要送到全球各地同頻道的人手上。Slack 在 2023 年 4 月 11 日的〈[Real-time Messaging](https://slack.engineering/real-time-messaging/)〉寫的是「our system delivers messages across the world in 500ms」，也就是全球投遞在 500 毫秒內。

這篇依 Slack 工程部落格的三篇原文整理這條路徑，三篇的年份不同：

- 〈[Flannel: An Application-Level Edge Cache to Make Slack Scale](https://slack.engineering/flannel-an-application-level-edge-cache-to-make-slack-scale/)〉，2017 年 5 月 31 日：邊緣快取 Flannel。
- 〈[Scaling Datastores at Slack with Vitess](https://slack.engineering/scaling-datastores-at-slack-with-vitess/)〉，2020 年 12 月 1 日：MySQL 遷移到 Vitess。
- 〈[Real-time Messaging](https://slack.engineering/real-time-messaging/)〉，2023 年 4 月 11 日：Gateway Server、Channel Server 這套即時訊息架構。

2023 年那篇沒有提到 Flannel，所以我不會把 2017 年的 Flannel 和 2023 年的 Gateway Server 畫成同一條路徑。文中標「通用設計示意」的段落（抖動重連、樂觀 UI、斷線補齊），是我補上的常見做法，Slack 一手資料裡沒有對應的描述。

<SlackMessagePipelineDiagram />

依 2023 年的文章，一則訊息的路徑是：

1. 客戶端呼叫 Webapp API 送出訊息。
2. Webapp 把訊息交給 Admin Server（AS）。
3. AS 用頻道 ID 查一致性雜湊環，找到負責這個頻道的 Channel Server（CS）。
4. CS 把訊息送給全球每一台有訂閱這個頻道的 Gateway Server（GS）。
5. 每台 GS 再送給連在自己身上、訂閱了這個頻道的客戶端。

## 1. 連線層：Envoy 與 Gateway Server（2023）

### 1.1 客戶端啟動與連線

2023 年的文章這樣描述客戶端啟動時的連線流程：

1. 客戶端開機時，先向 Webapp 後端取得使用者 token 和 WebSocket 連線設定。
2. 客戶端向最近的邊緣區域建立 WebSocket 連線。
3. Envoy 把連線轉給 GS，GS 再向 Webapp 取得這位使用者的資訊與頻道。
4. GS 先送出第一則訊息給客戶端，接著非同步訂閱持有這些頻道的 CS。

- **Envoy**：Slack 用它做負載平衡與 TLS 終結，並把客戶端的 WebSocket 連線轉給 GS。
- **Gateway Server**：有狀態、放在記憶體裡，存使用者資訊和 WebSocket 頻道訂閱。原文特別寫到，只有 GS 部署在多個地理區域，其他伺服器都不是。
- **Presence Server**：同樣在記憶體裡，追蹤哪些使用者在線上，客戶端的在線指示由它驅動。

### 1.2 驚群防禦與抖動重連（Jitter Reconnect，通用設計示意）

Slack 沒有公開客戶端的重連演算法，下面是常見的做法。某個區域或網路業者出狀況時，大量客戶端會同時斷線重連，如果不錯開，重連風暴會壓垮前端的連線伺服器。常見解法是**全抖動指數退避（Full Jitter Exponential Backoff）**：

```text
T_sleep = min(T_max, random(0, 2^attempt * T_base))
```

```typescript
// 通用抖動重連範例（不是 Slack 的程式碼，參數為假設值）
function calculateReconnectDelay(
  attempt: number,
  baseMs = 500,
  maxMs = 30000,
): number {
  const exponential = Math.min(maxMs, baseMs * Math.pow(2, attempt));
  // 完全隨機化，把重連流量的尖峰攤開
  return Math.floor(Math.random() * exponential);
}
```

## 2. 訊息寫入與訊息 ID（`ts`）

依 2023 年的文章，客戶端送訊息是呼叫 Webapp API；WebSocket 這條線負責把訊息推回給客戶端。

### 2.1 樂觀 UI 與 `client_msg_id`

Slack 的訊息事件裡有一個選填欄位 `client_msg_id`（見 Node SDK 的 [`GenericMessageEvent`](https://docs.slack.dev/tools/node-slack-sdk/reference/web-api/interfaces/GenericMessageEvent)）。Slack 客戶端怎麼用它，一手資料沒有說明。下面的流程是常見的樂觀 UI 做法（通用設計示意）：

1. 客戶端產生一個本地臨時 UUID 當 `client_msg_id`。
2. 立刻把訊息畫到聊天視窗，標成 `sending`。
3. 送出的 payload 帶上 `client_msg_id`。
4. 伺服器回傳正式的訊息 ID 後，客戶端改成 `sent`；逾時沒收到回應就顯示重送提示。

### 2.2 訊息 ID：看起來像時間戳的 `ts`

Slack 訊息的 `ts`（例如 `1725278400.000200`）長得像 UNIX 時間戳，但[官方文件](https://docs.slack.dev/messaging/retrieving-messages)說它其實是訊息 ID：「The `ts` value is essentially the ID of the message, guaranteed unique within the context of a channel or conversation.」文件也寫明它只是「partially composed in seconds-since-the-epoch」，只有一部分是 epoch 秒數。

官方保證的範圍是**同一個頻道或對話內唯一**，沒有保證全域唯一，也沒有承諾全域單調遞增。`ts` 怎麼產生、同時抵達的兩則訊息怎麼處理，Slack 沒有公開。

```sql
-- 訊息資料表結構示意（不是 Slack 的實際 schema）
CREATE TABLE channel_messages (
    workspace_id BIGINT UNSIGNED NOT NULL,
    channel_id BIGINT UNSIGNED NOT NULL,
    message_ts DECIMAL(16, 6) NOT NULL, -- 訊息 ID，只保證在頻道內唯一
    user_id BIGINT UNSIGNED NOT NULL,
    content TEXT NOT NULL,
    client_msg_id VARCHAR(64) NOT NULL,
    thread_ts DECIMAL(16, 6) DEFAULT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (channel_id, message_ts),
    UNIQUE KEY uk_client_msg (channel_id, client_msg_id)
) ENGINE=InnoDB;
```

## 3. 頻道扇出：Channel Server（2023）

訊息交給 AS 之後，接下來要分送給頻道裡在線上的成員。

### 3.1 我的推論：單純的 Redis Pub/Sub 會卡在哪

Slack 的原文沒有拿 Redis Pub/Sub 做比較，下面是我自己的推論，不是 Slack 寫出來的設計理由：

- **訂閱表膨脹**：如果每個使用者都向 Redis 訂閱自己加入的數百個頻道，訂閱表會膨脹到數千萬筆，記憶體和廣播的 CPU 開銷跟著上升。
- **大頻道廣播集中在單點**：5 萬人的頻道發一則訊息，單一節點要複製 5 萬次封包，網卡頻寬會先撐不住。

2023 年文章裡各元件的分工：

1. **Admin Server**：無狀態，介接 Webapp 後端和 CS。它透過一致性雜湊環找到負責某個頻道的 CS。
2. **CHARMs（consistent hash ring managers）**：管理 CS 的一致性雜湊環。雜湊設定登記在服務探索工具 Consul，AS 和 CS 都從 Consul 查。
3. **Channel Server**：有狀態、放在記憶體裡，保存頻道的一部分歷史。每個頻道 ID 經雜湊後對應到唯一一台 CS。原文寫尖峰時「about 16 million channels are served per host」，每台約 1,600 萬個頻道；文末另一處寫的是「tens of millions of channels per host」，原文前後的寫法不完全一致。
4. **故障替換**：不健康的 CS 會被很快換掉，新的 CS 不到 20 秒就能接手。替換期間，那些頻道的使用者會遇到不到 20 秒的投遞延遲升高。

扇出分成兩段：CS 送給每台有訂閱的 GS，GS 再送給自己身上的客戶端。CS 只面對 GS，不直接面對每個使用者。

推播通知不在這條路徑上。Slack 2017 年 12 月 6 日的〈[Scaling Slack's Job Queue](https://slack.engineering/scaling-slacks-job-queue/)〉把「every Slack message post, push notification, URL unfurl, calendar reminder, and billing calculation」列為 job queue 處理的工作。當時 job queue 前面用 Kafka 當持久緩衝，經 JQRelay 再進 Redis。推播由哪個元件觸發，原文沒有寫。

## 4. 儲存：Vitess 分片（2020）與 Flannel 邊緣快取（2017）

### 4.1 從按 workspace 分片，改成訊息按頻道分片

依 2020 年 12 月 1 日的 Vitess 文章，Slack 在遷移 Vitess 之前，資料是**按 workspace ID 分片**：一個 workspace 的資料全在同一個 shard，另有一個 metadata 叢集記錄 workspace 對應到哪個 shard。

這個做法碰到兩個問題：

- **大客戶撐爆單一 shard**：大型客戶的 shard「reached the largest available hardware」，已經用到能買到的最大機器，還是跟不上。
- **熱點**：原文寫「We found that we were hitting some major hotspots」。大型企業客戶把負載集中在少數 shard，其他大部分機器閒置，只好過度配置硬體。

原文寫 2016 年秋天時，Slack 的 MySQL 每秒要處理數十萬次查詢（「hundreds of thousands of MySQL queries per second」）。遷移到 Vitess 則從 2017 年開始。遷移的目標之一是「we wanted to shard the message data by the unique id of the channel」，訊息資料改按**頻道 ID** 分片，大客戶的訊息就不會全擠在一個 shard 上。

文章發表時（2020 年 12 月），「Vitess now serves 99% of our overall query load」，剩下 1% 預計兩個月內搬完。當時的尖峰約 230 萬 QPS（約 200 萬讀、30 萬寫），查詢延遲中位數 2 ms、p99 11 ms。

### 4.2 Flannel 邊緣快取（2017）

Flannel 是 2017 年的設計，2023 年的即時訊息文章沒有提到它。

當時客戶端連線時，伺服器會透過 `rtm.start` API 一次送出整個團隊的資料快照。團隊越大，頻道、使用者和 bot 的數量越多，這包資料就越笨重，客戶端啟動也跟著變慢。

Slack 的解法是自己開發 Flannel，「deployed to our edge points-of-presence」，部署在邊緣 PoP：

| 面向       | 原本：`rtm.start`      | Flannel                                                    |
| :--------- | :--------------------- | :--------------------------------------------------------- |
| 客戶端連線 | 向伺服器取完整快照     | 客戶端直接連 Flannel                                       |
| 啟動資料   | 整個團隊的資料一次送完 | 只回傳精簡過的啟動資料，其他依需要延遲載入                 |
| 快取內容   | 無                     | 使用者、頻道、bot 等相關資料                               |
| 保持更新   | 無                     | 對主 AWS 區域的 Slack 伺服器開一條 WebSocket，接收即時事件 |

原文給的數字：尖峰 400 萬個同時連線、每秒 60 萬次客戶端查詢。延遲載入讓啟動資料變小，1,500 人的團隊縮小為原來的 1/7，3.2 萬人的團隊縮小為 1/44。

## 6. 整理

| 問題             | Slack 公開過的做法                                             | 出處與時期                |
| :--------------- | :------------------------------------------------------------- | :------------------------ |
| **大量長連線**   | Envoy 做負載平衡與 TLS 終結，GS 部署在多個區域，存使用者與訂閱 | Real-time Messaging，2023 |
| **頻道扇出**     | AS 依 CHARMs 管理的雜湊環找到 CS，CS 送給有訂閱的 GS           | Real-time Messaging，2023 |
| **投遞延遲**     | 全球投遞 500ms                                                 | Real-time Messaging，2023 |
| **訊息 ID**      | `ts` 看起來像時間戳，實際是頻道內唯一的訊息 ID                 | 官方開發者文件            |
| **儲存擴展**     | 遷移 Vitess，訊息資料從按 workspace 改成按頻道 ID 分片         | Vitess 文，2020           |
| **啟動資料過大** | 邊緣 PoP 部署 Flannel，精簡啟動資料並延遲載入                  | Flannel 文，2017          |

三篇合起來看，我讀到的共同點是**按頻道切分**：2023 年的 CS 以頻道 ID 雜湊決定由哪台負責，2020 年的 Vitess 遷移把訊息資料改按頻道 ID 分片，取代原本按 workspace 切、會產生熱點的做法。這是我對三篇的歸納，Slack 沒有這樣總結過。
