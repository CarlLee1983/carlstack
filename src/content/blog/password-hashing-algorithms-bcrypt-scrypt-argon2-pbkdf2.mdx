資料庫外洩後，攻擊者能拿雜湊值離線猜密碼。單次 SHA-256 運算太便宜，加鹽也無法增加每次猜測的工作量；密碼儲存需要可調成本的專用演算法。

以大小寫英文字母及數字為例，8 位密碼空間是 `62⁸ = 218,340,105,584,896`。若假設每秒測試 100 億次，完整枚舉約 6.1 小時，均勻分布下平均約 3 小時。這是算式示例，不是特定 GPU benchmark；真實人選密碼常有偏好，攻擊也不一定完整枚舉。

選型依據為 [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) 與 [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)。程式範例聚焦雜湊 API 與輸入限制，完整認證系統還需限流、帳號保護與憑證生命週期管理。

## 1. 為什麼快速雜湊無法保護密碼？

SHA-256 適合快速計算摘要，直接用它儲存密碼會讓攻擊者以相同低成本大量猜測。

### 威脅核心：彩虹表與硬體暴力枚舉

1. **未加鹽的彩虹表攻擊（Rainbow Tables）**：若密碼僅經過單純雜湊，攻擊者可預先計算常見密碼的雜湊映射表，在取得資料庫時透過查表瞬間反解。
2. **GPU 與專用 ASIC 平行算力碾壓**：SHA-256 單次運算的記憶體需求低，不同候選密碼可平行測試。實際速率取決於硬體與實作。

### 防禦核心哲學：可調工作因子與記憶體硬性

安全密碼雜湊演算法的核心思想是**讓運算故意變慢，並強制消耗特定實體資源**：

- **正常使用者登入**：以產品可接受的延遲預算選擇參數，並在預期併發下量測尾端延遲。
- **攻擊者離線暴力破解**：若單一工作者每次花 200 毫秒，依序猜 1 億次約需 231 天。攻擊者可增加工作者；記憶體硬性提高平行攻擊的資源成本，無法完全禁止加速。

## 3. 四大現代密碼雜湊演算法技術對決

不同演算法在運算瓶頸與防禦維度上具備不同特性：

- **Argon2id**：新系統可優先考慮。OWASP 最低建議之一是 `m=19456 KiB, t=2, p=1`；成本須在目標硬體與併發下量測。
- **scrypt**：Argon2id 不可用時的選項。OWASP 列出的最低配置之一為 `N=2¹⁷, r=8, p=1`。
- **bcrypt**：主要用於既有系統。OWASP 建議 cost 至少 10，並處理實作的輸入長度限制。
- **PBKDF2-HMAC-SHA256**：有 FIPS 要求時可評估經驗證的模組與至少 600,000 次迭代；採用演算法名稱本身不代表產品已合規。

## 4. 架構防禦升級：Pepper 與 KMS/HSM 整合

許多團隊實作了加鹽（Salt），但鹽的作用僅在於**讓不同密碼記錄使用不同隨機值，降低預計算重用與相同密碼辨識的效益**。鹽隨同雜湊值明文儲存於資料庫內，一旦資料庫發生整庫外洩（如 SQL 注入、備份檔遺失），攻擊者依然能直接取得鹽與雜湊值，立即展開離線運算。

### Salt vs. Pepper

- **Salt（鹽）**：由 CSPRNG（加密安全隨機數產生器）動態生成，每個使用者各自獨立，公開儲存於資料庫中。
- **Pepper（胡椒）**：全系統共用的高熵機密值（例如 256 位元隨機字串），**絕對不與雜湊值存放於同一個資料庫**。

### 縱深防禦實踐：HMAC 與 KMS 託管

若採用 Pepper，可將金鑰託管於 AWS KMS、GCP Cloud KMS 或 HashiCorp Vault：

```
密碼輸入 ──> HMAC-SHA256(password, KMS_Pepper) ──> Argon2id 雜湊計算 ──> 儲存 DB
```

1. **SQL 注入防護**：攻擊者拖庫取得雜湊資料，但無法取得應用程式執行時記憶體或受嚴格 IAM 控管的 KMS 金鑰，在 Pepper 未洩漏且無法呼叫 HMAC 服務的前提下，無法只靠資料庫驗證猜測。應用權限或金鑰服務一起失守時，這層保護也會失效。
2. **權限分離與稽核**：若由 KMS 執行每次 HMAC，可稽核服務呼叫；若應用取回並快取 Pepper，日誌只記錄取用，不能代表每次驗證。另需規劃金鑰版本、輪替與服務故障處理。

> [!TIP]
> 採用「前置 HMAC」處理 Pepper（即先將密碼與 Pepper 經由 HMAC 運算，再傳入 Argon2id）能在維持固定輸入長度的同時，確保 Argon2id 原生計算流程不受干擾。

## 5. 既有系統盲區：Bcrypt 的 72 位元組截斷陷阱

儘管 Bcrypt 應用廣泛，但其底層繼承自 Eksblowfish 區塊加密演算法，存在一個廣為人知卻常被忽略的先天限制：**密碼有效輸入長度上限為 72 位元組**。

### 72-byte 截斷機制與安全隱患

部分 bcrypt 實作會截斷超過 72 位元組的輸入，另一些會直接拒絕。以截斷實作、相同 salt 與成本參數為例：

- `SuperSecretPassword...`（長度 72 位元組）
- `SuperSecretPassword...ExtraCharactersHere`（長度 100 位元組）

若兩個輸入的前 72 位元組相同，在上述條件下會得到相同結果。不同隨機 salt 則不會產生相同儲存字串。這意味著使用者設定更長的密碼並未提升安全性，甚至可能造成不同密碼驗證通過的非預期行為。

### 因應策略比較

1. 既有 bcrypt 系統應明確拒絕超過實作限制的輸入，並以 UTF-8 位元組計數。不要悄悄改變既有密碼的編碼或正規化規則。
2. 預雜湊需要獨立格式版本。直接 `bcrypt(SHA256(password))` 可能引入 password shucking 風險，不能只修正長度就視為安全。若有既定預雜湊設計，須按 OWASP 核對具 Pepper 的 HMAC、編碼及金鑰管理；原始二進位可能含 NUL，部分綁定會提早截斷。
3. 新系統可用 Argon2id 避開 bcrypt 的 72-byte 限制，仍需設定合理的輸入長度上限，且不靜默截斷。

## 6. 伺服器端的可用性挑戰：高併發與 DoS 防禦

慢速記憶體硬性雜湊是一把雙面刃：它拉高了攻擊者的算力成本，同時也佔用了伺服器的寶貴運算資源。

### 威脅情境：記憶體與 CPU 資源耗盡

假設系統 Argon2id 設定為 `m=65536`（64 MiB RAM）、單次運算 150 毫秒：

- 若同時執行 1,000 個雜湊工作，後端將在短瞬間需要配置62.5 GiB 的記憶體與巨量 CPU 核心。
- 在 Node.js、Go 或 Python 單體應用中，這可能導致作業系統觸發 OOM Killer 強制結束服務，或使主執行緒 Event Loop 嚴重阻塞，造成正常使用者無法連線。

### 工程防護措施

1. **執行緒池或獨立微服務隔離（Worker Isolation）**：
   將雜湊驗證與計算任務移至獨立的 Worker Thread 池或專門的認證微服務，避免阻塞主 Web 伺服器；同時設定工作者數與佇列上限。僅移到另一個執行緒，沒有降低總記憶體需求。
2. **前置限流（Rate Limiting）**：
   在入口 API Gateway 或反向代理層實施 Token Bucket / Leaky Bucket 限流，針對單一 IP 與單一使用者帳號設定嚴格登入頻率限制（例如每分鐘最多 5 次嘗試）。
3. **應用層長度硬性驗證**：
   在密碼進入雜湊運算前，於驗證層強制拒絕異常超長字串（例如上限 128 位元組），直接防止攻擊者以數十 MB 的畸形字串消耗伺服器記憶體。

## 7. 多語言生態系實作範例

### 7.1 Python (`argon2-cffi`)

以下 `64 MiB, t=3, p=4` 對應 RFC 9106 的第二組建議，不是 OWASP 的最低配置，也不保證 200 毫秒內完成。`memory_cost` 是總 KiB，`parallelism` 是 lane 數，不能再乘一次記憶體。

```python
import argon2

hasher = argon2.PasswordHasher(
    time_cost=3,        # 迭代輪數 (Iterations)
    memory_cost=65536,  # 記憶體消耗 (64 MiB RAM)
    parallelism=4,      # 平行執行緒數 (4 Threads)
    hash_len=32,        # 輸出雜湊長度 (Bytes)
    salt_len=16         # 隨機鹽長度 (16 Bytes CSPRNG 生成)
)

# 1. 密碼雜湊
hashed_str = hasher.hash("MySuperSecurePassword123!")
# 輸出標準格式: $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>

# 2. 登入驗證
try:
    hasher.verify(hashed_str, "MySuperSecurePassword123!")
    print("驗證成功")
except argon2.exceptions.VerifyMismatchError:
    print("密碼錯誤")
```

### 7.2 Node.js / Bun (`@node-rs/argon2`)

`@node-rs/argon2` 的 [API 型別定義](https://github.com/napi-rs/node-rs/blob/main/packages/argon2/index.d.ts)使用 `Algorithm.Argon2id`。驗證端只應接受資料庫內、由受控寫入流程產生的雜湊，並在呼叫前限制可接受的成本參數與字串長度：

```typescript
import { hash, verify, Algorithm } from "@node-rs/argon2";

const hashingOptions = {
  algorithm: Algorithm.Argon2id,
  memoryCost: 65536, // 64 MiB
  timeCost: 3, // 3 輪迭代
  parallelism: 4, // 4 執行緒
  outputLen: 32,
};

// 1. 產生雜湊
export async function hashPassword(password: string): Promise<string> {
  return await hash(password, hashingOptions);
}

// 2. 驗證密碼
export async function verifyPassword(
  password: string,
  hashString: string,
): Promise<boolean> {
  return await verify(hashString, password);
}
```

### 7.3 Go (`golang.org/x/crypto/argon2`)

Go 延伸庫提供底層 Argon2id。這個教學版本以參數白名單避免從不可信字串配置任意記憶體或零次數；仍須在外層限制併發與記錄驗證錯誤：

```go
package password

import (
    "crypto/rand"
    "crypto/subtle"
    "encoding/base64"
    "errors"
    "fmt"
    "strings"

    "golang.org/x/crypto/argon2"
)

// 教學白名單：只接受這一組參數。遷移需明列其他核准版本，不能直接信任字串內成本。
const prefix = "$argon2id$v=19$m=65536,t=3,p=4$"
const maxPasswordBytes = 1024

func HashPassword(password string) (string, error) {
    if len(password) > maxPasswordBytes {
        return "", errors.New("密碼過長")
    }
    salt := make([]byte, 16)
    if _, err := rand.Read(salt); err != nil {
        return "", err
    }
    key := argon2.IDKey([]byte(password), salt, 3, 65536, 4, 32)
    return fmt.Sprintf("%s%s$%s", prefix,
        base64.RawStdEncoding.EncodeToString(salt),
        base64.RawStdEncoding.EncodeToString(key)), nil
}

func VerifyPassword(password, encoded string) (bool, error) {
    if len(password) > maxPasswordBytes || len(encoded) > 256 ||
        !strings.HasPrefix(encoded, prefix) {
        return false, errors.New("不支援的格式或成本參數")
    }
    parts := strings.Split(strings.TrimPrefix(encoded, prefix), "$")
    if len(parts) != 2 || len(parts[0]) != 22 || len(parts[1]) != 43 {
        return false, errors.New("無效的鹽或雜湊長度")
    }
    salt, err := base64.RawStdEncoding.Strict().DecodeString(parts[0])
    if err != nil || len(salt) != 16 {
        return false, errors.New("無效的鹽")
    }
    expected, err := base64.RawStdEncoding.Strict().DecodeString(parts[1])
    if err != nil || len(expected) != 32 {
        return false, errors.New("無效的雜湊")
    }
    actual := argon2.IDKey([]byte(password), salt, 3, 65536, 4, 32)
    return subtle.ConstantTimeCompare(actual, expected) == 1, nil
}
```

## 8. 漸進式遷移（Zero-downtime Migration）

將既有系統從舊演算法（如 Bcrypt 或 Legacy SHA-256）遷移至 Argon2id，或升級 Argon2id 的成本參數時，可採用登入時觸發的漸進式重新雜湊（Re-hash on Login）模式。已知外洩、Pepper 遺失或長期未登入帳號可能需要重設密碼。

```text
使用者提交密碼
       │
       ▼
 驗證演算法版本
 ├─ Legacy SHA-256 ──> SHA-256 校驗 ──> 驗證成功 ──> 標記需要升級
 ├─ Bcrypt ──────────> Bcrypt 校驗  ──> 驗證成功 ──> 標記需要升級
 └─ Argon2id ────────> Argon2 校驗  ──> 檢查參數 ──> 若低於現行標準則標記需要升級
       │
       ▼
 驗證通過且需要升級？
 ├─ 是 ──> 使用最新 Argon2id 參數重新計算雜湊 ──> 寫回 DB 覆蓋舊資料
 └─ 否 ──> 完成登入
```

### 遷移邏輯實作模式

```text
# 概念流程，verifyByVersion 與資料庫操作需由應用實作
current = readCredential(userId)  # 同時讀 hash、演算法版本與 credentialVersion
valid = verifyByVersion(current, password)  # 未知格式直接拒絕
if not valid:
    return authenticationFailed
if needsUpgrade(current):
    newHash = hashWithCurrentPolicy(password)
    changed = compareAndSwapCredential(
        userId, expectedVersion=current.credentialVersion, newHash=newHash)
    if not changed:
        return retryAuthentication  # 可能與改密碼／重設競爭，不覆寫新版
return authenticated
```

透過此機制，活躍使用者的憑證將在日常登入中自動完成無感升級；一段時間後未登入的冷資料，可進一步配合強制信件重設機制完成收尾。

## 9. 密碼儲存的工程檢核清單

1. **每次雜湊產生隨機 Salt**：由 CSPRNG 生成，長度至少 16 位元組，並隨雜湊值妥善保存以防禦彩虹表。
2. **引進 Pepper 建立縱深防禦**：全域金鑰託管於 KMS 或 HSM，與資料庫物理隔離，在金鑰與呼叫權限未失守時增加防護。
3. **前置長度與頻率限制**：應用層限制密碼長度上限（如 128 位元組），入口層落實 Token Bucket 限流，抵禦運算耗盡型 DoS 攻擊。
4. **防範 Bcrypt 72 位元組截斷**：若使用 Bcrypt，必須謹慎處理 Pre-hashing 編碼；新系統優先評估 Argon2id，仍保留輸入上限。
5. **落實自動重新雜湊架構**：系統保留 `needsRehash` 介面，支援演算法跨代演進與工作因子的平滑升級。
6. **嚴禁自創密碼學實作**：永遠採用經過嚴格同行評審的標準加密函式庫。

## 10. 結論與選型指引

- **全新系統規劃**：優先選用 **Argon2id**（RFC 9106），依伺服器負載配置適當記憶體硬性（建議 `m=65536`, `t=3`, `p=4`）。
- **現行 Bcrypt 系統**：若已穩定執行，可維持使用並依 OWASP 至少使用 cost 10，並以壓測決定更高值，同時注意 72 位元組邊界；有長密碼需求或重構計畫時再行規劃遷移。
- **絕對禁止情境**：切勿在任何正式環境中採用 MD5、SHA-1、SHA-256 或 SHA-512 單向雜湊直接儲存使用者密碼。
