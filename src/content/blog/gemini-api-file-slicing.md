問一份財報「去年營業利益的變動來自哪裡」，答案可能在一張圖表與下一頁的註腳。整份 PDF 可以一次交給模型。若同一份文件常被拿來回答不同問題，每次都讀整份，花在無關頁面上的用量就會累積。

Google 在 2026 年 11 月 23 日宣布 [Gemini API 的檔案分段功能](https://blog.google/innovation-and-ai/technology/developers-tools/file-slicing-controls/)。Gemini 4 系列可指定 PDF 或簡報頁面、試算表的工作表與儲存格範圍，以及音訊或影片的時間段。公告也新增 Office 與 OpenDocument 格式的原生上傳。格式、處理選項與計費說明依 Google 公開文件，以下未呼叫正式 API，也沒有實測節省比例。

## 同一份文件可以讀兩次

以財報問答為例，第一輪先看抽出的頁面文字，找圖表標題與註腳的位置。第二輪重用 Files API 回傳的 URI，指定候選頁碼，以頁面影像讀取圖表。圖表與註腳跨頁時，把兩頁一起交給模型。回覆要能追到來源頁碼，後端才能分辨引用的是主表還是附註。[Google 的文件處理說明](https://aistudio.google.com/docs/document-processing)列有頁面範圍、解析度及內容層的選項。

文字初掃容易錯過掃描頁上的字，圖表也可能只以圖片存在。如果找不到候選頁，或找到的頁面無法支持答案，應用可以先擴大到鄰頁，再依任務決定用全文或回覆「未找到足夠證據」。對只有幾頁的文件，一次讀完通常更容易做為比較基準。若任務要找出所有例外項目，也不宜把範圍限於第一輪找到的頁面。

這裡選的是模型此次要讀的範圍。走 Files API 時，完整原始檔仍先送到服務端，原檔也受檔案大小與頁數限制。若政策只准對外傳送指定頁，應在本地裁切或遮蔽後再上傳，另外保存原始頁碼對照。伺服器端的頁面選擇不能取代上傳前的資料檢查。[Files API 文件](https://aistudio.google.com/docs/files)說明檔案管理及重用方式；模型端點的資料處理則是另一個檢查項，可對照 [OpenRouter 的推論路由與資料保留](/blog/openrouter-inference-data-retention/)。

## 把漏掉的頁面算進成本

挑一份可公開上傳的 PDF，事先標好答案所在頁。題目至少要包含單頁文字、跨頁註腳、只在圖片裡的數值，以及文件根本沒寫的問題。用同一個模型、問題和輸出格式比較三條路徑：

- 全文直接讀取。記下答案有沒有引用正確頁碼，作為品質基準。
- 全文低成本初掃，接著讀取候選頁的影像。記下初掃漏掉的頁數，以及之後為了補頁增加的請求。
- 已知頁碼時，本地先裁切再上傳。這條路徑多了前處理，但可以控制哪些內容會離開本機。別忘了保留裁切後頁碼到原始頁碼的對照。

每次任務加總初掃、細讀、重試及全文回退的輸入與輸出用量。記錄從上傳到得到可引用答案的時間，另留「應該拒答卻猜了答案」的次數。Google 說模型只按這次檢查的內容計入相應的 token。若一題要連讀三次才能答對，單次 token 較少仍不代表整題便宜。

測第一批問題時，保留全文路徑，對照跨頁題和無答案題的結果。分段讀取得到同等的答案與引用品質，再依完整任務成本和延遲決定是否切換；需要逐頁無遺漏的任務則另外驗收，不沿用問答測試的結論。

工具清單也可以延後載入，但它有另一套用量與往返條件，見 [Gemini API 的工具檢索](/blog/gemini-api-tool-retrieval/)。
