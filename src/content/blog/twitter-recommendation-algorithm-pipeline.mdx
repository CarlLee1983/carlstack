2023 年 3 月 31 日，當時還叫 Twitter 的 X 發表 [_Twitter's Recommendation Algorithm_](https://blog.x.com/engineering/en_us/topics/open-source/2023/twitter-recommendation-algorithm)，同時開源 [`twitter/the-algorithm`](https://github.com/twitter/the-algorithm) 與 [`twitter/the-algorithm-ml`](https://github.com/twitter/the-algorithm-ml)。依那篇文章，「為你推薦（For You）」時間軸要把每天約 5 億則新推文篩到少數幾則，整條管線每天執行約 50 億次，**平均**不到 1.5 秒完成，單次執行要花 220 秒的 CPU 時間。

下面描述的都是 2023 年開源時的版本，依據是那篇部落格文、兩個 repo 的 README 與程式碼。X 在 2026 年 1 月另外開源了新的 For You 管線，元件已經不同，放在文末[另一節](#2026-年另外開源的-xai-orgx-algorithm)說明。

## 階段 1：候選檢索（從數億則到 1,500 則）

不可能對每天數億則推文都跑一次深度模型，所以第一步是**候選檢索（Candidate Sourcing）**。部落格寫的是：每次請求，從數億則推文的池子裡，透過幾個候選來源取出最好的 1,500 則。

候選分成兩類：使用者關注的人發的推文（**In-Network**），以及沒關注的人發的推文（**Out-of-Network**）。部落格說，For You 時間軸**平均**各占一半，但因人而異。這是最終時間軸的平均比例，不是候選池的固定配額。

### 1. In-Network 檢索：Earlybird 與 Real Graph

In-Network 找的是使用者關注的人最近發的推文，部落格說它是最大的候選來源。

- **索引**：依 [Earlybird 的 README](https://github.com/twitter/the-algorithm/blob/main/src/java/com/twitter/search/README.md)，Earlybird 是基於 Apache Lucene 的即時搜尋系統，用分片並複製的分散式倒排索引。其中 realtime 叢集索引大約最近 7 天的公開推文。Following 與 For You 兩個分頁的站內推文，主要都從它取得。
- **排序**：部落格寫，In-Network 來源用 logistic regression 模型依相關度排序關注對象的推文，最重要的元件是 **Real Graph**，它預測兩個使用者之間互動的可能性。你和作者的 Real Graph 分數越高，這位作者的推文就收得越多。
- **背景**：同一篇文章提到，Twitter 不久前才停用 Fanout Service。這個服務用了 12 年，原本為每個使用者維護一份推文快取，用來提供站內推文。

### 2. Out-of-Network 檢索：GraphJet 與 SimClusters

Out-of-Network 找的是使用者沒關注、但可能感興趣的推文。部落格提到兩類做法。

#### A. 社交圖遍歷：GraphJet

部落格用兩個問題描述這類做法：「我關注的人最近和哪些推文互動？」「和我喜歡相似推文的人，最近還喜歡什麼？」執行這些遍歷的是 **GraphJet**，一套維護「使用者 ⇄ 推文」即時互動圖的圖處理引擎。repo README 介紹的 User Tweet Entity Graph（UTEG）就建在 GraphJet 上，在記憶體中保存這張互動圖。

部落格也說，這類圖遍歷當時只供應約 15% 的首頁時間軸推文，關注圈外推文的主要來源已經是下面的嵌入空間做法。

#### B. 嵌入空間：SimClusters

- SimClusters 用自訂的矩陣分解（Matrix Factorization）演算法，以一群有影響力的使用者為核心找出社群。2023 年時有 **14.5 萬個社群**，每三週更新一次。
- 使用者和推文都表示在這個社群空間裡，可以同時屬於多個社群。
- 推文嵌入到各社群的方式，是看它目前在該社群的熱門程度。

## 階段 2：Home Mixer 與特徵取得

**Home Mixer** 負責串起整條管線。依部落格與 [`home-mixer/README.md`](https://github.com/twitter/the-algorithm/blob/main/home-mixer/README.md)，它建在 Twitter 自己的 Scala 框架 Product Mixer 上，把候選來源、評分函式、啟發式規則與過濾器接在一起。

1. **取得候選**：README 列出的候選來源是 Earlybird 搜尋索引、User Tweet Entity Graph、Cr Mixer 與 Follow Recommendations Service。這份清單沒有直接列出 SimClusters。2023 年的 repo 首頁說明，Cr Mixer 是從底層運算服務取得站外候選的協調層。
2. **取得特徵（Feature Hydration）**：README 寫的是取得排序需要的約 **6,000 個特徵**，部落格的說法是「數千個特徵」。

## 階段 3：Heavy Ranker，約 4,800 萬參數的 MaskNet

候選和特徵備齊後，交給 **Heavy Ranker** 評分。部落格寫，這是一個約 **4,800 萬參數**的神經網路，持續以推文互動資料訓練。這個階段不管候選來自哪個來源，一律同等對待。

依 [Heavy Ranker 的 README](https://github.com/twitter/the-algorithm-ml/blob/main/projects/home/recap/README.md)，模型架構是 parallel **MaskNet**，輸出 10 個介於 0 到 1 之間的數字，每個代表使用者以某種方式和這則推文互動的機率。

### 多目標預測與加權公式

十個機率再依權重加總，得到這則推文的分數。README 寫的公式是：

```text
Score = Σ [ w_i × P(Action_i) ]
```

權重來自設定檔，README 說它「隨時可以調整」。下表是 README 在 **2023 年 4 月 5 日**更新時列出的權重（3 月 31 日的初版數字有幾項不同，例如一般回覆是 27）：

| README 中的名稱           | 預測的行為                                 | 權重     |
| :------------------------ | :----------------------------------------- | :------- |
| `fav`                     | 按讚                                       | `0.5`    |
| `retweet`                 | 轉發                                       | `1.0`    |
| `reply`                   | 回覆                                       | `13.5`   |
| `good_profile_click`      | 點進作者個人頁，並按讚或回覆               | `12.0`   |
| `video_playback50`        | （影片推文）看完至少一半                   | `0.005`  |
| `reply_engaged_by_author` | 回覆，而且這則回覆獲得作者互動             | `75.0`   |
| `good_click`              | 點進對話串，並按讚或回覆                   | `11.0`   |
| `good_click_v2`           | 點進對話串，並停留至少 2 分鐘              | `10.0`   |
| `negative_feedback_v2`    | 負面回饋：要求「減少顯示」、封鎖或靜音作者 | `-74.0`  |
| `report`                  | 檢舉推文                                   | `-369.0` |

表中名稱省略了 README 的前綴 `scored_tweets_model_weight_`。

> [!TIP]
> 權重乘的是**預測機率**，不是互動次數，所以不能拿兩個權重相除，推出「一次檢舉抵消幾百個讚」。README 說明，各種互動的平均機率不同，權重最初的設定，是讓每一項加權後的機率平均貢獻差不多的分數，之後才為了平台指標定期調整。X 在 2026 年 8 月 14 日更新的 [`xai-org/x-algorithm` README](https://github.com/xai-org/x-algorithm) 也點名這種讀法是常見誤解。

### 1. 可見性過濾（Visibility Filtering）

- **使用者偏好**：排除使用者封鎖或靜音的作者與推文，並依 NSFW 設定過濾。
- **去重**：移除重複的推文，以及使用者已經看過的推文。
- **合規與品質**：repo README 介紹的 visibility-filters 負責過濾內容，用途包括法律遵循、提升產品品質與使用者信任。

### 2. 多樣性、平衡與疲勞（Heuristics）

部落格與 Home Mixer README 列出的規則包括：

- **Author Diversity**：避免同一位作者的推文連續出現太多則。
- **Content Balance**：讓站內與站外推文維持合理的比例。
- **Feedback-based Fatigue**：使用者對某些推文給過負面回饋，就降低相關推文的分數。
- **Social Proof**：站外推文必須和使用者有二度連結才會出現，也就是使用者關注的人和這則推文互動過，或關注了它的作者。

### 3. 混排（Mixing）

最後把推文和非推文內容混在一起，部落格列出的是廣告、追蹤推薦與新手引導提示，再送回裝置顯示。

## 兩個首頁分頁的對照

Home Mixer README 寫明，它同時負責 For You 與 Following 兩個分頁。下表依 2023 年的開源資料整理：

| 面向         | Following 分頁                            | For You 時間軸                                                       |
| :----------- | :---------------------------------------- | :------------------------------------------------------------------- |
| **候選來源** | 關注對象的推文，從 Earlybird 搜尋索引取得 | 站內（Earlybird）加站外（GraphJet、SimClusters 等），每次約 1,500 則 |
| **排序方式** | 時間倒序                                  | Heavy Ranker 加權分數，再套用啟發式規則與過濾                        |
| **執行成本** | 一手資料沒有給數字                        | 每天約 50 億次，平均不到 1.5 秒，單次約 220 秒 CPU 時間              |

## 2026 年另外開源的 xai-org/x-algorithm

上面四個階段都是 2023 年的快照。X 在 2026 年 1 月另外開源 [`xai-org/x-algorithm`](https://github.com/xai-org/x-algorithm)，README 說它包含決定 For You 顯示哪些貼文的核心程式碼。依 README：

- **站內來源**是 **Thunder**，在記憶體中保存使用者所關注帳號的近期貼文。
- **站外來源**是 **Phoenix retrieval** 與 SimClusters，另外由 `popular_posts_source` 加入一份共用的近期熱門貼文清單。
- **排序**用 transformer 模型 **Phoenix**：預測使用者對每則貼文採取各種行為的機率，再用程式碼中的權重合成一個分數。

拿兩份 README 對照，站內來源和排序模型的名稱都和 2023 年不同。想看 X 目前的 For You 怎麼運作，應該讀這個 repo，而不是 2023 年的 `twitter/the-algorithm`。

## 從這套管線看推薦系統設計

1. **多階段漏斗**：2023 年的版本先用相對便宜的方法，從數億則推文中取出約 1,500 則候選，才交給 4,800 萬參數的模型評分，最後再套用規則與過濾。要在平均 1.5 秒內完成，這樣的分層是必要的。
2. **讀權重要連著機率一起讀**：`report` 的權重是 `-369.0`，`fav` 只有 `0.5`，但 README 說權重最初是為了讓各項平均貢獻接近而設定的。照這個說法推下去，權重大的行為，通常是平均機率低的行為。單看權重的倍數，推不出一次檢舉等於幾個讚。
3. **開源資料有時期之分**：2023 年與 2026 年的兩個 repo 描述的是不同時期的系統。引用某個元件或數字時，先確認它出自哪一份資料、哪個日期。
