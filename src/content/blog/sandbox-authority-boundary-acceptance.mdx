假設一個內部工具讓使用者交給 AI 產生 Python 介面，再下載執行結果。團隊測過程式只能待在沙箱裡，就準備開放給更多部門。這份驗收還少一半：下載 API 究竟由誰開檔？如果由容器外的 worker 代辦，程式執行限制並沒有回答檔案代理能碰到哪裡。

2026 年 11 月 1 日公開的 Prefab UI 與 Beta9 CVE，剛好提供兩種不同失敗路徑。我會將它們分成兩份驗收紀錄：不可信程式執行時持有哪些權限，以及主機代辦操作最後碰到哪些資源。

我於 11 月 2 日核對 CNA 紀錄、修補 PR 與 release，沒有部署產品、重現漏洞或執行下述測試。已讀來源沒有提供實際惡意利用的事件證據。Prefab 的 vendor advisory 連結查核時回傳 404，漏洞細節以 JFrog CNA 紀錄為依據。

## Prefab 要查的是開始執行時還剩哪些權限

[Prefab UI 的 CVE-2026-120338](https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/120xxx/CVE-2026-120338.json) 涵蓋 `0.14.0 ≤ prefab-ui < 0.21.0`。遠端路徑的前提包括主動啟用 Generative UI、主機裝有 Deno，以及呼叫者能把程式交給相關工具。無認證情境的 CVSS 3.1 是 10.0；有認證且允許呼叫工具的情境仍為 9.9。

問題發生在 Pyodide 與 Deno 交界：Python 可經 JavaScript 橋接取得仍有讀寫權限的 Deno API，接觸伺服器作業系統使用者可存取的檔案。WebAssembly 這個執行形式，沒有自行撤掉宿主暴露的能力。

[修補 PR #538](https://github.com/PrefectHQ/prefab/pull/538) 於 2026 年 10 月 25 日合併，將初始化所需的檔案與網路權限，在生成程式執行前撤銷。[0.21.0 release](https://github.com/PrefectHQ/prefab/releases/tag/v0.21.0) 已於 10 月 26 日發布。CNA 另記載 `--no-prompt` 防止重新授權，啟動階段網路限制在 `cdn.jsdelivr.net`。

因此，盤點不能只找套件版本。還要記錄 Generative UI 是否啟用、實際工具授權與執行程序版本。登入驗證能縮小入口，已獲准的使用者提交不可信程式時，執行權限仍須收斂。

## Beta9 要查的是容器外誰在開檔

[Beta9 的 CVE-2026-120307](https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/120xxx/CVE-2026-120307.json) 影響早於 `0.1.756` 的 worker，前提為持有 workspace token 並有一個運作中的 sandbox。檔案 API 在容器外處理路徑，路徑正規化與 symbolic link 解析可能讓操作落到 worker 主機，權限可達 root，波及同機其他租戶。

CNA 記錄了研究者的唯讀驗證，沒有把它描述成已發生的入侵事件。上傳、下載、查詢與刪除等入口共用受影響的路徑處理，因此只驗收「容器內程式不能讀主機」，會漏掉外部代理。

[PR #1897](https://github.com/beam-cloud/beta9/pull/1897) 於 2026 年 9 月 15 日合併，[worker 0.1.756](https://github.com/beam-cloud/beta9/releases/tag/worker-0.1.756) 同日釋出。修補將 sandbox 檔案操作與 workspace sync 改用 `os.OpenRoot`，把路徑解析限制在容器根目錄或掛載來源。11 月 1 日是 CVE 公開日，不能拿來當修補起點。

站內的 [OpenWA 請求目標驗收](/blog/openwa-request-target-boundaries/)討論解析後的 HTTP 目的地；這裡要追到檔案實際被開啟的位置。兩者都有一項可沿用的要求：驗收觀測點應放在執行動作的那一層。

## 兩條路徑使用不同的通過條件

以下是針對前述虛構內部工具的驗收設計。只使用自有隔離測試環境、低權限測試帳號與無敏感資料的標記檔，讓合法操作及越界操作都有明確預期。

### 執行權限在第一筆工作前就要收斂

平台維護者應保存程序啟動參數，並觀察初始化完成、開始接受使用者程式時的權限狀態。測試至少包含：

- 正常生成介面仍能成功，確定測試環境與執行器可用。
- 生成程式不能讀寫預先準備的主機側標記檔，也不能連向測試用的非允許目的地。
- 請求額外權限時不會彈出可放行的提示，也不會自動取得權限。
- 冷啟動、重啟與後續請求都走相同的權限撤銷步驟。

**任何一條路徑會在權限收斂前接受不可信程式，就停止開放該功能。** 只確認最終回傳錯誤不夠，還要觀察標記檔內容與測試端的連線紀錄，排除失敗回應之前已產生副作用。

### 檔案代理逐項證明只能碰到自己的資源

檔案 API 維護者另準備容器內、掛載內與允許範圍外三組標記檔，逐項覆蓋產品支援的讀取、寫入、列舉、搜尋與刪除。合法檔案操作要成功，唯讀掛載上的寫入要拒絕。

邊界案例應包含父目錄片段、絕對連結，以及路徑檢查後連結被替換的情境。預期結果是拒絕越界，或仍解析到獲授權的範圍內；外部標記檔的內容與存在狀態都不得改變。再用兩個測試 workspace 確認租戶歸屬，避免把「待在某個目錄裡」誤認為「這個租戶有權讀」。

測試若只得到逾時或一般伺服器錯誤，我會保留為待查。先用合法案例確認服務可用，再把拒絕事件對回檔案代理的授權判斷。測試程式找錯目錄、工作尚未啟動與權限拒絕，對外可能呈現相似結果，卻只有最後一種能支持這次驗收。測試用的外部標記檔也應先由環境管理者確認存在，避免用「原本就沒有檔案」製造通過結果。

每次驗收留下 API 動作、測試 workspace、worker 版本、預期資源與觀測結果，不記錄完整 token。這份紀錄與執行器測試分開，往後更換容器技術或重寫檔案服務時，才知道需要重跑哪一組。

## 暫停入口有成本，擴大權限的成本更難界定

無法立刻升級時，我會評估暫停不可信程式入口或受影響檔案功能，並明確通知哪些工作流中斷。只在網關補認證，對已持有工具權限或 workspace token 的使用者沒有補上隔離。這是降低曝險的工程取捨，不取代官方修補。

升級清單則按執行節點逐一核對。假設新 worker 已啟動，舊 worker 還承接先前建立的 sandbox，部署工作顯示成功仍不足以結案。我會要求負責人交代舊工作如何排空、何時停止分派，以及最後一個舊節點是否退出服務。若採用內部回補版本，也要留下修補來源與映像識別，讓下一班值班工程師能核對，不能只寫「已更新」。

修補也可能改變既有使用方式。若生成程式原本直接下載資料，撤銷網路權限後就要重新設計資料供應路徑。我傾向由具明確資源授權的服務預先提供必要資料，避免為了恢復功能把整個執行器重新放寬。代價是多維護一層介面與授權測試。

下一張升級工作單可以直接拆成兩個簽核欄位：執行器負責人確認程式開始時的權限，檔案服務負責人確認主機實際操作的資源。再附上正在接收流量的 Prefab 與 worker 版本清單。任一欄沒有結果，就保留未完成狀態，不用另一欄的綠燈代簽。
