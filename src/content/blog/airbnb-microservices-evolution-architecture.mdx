這篇是參考設計，不是 Airbnb 的實際架構。下面的三階段、單向分層與統一資料層，是我參考 Airbnb 公開分享後整理的設計示意，除了下面列出、以及文中另外附來源的段落，其餘是設計示意。

Airbnb 自己公開過的部分如下：

- **分期**：Jessica Tai 在 QCon Plus 2021（2021-11-05）的演講把演進分成 Monolith（2008–2017）、Microservices（2017–2020）、Micro + macroservices（2020 至今）。來源：[The Human Side of Airbnb's Microservice Architecture](https://www.infoq.com/presentations/airbnb-culture-soa)。
- **單體與服務分層**：Rails 單體叫 Monorail。她在 QCon SF 2018（2018-12）說明，Presentation、Middle tier、Data service 這類服務類型，是 2017–2018 年第一次遷移時就訂下的設計，而不是事後補上的。來源：[The Great Migration: from Monolith to Service-Oriented](https://www.infoq.com/presentations/airbnb-soa-migration)。
- **Viaduct**：Airbnb 把它描述為 data-oriented service mesh，核心是單一的 central schema，團隊的商業邏輯直接放在 Viaduct 裡，官方明說這和「GraphQL 伺服器只當微服務的薄層」的常見做法相反。來源：[Viaduct, Five Years On](https://airbnb.tech/data/viaduct-five-years-on-modernizing-the-data-oriented-service-mesh/)（2025）與 [airbnb/viaduct](https://github.com/airbnb/viaduct)。

我沒有查到 Airbnb 公開過「DAG 三層」「架構委員會」「CI 依賴檢查」這些說法，下面凡是這類內容都是設計示意，不要當成 Airbnb 的做法引用。

## 微服務演進的參考設計全景圖

下圖把單體、無序 SOA、分層治理加統一資料層排成三個階段。這是設計示意，年份刻意不標。

<AirbnbMicroservicesEvolutionDiagram />

1. **階段一：Rails 單體**：單一 Rails Repo 加共用資料庫，所有業務邏輯緊密相連。
2. **階段二：無序 SOA**：各團隊各自拆出大量微服務，點對點 Thrift RPC 呼叫導致循環依賴與級聯雪崩。
3. **階段三：單向分層與統一資料層**：Presentation ➔ Mid-tier ➔ Data service 單向呼叫，並以 GraphQL 統一資料存取。

## 1. 單體的瓶頸

單體架構讓業務能快速上線，工程團隊變大之後，瓶頸會出現在部署與資料庫上。

### 1.1 開發與部署的惡性循環

- **部署佇列阻塞**：數百位工程師共用同一條部署管線，任何一個 Pull Request 測試失敗，整列部署就停擺。Airbnb 在 QCon SF 2018 提到，2015 年左右他們有 200 多名工程師，Monorail 的部署佇列慢到以小時計（[來源](https://www.infoq.com/presentations/airbnb-soa-migration)）。
- **程式碼所有權模糊**：核心 Active Record Model 累積大量回呼函式與業務邏輯時，修改單一欄位可能引發跨模組的 Bug。這是單體常見的情況，不是 Airbnb 公開過的細節。

### 1.2 資料庫單點瓶頸

所有業務共用同一個資料庫時，一支搜尋慢查詢就可能搶佔 CPU，拖慢結帳與支付交易。這是設計示意的假設情境。

## 2. 無序 SOA 的教訓：分散式單體

各團隊迅速建立自己的微服務，使用 Apache Thrift 進行跨服務 RPC 通訊。Airbnb 一開始就訂了服務類型，但沒有被強制執行；他們在 2021 的演講中也提到，服務之間出現過循環依賴，也很難追蹤 500 多個服務（[來源](https://www.infoq.com/presentations/airbnb-culture-soa)）。

### 痛點復盤

1. **循環依賴（Circular Dependencies）**：假設 `ListingService` 呼叫 `PricingService`，而 `PricingService` 又回呼 `ListingService` 取得房源元資料。網路抖動或逾時發生時，請求在服務間打轉，引發級聯雪崩。例子是我假設的。
2. **分散式交易與資料一致性**：單體裡一個 DB Transaction 就能完成的預訂流程，拆分後跨越多個獨立資料庫，沒有補償機制時，訂單與日曆狀態會不一致。
3. **分散式單體（Distributed Monolith）**：服務之間高度耦合，發布一個新功能仍要協調多個團隊同步部署，失去微服務獨立發布的好處。

## 3. 參考設計：單向分層

為了解決服務蜘蛛網，參考設計規定服務呼叫只能**由上向下單向傳遞**，禁止平級循環或向上逆流，形成有向無環圖（DAG）。Airbnb 的服務類型分層見開頭說明，下面的三層職責與命名是我的設計。

### 3.1 三層職責

#### 1. 展示層 (Presentation Services / BFF)

- 為不同前端（Web、iOS、Android）組裝視圖資料。
- 不包含核心業務邏輯，只負責協定轉換、欄位篩選與回應聚合。

#### 2. 中間業務層 (Mid-tier Services)

- 封裝領域業務規則，例如房源搜尋過濾、定價、違禁詞審查。這是設計示意；Airbnb 在 2018 年的說明裡，把 middle tier 定義為寫入 data service 前的共用驗證層。
- 呼叫多個 DAS 取得基礎資料，運算後回傳業務決策結果。

#### 3. 資料存取層 (Data Access Services, DAS)

- **設計原則**：每個資料儲存只允許一個 DAS 直接讀寫，其他服務不得直連資料庫。Airbnb 的 data service 也是這樣：只有該服務能讀寫自己的資料集（[來源](https://www.infoq.com/presentations/airbnb-soa-migration)）。
- 在這份設計裡，DAS 負責快取、讀寫分離、分片路由與資料格式驗證。

> [!TIP]
> **架構守門員（CI 依賴檢查）**：
> 參考設計建議在 CI/CD 管線加入靜態依賴分析工具。提交的程式碼違反單向依賴規則（例如 DAS 呼叫 Mid-tier，或服務間出現環狀路徑），CI 就阻擋並報錯。這是我的建議，不是 Airbnb 公開過的做法。

## 4. 統一的 GraphQL 資料層

服務數量變多之後，前端工程師要自己拼資料：渲染一個房源詳情頁，可能要分別呼叫房東資訊、評價、日曆價格、設施列表等多個服務。參考設計在前端 BFF 與後端服務之間放一層統一的 GraphQL 資料層。

Airbnb 的 Viaduct 走的是不同路線：單一 central schema，商業邏輯直接放在 Viaduct 裡（來源見開頭）。下面這份設計則是閘道式的變體，只借用「單一查詢入口」的想法，不代表 Viaduct 的運作方式。

1. **單一中央 Schema**：全站用一份 GraphQL Schema 描述領域實體，各領域團隊在這份 Schema 上新增自己的型別與欄位。
2. **自動批次與去重**：前端請求 20 個房源時，資料層把 20 個獨立的 `getUserById` 呼叫聚合為一次批次查詢 `getUsersByIds([1, 2, ...20])`，避免 N+1 查詢。Viaduct 的開源版也提供批次解析（Batch Resolvers），但批次的具體做法與範例不是 Airbnb 的實作。
3. **欄位級權限控制**：在圖譜解析層對欄位做存取檢查。Viaduct 引擎支援欄位級與型別級的存取檢查（[airbnb/viaduct](https://github.com/airbnb/viaduct)）。

## 5. 平台工程化：宣告式配置與自動化金絲雀

服務數量達到上千個時，維運複雜度會急速上升。Airbnb 在 CNCF 的分享中說，他們有一層建在 Kubernetes 上的內部抽象叫 OneTouch，服務配置放在專案的 `_infra` 目錄，可用範本化的 YAML 產生 Kubernetes 設定（[CNCF End User Lounge, 2021-07-22](https://www.cncf.io/online-programs/cncf-end-user-lounge-how-airbnb-manages-a-dense-soa-of-1000s-of-services-across-dozens-of-clusters/)、[KubeCon NA 2018 投影片](https://raw.githack.com/mm-k8s-ug/kubecon-slides/master/slides/2018-kubecon-na/Keynote%20Developing%20Kubernetes%20Services%20at%20Airbnb%20Scale%20-%20Melanie%20Cebula,%20Software%20Engineer,%20Airbnb%20-%20kubecon%202018.pdf)）。Airbnb 也在 [Continuous Delivery at Airbnb](https://medium.com/airbnb-engineering/continuous-delivery-at-airbnb-6ac042bc7876) 提到用 Spinnaker 的自動化金絲雀分析（ACA）降低有問題的部署所造成的影響範圍。

參考設計沿用這兩個方向，細節是我的假設：

- **宣告式服務配置**：開發者撰寫一份 YAML，定義資源、環境變數與相依服務，平台據此產生部署設定。
- **自動化金絲雀分析**：新版本先導入少量流量，比對金絲雀與基準節點的錯誤率、延遲與 CPU，指標偏離時自動回滾。流量比例與回滾時限要依自己的服務決定。

## 6. 參考設計總結

| 演進階段   | 架構模式              | 優勢                             | 代價與瓶頸                                 |
| :--------- | :-------------------- | :------------------------------- | :----------------------------------------- |
| **階段一** | Rails 單體            | 開發快、交易簡單、部署單純       | 團隊擴展受阻、部署佇列癱瘓、單庫效能瓶頸   |
| **階段二** | 無序 SOA              | 團隊可獨立發布                   | 服務蜘蛛網、循環依賴、級聯崩潰、分散式單體 |
| **階段三** | 單向分層 + 統一資料層 | 依賴方向清楚、資料入口統一、批次 | 平台工程投入大、需要架構規範與 CI 治理     |

### 3 個建議

1. **單體還撐得住就不要拆**：沒遇到組織擴展或效能極限就拆，只是把記憶體內的呼叫換成昂貴又脆弱的網路 RPC。
2. **資料庫只由一個服務擁有**：禁止跨庫直接存取，並用單向呼叫避免循環。
3. **前端與細粒度服務之間，可以放統一的資料解析層**：Airbnb 的 Viaduct 是這個方向的一個實例，但它把商業邏輯放在層內，和本文閘道式的示意不同。
