在絕大多數傳統企業應用裡，我們習慣用 **CRUD（Create, Read, Update, Delete）** 模式。業務一有變更，系統就直接執行 SQL `UPDATE` 或 `DELETE` 語句，覆蓋資料庫裡的既有記錄。

這種「就地突變（In-place Mutation）」的做法，在業務變複雜後會出現幾個嚴重問題：

1. **歷史上下文丟失**：使用者把購物車的商品數量從 5 改成 2，資料庫只知道現在是 2，「使用者原本想買 5 件、後來刪掉 3 件」這段商業決策就沒了。
2. **審計與回溯極端困難**：財務對帳、交易爭議或安全審計時，只能依賴額外的 Log 表，而業務日誌與資料庫狀態往往難以保持嚴格原子性。
3. **讀寫模型強耦合**：同一套關聯式資料庫結構既要扛高併發的交易寫入，又要支援前端多維度、多條件的複雜 JOIN 聚合查詢，結果索引與鎖爭用崩潰。

**事件溯源（Event Sourcing）** 與 **CQRS（Command Query Responsibility Segregation，命令查詢職責分離）** 的組合，就是針對這些問題的架構。

## 1. 狀態是事件的累積

Event Sourcing 把 **「事件（Event）」當成一等公民，當前狀態（Current State）只是歷史事件流從第 0 筆開始重放、做左折疊（Left Fold / Reduce）的結果**。

```text
Current State = LeftFold(Initial State, [Event_1, Event_2, ..., Event_N])
```

### 1.1 Command vs. Event

領域模型要嚴格區分「命令」與「事件」：

- **Command（命令）**：代表使用者或外部系統的**操作意圖**（例如 `CreateOrderCommand`、`ApplyCouponCommand`）。業務規則驗證失敗時，Command 可能被**拒絕（Reject）**。
- **Domain Event（領域事件）**：代表系統中**已經發生的客觀事實**，使用過去式命名（例如 `OrderCreatedEvent`、`CouponAppliedEvent`）。Event 是**不可篡改、不可撤銷**的歷史事實。

### 1.2 Append-Only Event Store

Event Store 是事件溯源架構的唯一「真實來源（Single Source of Truth）」。它有這些特徵：

- **僅允許追加寫入（Append-only）**：禁止任何 `UPDATE` 或 `DELETE` 操作。
- **單調遞增版本號**：每個聚合根（Aggregate ID）擁有專屬的事件流（Event Stream），流內事件的 `SequenceNumber` 連續遞增。
- **樂觀並發控制（OCC）**：追加事件時必須檢查 `(AggregateId, ExpectedVersion)`，版本不符就拋出併發衝突例外。

```typescript
// Event Store 事件結構範例
interface DomainEvent<T = unknown> {
  eventId: string; // UUIDv7 唯一識別
  aggregateId: string; // 聚合根 ID (例如 order-88921)
  aggregateType: string; // 聚合類型 (Order)
  eventType: string; // OrderPaidEvent
  version: number; // 單調遞增版本號 (1, 2, 3...)
  timestamp: string; // ISO 8601 時間戳
  payload: T; // 事件業務主體
  metadata: {
    userId: string;
    correlationId: string; // 全鏈路追蹤 ID
    causationId: string; // 引發此事件的 Command ID
  };
}
```

## 2. CQRS 讀寫分離架構

Event Sourcing 記下了狀態與歷史事實，但如果每次查詢都要重放整個事件流，讀取效能會徹底崩潰，所以要搭配 **CQRS（命令查詢職責分離）**。

### 2.1 寫入側（Write Model / Command Side）

- **職責**：驗證業務規則，保證領域不變量（Invariants）。
- **流程**：
  1. 接收 `Command`。
  2. 從 Event Store 讀取該聚合根的歷史事件（或最新快照）。
  3. 重放事件還原記憶體中的 Aggregate 實體。
  4. 執行業務方法（例如 `order.pay(paymentInfo)`）。
  5. 業務驗證通過，就產生新的 `DomainEvent`。
  6. 原子追加寫入 Event Store。

### 2.2 讀取側（Read Model / Query Side）

- **職責**：高併發查詢、多維過濾與前端畫面呈現。
- **特徵**：
  - **多特化資料庫（Polyglot Persistence）**：讀模型不需要是關聯式資料庫。全文檢索可投遞至 Elasticsearch，即時計數可投遞至 Redis，報表可投遞至 ClickHouse 或 PostgreSQL 扁平表。
  - **反正規化（Denormalization）**：讀模型照前端 UI 的需求設計，查詢時**零 JOIN**，資料庫 CPU 負載大幅下降。

### 3.1 投影必須冪等（Idempotency）

分散式訊息佇列通常保證 **At-Least-Once** 交付，同一個事件可能被投遞多次，所以投影處理器必須冪等：

- 記錄已處理的最新 `LastHandledEventVersion`。
- 若接收到小於或等於已處理版本的事件，直接跳過。

### 3.2 支援「隨時打掉重建」（Re-projection）

Event Sourcing 最大的優勢之一：**未來的業務需求不需要預先設計表結構**。
產品經理一年後要一個全新的多維度統計視圖，我們只要：

1. 編寫一個全新的 Projector 邏輯。
2. 將該 Projector 的 Offset 重置為第 0 筆。
3. 重放過去一整年的所有歷史事件，新的讀資料庫就建好了。

## 4. 正式環境的挑戰與做法

### 4.1 事件重放耗時與快照機制（Snapshotting）

如果某個聚合根（例如一個活躍了 5 年的銀行帳戶）累積了 10 萬筆事件，每次執行 Command 都要重放 10 萬筆事件，延遲會到數秒以上。

**解決方案：快照（Snapshot）**

- 每隔固定事件數量（例如每 100 筆）或定期（每日凌晨）將聚合根的當前記憶體狀態序列化保存為快照。
- 載入聚合時，先讀最新快照（版本 `V_snap = 500`），再只拉 `V > 500` 的後續增量事件回放，載入時間從秒級降到 2 毫秒內。

### 4.2 事件結構版本演進（Schema Evolution / Upcasting）

隨著業務迭代，舊事件的格式可能與新系統不相容（例如 v1 事件包含 `name: string`，v2 拆分為 `firstName: string, lastName: string`）。

**解決方案：Upcasting（升級器）**

- **永不修改 Event Store 中的歷史事件**（保持不可篡改性）。
- 在讀取歷史事件時，透過記憶體中的 `Upcaster` 中介管線，將 v1 事件動態轉型為 v2 結構後再交給領域聚合或投影器。

```typescript
// Upcaster 記憶體動態轉型範例
function upcastOrderCreated(v1Event: OrderCreatedV1): OrderCreatedV2 {
  return {
    ...v1Event,
    version: 2,
    customer: {
      firstName: v1Event.customerName.split(" ")[0] || "",
      lastName: v1Event.customerName.split(" ")[1] || "",
    },
  };
}
```

### 4.3 最終一致性（Eventual Consistency）與「寫後讀」延遲

投影是非同步的。使用者送出 Command 成功後馬上重新整理頁面，讀模型可能還沒收到最新的 Event，使用者就會看到舊資料。

**解決方案**：

1. **樂觀 UI 渲染**：Command 成功回傳後，前端直接把本地狀態更新到畫面。
2. **帶版本號輪詢 / WebSocket 推播**：Command 回傳新生成的 `EventVersion`，前端查詢讀 API 時帶上 `min_version=v5`。讀模型還沒追上，就短暫等待，或由 WebSocket 通知更新完成。

## 5. 何時該用？何時是過度設計？

| 適合採用 Event Sourcing + CQRS   | 建議維持傳統 CRUD                  |
| :------------------------------- | :--------------------------------- |
| • 銀行、證券、支付等金融帳務系統 | • 單純的管理後台 (Admin Portal)    |
| • 供應鏈庫存調撥與物流軌跡追蹤   | • 簡單的部落格、內容管理系統 (CMS) |
| • 需要嚴格合法性審計與監管的系統 | • 業務邏輯單純的 CRUD 工具應用     |
| • 讀寫比極端懸殊 (如 100:1 以上) | • 團隊缺乏 DDD 與非同步架構經驗    |
| • 複雜的領域協作與狀態機流轉     | • 開發週期極短的早期 MVP 驗證專案  |

---

## 總結

Event Sourcing 與 CQRS 把每一次商業決策與狀態變更存成不可篡改的歷史事件流，資料庫裡不再只有當前狀態。系統因此能做**歷史審計**、**時間旅行回溯**，讀寫模型也能**徹底解耦**。

代價是快照維護、事件版本升級與最終一致性這些複雜度。選型時要評估業務是否真的需要事件溯源，避免為了技術而過度設計。
