Agent 啟動建置，等到工具逾時，接著重跑一次。若第一輪的編譯程序還活著，兩份工作就會同時寫入輸出目錄。畫面上多了一次重試，機器上卻多了一棵程序樹。

Chris Wellons 在 [2026 年 10 月 31 日介紹 Prospero](https://nullprogram.com/blog/2026/10/31/) 時，將這種殘留程序列為設計動機。這個用 C++ 與 Dear ImGui 製作的 coding harness，讓超過同步等待期限的 shell 命令轉成背景工作，再由 Agent 決定繼續等或停止。作者也提出整棵程序樹共同結束的設計原則。這比介面使用哪種技術，更值得放進團隊的選型測試。

查核截至 2026 年 11 月 1 日，依據作者原文及公開 repository 文件。尚未執行 Prospero、測量資源用量或重跑跨平台清理測試。文中的驗收設計可供試用時採用，產品是否通過仍待實測。作者聲稱資源用量比其他 harness 少約兩個數量級，未在這裡視為可直接採用的比較基準。

## 逾時之後，先查原工作是否還在

Prospero 原文要求網路請求與操作有期限，shell 命令超過同步等待期限後則轉入背景。Agent 可以繼續等待，並在下一個期限到達時重新取得控制。Plan mode 另有例外，提出計畫或透過 `ask_user` 等待澄清時可以持續等待。

這種做法適合編譯、測試與 fuzzing 等完成時間不固定的工作。短時間沒有輸出，不必立即把工作殺掉。代價是 harness 必須保留背景工作的識別、輸出與結束狀態，Agent 也要知道接下來是在追蹤既有工作。

假設團隊要評估一個 Laravel 加 TypeScript 的虛構專案。驗收用的建置替身先寫入獨有的執行識別，再等待超過工具的同步期限。這個替身只在可丟棄目錄運作，不接資料庫、不呼叫外部服務。檢查三個時點：

- 逾時前，只有一次啟動紀錄。
- 轉成背景後，仍能找到同一份工作及其輸出，Agent 沒有另開第二輪建置。
- 原工作結束後，完成事件與退出碼能對回那次啟動。

如果工具只回傳一個 `timeout`，無法查出原工作是否仍在，Agent 就缺少安全重試所需的資訊。**原工作的狀態不明時，停止自動重跑會寫入同一目錄的命令。**先讓操作人員確認殘留工作，再決定繼續或清理。

## Stop 應該有明確的清理範圍

[Prospero 使用文件](https://github.com/skeeto/prospero/blob/245ad548ff123318939f9b22c83d0474b931b565/docs/usage.md)說明，執行中命令旁的 Stop 會停止該命令，Agent 仍會接著處理目前已有的輸出。作者原文另外主張，停止命令時應讓整棵程序樹共同結束。取消一個工具工作之後，整個 Agent 任務仍可能繼續。

測試時可以讓無害的父程序啟動子程序，兩者各自在測試目錄寫入不同的心跳檔。按下該命令的 Stop 後，同時查父子程序是否退出、心跳是否停止、背景工作列表是否收斂到終止狀態。判定期限要由團隊事先訂定，例如測試環境採 5 秒作為清理目標；這是驗收假設，並非 Prospero 的保證。

接著讓 Agent 收到取消結果，觀察它是否又自動啟動同一項工作。程序清乾淨了，若上層任務仍要求「一直做到建置成功」，下一輪工具呼叫仍可能把工作開回來。驗收要分別記錄取消命令、取消任務兩種操作的結果。

只殺最外層 shell 是較簡單的替代方案，對沒有子程序的短指令可能足夠。用於會開編譯器、測試 worker 或背景服務的工具時，清理責任就得涵蓋它們。選型結果也應分 Windows、macOS、Linux 記錄，避免把單一平台的通過結果推廣到全部開發機。

## 關閉視窗與退出遠端 engine 要分開測

Prospero 的 [remote 文件](https://github.com/skeeto/prospero/blob/245ad548ff123318939f9b22c83d0474b931b565/docs/remote.md)說明，遠端 host 可以比 SSH 連線活得更久。視窗選擇 Keep running in background 後，也能留下工作，稍後再連回。[README](https://github.com/skeeto/prospero/blob/245ad548ff123318939f9b22c83d0474b931b565/README.md)則列出單一執行檔、headless 與遠端執行方式。

這對下班後繼續跑測試很有用，卻改變了退出驗收。試用時至少保留兩種案例：

1. 選擇保留背景工作後關閉視窗，再連回同一個 host。確認原工作仍可追蹤，沒有因重新連線而再啟動一份。
2. 明確要求停止工作並退出 host。從執行主機檢查程序與測試產物，確認結束範圍符合指令。

對遠端工作，失去連線只能證明目前看不到執行狀態。清理失敗或結果不明時，應將任務標成待確認，不能把它記成取消成功。這和本站 [持續型 Agent 的停止責任](/blog/openai-dots-ongoing-work-control/)相接。那篇談委派任務與排程，這裡驗的是工具工作及 OS 程序。

## 權限詢問不等於隔離環境

作者在原文直接提醒，Prospero 的權限介面主要協助遵守使用者意圖、攔下簡單錯誤，無法攔住能在電腦上執行程式的惡意 Agent。想限制可存取資源，必須限制 harness 本身的執行環境。

因此，試用帳號只放測試專案與假憑證。工具詢問權限時不回答，確認等待期限後確實拒絕該動作；這是權限互動測試。再用環境層的限制，驗證測試程序無法讀取預先指定的範圍外檔案；這是隔離測試。兩項要各自留下結果，不能用「有跳出 Allow 視窗」替代後者。

遠端設定也有需要審查的資料流。原文說 INI 可以包含 URL，即使遠端設定禁止放入部分可能出現在 shell 命令中的值，仍可能把環境變數當 API key 送往指定 endpoint。團隊共用設定應由可信來源維護，更新時檢查 endpoint 與憑證引用，不能只審查 shell 欄位。

## 用同一份失敗案例比較 harness

Prospero 提供了一組具體的產品設計，值得拿來檢查現有工具。比較時固定專案、模型端點與工作內容，分開記錄閒置資源、執行工作時的資源，以及取消後的殘留程序。換語言或縮小 binary 的收益，和工作是否正確結束，是不同的結果；本站的 [Copilot runtime 程序邊界分析](/blog/copilot-agent-runtime-rust-in-process/)另談前者。

下一次試用 coding harness，可以先準備一份會超過同步期限、會開子程序的無害測試工作。讓它經歷轉背景、取消、關閉視窗與重新連線，再保存每次啟動、退出及殘留程序的證據。用這份記錄確認，工具說工作停了之後，開發機是否回到可安全重跑的狀態。
