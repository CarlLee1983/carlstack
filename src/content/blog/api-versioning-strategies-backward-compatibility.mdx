API 一旦發布給行動 App、第三方開發者或企業客戶使用，一個看似很小的欄位改名（例如 `user_name` 改成 `username`）或型別變更（例如數字改成字串），都會直接讓舊版客戶端壞掉。

**API 版本控制（API Versioning）** 讓 API 可以繼續改，又不弄壞既有的客戶端。

下面比較 4 種主流版本控制策略，再看 **Stripe** 在 2017 年公開的做法：核心程式碼只有一套，舊版 API 的差異抽到一個個版本變更模組裡。到 2026 年 9 月，[Stripe changelog](https://docs.stripe.com/changelog) 列出的正式 API 版本共 124 個。

| 版本控制方式               | 範例                                  | 優點                                                  | 缺點                                                             | 適用場景                               |
| :------------------------- | :------------------------------------ | :---------------------------------------------------- | :--------------------------------------------------------------- | :------------------------------------- |
| **URI Path (路徑)**        | `/api/v1/orders` ➔ `/api/v2/orders`   | **直觀，可在瀏覽器直接開啟，CDN 快取依 URL 自然分開** | 違反 REST 資源唯一性（同一資源有多個 URL）、各版本程式碼容易重複 | **公開 API、大幅度的主版本破壞性重構** |
| **Custom Header (標頭)**   | `X-API-Version: 2026-09-02`           | **URL 保持一致，方便用日期標記版本**                  | 無法直接在瀏覽器網址列存取、CDN 要設定 Vary 標頭                 | **企業內部微服務、B2B SaaS 平台**      |
| **Accept 內容協商**        | `Accept: application/vnd.app.v1+json` | **URL 不帶版本，版本隨媒體類型協商**                  | 語法繁瑣、客戶端串接門檻高、除錯不易                             | 嚴格遵循 REST 規範的架構               |
| **Query Parameter (參數)** | `/api/orders?v=2`                     | 實作非常簡單，可設定預設版本                          | URL 雜亂、容易和業務篩選參數混在一起                             | 臨時過渡、輕量內部專案                 |

## 2. 什麼是相容變更 vs. 破壞性變更（Breaking Changes）？

### 2.1 ✅ 向後相容的變更（不用升級 API 版本）

1. **新增可選欄位（Optional Fields）**：在 Response JSON 加欄位。
2. **新增獨立 API 端點**：例如新增 `POST /v1/users/export`。
3. **放寬請求參數限制**：把原本必填的參數改成可選。

### 2.2 ❌ 破壞性變更（要發新版本）

1. **重新命名或刪除欄位**：例如把 `tele` 改成 `phone_number`。
2. **修改欄位資料型別**：例如把 `price: 100`（整數）改成 `price: "100.00"`（字串）。
3. **修改 HTTP 狀態碼語意**：例如原本回傳 `404`，改成回傳 `200 OK` 帶 `{ "data": null }`。
4. **新增必填請求參數**。

## 3. Stripe 的版本變更模組：回應逐版往回轉換

Brandur Leach 在 Stripe 官方部落格〈[APIs as infrastructure: future-proofing Stripe with versioning](https://stripe.com/blog/api-versioning)〉（2017-08-05）描述了這套做法。帳號第一次發出 API 請求時，會自動鎖定在當時最新的版本；之後每個請求的目標版本，取自 `Stripe-Version` 標頭，沒有帶標頭就用帳號鎖定的版本。API 資源的結構以目前版本為準，回應送出前，再從目前版本往回逐一套用沿途的版本變更模組，直到目標版本為止。

- **優勢**：每個破壞性變更封裝成一個模組，內含變更說明、轉換邏輯和它影響的 API 資源類型。舊版本的差異因此留在核心路徑之外。
- **代價**：有些變更有副作用，沒辦法關在模組裡。Stripe 會替這類模組加上 `has_side_effects` 註記，模組本身的轉換變成 no-op，改由程式碼其他地方檢查它是否生效。原文承認這會降低封裝、讓維護更複雜，所以盡量避免。

2017 年時，Stripe 說自 2011 年創立以來的每個 API 版本都維持相容，這套做法撐過了六年來近百次不相容升級；同一篇文章也說，預期最終會開始淘汰舊版本。現行的[版本控制文件](https://docs.stripe.com/api/versioning)沒有寫舊版本的支援期限。

發布流程在 2024 年也改了。依 Stripe 的版本控制文件與〈[Introducing Stripe's new API release process](https://stripe.com/blog/introducing-stripes-new-api-release-process)〉公告，從 `2024-09-30.acacia` 起，每月發布不含破壞性變更的版本，每年兩次 major release 才帶入破壞性變更。內部是否仍沿用版本變更模組，現行官方資料沒有說明。

## 4. API 廢棄（Deprecation）與退役

1. **Sunset 標頭（RFC 8594）**：
   在即將廢棄的 API 回應加上這些標頭：
   ```http
   Deprecation: @1756800000
   Sunset: Wed, 02 Sep 2026 00:00:00 GMT
   Link: <https://docs.carlstack.dev/migration-v2>; rel="sunset"
   ```
2. **主動通知與流量監控**：在 API 閘道器統計各版本的呼叫量，定期自動提醒還在用舊版本的使用者遷移。

---

## 5. 總結

- **對外公開 API 推薦 URI Path（`/v1/`）**：簡單直觀，工具支援也最完整。
- **複雜平台推薦 Date-based Header（`X-Version: YYYY-MM-DD`）**：搭配版本轉換層，兼顧靈活性與相容性。
- **遵守相容性規則**：欄位只增不刪，先標記廢棄再移除，留足遷移過渡期。
