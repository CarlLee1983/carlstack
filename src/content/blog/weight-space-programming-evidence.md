模型的數學答對率大幅提高，可能是它終於把答案寫完。這仍是有用的修復，但會改變我們該買什麼、測什麼，以及能對使用者承諾什麼。

2026 年 11 月 2 日，Rikiya Takehi 等人發表 [Weight-Space Programming 初步實驗](https://rikiyat.github.io/blog/weight-space-programming/)，讓通用 LLM 直接讀寫其他神經網路的權重。其中 Qwen3.5-0.8B 的結果值得工程團隊細讀。作者報告 MATH-500 正確率由 7.9% 提升到 48.1%，而達到輸出 token 上限的比例由 93.0% 降到 33.1%。兩個數字放在一起，才看得出修復發生在哪裡。

> [!NOTE]
> 查核日期為 2026 年 11 月 3 日。實驗結果來自作者文章與公開實驗紀錄，我沒有重跑模型或驗證效能。下方驗收流程是工程建議，不是這項研究已完成的額外測試。

## 50 次 forward pass 是工具預算，不是 50 道題

[Experiment 8 紀錄](https://github.com/RikiyaT/lm_understand-logs/tree/main/exp8_math) 把編輯者、目標模型與工具分得很清楚。編輯者是 GPT-6 Astra，目標是啟用 thinking 的 Qwen3.5-0.8B。Astra 可以透過 Python 分析權重，取得練習題回饋，再提交權重修改。研究禁止梯度下降與訓練。

它能接觸 GSM8K、MATH 的訓練題，最終評測題在執行後才使用。一次 forward-pass 工具呼叫可生成最多 512 題的回答，或讀取最多 1,024 段文字的模型內部資訊。因此「50 次」描述的是受限的批次工具預算，無法直接換算成 50 次一般聊天請求。

這會影響成本比較。紀錄中的 50-pass 執行用了 20.3 小時，其中包含一次模型無法連線造成的 4.7 小時等待。這是該次研究的牆鐘時間，不是部署後每次推論延遲，也不是可通用的成本估算。評估替代方案時，應把編輯者呼叫、目標模型運算、評測與人工分析分開記錄。

## 把「答不完」與「答錯」分開計算

作者將主要改善歸因於重複推理迴圈被抑制。最後修改觸及第 15、19 層 MLP 的部分輸出欄，總計 131,072 個權重，約為模型的 0.016%。[公開紀錄](https://github.com/RikiyaT/lm_understand-logs/blob/main/exp8_math/README.md) 還補充，轉成評測使用的 bfloat16 後，其中 130,188 個值與原始權重不同。「觸及多少」和「儲存後改變多少」有不同分母。

若把同一方法用在訂單問答助手，總正確率至少要拆成三份紀錄：

- 是否在輸出上限內產生可解析的最終答案。
- 所有請求中，最終答案正確的比例。
- 已完成回答中，最終答案正確的比例。

第三項要搭配前兩項看。假設新模型只回答簡單題，完成回答的正確率可能上升，整體服務卻拒絕了更多請求。反過來，成功消除重複輸出也可能提高總正確率，而不改變模型處理難題的方式。

實務上可為每題保存原始與修改後的結果，分成「原先未完成，現在答對」「原先答錯，現在答對」「原先答對，現在答錯」。這是建議的配對分析，能讓修復效益與退步同時出現在審查畫面，避免平均分數把兩者抵銷。

## Gemma 對照限制了能宣稱的能力

同一研究另測較少出現迴圈的 Gemma 3 270M。作者報告其 MATH-500 基線為 6.8%，50-pass 修改後為 7.0%，未建立有效的能力提升。這個結果讓「移除阻礙」與「學會原本不會的推理」有了具體對照。[原文的追加實驗](https://rikiyat.github.io/blog/weight-space-programming/) 也明確區分這兩件事。

我的判斷是，這項方法目前適合列入「已定位失敗行為的修復候選」。如果需求是讓小模型處理新的稅務規則、算出更複雜的費率，仍要另準備對應的能力證據。改動比例很小，只描述檔案變更規模，無法推導其他能力完全不受影響。

不同模型的結果也不宜直接當成同條成長曲線。它們有不同容量、推論設定和失敗型態。[Gemma 紀錄](https://github.com/RikiyaT/lm_understand-logs/blob/main/exp8_math/gemma_followup/README.md) 還說明，這組公布分數採較寬鬆的答案擷取，容許沒有 boxed 格式的最終答案。比較時應保留各自基線，再問同一模型在相同設定下改善了什麼。

## 實驗批准前，先凍結四項條件

對後端團隊而言，權重修改可以按一次模型版本變更管理。建議先凍結以下條件，再讓編輯程序接觸練習資料。

1. 模型版本、tokenizer、chat template、精度與原始權重雜湊。修復必須能套到指定版本，不能只寫「使用最新 Qwen」。
2. 推論設定，包括 thinking、取樣參數、最大輸出長度與答案擷取規則。原版與修改版使用同一套條件，否則無法區分權重與設定的影響。
3. 練習集與保留測試集。調整期間只能看練習集。若評測結果回流給編輯者，該批題目就應轉成開發資料，另取未暴露的測試集。
4. 業務回歸項目。例如訂單編號保留、金額格式、缺少資料時的拒答，以及工具參數是否符合 schema。它們是部署驗收需求，不能由數學基準代替。

可以從一種可重現的重複輸出故障開始，限定修改預算。若尚未定位故障，先調查 prompt、chat template、停止條件或推論設定通常更容易回復，也更容易確認哪一項改動有效。這是與權重編輯有意義的替代方案，兩者應使用相同測試集比較。

## 權重檔可重建，結果才有機會重現

[實驗紀錄的 README](https://github.com/RikiyaT/lm_understand-logs) 提供公開內容與缺項說明。[Experiment 8](https://github.com/RikiyaT/lm_understand-logs/tree/main/exp8_math) 保存權重差異、manifest、評測程式與每題結果，並以指定 base revision 和雜湊檢查重建後的 tensor。這比只有一張分數圖更適合交給另一個工程師核對。

但文件也列出未收錄的部分，例如完整工作目錄、部分中間輸出，以及該實驗的 agent harness 程式。公開紀錄提供了查核與重建線索，完整重跑仍需確認工具和評分依賴。

團隊內部可把交付物固定成原始模型識別值、權重差異、套用後雜湊、評測設定、逐題結果與回復方法。驗收者先檢查雜湊，再做配對評測，不接受只交一個「已最佳化」的模型目錄。

**若保留測試集已被用來挑選修改，停止把它的分數當作獨立驗收。** 這項規則也適用於 prompt、檢索策略與 agent harness 最佳化，不限於權重。

下一次看到模型分數上升，可以要求作者或團隊補一張逐題差異清單：哪些題目原本無法結束，哪些題目已能結束但答錯，哪些原本答對卻退步。拿得到這份清單，才開始討論是否值得加入服務的下一版。
