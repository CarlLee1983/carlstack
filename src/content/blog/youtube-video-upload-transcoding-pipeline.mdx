YouTube 在 [2021-04-21 的官方部落格](https://blog.youtube/inside-youtube/new-era-video-infrastructure/) 寫到，平台平均每分鐘有超過 **500 小時** 的影片上傳。使用者上傳的格式五花八門（手機拍的 4K MOV、直播錄下的 FLV、老舊攝影機的 AVI），檔案從幾 MB 到上百 GB 都有。這些影片要轉成多種解析度與格式，才能在 4K 電視、手機和頻寬很差的裝置上播放。

這篇只寫 YouTube 公開過的部分，主要來源有四個：

- Google 在 ASPLOS 2021 發表的 Argos VCU 論文 [_Warehouse-Scale Video Acceleration: Co-design and Deployment in the Wild_](https://research.google/pubs/warehouse-scale-video-acceleration-co-design-and-deployment-in-the-wild/)（Ranganathan 等人，2021），描述 YouTube 的影片處理平台與自研轉碼晶片 VCU。
- 同一時期的 YouTube 官方部落格 [_Reimagining video infrastructure to empower YouTube_](https://blog.youtube/inside-youtube/new-era-video-infrastructure/)（2021-04-21）。
- [YouTube Data API 的 Resumable Uploads 文件](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol)（我參照的是 2026-10 的版本）。
- [YouTube 說明中心的「上傳後影片畫質偏低」](https://support.google.com/youtube/answer/71674)。

論文與部落格描述的是 2021 年前後的架構，之後有沒有改，公開資料看不出來。上傳協定是公開 API 的規格，YouTube 網頁上傳器內部用什麼沒有公開。分塊大小、上傳狀態存在哪個資料庫、檢查碼、音訊與字幕怎麼處理，這些來源都沒有寫，所以文中不寫。

## 階段 1：可續傳上傳（Resumable Upload）

假設使用者要上傳一個 50 GB 的 4K 影片。如果只用一個 HTTP POST 傳完，中途 WiFi 斷掉或行動網路切換基地台，整個檔案就得從頭再傳一次。

YouTube Data API 為此提供了可續傳上傳協定：

<YoutubeResumableUploadDiagram />

### 協定怎麼運作

1. **建立工作階段**：對 `/upload/youtube/v3/videos?uploadType=resumable` 送 POST，用 `X-Upload-Content-Length` 與 `X-Upload-Content-Type` 宣告檔案大小與類型。成功時回 `200 OK`，`Location` 標頭就是這次上傳的工作階段網址。
2. **上傳影片**：對工作階段網址送 PUT，請求內容就是影片檔。文件寫明分塊上傳很少需要，而且不建議，因為多出來的請求會拖慢效能；只有在很不穩定的網路上需要顯示進度時才分塊。要分塊的話，每塊必須是 256 KB 的倍數（最後一塊除外），中間的分塊回 `308 Resume Incomplete`，最後一塊回 `201 Created`。
3. **中斷後查進度**：送一個空的 PUT，標頭帶 `Content-Length: 0` 與 `Content-Range: bytes */總長度`。還沒傳完時，伺服器回 `308 Resume Incomplete`，`Range` 標頭（例如 `bytes=0-999999`）表示已經收到的位元組。一個位元組都沒收到時，回應不會帶 `Range` 標頭。
4. **續傳**：從 `Range` 結尾的下一個位元組繼續 PUT。

哪些錯誤可以續傳，文件也有規定。連線中斷沒有回應，或收到 `500`、`502`、`503`、`504`，都可以續傳，5xx 要用指數退避重試，並遵守 `Retry-After`。工作階段過期會回 `404`，這時要重新建立工作階段。其他 4xx 視為永久失敗。

### 上傳完成之後

根據 [YouTube 說明中心](https://support.google.com/youtube/answer/71674)，影片上傳後會先處理出低畫質版本，1080p、4K 這類高畫質要花更久；上傳完成後，4K 畫質可能要多花 4 倍時間才會出現。

## 階段 2：GOP 分塊與任務依賴圖排程

把一整部 4K 影片丟給一台機器轉碼，會花很久；中途硬體故障，前面的計算也白做了。Argos 論文描述的做法是把影片切成可平行處理的分塊，再用任務依賴圖排程。

### 1. 依 closed GOP 切成分塊

- 視訊編碼由 **I 幀（關鍵幀，獨立圖像）**、**P 幀（前向預測）** 與 **B 幀（雙向預測）** 組成。
- 不能在任意時間點截斷，切點要落在 GOP 邊界。論文的說法是，轉碼器可以把影片切成分塊（也就是 closed Groups of Pictures），每個分塊都能平行處理。
- 論文沒有規定分塊長度。它在估算成本時舉的例子是一個 150 幀的 2160p 分塊，也就是 30 FPS 下的 5 秒：用多個 CPU 核心編成 VP9，常常要花 15 分鐘的實際時間、超過一個 CPU 小時。

### 2. 任務依賴圖與全域工作佇列

系統依照需要的輸出版本，產生一張無環的任務依賴圖（acyclic task dependency graph），放進全域工作佇列。圖上每個操作是一個大小不一的 step，由排程系統分配到資料中心的機器上，以發揮可用容量與並行度，並隨效能、負載變化以及服務或基礎設施故障調整。圖上除了轉碼，也有非轉碼的步驟。

<YoutubeDagTranscodingDiagram />

失敗的處理放在軟體層。某張 VCU 上的轉碼失敗，會由上層軟體重試，通常改派到另一張 VCU 或軟體 worker。論文提到一個實際遇過的問題：故障但還沒被停用的 VCU，往往比正常的「快」，結果不成比例的工作被送到壞掉的卡上（論文稱為 black-holing）。他們的緩解方式是 worker 一遇到硬體故障，就中止這張 VCU 上的所有工作，交回叢集層重試；新的 worker 接手一張 VCU 時，先重設並在每個核心跑一組短的 golden 轉碼任務，發現持續性故障就拒絕啟動。

## 階段 3：多輸出轉碼、VCU 與依熱度分級

### 單一輸出與多輸出轉碼

論文把轉碼分成兩種：單一輸出轉碼（SOT）一次只產出一種解析度；多輸出轉碼（MOT）由一個轉碼任務解碼一次，產出這個分塊需要的所有解析度與格式。MOT 省掉重複解碼，一般比 SOT 好；記憶體或延遲有限制時才用 SOT。論文說他們的正式環境工作量大多是 MOT，但導入 VCU 之前，因為 MOT 在 CPU 上延遲太高，正式環境用的是多個 SOT。

### 編碼格式

| 編碼格式        | 官方來源的說法                                                                               |
| :-------------- | :------------------------------------------------------------------------------------------- |
| **H.264 / AVC** | 舊有的基準編碼，VCU 的編碼核心支援（論文，2021）                                             |
| **VP9**         | 部落格說它的編碼要多用 5 倍運算資源；論文說軟體編碼一般比 H.264 慢且貴 6–8 倍。VCU 支援      |
| **AV1**         | 壓縮效率比 VP9 好，但編碼運算量更高；YouTube 在下一代 VCU 晶片加入 AV1（部落格，2021-04-21） |

部落格說 VCU 相對先前在一般伺服器上調校過的系統，運算效率最多提升 20–33 倍；論文給的也是 20–33 倍的單位成本效能提升。

### 依熱門程度分級投入算力

論文把影片熱度分成三級：

1. **非常熱門**：占了大部分觀看時間，卻只占轉碼與儲存成本的一小部分，值得多花處理時間，換取更低的傳輸頻寬。
2. **中等熱度**：觀看次數足以投入中等資源。
3. **長尾**：大多數影片都在這一級，觀看少，盡量壓低儲存與轉碼成本，維持可播放就好。

舊影片之後可能變熱門，這時要用更高等級的處理方式重新處理。

> [!IMPORTANT]
> **導入 VCU 前後，VP9 的產出時機不同**：
> 沒有硬體加速時，即使有分塊平行，在上傳時產出 VP9 的成本和延遲都不可行，所以 VP9 只在上傳後用低成本的批次 CPU 替最熱門的影片產出，而且每個解析度各跑一次 SOT。導入 VCU 後，VP9 與 H.264 都改在上傳時產出，並用 MOT 編碼（論文，2021）。說明中心把 4K 較晚出現歸因於處理時間。

論文也提到，上傳的端到端延遲要求是幾分鐘到幾小時，直播則是 100 ms。

## 階段 4：輸出儲存、邊緣分發與自適應碼率

依 Argos 論文的平台示意圖，轉碼產生的各版本影片存進雲端儲存系統，依需要提供，經內部網路與 CDN 送到觀眾端。Google 的 [Peering 說明頁](https://peering.google.com/#/infrastructure) 寫到，網路業者可以部署 Google 提供的伺服器，當地使用者常看的熱門靜態內容（包括 YouTube）會暫存在這些邊緣節點上。

播放端的部分，論文只寫到：解析度越低檔案越小，可以在裝置上放大，所以頻寬受限或變動時，客戶端可以改要較低的解析度，也就是自適應碼率（ABR）。YouTube 用哪種串流封裝格式，這些來源沒有寫。

### 通用的 Manifest 範例（HLS）

下面依 [RFC 8216](https://datatracker.ietf.org/doc/html/rfc8216) 的 HLS 主清單格式，示範多碼率階梯長什麼樣子，不是 YouTube 的實際清單：

```
#EXTM3U
#EXT-X-VERSION:6

# 4K AV1 高碼率流
#EXT-X-STREAM-INF:BANDWIDTH=15000000,RESOLUTION=3840x2160,CODECS="av01.0.12M.08"
4k_av1_master.m3u8

# 1080p VP9 中碼率流
#EXT-X-STREAM-INF:BANDWIDTH=4500000,RESOLUTION=1920x1080,CODECS="vp09.00.41.08"
1080p_vp9_master.m3u8

# 360p H.264 低碼率流
#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360,CODECS="avc1.4d401f"
360p_h264_master.m3u8
```

### 播放端的自適應碼率演算法（ABR Heuristics）

一般的 ABR 播放器會持續看兩個指標：

- **即時下載頻寬（Throughput-Based）**
- **本地緩衝區剩餘秒數（Buffer-Based）**

使用者走進電梯、訊號變差時，播放器請求下一個分塊就改拿 360p；回到 WiFi 後再拉回 1080p 或 4K，畫面不用中斷。

## 導入 VCU 前後的差別

下表整理自 Argos 論文（2021）：

| 比較項目         | 導入 VCU 前（CPU 軟體轉碼）               | 導入 VCU 後                                        |
| :--------------- | :---------------------------------------- | :------------------------------------------------- |
| **VP9 產出時機** | 只替最熱門的影片，在上傳後用批次 CPU 產出 | VP9 與 H.264 都在上傳時產出                        |
| **轉碼方式**     | 每個解析度各跑一次 SOT，重複解碼          | 以 MOT 為主，一次解碼產出多種輸出                  |
| **單位成本效能** | 基準                                      | 提升 20–33 倍                                      |
| **硬體故障**     | 論文沒有比較                              | 失敗的工作由上層軟體改派到另一張 VCU 或軟體 worker |

## 我從這些來源整理出的 4 點

以下是我的歸納。前兩點的主體有論文支撐，第 1 點的分塊重試部分是我的推論；後兩點是通用的設計判斷。

1. **把大工作切成可獨立處理的分塊**：closed GOP 分塊讓每塊可以平行轉碼。論文說失敗的轉碼由上層軟體改派重試；以分塊為單位重試、不必整部重來，是我依 step 粒度做的推論。

2. **依熱度決定要花多少算力**：論文的三級分法顯示，編碼成本高的格式值得花在觀看時間集中的熱門影片上，長尾影片則壓低成本；影片變熱門時再重新處理。
3. **畫質由客戶端決定**：伺服器準備好多種解析度，切換交給最清楚自己網路與硬體狀況的播放器。
4. **用一般的 HTTP 快取分發**：HLS、DASH 這類格式的分塊就是一般的 HTTP 檔案，可以直接用 CDN 快取，不必另建專用串流協定的伺服器（如 RTMP）。
