Jamstack / Serverless（如 Vercel、Cloudflare Workers、AWS Lambda）可以在數秒內把前端與邊緣函數部署到全球。傳統的關聯式資料庫（如 AWS RDS PostgreSQL / MySQL）在這種架構下有三個問題：

- **連線數瞬間耗盡**：數千個短暫的 Serverless 函數同時連線，瞬間打爆資料庫連線池（Connection Pool）；
- **無法縮容到零（Scale to Zero）**：即使夜間完全無流量，仍需支付全天候昂貴的實例租金；
- **分支開發極度痛苦**：無法像 Git Branch 一樣秒級為每個 Pull Request 複製一個獨立的資料庫副本進行測試。

**Neon** 與 **PlanetScale** 各自用不同的方式處理這些問題：Neon 做計算儲存分離，PlanetScale 用 Vitess 做分散式分片。下面分別看兩者的架構。

> 時間註記：PlanetScale 已在 2025-09-22 讓 PlanetScale for Postgres 正式上線（[官方公告](https://planetscale.com/blog/planetscale-for-postgres-is-generally-available)），所以「Neon 是 Postgres、PlanetScale 是 MySQL」只描述 PlanetScale 的 Vitess 產品線。

## 1. 兩大技術流派全景對比矩陣

| 評估維度                       | Neon (Serverless PostgreSQL)                                            | PlanetScale (Vitess 分散式 MySQL)                     |
| :----------------------------- | :---------------------------------------------------------------------- | :---------------------------------------------------- |
| **底層資料庫引擎**             | 託管的 **PostgreSQL**（與原生 Postgres 有部分差異）                     | 相容 **MySQL**（基於源自 YouTube 的 Vitess）          |
| **核心架構哲學**               | **計算與儲存徹底分離 (Disaggregated Compute & Storage)**                | **水平分片與連線池 (Horizontal Sharding & VTTablet)** |
| **資料庫分支 (Branching)**     | **基於儲存層 Copy-on-Write，官方稱可在約 1 秒內複製 1 TB 以上的資料庫** | 基於 Vitess 的分支，只複製 Schema，不複製資料         |
| **無流量縮容 (Scale-to-Zero)** | **✅ 支援（預設閒置 5 分鐘後暫停，約數百毫秒內恢復）**                  | 不支援依流量自動休眠                                  |
| **連線池治理**                 | PgBouncer 連線池，最高 10,000 併發連線；Rust 寫的 proxy 負責驗證與路由  | **VTGate 接收大量連線並路由，連線池在 VTTablet 層**   |
| **水平擴展極限**               | 單計算節點垂直擴展 + 付費方案儲存無上限 + 多唯讀副本                    | **跨節點水平 Sharding 分片**                          |

## 2. Neon 底層架構：PostgreSQL 內核級計算儲存分離

Neon 把 PostgreSQL 的計算節點（Compute Node）改成不持有持久狀態、可隨時替換的節點，儲存層則換成自研的 Rust 分散式儲存引擎（[neondatabase/neon](https://github.com/neondatabase/neon)）。

### 秒級資料庫分支（Copy-on-Write Branching）

- 儲存層以不可變檔案組織，開發者執行 `neon branches create --name pr-123`（[CLI 參考](https://neon.com/docs/reference/cli-branches)）時，不需要複製實體資料。分支和父分支共用資料，從建立分支的時間點開始各自寫入。
- 官方部落格（2024-03）稱，用分支複製超過 1 TB 的 Postgres 資料庫只要約 1 秒（[說明](https://neon.com/blog/how-to-copy-large-postgres-databases-in-seconds)），所以每個 PR 都能有一份含生產資料的獨立測試庫。

連線池的位置值得留意：官方部落格說明，Vitess 與 PlanetScale 的連線池在 VTTablet 層（[一百萬連線](https://planetscale.com/blog/one-million-connections)，2022-11）。VTGate 負責接收客戶端連線並路由。

### 線上 Schema 變更（Deploy Requests）

在生產環境執行 `ALTER TABLE` 傳統上容易長時間鎖表：

- PlanetScale 的 **Deploy Request** 流程類似 GitHub PR：在開發分支修改 Schema，檢視 Schema diff 後部署（[文件](https://planetscale.com/docs/vitess/schema-changes/deploy-requests)）。
- 底層用 Vitess 的 `vitess` 線上 DDL 策略，由 VReplication 在後台建立影子表並同步資料。Vitess 自 v22 起不再支援 `gh-ost` 與 `pt-osc` 策略（[DDL 策略](https://vitess.io/docs/24.0/user-guides/schema-changes/ddl-strategies/)）。
- 官方稱部署零停機。切換（cut-over）時需要取得表的 metadata lock，進來的查詢會被短暫阻擋，但不會遺失（[運作方式](https://planetscale.com/docs/vitess/schema-changes/how-online-schema-change-tools-work)）。

## 4. 總結與架構選型指南

- **選 Neon (Postgres)**：
  - 開發現代 Serverless 全端應用（Next.js、FastAPI）；
  - 需要 **Git-like 資料庫分支** 進行 CI/CD 預覽與測試；
  - 流量有明顯的尖離峰，需要 **Scale-to-Zero**（閒置時暫停計算節點）。
- **選 PlanetScale (MySQL / Vitess)**：
  - 大型核心交易業務，資料量達數十 TB 且持續快速增長；
  - 需要 **水平分片（Horizontal Sharding）** 與大量併發連線的支援。
