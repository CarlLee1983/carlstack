需求寫著「尖峰每秒 20 次下單」，還不能拿去採購機器。這 20 次可能包含重試；一個請求可能占用資料庫 20 ms，也可能等熱門商品的鎖等到 800 ms。相同入口流量，後面的資源需求可以差很多。

今天要做的決策是：保留同步模組化單體，把流量換成一份有單位、假設與失敗條件的容量預算，用它選首輪壓測環境。機器規格只是待驗證的候選，通過測試後才有資格成為部署依據。

這是「系統設計每日實戰」第 2 篇，不需要先完成上一題。沿用[第一篇的訂單契約](/blog/order-system-requirements-slo/)：單倉、單幣別、每張訂單只有一種商品，尚不處理付款。`201` 表示訂單、價格快照與庫存預留已在同筆 MySQL 交易提交；原鍵重送不能多扣庫存，成立後查詢讀主庫。入口目標仍是 28 天內，至少 99.5% 的合格嘗試，自可信任入口收完請求起算，在 1,000 ms 內送完符合契約的終局回覆。

本文所有流量、耗時、位元組與機器規格都是教學假設。沒有建置或壓測這個訂單服務，也沒有聲稱它已達到 SLO。

## 先算清楚 12,000 次嘗試會留下幾張訂單

沿用尖峰 `20 次 HTTP 嘗試／秒`、持續 `600 秒`。新增一組方便推算的情境：20% 的嘗試是同鍵重送；其餘是新操作，每個新操作在這段觀察期都有一次首次嘗試。新操作的 90% 成立，其餘缺貨。這裡暫不混入跨觀察期重送、格式錯誤或同鍵不同內容，壓測時再各自加入。

- 入口負載：`20 × 600 = 12,000 次嘗試`。
- 新操作：`12,000 × 80% = 9,600 個`，平均 `16 個／秒`。
- 新訂單：`9,600 × 90% = 8,640 張`。
- 其餘 `960 個`新操作保存缺貨終局結果；`2,400 次`重送重放既有結果。

「20% 是重送」的分母是全部嘗試，不能改成每個新操作額外重試 20%。後一種假設會得到 `12,000 ÷ 1.2 = 10,000 個`新操作，兩者不同。

容量預算因此至少有兩個計數器。HTTP 嘗試決定入口、驗證、日誌與查詢壓力；唯一操作決定去重紀錄與新訂單成長。重送雖然不應增加訂單，仍會消耗運算與資料庫資源。第一篇的 SLI 也以嘗試為分母，不能把重送從容量報表或 SLO 報表抹掉。

## 平均在途 4 個，不等於只開 4 個 worker

Little's Law 把穩定系統的長期平均量連起來：`平均系統內數量 L = 平均進入率 λ × 平均停留時間 W`。必須選定同一個觀測邊界，並滿足長期平均存在等條件；排隊時間若在邊界內，就要算進停留時間。[Columbia 的 Little's Law 講義](https://www.columbia.edu/~ks20/stochastic-I/stochastic-I-LL.pdf)

假設在 20 次／秒的穩定階段，從入口收完請求到送完回覆的平均耗時是 `0.20 秒`，則平均在途量為 `20 × 0.20 = 4 個`。這是用待驗證耗時建立的算例。實際量測若是 `0.80 秒`，同樣流量對應平均 `16 個`在途。

`1,000 ms` 是契約期限，不能直接當成平均耗時代入；`λ × p99` 也不是 Little's Law。平均值更不會告訴你短暫尖峰需要多少 worker，或哪個上限能滿足尾端延遲。若輸入已超過可處理能力、佇列持續增長，就不能拿一個穩態平均數替它背書。

DB 的邊界要另外量。假設每次 HTTP 嘗試合計借用 DB 連線的時間平均為 `0.08 連線秒`，包含不借連線的零值，以及同一次嘗試所有借用區間的加總，則平均被借用的連線數是 `20 × 0.08 = 1.6 條`。若一個請求同時借兩條，各自的占用時間都要累加。借用時間包含持有連線時的鎖等待，卻不包含還沒借到連線的 pool 排隊。

因此要同時記錄 pool 等待、借用時間與資料庫內部鎖等待。平均 1.6 條既不能代表最高需求，也不能把開著但閒置的連線忽略：閒置連線仍計入 MySQL 連線上限，資源占用則需另外量測。[MySQL 連線管理](https://dev.mysql.com/doc/refman/8.4/en/connection-interfaces.html)

## 最小方案維持一個交易邊界，規格先當測試起點

首輪仍用一個應用部署單位，加一個獨立 MySQL InnoDB 實例；訂單與庫存保留程式內模組介面，共用本地交易。不加入 Redis、Elasticsearch 或訊息佇列，因為這次要確認的是同步成立路徑，還沒有證據顯示它們能解除瓶頸。

可先寫下這份候選測試規格，實際實例型號、CPU 架構、磁碟 IOPS 與版本在測試紀錄中固定：

- 應用：`2 vCPU、4 GiB RAM`，一個副本；在途請求、工作程序數與 DB 連線總量都要量測。
- 資料庫：`2 vCPU、8 GiB RAM、100 GiB SSD`，用 90 天規模的測試資料與實際索引，不只測空表。磁碟容量與 IOPS 是不同限制。
- 應用連線預算：每個副本最多合計 `8 條`；若滾動部署最多同時存在兩個副本，就按 `16 條`計算。
- DB 預算：假設一般客戶端總上限為 `40 條`，預留 `8 條`給維運、`4 條`給遷移與背景工作，應用可分配 `28 條`。`16 ≤ 28` 只是靜態配置檢查，還要靠連線監控與程序上限讓預留實際生效。

這些數字不是最低硬體保證，也不是生產容量結論。選它們是為了取得第一組可比較的資料；CPU、記憶體或磁碟任一飽和，都可能推翻這個候選。MySQL 官方說明每個連線有自己的記憶體需求；把 `max_connections` 加大並不免費，也不代表資料庫能同時有效執行更多工作。[MySQL 記憶體使用](https://dev.mysql.com/doc/refman/8.4/en/memory-use.html)

若 Node.js 每個程序各建立一個 pool，連線上限須跨程序加總；同一程序建立多個 pool，也要全部計入。Laravel／PHP 的預算要按實際 worker 與持久連線模式加總。不能在每個程序都填 8，再說整個容器最多 8。這裡的「每副本 8 條」是部署必須履行的總額，具體限制方式要依 driver 與執行模式設定、驗證。

單一應用副本與單一資料庫仍有故障風險。這份規格用來找容量瓶頸，尚未回答正式環境的高可用、RPO、RTO 與故障切換；通過 10 分鐘壓測，也不能證明已達成 28 天 SLO。

### 真的替代方案：兩個應用副本，還是先把單個副本加大？

若觀測顯示應用 CPU 飽和、DB 等待低，兩個副本可能讓應用工作分散，也增加部署與路由成本；連線、日誌、健康檢查及故障切換都要按副本數重算。單副本加到 `4 vCPU、8 GiB` 則少一層協調，但單點風險不變，程式若受單執行緒或鎖限制，也未必用得到新增核心。

若瓶頸在同一 SKU 的庫存鎖，兩者都可能沒用。InnoDB 在 `UPDATE` 時會對掃描到的索引紀錄加鎖，選用的索引與掃描範圍會影響鎖定範圍；同一列的互斥更新仍會互相等待。[InnoDB 各種敘述設定的鎖](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)

用一個刻意簡化的反例檢查：所有新操作都爭同一列，若每筆把該互斥鎖持有 `80 ms`，理想串行上界約為 `1 ÷ 0.08 = 12.5 次／秒`，還未扣除其他開銷。前面假設的新操作有 `16 個／秒`，若每個都走這段鎖，就已超過上界。這裡的 80 ms 是另一個熱點反例假設，不能和上節「每 HTTP 嘗試平均 0.08 連線秒」混為同一項量測。

處理順序是查索引、縮短持鎖區段、移除交易內不必要的外部等待，再用同一負載重測。Redis 快取不能取代權威庫存交易；改成非同步受理會改變回覆承諾，須回到第一篇重新協商。**熱點等待持續增加時，停止以加應用副本作為已解決容量問題的結論。**

## 儲存預算要把不刪除的去重紀錄算進去

10 分鐘尖峰不能外推成每天全天尖峰。另作每日 `50,000 個新操作`、其中 90% 成立的教學假設；尖峰包含在當日總量內。假設每張訂單連同品項與預留的邏輯資料為 `2 KiB`，每個新操作的精簡去重紀錄為 `0.5 KiB`，完整回覆快取額外為 `1 KiB`。

第一篇約定完整回覆快取保留 7 天，精簡去重索引首版不自動刪除。據此估算：

- 長期邏輯資料每天增加：`45,000 × 2 KiB + 50,000 × 0.5 KiB ≈ 112.3 MiB`。
- 90 天約 `9.87 GiB`；365 天約 `40.03 GiB`，沒有因為回覆快取到期而停止成長。
- 7 天完整回覆快取上限按每操作一份估：`50,000 × 7 × 1 KiB ≈ 341.8 MiB`，前提是到期清理確實執行。

KiB、MiB、GiB 在這裡依序是 2¹⁰、2²⁰、2³⁰ bytes。這些 payload 數字尚未包含索引、頁面空間與資料庫額外開銷。為了選首輪磁碟，暫以「長期資料加回覆快取」乘 `3 倍`做占用假設；它不是 MySQL 的固定倍率，後續要用真實 schema、索引與資料分布測出來。

90 天估計約 `30.6 GiB`。再暫留 `20 GiB`給 binlog、redo、暫存與操作空間，合計約 `50.6 GiB`，可放入上述 100 GiB 候選磁碟。這筆預留同樣待實測，不能拿來保證索引重建或大量排序一定有空間。備份另存獨立位置，備份保留與還原空間另列預算。

若維持相同成長，365 天的資料占用假設已約 `121.1 GiB`，還沒加那 20 GiB。100 GiB 顯然不能原封不動撐一年。本文提案的操作門檻是：每週更新趨勢，當預估 30 天後使用量會超過配置的 70%，啟動擴容或保留政策審查。70% 與 30 天是本案例的保守工作門檻，需配合擴容交付時間調整；不得為了騰空間擅自刪掉仍承擔冪等契約的索引。

## 壓測要送出承諾的流量，不能等服務慢了就少送

固定 20 個虛擬使用者、每人等回覆後才送下一次，可能在系統變慢時自動降低到達率。k6 官方把這種回饋稱為 closed model 的 coordinated omission 問題；arrival-rate executor 則按預定速率啟動 iteration，使到達節奏不依賴前一個 iteration 是否完成。[Open and closed models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)

本次測試規格可以寫成以下待執行清單，並保留每次測試的程式版本、資料快照、環境規格與原始結果：

1. 先暖機，再以固定到達率執行 20 次下單嘗試／秒、持續 10 分鐘。每個 iteration 恰好送一次下單 HTTP 請求；關閉腳本與 HTTP client 的隱式重試、redirect，另外安排已知原鍵的重送。否則 iteration／秒不能直接視為下單嘗試／秒。
2. 基線跑分散 SKU、0% 重送；第二輪保持 0% 重送，將所有新操作集中同一 SKU；第三輪回到分散 SKU，加入 20% 同鍵重送。前兩輪都是 20 個新操作／秒，第三輪是 16 個／秒。重送必須指向同測試中可追蹤的原操作，不能拿隨機新鍵冒充。缺貨與成立比例以結果核對，不只相信輸入腳本。
3. 訂單詳情查詢另以 `10 次／秒`作本輪新增假設，與下單同時打到主庫；監控、背景工作與必要健康檢查也記入資源預算。前面的 1.6 條只估了下單部分，不能當整台 DB 的平均占用。
4. 收集入口嘗試與契約結果、延遲分布、應用 CPU／RSS、pool 等待、DB 連線、查詢耗時、鎖等待、磁碟延遲與實際資料成長。每次成立仍需對帳訂單與預留，不能以 HTTP 成功率代替正確性驗收。
5. 另跑 `40 次／秒`的 60 秒突發，之後回到 20 次／秒並觀察是否恢復。這是探索餘裕的壓力情境，不是把產品需求悄悄加倍；記錄限流、錯誤與排隊，不期待靠無限佇列把超載藏起來。

額定負載的每輪短期 gate 可暫沿用 99.5% 的及時正確終局回覆比例，另要求零重複預留、零負庫存與完整負載交付；任何不變量失敗都停止，不拿比例抵銷。這只是壓測驗收門檻，不能代替 28 天 SLO 的正式觀測。

[k6 constant-arrival-rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/) 的速率單位是 iteration；若沒有可用 VU，會出現 [dropped_iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/)。它們是測試器沒送出的工作，不能加進服務端「已收到 HTTP 嘗試」的分母，也不能當作服務成功。此時要報告目標流量未達，調查測試器資源或被拉長的請求；只看到低錯誤率，不能宣告通過。

AWS 在[避免過載的負載卸除設計](https://aws.amazon.com/builders-library/using-load-shedding-to-avoid-overload/)討論超過容量後的行為與測試。本例採用的驗收判斷是：額定負載先檢查既有契約與延遲，超載則確認排隊有界、拒絕可觀測且降回額定負載後可恢復。合格嘗試因容量不足收到 `429`，仍是第一篇 SLI 的不良事件；保護系統不能靠改分母變成達標。

## 今日練習：流量沒變，連線為什麼開始排隊？

假設後續真的量到以下結果：下單仍是 20 次／秒，但每次下單合計借用 DB 的時間由平均 `0.08` 增至 `0.30 連線秒`。另有 10 次／秒的詳情查詢，每次借用 `0.05 秒`。應用仍是一個副本，這個應用副本的 DB 連線池合計上限仍為 8。

請算出平均占用，並在「連線上限改成 16」與「先查借用時間增加原因」之間選一個第一步。再寫下一個足以推翻你選擇的觀測結果。不要只回答「看情況」。

### 參考思路：6.5 條是警訊，還不是加倍連線的理由

下單平均占用為 `20 × 0.30 = 6 條`，查詢為 `10 × 0.05 = 0.5 條`，合計 `6.5 條`；相對 8 條上限約 81.25%。這是假設穩態下的平均推算，無法單獨推出 pool 等待的 p99，也不能斷言上限 8 一定不足。

我的第一步會查借用時間增加的來源。如果熱門 SKU 的鎖等待升高，擴大 pool 很可能只是允許更多請求同時等待；先處理持鎖區段。如果 pool 等待升高，但借用後的 SQL、鎖等待與 DB 資源都保持穩定，且小範圍增加連線的對照測試改善延遲、沒有增加錯誤與資源飽和，就有理由修正原判斷。改成 16 前，也要重算滾動部署時 `2 × 16 = 32` 已超過原先分配的 28 條應用預算。

今天留下的成果是一頁容量預算：每個數字標明單位、觀測邊界、假設或實測，以及哪個結果會觸發改變。拿這一頁去排第一輪壓測，下一次討論加機器時，就能指出要解除的是哪一段等待。
