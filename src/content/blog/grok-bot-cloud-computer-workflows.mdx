過去要讓 AI Agent 執行全自動任務，開發者往往需要在本機配置複雜的 Python 環境、設定 Docker 容器，並冒著本機檔案被誤刪或憑證洩漏的風險。

隨著以 Grok Bot 為代表的**「雲端電腦（Cloud Computer）型 Agent」**出現，自動化應用的門檻被大幅降低。

[@maiyangai 的實作解析](https://x.com/maiyangai/status/2090919833366040919)以 Grok Bot 為例說明：Bot 可在雲端電腦使用瀏覽器、檔案系統與終端，並藉由 Skill、Routine 與多人 Bot 協作處理日常工作。重要限制是：**同一使用者帳號下的所有 Bot 共用同一台雲端電腦、檔案、瀏覽器 Session 與登入狀態**；Bot 是工作分工，不是彼此隔離的安全邊界。

---

## 為什麼需要「雲端電腦」型 Agent？

將工作從本機移至雲端電腦，可帶來三項能力；但隔離單位是使用者帳號的雲端電腦，而不是單一 Bot：

1. **與本機分離的執行環境**：
   - 雲端電腦可降低對本機檔案的直接影響；但同帳號 Bot 之間可互見檔案與登入，因此敏感資料與高權限登入仍應排除或嚴格限制。
2. **24/7 持久自走（Continuous Execution）**：
   - 不受限於個人電腦開關機，任務可在雲端依 Routine 排程持續執行。
3. **帳號層級的工具與身分管理**：
   - 外部服務的登入會在共享雲端電腦中可見；密碼、2FA、CAPTCHA 與付款確認需由人接管，而 API key 應走平台的 secure secret card。

## Skill、Routine 與審批邊界的三層治理

| 機制層級                      | 定位與作用                                   | 實例場景                                           |
| ----------------------------- | -------------------------------------------- | -------------------------------------------------- |
| **Skill（原子能力）**         | 擴展 Bot 能調用的外部 API 或特定腳本         | 「PDF 研報結構化抽取」、「SQL 查詢編譯器」         |
| **Routine（例行排程）**       | 定義「何時」以及「觸發什麼條件」來執行工作流 | 「每日上午 8 點抓取特定領域技術論文並產出摘要」    |
| **Approval Gate（審批閘門）** | 防止未授權的破壞性或對外操作                 | 「發布文章至社群媒體或發送重要通知前需經人工核准」 |

## 多 Bot 協作：分工不是隔離

在進階應用中，複雜任務不再由單一龐大的 Bot 獨立承擔，而是拆解為**多 Bot 協作流水線**：

1. **偵測與抓取 Bot（Scraper Bot）**：專門監聽 RSS、新聞或特定社群來源，過濾出高價值資訊；
2. **分析與合成 Bot（Analyst Bot）**：接手原始資料，進行跨來源比對、邏輯推理與結構化總結；
3. **分發與通知 Bot（Dispatcher Bot）**：將通過審批的最終產物推播至 Slack、Email 或內部知識庫。

原文建議先把一隻 Bot 的真實工作跑順、確認交付格式後，再沉澱成 Skill 或 Routine，最後才增加第二、第三隻 Bot。這種模組化能讓責任較清楚，但不會自動提供獨立容錯、獨立登入或安全隔離；共享雲端電腦的 blast radius 仍需由審批規則與最小權限管理。

## 結語：AI 代理的基礎設施進化

從本地 CLI 提示詞到擁有獨立雲端電腦與審批邊界的長駐 Agent，AI 自動化的技術棧正在迅速標準化。

掌握「環境隔離、受控排程與多 Agent 協作」的架構思維，將是工程師在下一階段構建高可用企業級 AI 系統的關鍵能力。
