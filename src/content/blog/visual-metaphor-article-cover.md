一張文章封面最容易犯的錯，是把標題、摘要和三個重點全塞進圖片。它看起來努力說明，卻在縮成卡片後什麼都讀不見；讀者既沒得到資訊，也沒有理由點進去。

[@AdrianPunk115 的封面實驗](https://x.com/AdrianPunk115/status/2096577625074680225)提出另一條路：用黑白蝕刻與超現實場景，把抽象題目改成一個可以立刻辨識的關係。他觀察 Dan Koe 的長文封面幾乎不用文字，而是讓一個場景或象徵承接文章方向。這是原作者的視覺判斷，不是「無文字封面一定比較有效」的實證。

我的立場是：**封面不負責重述文章；它只要先交付一個值得打開的關係。**標題、摘要與 `alt` 文字仍各有不可替代的工作。把四者混在一起，通常只會產生一張既難讀也難記的圖片。

## 先定義封面要交付的關係

文章主題常是名詞，例如「Agent 記憶」、「架構取捨」或「提示詞」。名詞本身沒有畫面，直接畫一顆發光大腦、齒輪或聊天泡泡，也很難區分文章真正的主張。

先把主題寫成一句有方向的關係，再找可視化的事物：

| 文章真正要說的關係                   | 可以畫出的視覺關係                     | 不該只畫               |
| ------------------------------------ | -------------------------------------- | ---------------------- |
| 模型變強後，該刪除沒有新增證據的流程 | 被移開的障礙，留下通往驗收訊號的路徑   | 發光 AI 大腦           |
| Prompt 要能被驗收，而非只要語氣漂亮  | 零散紙片收束成有封印的任務卷宗         | 一段放大的 Prompt 文字 |
| 記憶系統必須區分舊資訊與權威事實     | 不同新舊標記的檔案，通過可追溯的檢查站 | 一個資料庫圓柱         |
| 文章封面應把抽象題目變成可見線索     | 一本書長出橋，連接燈塔與入口           | 文章標題的另一種排版   |

這張表不是找「唯一正確」的圖。它迫使作者回答：讀者打開文章以前，究竟該先理解哪一個差異、因果或取捨？如果答不出來，問題通常不在繪圖工具，而在文章主張尚未收斂。

## 讓圖片處理直覺，讓文字處理精確

無文字不代表沒有文字工作。封面中的每個載體要分工，才不會把可搜尋性和可近用性一起犧牲：

| 載體        | 要負責的事                                   | 不要拿它來做的事             |
| ----------- | -------------------------------------------- | ---------------------------- |
| 封面圖      | 一個可辨識的主題關係與情緒                   | 完整解釋、資料表或小字註解   |
| 標題        | 明確提出文章主張                             | 描述畫面每個物件             |
| description | 說清讀者會得到的範圍與結果                   | 用抽象形容詞補強圖片         |
| `coverAlt`  | 描述畫面資訊與關係，讓非視覺讀者取得同等線索 | 重複檔名或只寫「文章封面」   |
| 正文        | 提供判斷依據、限制與可執行步驟               | 假設讀者已從圖中理解所有細節 |

例如本文的封面是一冊空白筆記本、燈塔、機械橋與敞開的門。它不是在宣稱文章真的提供一條萬用設計流程；它只傳達「把還沒說清楚的概念，接到可進入的閱讀路徑」這個關係。完整主張仍必須由標題和正文說出來。

## 生成前先寫一條封面契約

生成圖片前不必做一份龐大的品牌手冊。先寫下這個最小契約即可：

```yaml
cover:
  claim: "抽象概念必須先被看成一個關係"
  metaphor: "燈塔經由橋連到入口"
  signal: "從理解到行動的路徑"
  style: "黑白蝕刻、超現實、無文字"
  must_not:
    - "把標題塞進圖裡"
    - "出現產品 logo 或假 UI"
    - "用看不懂的裝飾取代關係"
```

`claim` 決定圖不能背離的主張；`metaphor` 讓生成器有具體場景；`signal` 是縮圖時仍要留下的資訊；`must_not` 則防止圖片回到常見的「字很多、元素很多，但沒有重點」。對工程文章而言，這比列十個藝術風格形容詞更有用。

## 用縮圖測試，而不是在全尺寸自我感動

封面常在生成介面裡看起來精緻，放到文章卡片卻失去意思。驗收只要三步：

1. 把圖縮到網站卡片大約會出現的尺寸；一眼能否說出主要關係？
2. 拿掉標題後，是否仍能判斷大致主題，而不是只看到泛用的科技裝飾？
3. 對照 `coverAlt`；它有沒有描述圖中的資訊關係，而不是只補一串關鍵字？

若第一步失敗，先刪掉配角、降低背景細節或換更直接的隱喻；不要急著加字。若第二步失敗，則回到文章主張，而不是換一個更炫的風格。第三步失敗時，問題不是視覺美感，而是讀者取得資訊的路徑不完整。

> [!IMPORTANT]
> 封面可以留白，事實不能留白。圖片不應承載技術規格、數據或安全結論；這些必須在可引用、可搜尋的標題與正文中說明。

## 何時不要用隱喻封面

視覺隱喻不是所有文章的預設答案。教學要辨認操作介面、硬體裝置或錯誤現象時，真實截圖、清楚標註的圖表或原生 SVG 反而更誠實。比較兩個 API 回應、解釋資料流、呈現數值趨勢時，也不該為了「風格感」把可查核資訊藏進抽象畫面。

停止規則很簡單：**讀者必須從圖片取得精確資訊時，優先用可讀的圖解；圖片只需建立閱讀入口時，才使用隱喻。**

下一篇文章要選封面時，先寫出「讀者第一眼必須看懂的關係」，再決定是否需要畫它。若只能想到把標題做成大字，先回頭修改主張；封面通常只是第一個暴露文章還沒想清楚的地方。
