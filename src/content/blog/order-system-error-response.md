## 取消失敗之後，畫面要做什麼

使用者按下取消訂單，API 回傳 `409`，訊息是「訂單無法取消」。前端工程師需要知道接下來要顯示什麼。訂單已出貨，應重新讀取狀態並收起取消按鈕；訂單正在結算，則可能要等狀態確認。兩者都可能與目前狀態衝突，單看 `409` 分不出來。

若前端開始寫 `message.includes("已出貨")`，後端調整文案或加入英文版，就可能改變程式行為。這一課練習選出值得成為穩定 API 契約的失敗情況，讓呼叫端可以據此採取不同動作。

沿用虛構的模組化單體訂單系統。假設有一個網頁前端和一個合作方呼叫取消 API，兩者不會同時更新版本。資料庫交易與[重複請求處理](/blog/order-system-idempotency-receipt/)沿用既有設計，這次只處理錯誤輸出，不更改取消規則。以下數字是教學假設；範例只展示契約，沒有宣稱完成 HTTP 整合或壓力測試。

## 先列出呼叫端真的需要的差別

取消 API 仍先驗證登入與[訂單存取權限](/blog/order-system-detail-authorization/)，通過後才判斷業務狀態。錯誤回應要滿足三件事：使用者看得懂原因、程式可以選擇下一步、客服可以找到這次失敗的紀錄。

先定義三種處理方式就夠了。

- **輸入有誤**：取消原因超過允許長度。畫面保留輸入並指出欄位，讓使用者修改。這裡選 `422`。
- **訂單狀態不允許取消**：訂單已出貨。畫面重新查詢訂單，再依新狀態更新操作選項。這裡選 `409`。
- **未預期的內部錯誤**：資料庫或程式出錯，尚未取得可信的業務結果。顯示通用訊息與查詢編號，回傳 `500`，不透露底層例外。

[RFC 9110 的 409 定義](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.10)談目前資源狀態的衝突；[422 定義](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.21)則適用於內容型別與語法都能理解，但無法處理其中指令的情況。上面的對應是這個案例的設計選擇，不能套用到所有取消 API。JSON 破損、登入失效與權限不足，仍各自遵循既有 HTTP 契約。

「重新查詢」不代表原操作一定失敗，也不授權自動重送。尤其收到 `500` 或連線中斷時，呼叫端可能不知道交易是否已提交。需要重送寫入請求，仍要依原本的冪等契約處理。

## 採用一個共用格式

新 API 可以採用 [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html#section-3)。以下是教學用回應，`example.com` 是示意網域，正式系統應換成自己控制的穩定文件網址。

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
Cache-Control: no-store

{
  "type": "https://api.example.com/problems/order-not-cancellable",
  "title": "訂單無法取消",
  "status": 409,
  "detail": "訂單已出貨，請重新查看訂單狀態。",
  "instance": "urn:uuid:6633eafa-6441-4589-b966-a420fcd23801"
}
```

程式以 `type` 識別錯誤類型。`title` 是簡短名稱，`detail` 說明這次失敗，兩者供人閱讀。`instance` 識別個別事件，此例不提供可開啟的查詢頁面。[標準要求](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1)回應產生端讓本文 `status` 與實際 HTTP 狀態碼一致，也不建議呼叫端解析 `detail` 取得程式資訊。

在單體裡，一個共用的錯誤轉換函式就能負責組出回應。業務模組回傳已知的失敗種類，HTTP 層決定狀態碼與公開欄位；未知例外統一轉成內部錯誤。不要直接把例外物件序列化，也不要把資料庫錯誤碼變成對外錯誤類型。換資料庫不應迫使前端更新。

目前已出貨與結算中的情況，都先讓畫面重新取得訂單狀態，因此暫時共用「目前不能取消」這個類型。如果之後真的需要顯示不同操作，例如「申請退貨」和「等待結算」，再為它們設計明確契約。每個內部失敗分支都新增一個公開類型，維護成本會很快超過用途。

## 前端保留不知道的情況

前端只對認得的類型做特殊處理。收到未知類型時，仍顯示通用錯誤，留下事件識別值供客服查詢。新增錯誤類型不該讓舊版畫面崩潰，也不該預設所有未知失敗都能自動重試。

欄位驗證可以加上自訂的 `errors` 陣列，內容包含欄位位置和穩定的規則名稱。這個陣列的結構要另外寫成團隊契約，並非只要用了 Problem Details 就自動統一。呼叫端要容忍不認識的擴充欄位，這也是 [RFC 9457 的擴充規則](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.2)。

類型網址用來識別與查閱文件，不必每次遇到錯誤都發 HTTP 請求去讀它。範例選完整網址，也能避免相對路徑隨 API 路徑改變而得到不同識別值。文件搬家時，保留原識別值的支援，別把網址整理當成沒有影響的改名。

## 內部紀錄保留多少資料

假設尖峰每秒有 100 個取消請求，其中 2% 失敗，每個公開錯誤本文限制在 2 KiB 以內。錯誤本文的傳輸量約為：

```text
100 requests/s × 0.02 × 2 KiB = 4 KiB/s
```

這只是本文大小的估算，不含 HTTP/TLS 開銷，也沒有證明服務能承受這個流量。2 KiB 是案例設定的上限，不是標準規定。錯誤回應處理目標先訂為 p95 小於 300 毫秒，仍須在包含權限查核與記錄寫入的實際路徑測量。

內部紀錄可用同一事件識別值關聯路由、錯誤類型、時間與受控的診斷資訊。不要把整個請求、付款資料或取消原因原文自動寫入紀錄。公開錯誤也不附 SQL、堆疊或內部主機名稱；[標準的安全考量](https://www.rfc-editor.org/rfc/rfc9457.html#section-5)特別提醒實作細節洩漏風險。

假設每筆內部紀錄 1 KiB，且上述 2 次失敗／秒連續維持一天，便是 172,800 KiB，約 168.75 MiB／日。這是持續尖峰情境，實際容量還要納入索引、副本、保留天數與非尖峰分布。事件識別值適合查單筆紀錄，不要當成監控指標的標籤；錯誤率以有限集合的類型與路由彙總即可。

## 已有錯誤格式時，不急著換

另一個合理方案是沿用既有 `{ code, message, requestId }`。只要 `code` 穩定、HTTP 狀態碼正確、公開與內部資料分開，仍能達成這一課的目的。代價是欄位意義與擴充方式由團隊維護。

Problem Details 適合新 API 或需要共同格式的合作介面。既有客戶已依賴舊格式時，直接換媒體型別與欄位名稱會破壞相容性。先調查呼叫端，再透過新版本或明確的內容協商逐步轉換。兩種格式並存期間，共用內部錯誤分類，避免同一筆失敗在不同輸出格式下有不同語意。

只有一個前端、少數 API 時，不需要另開錯誤服務。等多個團隊需要共同維護類型、舊版客戶長期存在，才把類型定義、相容性測試和產生文件的流程集中管理。這是契約管理的升級，無須先拆微服務。

## 用失敗案例驗收

先對實際 HTTP 路徑做契約測試，而非只檢查 JSON 有哪些鍵。

1. 已出貨訂單取消時，驗證 HTTP `409`、媒體型別、本文 `status` 和 `type` 都正確。前端重新查詢，不重送取消。
2. 同一類錯誤切換中文與英文訊息，前端動作維持一致。
3. 新增未知擴充欄位，舊版呼叫端仍可處理；換成未知類型，則回到通用錯誤畫面。
4. 注入底層例外，回應只有允許公開的欄位，內部紀錄可依事件識別值找到。檢查代理伺服器自行回傳 HTML 錯誤時，前端也不因 JSON 解析失敗而空白。
5. 未取得訂單存取權限的請求，不得因錯誤差異得知訂單是否已出貨。這項檢查接續既有授權設計，不以業務錯誤覆蓋權限結果。

這些是待在產品中執行的驗收案例，沒有宣稱已跑過真實訂單服務。若正式環境突然大量出現未知類型，先查版本與契約落差；若是已知類型比例上升，再查業務狀態與相應依賴。兩者需要的處理不同。

## 練習

前端目前把所有 `409` 都顯示成「請稍後再試」。後端新增「訂單已出貨」的錯誤，但仍有合作方使用舊版 API。你會保留哪些欄位、增加什麼識別方式？請寫出新舊呼叫端各自的處理方式，以及兩項相容性測試。

### 參考思路

先保留合作方依賴的格式與欄位，在可相容的範圍新增穩定錯誤識別值；若要完整換成 Problem Details，另設明確版本或協商方式。新版前端依類型重新查詢訂單，舊版至少能顯示既有錯誤，不應由伺服器假定它已懂新行為。

測試可以先選「改訊息語言仍採取相同動作」與「收到未知類型仍可顯示錯誤」。接著追查舊版的『稍後再試』是否會自動重送；若會，必須另外修正客戶端行為，新增回應欄位本身無法阻止舊程式重試。
