企業每天都有大量使用者行為日誌、交易資料和 IoT 裝置的感測器資料進入系統。

這些原始資料（Raw Data）來源不同、格式雜亂。**資料工程管線（Data Pipeline）** 負責把它們清洗、轉換，整理成 BI 分析、推薦系統和 AI 模型可以使用的高品質資料集。

過去十年，資料管線的架構有兩次大轉變：

1. **處理順序**：從成本高、限制多的 **ETL**，轉向更有彈性的 **ELT**。
2. **計算架構**：從批次、串流分開維護的 **Lambda 雙軌架構**，轉向只用串流的 **Kappa / 串流一體架構**。

| :----------------- | :------------------------------------------------------ | :------------------------------------------------------ |
| **轉換發生位置**   | 獨立的中間層 ETL 引擎（如 Informatica, Pentaho, Spark） | 現代雲端資料倉儲內部（Snowflake, BigQuery, ClickHouse） |
| **原始資料保留**   | 否（通常只載入清洗後的精簡欄位）                        | **是（完整保留 Raw Data 於 Object Storage）**           |
| **靈活性與敏捷度** | 低（商業指標一變更，就得重新從源頭提取歷史資料）        | **極高（直接修改 dbt SQL 模型即時重新計算）**           |
| **維護成本**       | 高（需維護專屬 ETL 運算叢集）                           | **低（計算與儲存分離，依用量彈性計費）**                |

## 3. 即時資料湖入庫與 Schema 漂移治理

在 Lakehouse 架構中，Kafka 裡的即時 JSON 資料通常每分鐘以非同步方式寫入 S3 / GCS 上的 Parquet 檔案。這一步有兩個工程問題要處理：

### 3.1 Schema 漂移（Schema Drift）

- 上游隨時可能在 JSON 裡新增欄位、修改欄位型別，甚至刪除欄位。
- **解法**：在 API 與 Kafka 層導入 **Schema Registry（如 Confluent Schema Registry / Avro）**，強制執行相容性規則（Backward Compatibility），在資料產生的源頭就擋下破壞性變更。

### 3.2 資料品質驗證：Great Expectations 實戰

資料載入分析層之前，必須先設定嚴格的斷言（Assertions）：

```python
# 使用 Great Expectations 定義資料品質守門員規則
import great_expectations as ge

df = ge.read_parquet("s3://data-lake/transactions/date=2026-09-02/")
# 1. 斷言金額不能為負數
df.expect_column_values_to_be_between("amount", min_value=0)
# 2. 斷言用戶 ID 欄位不能為 null
df.expect_column_values_to_not_be_null("user_id")
# 3. 斷言幣別必須在合法枚舉值內
df.expect_column_values_to_be_in_set("currency", ["USD", "TWD", "EUR", "JPY"])
```

## 4. 總結

1. **全面轉向 ELT + dbt**：保留完整原始資料，把轉換下推到資料倉儲，工程迭代更快。
2. **走向串流與批次整合**：用 Kappa 架構與 Apache Flink 統一計算語意，不必再像 Lambda 那樣維護兩套程式碼。
3. **建立資料品質防火牆**：用 Schema Registry 管理 Schema 漂移，用 Great Expectations 做自動化測試，確保下游報表與 AI 模型穩定可靠。
