## 以呼叫端需要知道的細節判斷模組深度

Matt Pocock 的 [Codebase Design](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/SKILL.md) 將介面定義為呼叫端使用模組所需知道的全部資訊，包括參數、不變量、呼叫順序、錯誤與設定。模組深度取決於這些資訊能換得多少行為，不能只看實作行數。（來源查閱：2026-11-05。）

這個 Stripe 包裝範例可用來練習審查。省略了 SDK 匯入與錯誤處理，不能直接當成完整付款實作：

```typescript
export class StripePaymentService {
  private stripe: Stripe;
  constructor(apiKey: string) {
    this.stripe = new Stripe(apiKey);
  }

  async createPaymentIntent(
    amount: number,
    currency: string,
    customerId: string,
  ) {
    return await this.stripe.paymentIntents.create({
      amount,
      currency,
      customer: customerId,
    });
  }
}
```

這個片段轉發金額、幣別與客戶識別碼，尚未展示業務驗證或錯誤轉換。它可能集中 SDK 初始化，也可能是測試替身的替換位置。審查時要檢查實際呼叫端和測試，才能判斷這層包裝是否值得保留。僅憑這段程式，無法斷言它完全沒有隔離價值。

## 刪除測試用來找出模組承擔的責任

Pocock 的同一份文件提出 deletion test。其要點可轉述為：想像刪除模組後，複雜度會消失，還是重新分散到多個呼叫端。後者表示模組正在集中處理共同問題。

刪除前還要檢查相容介面、授權、記錄、監測及測試接縫。這些責任可能只佔少量程式碼。可把審查要求交給 Agent：

```markdown
## 模組審查守則

- 列出模組的呼叫端與現有測試。
- 說明介面隱藏了哪些規則、順序與錯誤處理。
- 檢查相容性、授權、記錄及監測責任。
- 模擬移除後，各呼叫端需要新增或重複哪些邏輯。
- 提出保留、合併或內聯的理由，附上回歸測試範圍。
- 尚未釐清對外契約時，停止自動刪除。
```

## 把審查結果轉成模組加深步驟

下列三步是依前述原則整理的審查流程，不是來源命名的固定三部曲。

### 簡化呼叫端的參數與操作

檢查每個參數由誰決定。例如訂單結算若能從訂單讀取幣別，就不必讓每個呼叫端重複傳入另一份幣別。只有在資料來源與覆寫需求確定後，才能移除參數。

多個動作若總是一起使用，可以考慮提供一個高層次操作。同時保留失敗回報與重試的契約，避免把多次副作用藏在一個含義不清的函式後面。

### 將必要的順序放進模組

如果所有呼叫端都必須先呼叫 `module.doA()` 再呼叫 `module.doB()`，可以檢查是否應由 `module.execute()` 管理順序。測試要涵蓋中途失敗與重複呼叫，而不只確認成功路徑。

### 在確有變動需求的地方設計 seam

外部 SDK 或儲存系統需要被測試替身替換時，可以把依賴傳入模組。Pocock 的文件也提醒，只有假設中的替換需求，不足以支持增加 seam。審查應說清楚實際要替換什麼，以及哪些行為由共用契約測試驗證。

以下僅示意結算入口，`SettlementResult` 的成功與失敗型別仍需依業務定義：

```typescript
export interface OrderSettlementModule {
  settleOrder(orderId: string): Promise<SettlementResult>;
}
```

一個方法不代表介面一定簡單。呼叫端還需要知道重複結算、支付失敗與發票失敗會得到什麼結果，才能安全使用它。

## 把下一次重構限制在可驗收的範圍

挑一個重複轉發參數的模組，先留下呼叫端清單與現有測試結果，再做一次合併或介面簡化。比較前後哪些規則移進模組、哪些仍由呼叫端承擔，以及失敗與重試行為是否保持一致。確認這些結果後，再處理下一個模組。
