顧客按下結帳，畫面轉了幾秒，顯示逾時。他再按一次，後台卻出現兩張訂單。第一次可能已經提交，只是回覆沒有送到手機；第二次若換一個操作識別值，後端很難知道這是重試，還是顧客確實想再買一份。

這一篇的決策是：把辨認操作的收據，和訂單、庫存預留放在同一筆 MySQL 交易裡。收據保存這次操作已作出的結果，讓回覆遺失之後仍有地方查證。

這是「系統設計每日實戰」第 4 篇，不預設你已完成前面的練習。沿用[需求篇](/blog/order-system-requirements-slo/)的虛構案例：單倉、單幣別、每張訂單一種商品，尚未付款；`201` 前必須共同提交訂單、成交快照與庫存預留。[上一篇](/blog/order-system-write-ownership/)已決定由下單用例協調共同連線，今天補上其中刻意留白的 `findOrClaimOperation`。

本文所有欄位、容量與時限都是教學假設。流程是待實作設計，沒有執行真實 MySQL 併發測試或壓測。

## 同一鍵代表同一次購買意圖

收據可以叫 `order_operations`，最低限度包含：

- `customer_id` 與 `idempotency_key`：皆非空，建立複合唯一約束。本文這張表只服務下單；若未來共用到其他操作，鍵的範圍也要納入操作類型。
- `request_fingerprint` 與正規化版本：由已驗證的商品、正整數數量等業務欄位產生，不直接雜湊原始 JSON 字串。欄位排序、預設值或不同表示法不該誤判為新內容；也不納入稍後重讀的目前售價，以免改價讓原鍵重試變成衝突。
- 終局結果、訂單 ID 與必要的回覆資料：成功或已決定的缺貨都保存。認證失敗、格式錯誤則在進入這個流程之前拒絕。

使用者識別值必須來自已驗證身分；每次查收據或重放結果仍需授權。知道別人的 key 不代表能看別人的訂單。鍵值比較也應明確區分大小寫，例如採 binary 語意，不讓資料庫預設定序意外合併兩個鍵。

同鍵、同內容，重放原決定；同鍵、不同內容，回覆明確衝突。顧客真的要再買一份，才建立新鍵。AWS Builders' Library 的[冪等 API 設計](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)討論 caller-provided identifier、原子記錄操作，以及同一識別值攜帶不同參數的問題。這支持上述設計方向，具體欄位是本案例的選擇。

## 唯一收據和訂單一起提交

最小方案使用單一 MySQL InnoDB 寫入主庫。以下是流程規格，不是可直接執行的程式碼：

```text
開始交易，固定使用同一條連線
  INSERT order_operations 的唯一鍵與請求摘要
  讀取伺服器價格，請庫存模組嘗試預留
  若缺貨且沒有庫存副作用：保存缺貨終局結果
  否則：建立訂單與快照，保存成功收據及訂單 ID
COMMIT 確認成功後，才送出終局 HTTP 回覆
```

交易內可以有尚未填完的收據，但不能在中途把它提交為長期 `processing` 狀態。若程式在扣庫存後失敗，整筆交易回滾，收據也消失；若交易提交成功，收據與業務結果必須同時存在。不能留下「收據說成功，訂單沒建立」的半套事實。

缺貨走正常提交，保存已作出的拒絕決定，並保證沒有庫存或預留變更。補貨之後重送原鍵，仍回覆原本的缺貨；重新購買是新意圖，需要新鍵。這延續第一篇契約，避免同一次重試因庫存變化而突然成立。

代價是操作收據也參與鎖競爭。案例若每天 10 萬個新操作，每份收據連同索引假設平均 512 bytes，一天約 `100,000 × 512 = 51.2 MB`，365 天約 `18.7 GB`，均為十進位估算，不含回覆快取、複本與備份。這不是量測結果；實際欄位與索引大小必須抽樣驗證。

## 同時送來的兩個請求，由唯一約束裁決

「先 SELECT，查不到才 INSERT」不能單獨保證安全。兩個交易都可能先查不到，仍須由資料庫唯一約束擋下第二筆。

本方案讓兩個請求都嘗試插入同一唯一鍵。第一筆尚未結束時，另一筆可能等待；第一筆提交後，競爭者可能遇到 duplicate-key。MySQL 官方的[鎖定行為](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)也說明重複鍵檢查可能涉及 shared lock，特定交錯會造成 deadlock。因此不能把競爭流程只寫成「抓到 duplicate 就好了」。

只有插入操作收據時、對指定複合唯一索引發生的 duplicate-key，才進入重放分支；其他表或索引的重複錯誤不能冒充原單。此時先明確回滾本次整筆交易，再用新的主庫讀取核對收據：摘要相同則重放，相異則衝突。不要在舊交易裡吞掉錯誤，然後把先前做過的其他寫入一併提交。

新的讀取也避開舊快照。InnoDB 的預設 `REPEATABLE READ` 一致性讀可能沿用第一次讀取建立的快照，重複 SELECT 不一定看得到別人剛提交的收據。[MySQL 一致性非鎖定讀](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)說明這項語意。此處選擇 rollback 後在主庫以新 autocommit 查詢讀取，不從延遲複本判定操作不存在。

deadlock 和 lock timeout 也要分開。MySQL 的[錯誤處理文件](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)指出，deadlock 會回滾整筆交易；lock timeout 預設只回滾等待中的敘述。應用邊界仍統一確認整筆交易已結束，丟棄不確定的連線，再以原鍵做有限次重試。等待超過請求時限時，回報可重試的未決結果，不把它存成缺貨或成功。

## COMMIT 沒收到回覆，不能自行判成失敗

最容易漏掉的失敗點在最後一刻：應用送出 COMMIT，連線卻斷了。資料庫可能已提交，也可能沒有完成；應用看到連線錯誤，不能據此宣稱庫存已回復。

**提交結果不明時，保留原鍵，不建立新購買意圖。** 重新取得健康連線，查主庫的終局收據。查到就核對摘要並重放；查不到也不能只憑那一次讀取宣告第一次失敗，因為原交易可能仍在完成。

後續仍以同一鍵重新進入唯一約束保護的流程。若原交易最後提交，新的 INSERT 會被唯一約束擋住；若原交易回滾，新的交易才有機會取得該鍵。超過有界等待與重試預算，就保留「結果待確認」，提供查詢與後續確認入口。這是本案例的恢復方案，不是只要捕捉例外就能自動得到的能力。

此論證依賴同一個受唯一約束保護的權威寫入資料庫。若故障切換會遺失已確認的提交，或允許兩個主庫各自接受同鍵，仍可能破壞承諾；複寫、故障切換與災難恢復需要另外驗收。

## Redis 鎖與持久 processing 各自多帶來一份責任

Redis 的短效鎖可以降低同鍵流量同時打進資料庫，但鎖到期、程序停頓或快取遺失後，請求仍可能再次進入。若只靠它去重，資料庫已提交而 Redis 尚未保存結果的時間差也沒有消失。本案例保留 MySQL 唯一收據作為裁決依據；尚無量測證明需要額外 Redis 層。

另一個方案是先獨立提交 `processing` 收據，再非同步執行。它適合長時間工作，卻需要處理程序死掉後誰接手、租約到期與舊執行者是否仍能寫入、如何證明完成等問題。此時 API 通常要重新定義受理與完成的差別，不能沿用「201 就全部完成」而不改契約。

今天的同步下單只涉及本地資料。未來加入遠端付款、長時間供應商 API 或明顯鎖等待，才有理由重新評估非同步流程。遠端副作用不能靠 MySQL rollback 撤銷；站內[金流到對帳閱讀路徑](/blog/payment-to-reconciliation-reading-path/)處理的是那個較大的邊界，本篇不把它假裝成已解決。

## 驗收用兩條連線和一個斷線點

實作後至少補上這些真實 MySQL 整合測試：

- 同鍵同內容同時送出，最後只有一張訂單與一次預留，允許中途暫時未決，但以原鍵恢復後兩邊取得同一終局結果；重試不能用新鍵掩蓋問題。
- 第一個持有者回滾後，等待者可取得操作資格；另建立舊的 REPEATABLE READ 快照，驗證換成新交易後才正確讀到已提交收據。
- 同鍵改數量，回覆衝突，原摘要與訂單不被覆寫。
- 在庫存預留後注入例外，確認訂單、預留與收據一起回滾。再以原鍵重試應能正常成立。
- 在資料庫提交後丟棄 HTTP 回覆，重送後仍回原訂單。另安排 COMMIT 連線中斷，驗證系統先進入未決確認，而非直接回報已取消。
- 同鍵競爭造成等待、deadlock 或 timeout，驗證整筆回滾和有界重試，沒有持續占用 pool 的失聯交易。
- 缺貨後補貨再送原鍵，仍重放缺貨。清掉完整回覆快取後，也不能把原鍵當成新操作。

沿用第一篇假設，完整回覆快取保留 7 天，自動重試限 24 小時，去重索引首版不自動刪除。超過快取期時，保留的終局資料與訂單快照應足以重建契約回覆；若日後要刪索引，必須先重新定義晚到重試的行為。

## 練習：第八天的舊鍵，該不該再扣庫存？

一張訂單第 1 天已提交，回覆遺失。第 8 天顧客重送同一鍵、相同商品與數量；完整回覆快取已清除，但去重收據與原訂單仍在。商品現在漲價，庫存也補過貨。

請決定回覆哪個訂單與價格、要不要再預留，以及客戶端若想重新購買應做什麼。再寫一個能抓到錯誤實作的測試斷言。

### 參考思路

驗證身分與摘要後，從收據和原訂單成交快照重建原結果，不重新計價或預留。新的購買意圖才用新鍵。測試不只檢查回覆成功，還要確認訂單 ID 與原值相同、庫存未再減少，且價格仍是原成交快照。

下一步，把「提交後回覆遺失」加入下單流程的失敗注入清單。只有正常送出兩次請求的測試，還不足以證明最難的那段恢復路徑。
