一段 Skill 值不值得留下，可以用實際任務檢查。我建議先寫清楚任務範圍、驗收證據與副作用邊界，再比較刪減指令前後的結果。

[原始 X 來源](https://x.com/Yangtze_Seventh/status/2096449969808957948)是舊版所引「Skill 將死，方法論永生」討論的出處。2026-11-05 查核時無法讀取全文，因此不將舊版轉述的八個方法視為已核實引文。以下的任務契約與評估步驟是我的工程建議，尚未完成對照實驗。引用的供應商文件也沒有證明特定 Skill 數量或提示長度普遍勝出。

## 指令需要多詳細，由任務測試決定

Anthropic 在 2025-09-29 的 [context engineering 文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)建議保留高訊號脈絡，同時避免脆弱的逐步硬編碼與過度抽象的提示。文章特別區分「最小必要資訊」與「短」：是否足夠，仍要透過任務測試與失敗案例決定。

依照這個做法，應逐項檢查指令的用途。有些任務需要詳細格式與例外規則，有些只需提供專案特有的測試命令。已確認無用或重複的內容可以刪除；仍有必要的限制即使難以量化，也應保留。

我會先把指令分成三類：

- 專案資訊：repository 的啟動方式、測試命令、團隊術語與介面契約。模型無法可靠猜出，應保留可查證版本。
- 工作方法：先重現、提出假設、找反例、比較替代解。是否需要詳細說明，要看模型在代表性任務上的表現。
- 執行限制：可讀寫範圍、部署與付款的核准條件。文字只是在描述政策，真正的阻擋仍要由工具權限、沙盒或核准流程執行。

[Agent Skills 官方說明](https://agentskills.io/what-are-skills)也指出，Skill 不只有文字，可以包含腳本與參考資源，且採用分階段載入。因此已安裝的 Skill 數量，不等於每次進入上下文的全文量。評估成本時，應記錄實際載入內容與工具執行。跨宿主差異另見本站的 [Skills 可攜性討論](/blog/ai-productivity-skills-portability/)。

## 四個欄位能描述任務，但不能取代權限設定

下列 YAML 是任務契約示意，無法直接當成 Agent 產品設定執行。實際採用時，還要在宿主限制寫入路徑、工具與網路存取。

```yaml
goal: 修正重複付款的 checkout bug
method:
  - 只使用隔離測試環境與模擬付款資料
  - 先確認重現條件，再追查共用寫入路徑
evidence:
  - 回歸測試在修正前失敗、修正後通過
  - 列出未覆蓋的付款情境與已執行命令
stop_when:
  - 缺少可安全驗證的測試環境
  - 需要正式金鑰、真實扣款或超出授權的資料
  - 在約定的診斷範圍內仍無法重現
```

這份契約把「請仔細修好」拆成能檢查的行為。不能重現時，可以繼續做已授權的唯讀診斷，但不應宣稱問題已修復；測試通過也只代表已涵蓋的案例，不是所有付款路徑都安全。

**停止規則：一旦需要未授權的資料或副作用，先回報缺口，不以猜測補完。**這條規則應由執行環境配合落實，不能只期待模型自律。

## 審查要找反例，消融要保留比較條件

我建議在錯誤代價高、修改範圍跨模組，或現有測試不足時增加獨立審查。Reviewer 應交付可重現的反例、測試缺口與證據位置。另一個模型也可能共享同樣盲點；角色獨立不代表判斷必然獨立，更不能取代執行測試。

消融則用來回答較窄的問題：某一段指令，在目前模型與任務集上是否有可觀察的幫助？建議這樣做：

1. 保存原版，固定模型版本、工具權限、輸入與驗收標準；每次以相同初始狀態開始。
2. 只移除一段非安全性說明，在一般案例、邊界案例與過去失敗案例上比較。若輸出有隨機差異，重複執行並保留各次結果。
3. 記錄通過率、失敗類型、工具成本與完成時間。不要只看最後回覆是否流暢。
4. 事先約定可接受的退步幅度；結果不明確就保留或繼續測試，不把「沒看見差異」寫成「證明沒用」。

授權、安全與法遵限制不應因小樣本沒有觸發事故而刪除。

## 長任務要保存可接續的狀態

Anthropic 在 2026-09-04 發布的[費馬最後定理形式化報告](https://www.anthropic.com/research/formalizing-fermats-last-theorem)描述，早期多 Agent 嘗試曾因追蹤狀態與協作失敗而受阻，後續使用 Prove2Me 維護定理 DAG、自然語言描述與證明之間的關係。

這份供應商報告描述了平台如何保存狀態，沒有單獨比較角色指令的效果。我會把這個做法用在長任務交接，保存已驗證成果、依賴關係、未解問題與下一個驗收點。是否值得增加多 Agent 或另一層平台，仍須由自己的任務測試決定。

## 下一次修改 Skill，先留下比較紀錄

選一段重複的通用說明，保留原版，挑出能代表實際工作的案例，再比較刪除前後的證據。只有結果足以支持時才精簡；若那段文字承載專案知識或執行限制，就把內容寫得更明確。把測試紀錄和修改理由留在同一次變更裡，方便下次檢查。
