關聯式資料庫撐不住的時候，團隊通常要在兩條路之間選：遷移到 CockroachDB、TiDB、Spanner 這類分散式資料庫，或留在原本的資料庫，在架構層自己做水平擴展。Figma 選了後者。

Figma 用 PostgreSQL 存中繼資料，依它的工程部落格，內容包括權限、檔案資訊、留言、組織資料與檔案版本。2024 年那篇文章說，Figma 的資料庫堆疊「自 2020 年以來成長了接近 100 倍」。這四年裡它沒有換掉 AWS RDS PostgreSQL，而是分三步走：先把單一資料庫撐大，再依資料表群組垂直拆庫，最後自建 Go 寫的 DBProxy 做水平分片。遷移也不是零停機：垂直拆庫時每次切換約 30 秒部分不可用（約 2% 請求失敗），水平分片的第一次實體切換，主庫約 10 秒部分不可用，replica 不受影響。

這篇依 Figma 官方的兩篇文章整理：

- 【垂直拆庫文】Tim Liang，[_The growing pains of database architecture_](https://www.figma.com/blog/how-figma-scaled-to-multiple-databases/)，2023-04-04。
- 【水平分片文】Sammy Steele，[_How Figma's databases team lived to tell the scale_](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/)，2024-03-14。

文中標明「示意」或「我的看法」的部分是我補充的，不是 Figma 公開過的做法。

## 階段 1：2020 年，單一 RDS 撐到極限

依垂直拆庫文，2020 年 Figma 的大部分中繼資料還放在單一的大型 Amazon RDS 資料庫，尖峰時 CPU 使用率超過 65%，資料庫流量大約每年成長 3 倍。團隊先做了幾項戰術性修補，為自己多爭取一年：

1. **升級機型**：從 `r5.12xlarge` 升到當時最大的 `r5.24xlarge`。
2. **加 read replica**：建立多個 read replica 分擔讀取流量。
3. **新用途開新庫**：新功能直接用新的資料庫，限制原本那台的成長。
4. **加 PgBouncer**：連線數已經到數千條，用 PgBouncer 當連線池，降低連線數成長的衝擊。

這些修補有上限。垂直拆庫文提到，因為應用程式對複寫延遲（replication lag）很敏感，並不是所有讀取都能搬到 replica。

---

## 階段 2：2022 年，依資料表群組垂直拆庫

下一步是垂直拆庫：不把一張表拆到多個庫，而是把一組組相關的資料表搬到各自的資料庫。水平分片文舉的例子是「Figma files」和「Organizations」這類表群組。

拆庫分成多次進行。垂直拆庫文寫道，第一次只搬了兩張高流量的表，2022 年 10 月最後一次搬了 50 張。挑哪些表先搬，依據是查詢的平均活躍工作階段（average active sessions，AAS）。Figma 後端用 Ruby 和 ActiveRecord，靜態分析很難判斷一個查詢碰到哪些實體表，所以團隊先在 ActiveRecord 上掛了執行期驗證器，找出跨群組的查詢再拆。

垂直拆庫文給的結果是：最大的分割庫 CPU 使用率降到約 10%。

### 拆庫的代價

垂直拆庫文直接點出，表分到不同的庫之後，會失去表之間的原子交易、foreign key 驗證和 join。

### 為什麼還要水平分片

依水平分片文，到 2022 年底，Figma 已經有快取、read replica 和十幾個垂直分割庫。但有些表長到幾 TB、數十億列，單一資料庫放不下：Postgres vacuum 開始影響可靠性，寫入量最大的幾張表也很快會超過 RDS 支援的最大 IOPS。下一步是把同一張表的資料列分散到多個資料庫。

## 階段 3：2022 年底起，自建 DBProxy 做水平分片

### 為什麼不換成分散式資料庫

水平分片文說，團隊評估過 CockroachDB、TiDB、Spanner 和 Vitess。不選的理由有三個：

- **遷移風險**：換資料庫要做複雜的資料遷移。
- **專業要重建**：團隊已經累積了大量在內部穩定、高效地運作 RDS Postgres 的經驗，換掉就得從頭學。
- **時間不夠**：成長太快，只剩幾個月的餘裕。

垂直拆庫文在 2023 年也提過類似的考量：如果改用雲端代管的分散式 Postgres，Figma 會是規模最大的單一叢集客戶之一，團隊不想第一個撞上某些擴展問題。至於 Vitess，它是 MySQL 的方案，改用它或 NoSQL 都要做複雜的雙讀雙寫遷移。

最後的選擇是留在既有的 RDS Postgres，在上面自建水平分片。

### DBProxy 的位置與功能

DBProxy 是用 Go 寫的新服務，位於應用層與 PgBouncer 之間。水平分片文列出它負責負載卸除（load-shedding）、可觀測性、交易支援、資料庫拓撲管理，以及一個輕量的查詢引擎；有了它之後，團隊也能做動態負載卸除和 request hedging。

查詢引擎的流程是：查詢解析器把應用送來的 SQL 轉成抽象語法樹（AST），邏輯規劃器從 AST 取出查詢類型和邏輯分片 ID，實體規劃器再把邏輯分片 ID 對應到實體資料庫。

### 邏輯分片與實體分片分開

水平分片文把應用層的「邏輯分片」和 Postgres 層的「實體分片」拆成兩件事。邏輯分片用 Postgres view 表示，應用先在邏輯分片上跑，資料還沒搬離原本的庫。確定邏輯分片運作正常之後，才做實體分片，把資料真的分散到多台資料庫。

這樣拆的好處是，一張表一旦在應用層完成水平分片，實體層要用幾個分片都可以，之後要擴充只要再做一次實體分片拆分。

Figma 沒有公開分片數量。原文示意圖畫的是「兩個實體分片承載四個邏輯分片」。

### Shard key 與 colo

Figma 挑了幾個 shard key，例如 `UserID`、`FileID`、`OrgID`，路由時用 shard key 的雜湊值。

強關聯的表會放進同一個 colo（colocation）：同一個 colo 的表共用 shard key 和實體分片配置。原文的示意是「以 UserID 分片的表放在一起，以 FileID 分片的表放在一起」。只要查詢限定在單一 shard key，同一個 colo 內的表就能做跨表 join 和完整交易。

下面是我寫的示意，表名不是 Figma 的實際 schema：

```sql
-- 示意：同一個 colo、同一個 shard key（file_id）內，可以用一般交易
BEGIN;
  INSERT INTO comments (file_id, comment_id, body) VALUES ('f_123', 'c_999', '...');
  UPDATE files SET updated_at = NOW() WHERE file_id = 'f_123';
COMMIT;
```

### Scatter-gather 與支援的查詢範圍

查詢帶有 shard key 時，只會送到一個分片。缺 shard key 時，查詢引擎要做 scatter-gather：把查詢送到每個分片，再合併結果。水平分片文指出，每個 scatter-gather 都會對所有資料庫造成同樣的負載，太多的話，分片就失去意義。

為了控制範圍，團隊用 shadow planning 分析實際的查詢，選出能涵蓋最常見 90% 查詢的語法子集：範圍掃描和單點查詢都允許，join 只允許在同一個 colo 內、並以 shard key 連接。團隊另外做了一個「shadow application readiness」框架，預測正式流量在不同 shard key 下的表現。

## 階段 4：遷移流程

水平分片文說，團隊希望能在「接近零停機」（near-zero downtime）的情況下擴充，而且每一步都能回滾。實際遷移分兩段：先做邏輯分片，再做實體分片。

第 3 步的細節出自垂直拆庫文。水平分片文說，水平分片沿用了垂直拆庫的大部分邏輯，風險最高的元件在垂直拆庫時已經處理過，但沒有逐步重述切換流程。

1. **用 view 做邏輯分片**：先讓應用透過 Postgres view 讀寫，以百分比逐步放量。同時用影子讀（shadow reads）框架，讓所有正式讀取流量也走一次 view，比對經過 view 與不經過 view 的查詢在效能與正確性上有沒有差異。這一步比對的是兩種查詢路徑，不是新舊兩台資料庫。
2. **邏輯複製整份資料**：水平分片文說，團隊刻意不做「filtered logical replication」（只把屬於該分片的資料複製過去），而是每個分片都複製整份資料，再只允許讀寫屬於該分片的那一部分。垂直拆庫文也說明了為什麼用邏輯複製而不是快照還原：快照還原沒辦法讓目的庫的儲存空間變小。團隊先刪掉目的庫的索引，初始複製完成後再重建，把複製時間縮短到幾個小時。
3. **暫停與同步**：依垂直拆庫文，切換時用 PgBouncer 暫停新連線，撤銷客戶端在原資料庫上對這些表的查詢權限，短暫等待後取消仍在執行的查詢（通常不到 10 個），再用 LSN 確認兩邊資料庫已經同步。
4. **切換與回滾**：同步後把流量導到新的資料庫。垂直拆庫文的流程包含建立反向複寫，新庫的修改會複寫回舊庫，必要時可以回滾。水平分片文則說，實體分片的回滾做得到，但需要更複雜的協調來確保資料一致。

切換代價依兩篇原文的數字：垂直拆庫時，每次操作約 30 秒部分不可用（約 2% 請求失敗）。水平分片的第一張表在 2023 年 9 月上線，主庫約 10 秒部分不可用，replica 沒有受到影響。

## 2024 年時還沒完成的部分

## 三種做法比較（我的看法）

下表是我依上文整理的比較，不是 Figma 原文的評估：

| 評估面向         | 單一 RDS     | 換成分散式資料庫     | DBProxy＋分片（Figma 的選擇）       |
| :--------------- | :----------- | :------------------- | :---------------------------------- |
| **擴展方式**     | 只能升級機型 | 由資料庫本身水平擴展 | 先做邏輯分片，實體分片數量可以再拆  |
| **對應用的影響** | 無           | 要做完整資料遷移     | 查詢要帶 shard key，join 限同 colo  |
| **維運經驗**     | 沿用既有經驗 | 要從頭累積           | 底層仍是 RDS Postgres，經驗可以沿用 |
| **跨分片查詢**   | 不需要       | 由資料庫處理         | scatter-gather，限縮在少數查詢      |

## 我從這個案例看到的幾點

1. **先用便宜的方法爭取時間**：Figma 先升級機型、加 replica 和 PgBouncer，換到一年；再垂直拆庫，等到個別大表真的撞上 IOPS 和 vacuum 的限制，才做水平分片。
2. **邏輯分片先上線，實體分片後做**：用 Postgres view 先驗證路由和查詢，資料還沒搬，出問題可以退回。
3. **用 colo 保留交易**：把常一起查的表綁同一個 shard key，join 和交易在單一 shard key 內還能用。
4. **影子讀比對的是查詢路徑**：Figma 的影子讀比對的是經過 view 與不經過 view 的查詢，在資料搬動前先確認分片後的查詢結果與效能。
5. **代理層集中處理分片邏輯**：查詢解析、路由、負載卸除都放在 DBProxy，應用程式不用各自處理。
