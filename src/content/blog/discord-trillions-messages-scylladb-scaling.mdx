Discord 的訊息儲存換過三次資料庫，兩篇官方文章各記錄了一段：

1. **2015 年（單一 MongoDB replica set）**：Discord 第一版在 2015 年初用不到兩個月做出來，所有資料都放在一個 MongoDB replica set。2015 年 11 月左右累積到 1 億則訊息，資料和索引已經塞不進 RAM，延遲開始變得不可預測（[_How Discord Stores Billions of Messages_](https://discord.com/blog/how-discord-stores-billions-of-messages)，2017-01-13）。
2. **2015 年底至 2016 年初起（Apache Cassandra）**：2017 年 1 月那篇文章說，切換到 Cassandra 已經「just over a year」。2017 年叢集是 12 個節點、存數十億則訊息；到 2022 年初變成 177 個節點、數兆則訊息，GC 停頓、熱點分區和維運負擔都越來越重（[_How Discord Stores Trillions of Messages_](https://discord.com/blog/how-discord-stores-trillions-of-messages)，2023-03-06）。
3. **2022 年 5 月起（ScyllaDB）**：在這之前，Discord 先在 API 和資料庫之間加了一層 Rust 寫的資料服務，用 **Request Coalescing（請求合併）** 擋住熱點流量，這層在還跑 Cassandra 時就上線了。2022 年 5 月訊息資料庫切換到 ScyllaDB，幾個月後量到的歷史訊息讀取 p99 從 Cassandra 的 40–125ms 降到 15ms，寫入 p99 從 5–70ms 降到 5ms。

下面以 Discord 這兩篇官方文章為準。[ByteByteGo 的整理](https://bytebytego.com/guides/how-discord-stores-trillions-of-messages)是二手資料，數字與 Discord 原文一致。

## 一、Cassandra 為何在「數兆級訊息」規模下撞牆？

2017 年的文章說，Discord 訊息的讀寫比約 50/50。當時列的需求是：線性擴展、自動容錯移轉、維護成本低、經過實戰驗證、效能可預測、不是 blob store、開源，而 Cassandra 是唯一全部符合的選項。資料模型如下（Discord 文中的精簡版，2017 年的文章註明省略了約 10 個欄位）：

```sql
CREATE TABLE messages (
    channel_id bigint,
    bucket int,
    message_id bigint, -- Snowflake ID (內嵌毫秒時間戳)
    author_id bigint,
    content text,
    PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

- **分區鍵（Partition Key）**：`((channel_id, bucket))`。同一個頻道的訊息依時間切成靜態分桶（Bucket），每桶約 10 天。Discord 看過最大的幾個頻道後，判斷 10 天的訊息量可以讓單一 partition 穩定低於 100MB。
- **叢集鍵（Clustering Key）**：`message_id DESC`。Discord 的 ID 都是 Snowflake，可以依時間排序，載入頻道時能告訴 Cassandra 從哪裡開始做範圍掃描，相關資料在磁碟上也是連續存放的。

### 177 個節點時期的問題

2022 年初，叢集是 177 個節點、存數兆則訊息。Discord 2023 年的文章列出的問題如下：

1. **熱點分區（Hot Partition）**：
   大量使用者同時讀同一個頻道，會讓那個 partition 變熱。Discord 的讀寫都用 quorum 一致性，所以負責這個熱 partition 的節點一變慢，經過這些節點的查詢延遲都會上升。Discord 的說法是，遇到熱點分區時，經常會拖累整個叢集的延遲。
2. **JVM GC 停頓**：
   Cassandra 跑在 JVM 上，GC 停頓會造成明顯的延遲尖峰。嚴重時會出現連續的長時間 GC 停頓，得由維運人員手動重開節點、在旁邊盯著。
3. **壓實（Compaction）落後**：
   壓實常常跟不上，節點在壓實時延遲會一路往外擴散。
4. **維運負擔重（High Toil）**：
   on-call 團隊經常被呼叫，有些維護作業成本太高，只好減少執行次數。

墓碑（Tombstone）是更早的問題。在 LSM-Tree 裡，刪除只會寫入一個墓碑標記。2017 年的文章記錄過 2016 年的一次事件：一個大多數訊息都被刪掉的頻道，載入要 20 秒，因為 Cassandra 得掃過數百萬個墓碑，產生垃圾的速度比 JVM 回收得還快，節點持續出現 10 秒的 stop-the-world GC。當時 Discord 把墓碑保留期從 10 天降到 2 天，並開始追蹤空的 bucket 來避開這個問題。

## 二、儲存引擎選型：為什麼選擇 ScyllaDB？

Discord 2023 年的文章列出選 ScyllaDB 的理由：效能較好、修復較快、shard-per-core 架構帶來更強的負載隔離，以及沒有 GC。到 2020 年，Discord 已經把訊息以外的資料庫都遷到 ScyllaDB；最後一個障礙是反向查詢（reverse query）效能不夠，ScyllaDB 團隊改善之後，訊息資料庫才能搬。

ScyllaDB 的特性：

- **相容 Cassandra**：ScyllaDB 相容 Cassandra 的資料模型與 CQL 驅動，應用層幾乎不需要改寫查詢邏輯。
- **C++ 與 Seastar 非同步框架**：ScyllaDB 用 C++ 寫成，建立在 [Seastar](https://seastar.io/) 框架上，採用 **Thread-per-Core** 的 Shared-Nothing 無共享架構。
- **沒有 GC**：沒有 JVM GC 的負擔，記憶體由每個 CPU 核心各自管理，延遲分佈比較可預測。
- **節點數**：Discord 用 **72 個 ScyllaDB 節點**取代原本 177 個 Cassandra 節點。節點變少有一部分是因為單機磁碟變大：每個 ScyllaDB 節點有 9 TB，Cassandra 節點平均是 4 TB。

## 三、先在 Cassandra 前面加一層 Rust 資料服務

Discord 沒有等新資料庫就緒，先處理熱點分區。2023 年的文章舉的例子是：大型伺服器發了一則 `@everyone` 公告，使用者紛紛打開 App 讀這則訊息，大量流量同時打到資料庫裡同一個頻道的 partition。

為此，Discord 在 API 單體（Python，見 Discord 另一篇文章 [_Pytest Daemon: 10X Local Test Iteration Speed_](https://discord.com/blog/pytest-daemon-10x-local-test-iteration-speed)）與資料庫叢集之間加了一層 **Rust 實作的資料服務（Data Service）**。這層大致是一個資料庫查詢對應一個 gRPC endpoint，刻意不放業務邏輯。

這層上線時，底下仍是 Cassandra。Discord 的說法是它幫助很大，但沒有解決所有問題：熱點分區和延遲上升還是會發生，只是沒那麼頻繁。它爭取到的時間，讓團隊準備 ScyllaDB 叢集並執行遷移。

### 1. 一致性雜湊路由（Consistent Hashing）

API 呼叫資料服務時，依照 `Hash(channel_id)` 做一致性雜湊路由，**同一個頻道的請求都會進到同一個資料服務實例**。

### 2. Request Coalescing（請求合併 / Singleflight）

同一個實例收到多個查詢同一筆資料的請求時，資料服務只查一次資料庫。第一個請求會在服務裡啟動一個 worker task；後續請求發現這個 task 存在，就訂閱它；task 查完資料庫後，把結果回給所有訂閱者。資料服務建立在 Tokio 非同步生態系上。

下面的程式碼是概念示意，不是 Discord 的實作。Discord 原文講的是同一個 row，程式碼以 `(channel_id, bucket)` 為 key 回傳整串訊息，是延伸寫法：

```rust
// 概念實作：請求合併邏輯 (Singleflight Pattern)
async fn get_messages(&self, channel_id: ChannelId, bucket: BucketId) -> Result<Vec<Message>, Error> {
    let key = (channel_id, bucket);

    // 檢查是否已有相同查詢正在進行中 (In-flight Task)
    let (task, is_leader) = self.in_flight.entry(key.clone()).or_insert_with(|| {
        let (tx, rx) = tokio::sync::watch::channel(None);
        (tx, true)
    });

    if is_leader {
        // 第一個發起者負責去資料庫撈取資料
        let result = self.db_client.query_messages(channel_id, bucket).await?;
        task.send(Some(result.clone())); // 廣播給所有訂閱者
        self.in_flight.remove(&key);
        Ok(result)
    } else {
        // 後續到達的請求直接等待 Leader 廣播結果，不發送資料庫查詢
        let mut rx = task.subscribe();
        rx.wait_for(|res| res.is_some()).await;
        Ok(rx.borrow().as_ref().unwrap().clone())
    }
}
```

- **第一筆請求**：在 `in_flight` 雜湊表中註冊任務，成為 Leader，向資料庫發出一次查詢。
- **後續請求**：發現已有相同 key 的任務在執行，直接掛起並訂閱該任務的結果。
- **查詢完成時**：Leader 把資料廣播給所有等待中的協程。

> [!TIP]
> **削峰成果**：Discord 只說這能大幅降低打到資料庫的流量尖峰，沒有公布量化數字。

## 四、零停機遷移數兆則訊息

Discord 的目標是在不停機的情況下搬完數兆則訊息，步驟如下：

1. **雙寫（Dual-Writing）**：
   新資料同時寫入 Cassandra 與 ScyllaDB。新的 ScyllaDB 叢集採用 Discord 的 super-disk 儲存拓撲：用 Local SSD 取得速度，再以 RAID 把資料鏡像到持久磁碟。
2. **Rust Migrator 搬歷史資料**：
   最初用 Spark 寫的 migrator 估計要三個月。團隊改用擴充過的資料服務函式庫寫遷移工具：從 Cassandra 讀 token range，用 SQLite 在本機記錄檢查點，再把資料 firehose 進 ScyllaDB。估計時間降到九天，速度最高每秒 320 萬則訊息。
3. **卡在 99.9999%**：
   最後幾個 token range 讀取逾時，原因是裡面有大段從未在 Cassandra 被壓實掉的墓碑。把那段 token range 壓實之後，幾秒內就搬完了。
4. **資料驗證**：
   把一小部分讀取同時送到兩個資料庫，自動比對結果。
5. **切換**：
   ScyllaDB 叢集在完整的正式環境流量下表現穩定，而 Cassandra 的延遲問題越來越頻繁，Discord 就把 ScyllaDB 切成主要資料庫。時間是 2022 年 5 月。前面提到的 15ms p99，是切換幾個月後量到的結果。

## 五、架構演進的對比與總結

| 評估維度             | Cassandra（2022 年初）                   | ScyllaDB（2022 年 5 月切換後）           |
| :------------------- | :--------------------------------------- | :--------------------------------------- |
| **節點數量**         | 177 個（單機磁碟平均 4 TB）              | 72 個（單機磁碟 9 TB）                   |
| **執行環境**         | Java JVM（受 GC 停頓影響）               | C++ Seastar（無 GC、Thread-per-core）    |
| **歷史訊息讀取 p99** | 40–125ms                                 | 15ms                                     |
| **訊息寫入 p99**     | 5–70ms                                   | 5ms                                      |
| **Rust 資料服務**    | 遷移前已上線，緩解熱點但沒有根治         | 沿用 Request Coalescing 與一致性雜湊路由 |
| **維運成本 (Toil)**  | 高（on-call 經常被呼叫、得減少維護作業） | 低（硬體利用率高；推論可省下 JVM 調優）  |

### 從這個案例帶走的三點

1. **儲存引擎的 runtime 會影響尾延遲**：Discord 在 Cassandra 上反覆遇到 GC 停頓造成的延遲尖峰。換成沒有 GC 的 ScyllaDB 後 p99 穩定下來，但同期單機磁碟加大、Request Coalescing 也已上線。原文沒有拆開各因素的貢獻，所以「GC 是原因之一」只是推論。追求低 P99/P999 的系統，選型時值得把 GC 列進評估。
2. **在資料庫前面收斂請求**：熱點不能全靠資料庫自己處理。一致性雜湊加 Request Coalescing，可以在應用和資料庫之間把重複請求合併掉。Discord 的經驗也顯示，這一層能緩解熱點、爭取時間，但沒有取代換資料庫。
3. **用時間分桶限制 partition 大小**：不管用哪種分散式資料庫，把持續增長的訊息或時序資料用 `(entity_id, bucket)` 切成時間窗口，可以避免單一 partition（Wide Partition）無限長大、拖垮叢集。
