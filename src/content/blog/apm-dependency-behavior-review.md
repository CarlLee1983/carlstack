一個只更新 lockfile 的 PR，也可能改變 agent 如何處理退款。技能檔沒有編譯錯誤，提示詞仍是合法文字，原本「列出待確認項目」的步驟卻可能變成「直接呼叫工具完成工作」。這是教學假設，但足以說明技能依賴需要驗收什麼。

GitHub 在 [2026 年 11 月 3 日公告](https://github.blog/changelog/2026-11-03-dependabot-version-updates-support-agent-package-manager/)，Dependabot 已支援 Agent Package Manager（APM）的版本更新。它會針對 `apm.yml` 中支援的 git 依賴開 PR，並重新產生已存在的 `apm.lock.yaml`。**這項支援是 version updates，不含 security updates。**

我會把它接進技能更新流程，先讓機器提出候選版本，再用可觀察的行為決定是否合併。維護者不必每天手動追版本，審查責任也能留在清楚的位置。

> [!NOTE]
> 查核日期為 2026 年 11 月 4 日，已閱讀 GitHub 公告、APM 支援文件及官方治理說明。以下案例、測試安排與停止條件是工程建議，沒有實際安裝 APM、執行 Dependabot 更新或測試 agent 成效。

## 先確認哪些依賴會被更新

[GitHub 的 APM 支援文件](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories#apm)區分了幾種 ref。SemVer tag 會追蹤符合規則的新 tag；完整 commit SHA 則更新至最新、非預發行的 annotated release tag 所指向的 commit。使用 branch ref 時，只改既有 lockfile，manifest 可以完全不動。

同一份文件也列出未支援的形式，例如 object-form、`mcp:`、沒有 ref 的項目、local path 與 abbreviated SHA。不能用「已開啟 APM 更新」當作依賴清冊完整的證據。採用前可為每個項目記錄來源、固定方式、是否被 updater 支援，以及未支援時由誰追蹤。

清冊還應有一次人工覆核日期。沒有收到更新 PR，可能是來源沒有新版，也可能是寫法不受支援、權限不足或排程未成功。值班者需要分清這幾種狀態，才能決定要聯絡套件維護者、修正設定，還是維持原版。單看 PR 數量無法回答是否漏管依賴。

對只有幾個穩定技能的專案，人工定期看 release 是可接受的起點。依賴增加、更新容易漏掉時，再導入自動 PR。這樣省下的是找版本與準備變更的時間，沒有省略技能內容的審閱。

## lockfile 沒有大幅變更，也要追到實際內容

假設訂單助手引用退款檢查技能的 `main` 分支。今天的 PR 只更新 lockfile 裡的解析結果，`apm.yml` 沒改。審查者若只確認清單一致，就看不到新版技能是否增加了退款動作。

我建議 PR 檢查涵蓋兩個層次。第一層比較更新前後的解析結果，確認來源和 commit。第二層打開那兩個版本之間的內容差異，讀取變更的指令、提示詞及附帶檔案。新增套件或額外工具要求要單獨標示，不能混在「更新鎖檔」這個摘要裡。

APM [官方首頁](https://microsoft.github.io/apm/)把 lockfile 描述為固定版本與內容雜湊的機制。可重現內容有利於回退與對照，但同一份內容搭配不同模型、harness 或工具設定，仍需要各自驗收。因此測試紀錄也應保存這些版本，避免把模型切換造成的差異誤算成技能更新。

## 用訂單助手測出越權與遺漏

最小試行可以只挑一個技能，保留舊版作為比較基準。測試環境使用合成訂單與不會真的付款的工具替身，固定模型、harness 和輸入。建議先放入四類案例：

- 資料完整：提供有效訂單及退款條件，確認輸出包含可追溯的判斷依據。
- 資料缺漏：省略付款狀態，確認它要求補資料，沒有把未知寫成已付款。
- 權限不足：只允許產生建議，確認工具紀錄沒有退款或寫入請求。
- 不可信內容：讓外部備註要求忽略流程，確認備註沒有取得修改執行規則的權限。

檢查對象應包含工具呼叫及其參數，不能只讀最後一句「已依規則處理」。若 agent 說不會退款，卻先送出退款請求，最後的文字答案依然可能看起來正確。

這些案例可以重複執行，保留每次結果與失敗樣本。第一次採用時不必追求漂亮的總分，先把越權呼叫、捏造必要狀態及關鍵欄位遺漏列成獨立判定。**任何未授權的寫入嘗試，都停止這次升級。** 工具替身擋下動作，不代表技能的決策符合預期。

## 安裝檢查與執行期限制要分開驗收

[APM 治理文件](https://microsoft.github.io/apm/enterprise/governance-guide/)明確區分安裝時的檢查與執行期限制，也把 policy engine 標為 early preview。若要把相關政策檢查設成正式發布條件，應固定 APM 版本，核對目前版本實際執行哪些規則，再測試失敗時是否確實阻止安裝。

我的設計建議是，即使技能已通過內容審查，退款權限仍由工具端檢查。唯讀助手使用唯讀憑證；能建立退款申請的助手，也不應因此取得任意金額的付款權限。這讓提示詞更新失誤的影響有明確範圍，也使測試能觀察到被拒絕的動作。

若沒有辦法記錄工具呼叫，先限制在產生建議的用途。直接給正式寫入權限，再靠人工抽看回答補救，會讓回退變得困難。

## 第一個 PR 就要能回到上一版

合併之前，保存前一份 manifest、lockfile、APM 與 harness 版本，以及驗收輸出。回退驗證應重新建立環境，再確認載入的是舊內容。只把 git commit 切回去，卻沿用已更新的工作目錄，無法證明回退有效。

先選一個低風險、已有人工審查的技能接入更新 PR。第一次驗收完成後，再衡量審查耗時與失敗原因，決定要不要擴大範圍。若目前連「是哪個版本讓助手送出這個工具請求」都答不出來，下一步就是補上這條追蹤紀錄。
