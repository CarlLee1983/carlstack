內容研究、寫作與發布會共用背景，卻需要不同工具和核准步驟。把它們交給不同 Agent 之前，值得先確認哪些工作反覆出現、哪些資源需要分開管理。

這個題目最初來自[金塵馬的 Codex 多 Agent 貼文](https://x.com/jinchenma_ai/status/2095713255968694405)。2026 年 11 月 5 日更新時無法重新讀取原貼文，因此保留來源連結，以下目錄結構改作設計範例，產品行為則依 OpenAI 官方文件核對。範例沒有實際啟動多 Agent，也沒有路由成功率的測量結果。

我建議只有在工作反覆出現、又需要獨立規則或資源時，才建立長期維護的職責。這是一項維護成本的取捨；一次性研究也可以使用短期子 Agent，不需要先替它設一個永久角色。

## 長期職責與專案保存不同的東西

專案圍繞一個交付目標，保存素材、目前狀態與成果。例如「為 CarlStack 寫這篇文章」完成後，任務就可以結束。

長期職責保存反覆使用的做法，例如來源查核、繁中寫作、封面與發布檢查。同一套內容工作流程可以服務多篇文章，也可以拆成 Skill，交給現有 Agent 使用。是否需要另一個 Agent，要看它是否真的需要獨立執行、工具或權限。

OpenAI 文件描述的 `AGENTS.md` 是指令載入機制。Codex 啟動時會依全域設定及專案根目錄到目前工作目錄的路徑建立指令鏈。把檔案命名為 `AGENTS.md`，不會因此建立一個持續執行、獨立授權的 Agent。[AGENTS.md 官方說明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 五個訊號用來評估拆分成本

工作反覆出現後，可以檢查以下差異：

- 規則：內容發布有固定的來源查核與檢查流程，是否適合抽成 Skill？
- 資料：某項工作只能接觸發票或指定知識庫，是否需要獨立的存取範圍？
- 工具：某個職責需要特定連接器或資料庫，其他任務是否根本不需要它？
- 權限：草稿製作者與發布者是否需要分開授權？
- 交付與驗收：是否有專屬成果與檢查方式，例如可合併的 PR 或對帳結果？

至少一項差異值得長期維護，才繼續評估拆分。只有文章主題改變，通常沿用既有寫作流程即可。若同一類錯誤反覆出現，先驗證修正方法，再把它寫進共用規則，避免每個角色各留一份略有不同的版本。

## 目錄路由必須明確載入指令

以下保留「共用入口、職責規則、專案資料分開」的結構。這是指令組織範例，尚未包含子 Agent 建立或派工設定。

```text
digital-team/
├── AGENTS.md                # 共用入口與邊界
└── agents/
    ├── main-agent/AGENTS.md # 路由與結果整合
    └── content/AGENTS.md    # 內容職責的規則

carlstack/                   # 實際文章專案與資料
```

Codex 不會為了組成指令鏈，自動掃描所有兄弟目錄。從 `digital-team/` 啟動時，下面兩個角色檔需要明確要求讀取；從旁邊的 `carlstack/` 啟動，也不能假設會載入 `digital-team/AGENTS.md`。官方的探索路徑是專案根目錄到目前工作目錄，每層按 `AGENTS.override.md`、`AGENTS.md` 與設定的備援檔名選取，並有總大小限制。[指令探索與優先順序](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

根目錄可放以下示意規則。相對路徑以 `digital-team/` 為基準，正式使用前要確認檔案存在且可讀。

```markdown
# Digital Team

## 入口

- 先讀取 `agents/main-agent/AGENTS.md`。
- 使用者明確要求撰寫或修改正式文章時，讀取 `agents/content/AGENTS.md`。
- 僅詢問選題或工具用法時，直接回答，不啟動文章製作流程。
- 發布另查使用者授權；載入內容規則本身不構成發布授權。
- 所需規則檔無法讀取時，回報缺少的路徑，不假設已載入。
```

同一個 Agent 讀取另一份規則，仍然是同一個執行者。若要平行分工，還需要實際的派工機制，並明確傳入任務、工作目錄與可用工具。指令檔只處理其中的行為要求。

## 用正例與反例測試路由

新增內容職責後，至少試兩種請求，並檢查載入的規則和實際動作。

「把這則來源寫成正式文章並發布」應進入內容工作流程。驗收需要來源、文章、必要檢查與發布結果；發布權限不足時應停在核准步驟，不能只因讀到發布規則就自行執行。

「這個選題值得寫嗎？」應只回覆選題判斷。它可以做必要的查核，但不應建立文章或啟動發布。反例能找出描述過寬的角色，例如看到「文章」兩字就誤判成製作任務。

兩個例子只能作為起步檢查。還應加入「只寫草稿、不要發布」、來源無法讀取、缺少規則檔等情境，觀察是否停在正確步驟。錯誤出現時先縮小職責描述，再決定是否需要更複雜的路由。

Skill 也需要同樣的觸發測試。官方文件說明，Codex 可以依 Skill 的 `description` 自行選用，完整指令則在選用時才載入。因此，描述應明確寫出適用與不適用情境。[Skills 官方說明](https://learn.chatgpt.com/docs/build-skills)

## 權限必須由執行環境限制

內容職責通常不需要帳務資料，財務職責也不應預設取得社群發文權限。這些要求除了寫在規則裡，也要落實到工具、帳號與檔案權限。

Codex 的 sandbox 控制程式在技術上能做什麼，approval policy 控制哪些動作需要核准。設定可寫目錄，不代表自動禁止讀取其他資料；連接器也有自己的服務權限，不能把終端機的 sandbox 當成所有工具共用的限制。[Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security)

對這套工作流程，我建議採取以下分級：

1. 在已授權的來源內查詢與產生草稿。
2. 修改資料前列出精確目標與預期差異。
3. 刪除、批次寫入、付款、發送與公開發布，另設明確的核准步驟。

這是流程建議，不是 Codex 所有模式的預設保證。**未取得必要授權，就停在草稿或變更提案。**驗收時除了確認允許的動作能成功，也要在測試資料上確認禁止的動作確實被拒絕。敏感資料需要額外的讀取限制或獨立帳號，不能只靠一句「不准讀」。

## 從一項每週重複的工作開始

挑一項每週都得重新交代背景的工作，列出它專屬的規則、資料、工具、權限與驗收方式。若主要差異只是流程，先整理成 Skill；需要獨立執行或資源範圍時，再評估另一個 Agent。

完成後記錄實際讀到哪些規則，跑過應命中、不應命中與禁止動作的測試。等這些結果可重現，再增加第二個職責。
