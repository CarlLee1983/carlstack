在網際網路初期，伺服器通常採用**同步阻塞 I/O（Blocking I/O）** 結合「一個連線對應一個執行緒（Thread-per-Connection）」的模型（如早期 Apache HTTP Server）。

連線數到了數千，數千個作業系統執行緒帶來的**執行緒堆疊記憶體消耗**與**劇烈的 CPU 核心上下文切換（Context Switch）** 會讓伺服器瀕臨崩潰，也就是著名的 **C10K 難題**。

為了用單一或少量執行緒同時監聽數萬到數百萬個 Socket 連線，Linux 核心發展出 **I/O 多工（I/O Multiplexing）**，從 `select`、`poll` 一路演進到 `epoll`。

下面拆解這三代技術的底層資料結構、核心與使用者空間之間的複製開銷，以及 Nginx 和 Netty 依賴的 **Reactor 事件驅動模式**。

---

## 1. 三代 I/O 多工架構比較

| 比較項目                  | select (1983)          | poll (1997)            | epoll (2002)              |
| :------------------------ | :--------------------- | :--------------------- | :------------------------ |
| 底層核心資料結構          | 固定大小位元遮罩 Array | 動態陣列 / 鏈結串列    | 紅黑樹 + 就緒雙向鏈結串列 |
| 最大監聽連線數限制        | 預設 1024 (FD_SETSIZE) | 無上限 (受記憶體限制)  | 無上限 (受系統 FD 限制)   |
| FD 從使用者空間複製到核心 | 每次呼叫都整份重新複製 | 每次呼叫都整份重新複製 | 僅 epoll_ctl 註冊一次     |
| 核心就緒檢索複雜度        | O(N) 線性輪詢全部 FD   | O(N) 線性輪詢全部 FD   | O(1) 回呼通知立即回傳     |
| 事件觸發模式              | 僅支援水平觸發 (LT)    | 僅支援水平觸發 (LT)    | 支援 LT 與邊緣觸發 (ET)   |
| 適用高併發規模            | 連線數極少 (`< 100`)   | 連線數較少 (`< 1000`)  | 百萬級長連線 (C1000K)     |

## 2. 第一代 `select` 與第二代 `poll` 的瓶頸

### 2.1 `select` 的兩大缺陷

`select` 系統呼叫用 `fd_set` 位元向量傳遞要監聽的檔案描述子：

1. **1024 限制**：核心標頭檔以巨集定義 `FD_SETSIZE` 固定為 1024，無法直接突破。
2. **整份複製與 `O(N)` 線性輪詢**：
   - 應用程式每次呼叫 `select`，都要把包含所有監聽 FD 的陣列**從使用者空間完整複製到核心空間**。
   - 核心不知道是哪一個 Socket 收到資料，只能以 `O(N)` 走訪所有 1024 個 FD。
   - 回傳後，使用者端應用程式還要再以 `O(N)` 逐一檢查 `FD_ISSET`，造成嚴重的 CPU 空轉。

### 2.2 `poll` 的微幅改進

`poll` 用 `pollfd` 結構陣列取代位元遮罩，突破了 1024 的數量限制。但**每次呼叫都要整份複製到核心**，**核心與使用者空間兩邊也各要做一次 `O(N)` 線性輪詢**，這兩個問題都沒有解決。監聽 10 萬個連線、只有 10 個有活動時，系統 99.99% 的時間都在做無效掃描。

## 3. `epoll` 核心架構解析

Linux 2.6 核心引入了 `epoll`，在核心層面把「註冊監聽」與「等待事件就緒」拆開。

### 3.1 `epoll` 的三個核心 API

1. `int epoll_create(int size)`：在核心中建立一個 `eventpoll` 物件。
2. `int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event)`：向核心註冊、修改或刪除需要監聽的 Socket。
3. `int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout)`：等待就緒事件，只回傳**有 I/O 事件發生的 Socket 清單**。

- **零無效輪詢**：`epoll_wait` 只回傳就緒清單中的項目，時間複雜度是 `O(就緒連線數)`，與總連線數 N 無關。
- **避免重複複製**：透過 `epoll_ctl` 註冊的 Socket 會長期保留在核心紅黑樹中，呼叫 `epoll_wait` 時不必再傳一次監聽清單。

## 4. 水平觸發（LT）vs. 邊緣觸發（ET）

`epoll` 支援兩種事件通知模式：

### 4.1 水平觸發（Level-Triggered, LT - 預設模式）

- **行為**：只要 Socket 的接收緩衝區（Receive Buffer）中**還有未讀取的資料**，每次呼叫 `epoll_wait` 都會通知該事件。
- **優缺點**：程式寫起來簡單安全，不容易漏讀資料；但重複通知可能帶來少量額外開銷。

### 4.2 邊緣觸發（Edge-Triggered, ET - 高效能極限）

- **行為**：僅在 Socket 狀態**由「未就緒」變為「就緒」的瞬間（狀態跳變）** 通知一次。應用程式如果沒有一次把緩衝區資料讀完，核心不會再發第二次通知。
- **程式要求**：
  1. Socket 必須設定為**非阻塞模式（`O_NONBLOCK`）**。
  2. 應用程式必須用 `while` 迴圈持續呼叫 `read()`，直到回傳 `EAGAIN` 或 `EWOULDBLOCK` 為止，否則會造成資料永久遺失。
- **實際案例**：Nginx 與 Netty 預設採用 ET 模式，追求最大吞吐量。
