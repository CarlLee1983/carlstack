Pod 反覆重啟時，重新部署可能暫時恢復服務，也可能同時觸發快取預熱與資料庫連線高峰。先保存 Pod 狀態、事件與上一個容器的日誌，才能比較重啟前後差異。

這裡使用診斷順序與設定範例，非特定事故紀錄。範例日誌為示意，YAML 需依實際映像檔、健康端點與容量調整。行為以 [Pod 生命週期](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)、[QoS 定義](https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/)與叢集實際版本／設定共同核對。

## 為什麼必須抗拒「直覺式重啟」？

Kubernetes 本身就是一個巨型的狀態收斂引擎（Reconciliation Loop）。當 Pod 進入異常狀態時，Controller-Manager、Kube-Scheduler 與 Kubelet 已經在背後執行了大量的自我修復邏輯。

`CrashLoopBackOff` 是容器重啟退避的顯示狀態，不是 Pod phase。常見預設退避從 10 秒倍增到 300 秒，版本與功能閘門可能調整這些值。刪除 Pod 會建立新的實例，也可能使下游再承受一次啟動負載。

> [!IMPORTANT]
> **保存診斷資料後再決定修復方式。** 若必須立即恢復服務，依事故 runbook 決定是否重啟，並盡量同步保留日誌。不要直接移除控制器 selector 使用的 label 當作隔離手段，以免控制器補建 Pod；隔離方式應先確認路由與控制器行為。

## Kubernetes 故障排查的 5 步定位管線

先判斷故障出現在哪個階段，再選擇下一個證據來源。

### Step 1: Pod 生命週期與控制面事件（Lifecycle & Events）

所有診斷的第一個動作，永遠是檢查控制面給出的歷史判決：

```bash
kubectl describe pod <pod-name> -n <namespace>
```

不要直接略過輸出跳到最後，必須先看最底部的 `Events` 區塊與中段的 `State` 狀態機：

- **Pending 狀態：** 代表 Pod 尚未完成啟動，可能尚未排程，也可能正在下載映像檔或準備容器。常見原因包含節點資源不足（Insufficient cpu/memory）、節點具備不可容忍的污點（Taints/Tolerations 不匹配），或是 PVC 處於 `WaitForFirstConsumer` 卻找不到符合拓撲條件的儲存節點。
- **ImagePullBackOff / ErrImagePull：** 映像檔拉取受阻。可能是名稱或 Tag 錯誤、網路或驗證失敗（詳見後文陷阱拆解）。
- **FailedMount：** 磁碟卷掛載逾時。常見於雲端 EBS 仍被前一台當機的 Worker 鎖定尚未卸載（Multi-Attach error），或是 ConfigMap/Secret 鍵值遺失。

**停止規則：** 若 Events 明顯卡在排程、映像檔或儲存掛載階段，排查邊界停留在控制面與雲基礎設施，**絕不要進入容器內部查應用程式碼**。

---

### Step 2: 退出碼語義與歷史崩潰日誌（Exit Code & Crash Logs）

當 Pod 狀態為 `CrashLoopBackOff` 時，容器已經成功被 Kubelet 啟動過，但行程隨後終止。先讀取上一個容器實例的日誌：

```bash
# 抓取容器死前最後吐出的標準輸出
kubectl logs <pod-name> -c <container-name> --previous --tail=200
```

搭配 `kubectl get pod <pod-name> -o yaml` 觀察 `lastState.terminated` 中的數值。退出碼需搭配 reason、signal、事件與日誌判讀，應用也可能自行回傳相同數字：

- **Exit Code 0：** 代表主行程「正常退出」。容器內部的 PID 1 行程跑完了任務並正常結束。這通常發生在 Web 應用被錯誤包裝在非守護行程的啟動指令中，或者背景 Job 提前執行完畢。
- **Exit Code 1 / 2：** 通常是程式或命令列錯誤，意義由應用定義。可能沒有堆疊，需查 stdout、stderr 與啟動參數。
- **Exit Code 137（128 + 9）：** 常見於 SIGKILL。OOM、人工強制終止或超過停機寬限期都可能造成，不能單憑 137 判定 OOM。核對 `reason: OOMKilled`、核心日誌與 cgroup 事件。
- **Exit Code 143（128 + 15）：** 常見於 SIGTERM 終止。若寬限期後再遭 SIGKILL，通常會看到 137，而非用 143 證明強殺。能處理 SIGTERM 的程式也可能自行正常退出。

---

### Step 3: 探針合約與端點健康路由（Probe Contract & Endpoints）

容器明明正在執行，日誌裡沒有任何報錯，但外部流量卻瘋狂收到 HTTP 502/503？或者容器啟動到一半，日誌剛印出 "Starting server..." 就突然重啟？

檢查端點與探針事件：

```bash
# 檢查 Pod 是否實際進入端點列表
kubectl get endpointslices -n <namespace> -l kubernetes.io/service-name=<service-name>
```

- `Running` 但沒有可用端點時，核對 Service selector、Pod labels、namespace、Pod Ready condition 與 EndpointSlice 的 `ready`。Readiness 失敗是其中一種原因，沒有匹配 Pod 也會沒有端點。
- 若 Events 顯示 Liveness 連續失敗，檢查是否達到 `failureThreshold` 並觸發重啟，再對照當時負載與健康端點回應。

**停止規則：** 確認探針失敗原因再調閾值。Liveness 應識別適合靠重啟恢復的狀態，不能把所有依賴失敗與瞬間過載都當成容器需要重啟。

---

### Step 4: Worker 節點狀態與 Kubelet CRI 鏈路（Node & Kubelet CRI）

若同一個節點上的多個不同業務 Pod 同步出現不可預期的異常，問題焦點必須立即從單一 Pod 提升到 Worker 實體節點：

```bash
# 查看節點是否有異常壓力標記
kubectl describe node <node-name>
```

重點檢查 `Conditions` 欄位中的四個關鍵指標：

- **MemoryPressure：** 節點可用記憶體觸及設定閾值。驅逐順位還考慮是否超過 request、Pod priority 與相對用量，不是單純按 QoS 類別依序刪除。
- **DiskPressure：** 檔案系統可用空間或 inode 觸及閾值。檢查實際檔案系統與 kubelet eviction 設定，回收映像檔後仍可能需要驅逐。
- **PIDPressure：** 可用 PID 低於設定閾值。
- **Ready = False / Unknown：** False 表示節點回報未就緒，Unknown 常見於心跳逾時。分別檢查 kubelet、runtime 與控制面連線。

**現場搶修指令：**  
登入該 Worker 節點，調閱 Kubelet 與 Container Runtime（containerd）的系統日誌：

```bash
journalctl -u kubelet -u containerd -n 200 --no-pager
```

---

### Step 5: 作業系統核心與 cgroups 實體收割（Kernel & OOM Killer）

核心日誌可補充容器終止原因。

當容器因為 Exit Code 137 消失，且應用日誌中一片空白時，不要在 Pod 層級漫無目的地翻找，直接登入該 Pod 所在的宿主機，調閱內核緩衝區：

```bash
dmesg -T | grep -E -i "oom-killer|killed process"
```

若確實發生 OOM，可能看到類似的示意日誌：

```text
[Tue Sep 29 16:12:04 2026] Memory cgroup out of memory: Kill process 28491 (node) score 982 or sacrifice child
[Tue Sep 29 16:12:04 2026] Killed process 28491 (node) total-vm:2847120kB, anon-rss:1048576kB, file-rss:0kB, shmem-rss:0kB
[Tue Sep 29 16:12:04 2026] oom_reaper: reaped process 28491 (node), now anon-rss:0kB
```

對照事件時間與 cgroup 路徑，確認是否屬於目標容器：

1. **Memory cgroup out of memory：** 表示 cgroup 層級發生 OOM；需沿 cgroup 階層確認命中的限制，不一定只來自這個容器的 Pod Spec。
2. **Killed process：** 標明了被終止的具體實體 PID 與當時佔用的實體記憶體大小（RSS）。

## 兩大經典故障陷阱深度拆解

映像檔拉取與 OOM 可各自再拆成幾個檢查方向。

### 陷阱 A：`ImagePullBackOff` 的三層真實邊界

多數人看到 `ImagePullBackOff`，下意識只會確認鏡像名稱與 Tag 是否打錯。然而在成熟的雲原生架構中，鏡像拉取失敗通常是由以下三層邊界破裂引起：

- **第一層：節點層 DNS 解析失效**  
  Worker 節點無法解析私人 Registry（例如 `harbor.internal.corp` 或 AWS ECR 域名）。嘗試登入節點執行 `dig <registry-domain>`，檢查是否因為 CoreDNS 轉發設定異常或節點 `/etc/resolv.conf` 被覆蓋。
- **第二層：公開 Registry 節流（Docker Hub Rate Limiting）**  
  若映像檔來自 Docker Hub 且未設定全域 ImagePullSecret，當整個叢集以相同的 NAT Gateway 公有 IP 對外拉取時，會迅速觸發 Docker Hub 匿名拉取配額（額度依當時方案與官方政策），回傳 `HTTP 429 Too Many Requests`。
- **第三層：雲端 IAM / OIDC 憑證輪替超時**  
  在 AWS EKS 或 GCP GKE 中，Kubelet 透過內部 Helper 取得動態存取 Token。若 Node IAM Role 權限收窄，或是節點中繼資料服務（IMDSv2）因 hop limit 限制被拒絕存取，拉取可能回傳 `401 Unauthorized` 或其他驗證錯誤，應以 Events 與節點日誌核對。

---

### 陷阱 B：`OOMKilled` 的真假邊界：Heap 限制 vs. cgroup 物理限制

很多 Java 與 Node.js 開發者感到困惑：「我的 JVM 明明設定了 `-Xmx4g`，Pod 的 memory limit 設為 `5Gi`，為什麼應用完全沒有噴出 `java.lang.OutOfMemoryError`，容器就暴斃了？」

Heap 上限只涵蓋行程記憶體的一部分。

- JVM 的 `-Xmx` 只限制了 **Java 堆積記憶體（Heap Memory）**。
- 但行程在 Linux 視角下消耗的記憶體，還包含 **非堆積記憶體（Metaspace / Off-Heap Direct Memory）、JIT 編譯快取、每個執行緒的 Native Stack（大小隨 JVM、平台及設定而異），以及 glibc 的記憶體碎片（Memory Fragmentation）**。
- 若 Heap 為 4 GiB、其他受 cgroup 計量的記憶體為 1.1 GiB，合計 5.1 GiB 會超過 5 GiB 限制。GB 與 GiB 需使用同一單位。
- 核心 OOM 終止不需先讓 JVM 拋出 Java 例外；SIGKILL 無法由應用攔截。

```yaml
# 錯誤示範：Heap 上限等同 cgroup limit（缺少非 Heap 預算）
spec:
  containers:
    - name: api-service
      resources:
        limits:
          memory: "4Gi"
      env:
        - name: JAVA_OPTS
          value: "-Xmx4g -Xms4g" # 沒有非 Heap 緩衝

---
# 示意 Pod spec 片段：暫留 25% 給非 Heap，仍需量測尖峰用量
spec:
  containers:
    - name: api-service
      resources:
        requests:
          memory: "4Gi"
        limits:
          memory: "4Gi"
      env:
        - name: JAVA_TOOL_OPTIONS
          value: "-XX:MaxRAMPercentage=75.0 -XX:+UseG1GC"
```

## 防禦型探針架構：終結「探針殺死容器」的雪崩循環

三種探針控制不同動作，設定時要分開測試啟動、接流量與重啟。

### 探針職責三要素

- **Startup Probe（啟動探針）：**  
  **只負責吸收慢啟動延遲。** 對於需要載入巨量機器學習模型、預載靜態快取或執行 JIT 預熱的服務，設定高容忍的 Startup Probe。在它通過之前，Kubelet 會完全停用 Liveness 與 Readiness 檢查，給容器充足的暖機空間。
- **Readiness Probe（就緒探針）：**  
  **只負責流量路由控制。** 當容器瞬間並發過高、暫時無力處理新請求時，Readiness 失敗會將其從負載平衡端點中剔除，讓容器能專注消化佇列，待恢復後自動掛回。若檢查共用 MySQL 或 Redis，故障時可能讓全部 Pod 同時未就緒。依賴檢查要依服務是否能降級決定，並限制逾時及呼叫頻率。
- **Liveness Probe（存活探針）：**  
  **負責偵測可由重啟恢復的故障。** 它應該只檢查最輕量級的行程健康狀態（例如 `/healthz` 回傳 200）。它的逾時時間（timeoutSeconds）與失敗閥值（failureThreshold）應依正常尾端延遲與恢復目標設定，避免在 CPU 滿載排隊時被視為死鎖而遭重啟。

### 生產級防禦範本

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: resilient-core-api
spec:
  replicas: 5
  selector:
    matchLabels:
      app: resilient-core-api
  strategy:
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 0 # 更新策略不主動減少可用副本，非整體可用性保證
  template:
    metadata:
      labels:
        app: resilient-core-api
    spec:
      terminationGracePeriodSeconds: 60 # 給予充裕的優雅停機時間
      containers:
        - name: core-api
          image: internal-registry.corp/core-api:v2.4.1
          resources:
            requests:
              cpu: "1000m"
              memory: "2Gi"
            limits:
              cpu: "2000m"
              memory: "2Gi" # Burstable：CPU request 與 limit 不同
          # 1. 吸收啟動峰值：最多允許 30 * 3s = 90s 的純啟動時間
          startupProbe:
            httpGet:
              path: /healthz/startup
              port: 8080
            failureThreshold: 30
            periodSeconds: 3
          # 2. 流量閥門：嚴格與外部依賴解耦，只探測本機 HTTP 伺服器
          readinessProbe:
            httpGet:
              path: /healthz/ready
              port: 8080
            periodSeconds: 5
            successThreshold: 1
            failureThreshold: 3
          # 3. Liveness 閾值需以負載與故障演練驗證
          livenessProbe:
            httpGet:
              path: /healthz/live
              port: 8080
            initialDelaySeconds: 0 # 由 startupProbe 承擔保護，此處設 0
            periodSeconds: 15
            timeoutSeconds: 3
            failureThreshold: 5
```

## 下一步：將 Diagnostic Loop 固化為工程防線

將五步指令與對應證據放進 runbook，並註明哪些情況允許立即復原服務。Event 保存時間受 API Server 設定影響，可用 exporter 補足長期紀錄。

驗收 Deployment 時核對 selector、template labels 與 QoS，再測慢啟動、短暫依賴故障及尖峰負載。若要 Guaranteed QoS，在傳統逐容器設定下每個容器的 CPU、記憶體 request 都要等於各自 limit；目前範例為 Burstable。
