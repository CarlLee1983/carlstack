營運人員一次送出二十份訂單報表。API 很快回覆「已排程」，背景 worker 隨即開二十條連線查主庫。下載按鈕不再逾時，下單卻開始等連線，資料庫的讀取負載也升高了。

把工作移到背景，只縮短了送出請求的等待時間。我的首版會替報表設定兩個上限：最多十二份等待、最多兩份執行。額度用完就拒收新的匯出，讓使用者稍後再送。**等待中的報表不占用匯出查詢連線；執行中的報表確認停止後，才釋放執行名額。**

這是虛構商店的設計練習，沿用模組化單體與 MySQL 8.4。數量、時間與服務目標都是教學假設，尚未執行資料庫整合測試或負載測試。前一篇[匯出快照](/blog/order-system-export-snapshot/)解決明細與合計讀到不同版本，這次處理多份正確報表同時執行時，誰可以使用資源。

## 接受排程，只承諾能追蹤處理結果

營運人員提交日期範圍後，服務保存工作識別值、提出者、篩選條件、建立時間與狀態，回覆查詢進度的位置。報表完成後才提供下載。存檔與下載都沿用營運權限，檔案不能因為有難猜的網址就跳過驗證。

狀態至少區分等待、執行、成功、失敗與過期。「已接受」代表工作已持久保存，可以查到結果，不保證每一份都產生檔案。等待超過三分鐘的工作會標成過期，畫面提示重新選擇範圍或稍後重送。這項約定要出現在操作介面，不能在服務繁忙時才偷偷丟棄工作。

首版只接受七天內、固定欄位的報表，執行最多輸出兩萬列，超出就失敗並要求縮小範圍。這些限制控制單次工作的形狀，但兩萬列輸出仍可能來自大量掃描，必須檢查索引與查詢計畫。不要在接單 API 先跑一遍昂貴的 `COUNT(*)`，讓拒收檢查本身變成另一份報表。

Google SRE 的 [Handling Overload](https://sre.google/sre-book/handling-overload/)提醒，請求成本可能相差很大，單看 QPS 難以代表資源需求。這裡同樣不能把「兩份報表」當成固定的 CPU 或 I/O 用量。

## 十二份等待，必須在同一個短交易內數清楚

首版使用資料庫工作表作為持久待辦，不另外引入訊息系統。接單端先完成便宜的參數與權限檢查，再用一筆短交易鎖定專屬的匯出接單控制列。

持有這把鎖時，先把已到等待期限的工作標成過期，再計算仍在等待的工作。少於十二份才插入新工作並提交，否則回覆忙碌。所有會增加等待數量的路徑，包括日後的重試，都要經過同一個控制列。兩個 API instance 因此不能各自讀到十一份，再同時插入第十二份。

這把鎖只保護接單，不包住產生報表的長查詢。取得控制列也要有短等待期限，拿不到就回覆繁忙，避免報表接單請求反過來塞滿 API 的連線池。工作表需要支援狀態與期限查找的索引，歷史完成工作則依保留政策清理。

同一位使用者重按按鈕，以請求識別值查回原工作，避免重複占額度。它和[下單冪等收據](/blog/order-system-idempotency-receipt/)有相同需求：回應遺失後，先辨識原請求，再決定是否新增。

## 兩個名額要限制整個部署，不能每台各算兩個

首版只啟動一個專用匯出 worker 程序，內部允許兩份工作同時執行。程序先取得空閒名額，再用短交易把一筆未過期工作由等待改成執行。兩個執行名額也可能同時領到同一筆資料，所以領取須鎖住工作列，或用帶狀態條件的更新並確認只改到一列；取得後再次檢查等待期限。提交後才借出專用匯出連線，建立前一篇的唯讀快照，查詢並產生檔案。

API、訂單處理與匯出各自配置連線額度，匯出池最多兩條工作連線。接單、領取、狀態更新及取消需要的短連線另外列入總預算，也不能無限增加。這樣可以避免匯出拿光同一個應用池，主庫的 CPU、磁碟與 buffer pool 仍由大家共享。

部署時必須先停止舊匯出程序領取工作，等既有查詢結束，再啟動新程序。若直接讓新舊兩個程序重疊，各自的併發二就會變成全站四。這個首版接受部署期間暫停匯出，換取容易查核的全站上限。需要多副本接手或不停機部署時，才引入可驗證的跨程序領取與執行協調，不能只複製 worker。

AWS 在 [Avoiding insurmountable queue backlogs](https://aws.amazon.com/builders-library/avoiding-insurmountable-queue-backlogs/)分別討論工作隔離、併發限制及向上游施加背壓。佇列保存工作，資源限制則決定現在能做多少工作，兩者需要一起設計。

## 三分鐘是等待期限，不是由算式算出的服務保證

假設每份工作連同清理都在三十秒內完成，兩個執行名額的估算處理率是 `2 ÷ 30 = 0.067 份／秒`，約每分鐘四份。兩份正在執行、十二份已在等待時，若先忽略等待過期規則，FIFO 最後一份約在第六輪取得名額，等待約一百八十秒。實際到達三分鐘期限就標成過期，不再開始。

這個估算依賴兩個 worker slot 持續可用、每輪不超過三十秒、沒有重試插隊及排程額外延遲。查詢取消、程序重啟或資料量改變，都會讓這些條件失效。因此三分鐘用來決定「等待多久就不再執行」，不能據此保證百分之九十五的報表都在三分鐘內開始。

若營運每分鐘持續送六份，每分鐘只能完成四份，等待量會持續增加。把上限從十二改成一百二十，只會延後拒收並延長等待。介面收到繁忙結果後，應顯示稍後重試並採退避，避免使用者端立刻重送。重試的流量控制可以延續[共同重試額度](/blog/order-system-retry-budget/)，不要另建一條不受限制的重試入口。

## 三十秒到了，查詢可能還沒停

工作執行期限設為三十秒，到期就停止新增查詢並進入取消程序。HTTP 請求結束、程式的 promise 逾時或 UI 顯示失敗，都不足以證明 MySQL 已停止工作。

MySQL 的 [KILL Statement](https://dev.mysql.com/doc/refman/8.4/en/kill.html)區分 `KILL QUERY` 與 `KILL CONNECTION`：前者中止目前陳述式但保留連線，後者還會終止連線。官方也說明 KILL 設定中止旗標後就回傳，不等待清理完成。因此不能送出取消指令就立刻把名額交給下一份報表。

匯出保持在執行或取消中的占額度狀態，直到驅動程式及資料庫狀態證明查詢已結束、交易已回滾或連線已終止。半成品檔案不公開。取消卡住時保留名額並告警，必要時暫停新的匯出，而不是讓新的查詢疊上去。

程序崩潰也沿用這個原則。執行查詢前，先持久記錄工作識別值、worker 世代與資料庫工作階段的對應。重啟時先停止領取，把原先執行中的工作列出，核對其資料庫工作是否已消失。連線識別值可能失效或被重用，不能只拿舊數字直接發送 KILL；無法確認歸屬或終止狀態時，維持暫停並交由人工查核。確認舊工作停止後才轉為失敗並恢復領取。首版不自動重試中斷工作，接受短暫人工處理。若需要自動接管，還要解決[舊 worker 寫回](/blog/order-system-worker-takeover/)與重複執行資源，僅加一個逾時 lease 不足以取消資料庫查詢。

## 下單變慢時，匯出要能停下來

延續[容量預算](/blog/order-system-capacity-budget/)的做法，驗收要同時看匯出與下單。假設測試負載固定每秒二十次下單，先量沒有匯出的基準，再加入兩份符合最大允許範圍的報表。

可先訂一組待驗證門檻：下單 p95 不超過五百毫秒、錯誤率不超過百分之一；同時觀察連線等待、DB CPU、讀取 I/O、查詢時間與最老等待工作年齡。測試資料分布、硬體、取樣期間與負載都要一併保存，這些數字才有比較意義。

若連續三個一分鐘觀察窗超過下單門檻，就停止領取新的匯出，拒收新匯出並告警。這是教學上的停止規則，需要另外驗證樣本數與恢復條件。已在執行的工作沿原期限收尾；若仍持續壓垮主庫，走受控取消。單純停領取不會立刻消除正在執行的負載。

最小方案的代價很清楚：營運可能拿不到報表，部署也會短暫停領。商店先保留下單流程，再讓報表稍後處理。若連一份匯出都會傷害下單，就該縮小查詢、改善索引，或移到報表副本。副本能隔離部分讀取負載，但報表要重新約定複製延遲與資料時點，不能直接沿用主庫的即時性假設。

也可以完全不排隊：名額已滿就同步拒收，少維護一套等待狀態，適合很少使用的內部工具。這次保留十二份等待，是為了吸收短暫集中提交；若沒有這個需求，直接拒收反而更容易維護。

## 驗收時故意讓取消比逾時慢

下面是實作時的測試計畫，並非已執行結果：

1. 同時送二十個不同工作，暫停 worker 領取，確認最多十二份進入等待，其餘明確拒收。再讓多個 API instance 同時提交，檢查接單競態。
2. 啟動 worker，從資料庫觀察匯出查詢，確認最多兩份執行，等待工作沒有長時間占用查詢連線。
3. 讓一份查詢超過三十秒，並延遲取消完成。確認第三份工作不會因應用層逾時而提前開始。
4. 在兩份工作執行時終止 worker，再啟動新程序。確認它先核對舊查詢，而不是直接把兩份工作改回等待。
5. 讓工作等到三分鐘後才有空位，確認它轉為過期，沒有繼續建立快照或輸出檔案。
6. 持續下單並加入最大報表，驗證停止規則及恢復流程；不能只測報表下載成功。

## 練習：多開一台 worker，速度會翻倍嗎？

目前一個 worker 程序、併發二。部署時多開一台相同設定的程序，資料庫連線池也各自限制二。團隊認為「每台都有上限，所以仍然安全」。請指出全站上限如何改變，以及上線前要補哪個驗收。

全站可能同時執行四份報表，兩個程序的本地限制不會自動合併。它也不保證速度翻倍，兩者仍競爭同一個資料庫。若保留首版設計，就避免新舊程序重疊並驗證停止領取、等待查詢結束的部署順序。若要多副本，需另設全站執行額度與安全接管，並在程序崩潰、取消延遲及網路失聯時觀察實際查詢數。驗收對象是仍在消耗資源的工作，不只是工作表裡的 running 數量。
