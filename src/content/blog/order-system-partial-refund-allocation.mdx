假設顧客買了三件各 100 元的商品，使用整單折扣 10 元，實付 290 元。後來只退其中一件，客服要退 100 元、96.67 元，還是等最後一件退貨時再補差額？

[報價有效期那一課](/blog/order-system-quote-validity/)保存了顧客接受的價格，當時還沒有折扣規則。現在增加整單折扣與部分退貨。**下單時把折扣分到每件商品，連同每件實付金額一起保存；退貨時讀取這份紀錄。**

這是「系統設計每日實戰」第 24 課。金額算法只是其中一步，還要決定退款依據存在哪裡、何時不能再改，以及兩次退款同時進來時怎麼避免重複退同一件。

> [!NOTE]
> 商店、金額、流量與退貨政策都是教學假設。官方文件查核日期為 2026 年 11 月 7 日。下方 Python 可獨立執行，交易流程則是設計規格，尚未執行 MySQL 併發、金流整合或負載測試。

## 退貨政策先說清楚

沿用單一 MySQL 寫入主庫與模組化單體。這次只處理已全額付款、已核准退貨的商品，一筆付款對應一張訂單，單一幣別，沒有運費、稅額與多張優惠券。退貨資格、物流驗收與庫存回補另有流程，不靠退款成功推定。

產品選擇以下規則：

- 整單折扣依每件商品的原成交金額比例分攤；零價贈品不分到折扣。
- 核准退貨後，退回該件保存的實付金額。退了一件，不重新檢查剩餘商品是否滿額，也不追討其他商品已享有的折扣。
- 分次退回全部商品，退款合計應等於原實付金額。退貨次序不影響每件金額。

這些是商店要選的政策，不是金流 API 替商店決定的規則。[Stripe 建立退款 API](https://docs.stripe.com/api/refunds/create)允許同一付款多次部分退款，總額不能超過尚未退回的金額。它會檢查付款餘額，卻不知道 A 商品的折扣該分到多少。

為了讓「一件」可被追蹤，成交時替每個購買單位保存固定的 `unit_id`。同 SKU 買兩件也有兩筆金額紀錄；這是訂單內部識別，不是實體商品序號。若同款商品可互換，退貨系統依固定的 `unit_id` 順序配對尚未退回、也未被其他退款申請占用的數量，客服看到的是這次配對後的金額。

## 10 元除以三，剩下的那一分給誰

這裡用 TWD 的兩位小數付款介面示範，100 元保存成 10,000。最小貨幣單位就是 API 能表達的最小金額；不能假設每種幣別都乘 100。Stripe 的[幣別文件](https://docs.stripe.com/currencies)另外列出零位小數與特殊規則，付款和撥款也可能不同。

三件原價合計 30,000，折扣是 1,000。若每件折扣都四捨五入成 333，總折扣只有 999，實付合計就多一分。若把這一分留到退款當下才決定，同一件商品可能因為先退或後退而得到不同金額。

可以在成交前一次算完：

1. 每件原價乘上總折扣，再除以商品原價總和。先取整數商，保留餘數。
2. 總折扣減去已分出去的整數部分，得到還剩幾個最小單位。
3. 依餘數由大到小，每件補一個單位，直到補完。同餘數時，依固定 `unit_id` 排序。

三件同價、識別依序是 A、B、C，折扣會分成 334、333、333。實付是 9,666、9,667、9,667，合計恰好 29,000。A 比 B 少付一分，是成交時就確定的差異，訂單明細與退貨確認頁都應顯示同一份數字。

以下純函式用 Python 整數運算，輸入金額均為最小貨幣單位。它回傳每件折扣，沒有讀取價目、資料庫或金流。

```python
def allocate_discount(prices: dict[str, int], discount: int) -> dict[str, int]:
    if not prices or any(type(p) is not int or p < 0 for p in prices.values()):
        raise ValueError("prices must be non-negative integers")
    if type(discount) is not int:
        raise ValueError("discount must be an integer")
    total = sum(prices.values())
    if not 0 <= discount <= total:
        raise ValueError("discount exceeds the order amount")
    if total == 0:
        return {unit_id: 0 for unit_id in prices}

    parts = {
        unit_id: divmod(price * discount, total)
        for unit_id, price in prices.items()
    }
    result = {unit_id: part[0] for unit_id, part in parts.items()}
    remaining = discount - sum(result.values())
    ranked = sorted(prices, key=lambda unit_id: (-parts[unit_id][1], unit_id))
    for unit_id in ranked[:remaining]:
        result[unit_id] += 1
    return result


prices = {"A": 10000, "B": 10000, "C": 10000}
discounts = allocate_discount(prices, 1000)
assert discounts == {"A": 334, "B": 333, "C": 333}
assert sum(prices[k] - discounts[k] for k in prices) == 29000
```

所有餘數都小於除數，所以待補的單位數少於商品件數，一輪就能分完。固定識別也讓輸入順序改變時仍得到相同結果。正式實作須固定 ID 的比較方式，例如 ASCII 字串序，不要讓不同服務各用不同地區的排序規則。

Python 的整數可隨數值擴大；換成有固定整數寬度的語言時，`price × discount` 的中間值也要檢查溢位。資料庫可使用有範圍檢查的整數欄位，或適當精度的 DECIMAL。MySQL 的[精確數值運算](https://dev.mysql.com/doc/refman/8.4/en/precision-math.html)能避免二進位浮點誤差，但欄位精度、捨入方式與溢位處理仍要明確設定。

## 下單保存結果，退款不用重新算

報價階段就產生穩定的購買單位 ID 與分攤結果，讓結帳畫面能顯示。接受報價後，沿用[共同下單交易](/blog/order-system-write-ownership/)，將以下資料與訂單一起提交：

- 訂單：幣別、金額單位、商品原價合計、折扣總額、實付總額，以及分攤規則版本。
- 每個購買單位：`unit_id`、SKU、原成交金額、分攤折扣與實付金額。
- 報價與訂單的對應，供重試與客服核對。

「成交快照」就是這份不再跟著目前價目更新的交易資料。保存後，後台改價、停用優惠券或升級分攤算法，都不重寫舊訂單的結果。規則版本用來解釋當初怎麼算，退款直接讀已保存的數值，不要求所有歷史算法永遠留在退款服務裡。

提交前檢查每件折扣介於零與該件原價之間，每件實付等於該件原成交金額減去分攤折扣。各件折扣合計須等於整單折扣，各件實付合計須等於訂單實付。若價目與報價不一致，應在接受報價的既有規則處理，不能在寫快照時悄悄改成新價。

## 同一件商品不能同時退兩次

金額固定後，仍有一個競爭問題。客服與顧客入口可能同時要求退 A，兩邊都查到「還沒退款」，接著各自送出 9,666。

最小方案沿用持久退款待辦，讓所有退款入口在短交易中先鎖同一張訂單。MySQL 的 [`FOR UPDATE`](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)須放在明確交易內，鎖會維持到提交或回滾。流程可以寫成：

```text
BEGIN
  檢查操作者權限，鎖定訂單，讀取可信的付款與成交資料
  以客戶端操作鍵查原結果；同鍵不同退貨內容則拒絕
  核對本次核准退貨的 unit_id，皆尚未被其他退款申請占用
  加總這些單位已保存的實付金額，建立固定的 refund_request_id
  保存單位與申請的對應，標成處理中，建立同金額的退款待辦
  保存操作結果
COMMIT
提交之後，背景程序才呼叫金流
```

這裡的「占用」表示該件已交給某份退款申請，其他申請不得再取用。同一申請重試會找到原結果。若所有選定商品實付均為零，只記錄零金額退貨結案，不送出要求正金額的退款 API。

所有正常退款與人工調整都必須經過同一套控制，並核對成功退款加上仍可能成功的申請，沒有超出原收款。若有人在金流後台直接退款，本地會少一筆紀錄。本地鎖擋不住金流後台同時操作；發現外部退款或付款狀態不明時，暫停該付款的新退款，核對歸屬後再恢復。只靠每件商品去重，無法涵蓋站外操作或拒付。

收到逾時時，原申請仍占著那些商品。遠端可能已退錢，不能釋放後再開一張新申請。沿用[退款工作接手的設計](/blog/order-system-worker-takeover/)與固定冪等鍵，核對同一個退款操作。冪等鍵是讓供應商辨識重試屬於同一次操作的識別；[Stripe API v1](https://docs.stripe.com/api/idempotent_requests)可能在至少 24 小時後清除鍵，超出保證範圍又查不清結果時，停止自動重送。

即使供應商回傳失敗，也保留原退款申請和單位對應，交給核對或原申請的恢復流程，不立刻讓另一個入口重新領走。只有符合供應商契約的成功結果才標記已退款；[退款可能待處理或失敗](https://docs.stripe.com/refunds#handle-failed-refunds)，建立待辦不等於顧客已收到錢。

## 為什麼先選逐件保存

假設每天 10,000 張訂單、平均 4 件、最多 100 件，需新增約 40,000 筆購買單位紀錄。若每筆連同主要索引暫估 160 bytes，一天約 6.4 MB，30 天約 192 MB。這是估算輸入，不含副本、備份、交易日誌與額外索引，應用實際 schema 測量後替換。單筆最多 100 件，分攤排序為 `O(n log n)`，目前沒有必要為它拆出遠端服務。

只保存 SKU 明細總額，退貨時再按剩餘數量平均分，儲存更少。不過最後剩下的一分會跟著退貨次序移動，客服也較難預先解釋每件退款。這個商店選擇多存一些紀錄，換取成交後可直接查出的金額。

另一種政策是退貨後重算滿額門檻。例如原滿 300 減 10，退掉 100 元後剩 200 元，取消優惠，可能只退 90 元。這可以是產品決定，但要保存原促銷條件、重算版本與調整原因，並在退貨確認頁先顯示新的退款金額。不能只換掉分攤函式，就把既有訂單的承諾改掉。

若訂單出現大量同 SKU 數量，逐件紀錄造成明顯儲存或寫入成本，再考慮保存「有幾件分到 334、有幾件分到 333」與剩餘可退數量。引入稅額、運費、多種折扣或分次請款時，也要重新定義各項退款責任。這些都以量測或新需求為升級理由。

## 驗收金額，再驗收退款流程

純函式可以大量產生非負整數價格與合法折扣，檢查分攤總額、單件上限與輸入重排不變。加入零價商品、零折扣、全額折扣，以及所有商品同餘數的資料，確認規則沒有藏在陣列順序裡。

交易與金流另做下列驗收，不能用算法測試替代：

1. 建立三件各 100 元、折 10 元的訂單，之後改價。分別依 A→B→C 與 C→A→B 退回，逐件金額仍為 96.66、96.67、96.67，總額都是 290 元。
2. 以兩條資料庫連線同時申請退 A，只能有一份申請占用 A。相同操作鍵重送要回原結果，換退貨內容要拒絕。
3. 在保存單位對應後、建立待辦前注入錯誤，確認整筆回滾；提交後讓程序中止，確認原待辦可恢復。
4. 讓金流完成退款但丟棄回覆，確認 A 維持處理中，其他申請不能再次退 A。核對成功後更新原申請，而非另建一筆。
5. 加入不屬於訂單的 `unit_id`、其他顧客的訂單與金流後台額外退款，分別驗證授權、歸屬與對帳阻擋。

監控應分開看金額不一致的訂單數、重複占用拒絕數，以及最老的退款結果待確認時間。第一個指向成交資料，後兩個幫助判斷重試或遠端結果是否卡住。

### 練習

三件商品 A、B、C 的原價分別是 1,001、1,000、999 個最小貨幣單位，整單折扣 100。請算出各件實付。若 C 先退款且回覆遺失，接著 A 申請退款，能不能重算折扣、把 C 的差額移給 A？

### 參考思路

原價合計 3,000。三件先各分到 33，餘數依序為 1,100、1,000、900，剩下一單位分給 A。折扣為 34、33、33，實付為 967、967、966，合計 2,900。

C 的原申請保留 966，等待核對，不重算折扣也不釋放 C。A 若符合退貨資格且付款對帳沒有衝突，可以依原快照建立 967 的獨立申請。把這組案例加進測試，再檢查退款程式是否仍在讀目前商品價目。
