如果 Laravel 專案每次升版都卡在依賴，先找出哪個套件真的拖住上線。支付回呼測試不完整，也是問題，但它和框架升不上去需要不同的修法。先拆開這兩件事，才知道第一個 PR 要改什麼。

GitHub 的 Sam Quakenbush 在 [11 月 25 日的改造案例](https://github.blog/ai-and-ml/github-copilot/how-to-choose-the-next-safe-step-in-application-modernization/)使用四個公開專案，先找實際執行環境、既有測試與要保留的介面，再選下一步實驗。文中的 Copilot skill 用於重複蒐集這些證據。本文的 Laravel 訂單流程是借這個方法做的教學案例，不是原文的實作結果。

## 先確認升級卡在執行環境，還是卡在業務行為

假設一個舊訂單系統升不上目標 PHP 版本。先在隔離環境記錄現行的 runtime、鎖檔與 CI 建置條件，再用 Composer 的 [prohibits](https://getcomposer.org/doc/03-cli.md#prohibits-why-not) 列出擋住升級的相依項。若只是一個停止維護、又只用在報表的套件，先換掉報表套件；如果付款模組同時依賴它的日期或金額轉換，先找出那個用法並補上測試，別直接換整套框架。

若平台可以正常升級，但訂單付款牽涉控制器、ORM 和工作佇列的相互呼叫，第一步可以留在同一個 Laravel 應用。挑支付回呼這條路徑，把判斷「這筆通知是否已入帳」的規則集中到一個可測試的用例。路由、資料庫交易和回應格式暫時不搬，讓出錯時要比對的地方少一些。

## 先固定重送時的結果，再搬程式

同一筆支付通知到了兩次，預期只產生一筆入帳。如果處理結果成功但回覆沒送到，金流商重送後仍要得到契約允許的回應。把這兩個例子，以及資料庫回滾時不留下半套結果，寫成可跑的驗收案例。然後用同一組固定資料，比對改動前後的 HTTP 回應、入帳筆數、訂單狀態和副作用。

基準結果也可能藏有 bug。若現況真的會重複入帳，先記下這個差異並單獨修好，不要把有問題的行為寫成必須保留的相容契約。上述例子未在實際 Laravel 專案執行；實作前應對照現有交易狀態與資料表約束。

## 何時才需要新服務

把規則留在原應用，部署與交易邊界較少；代價是它還要跟主程式一起發版。抽成獨立服務適合已經有不同部署或流量需求，而且介面、重試責任與資料歸屬能說清楚的部分。若目前只需要定期更新 PHP，不必先背下多一套部署、觀測與事件一致性的成本。

下一步，把一個具體升級阻礙和一條要驗的業務路徑寫進 issue，指定能證明行為沒壞的測試。讓 agent 收集檔案與測試證據，讓 PR 只處理其中一個阻礙。這樣審查時可以回答：「這次讓哪一步變得能做了？」
