LLM 推論服務的併發上限，除了模型權重，也受 KV Cache、執行期緩衝與請求長度影響。增加批次可能改善吞吐，同時拉長等待時間。

[vLLM 的 SOSP 2023 論文](https://arxiv.org/abs/2309.06180)用分頁管理減少 KV Cache 的碎片與重複配置。以下容量是公式試算，效能數字只引用論文受測條件，沒有在此重跑 GPU benchmark。相關概念也可參考 [ByteByteGo System Design 101](https://github.com/ByteByteGoHq/system-design-101)。

## 一、Prefill 階段 vs. Decode 階段：兩種完全不同的效能瓶頸

Transformer 模型在生成文本時，每個 Request 都必須經歷兩個截然不同的計算階段：

### 1. Prefill 階段（首字生成階段 / Prompt Processing）

- **任務**：接收使用者輸入的完整 Prompt（例如 2,000 字），計算所有輸入 Token 的 Self-Attention 矩陣，並生成第一個 Output Token。
- **瓶頸特徵**：**計算密集型（Compute-Bound）**。Prompt 的 token 可批次計算，較容易提高矩陣運算利用率；短 Prompt、小批次或通訊開銷仍可能讓 GPU 無法飽和。
- **核心指標**：**TTFT（Time-to-First-Token，首字延遲）**。

### 2. Decode 階段（自迴歸逐字生成階段 / Token Generation）

- **任務**：每次將新生成的 1 個 Token 與過去所有的歷史 Token 結合，預測下 1 個 Token。
- **瓶頸特徵**：**記憶體頻寬受限（Memory-Bound）**。小批次解碼常受權重與 KV 的讀取頻寬限制。實際讀取量取決於模型、注意力機制、量化、批次大小與快取；大批次也可能轉為計算受限。
- **核心指標**：**ITL（Inter-Token Latency，詞間生成延遲）** 與每秒整體吞吐量。

## 二、KV Cache 容量與配置浪費

在 Attention 計算中：

```text
Attention(Q, K, V) = softmax((Q * K^T) / sqrt(d_k)) * V
```

在自迴歸解碼（Autoregressive Decoding）過程中，每生成一個新 Token，模型需要與歷史上所有的 Token 計算注意力。為了避免重複計算歷史 Token 的 Key 和 Value 向量，系統會將歷史各層的 `K` 與 `V` 矩陣快取在顯存中，稱為 **KV Cache**。

### 1.2 KV Cache 顯存容量估算公式

每個 Token 所需的 KV Cache 顯存大小計算公式為：

```text
KV_Size_Per_Token = 2 * n_layers * n_kv_heads * d_head * precision_bytes
```

以 **Llama 3 70B**（80 層、8 個 KV Heads、Head Dim 128、FP16 2 Bytes）為例：

- 單一 Token 的 KV Cache = `2 * 80 * 8 * 128 * 2 Bytes = 327,680 Bytes = 320 KiB`。
- 若 Context 長度達到 8,192（8K），單一請求的 KV Cache 為 `327,680 × 8,192 = 2,684,354,560 B = 2.5 GiB`（約 2.684 GB）。
- 若同時有 100 個併發請求，僅 KV Cache 就需要 250 GiB（約 268.4 GB），尚未加上權重與執行期緩衝。這是未共享、未量化、所有請求皆達 8,192 tokens 的合計，並非每張 GPU 的用量。

### 2. 傳統推理框架的碎片化危機（Fragmentation）

原論文討論的連續配置方式可能產生以下浪費；現代框架可有不同快取實作：

1. **內部碎片（Internal Fragmentation）**：若系統替每個請求預留 8,192 tokens，但 Prompt 加輸出只用到 200 tokens，則剩下 7,992 個 token 槽位未被使用。
2. **外部碎片（External Fragmentation）**：請求長短不一，不同長度的動態分配在顯存中產生大量無法利用的離散空洞。
3. **保留碎片（Reservation Fragmentation）**：為未來可能生成的 Token 提前鎖定顯存配額。

> [!WARNING]
> 原論文的 20%～40% 有效使用量是特定工作負載下分配給 KV Cache 的記憶體利用率。其餘包含預留及碎片，不能把這個比例套到全部 HBM，因為權重與其他緩衝也佔顯存。

## 三、PagedAttention 的分頁區塊架構

PagedAttention 以固定大小區塊管理 KV Cache，讓序列不必佔據連續顯存。

### 1. Logical Block Table 映射機制

- vLLM 將每個序列的 KV Cache 邏輯上切分為固定大小的 **Block（如每個 Block 容納 16 個 Tokens）**。
- 物理顯存不再要求連續存放，而是劃分為一個個不連續的物理塊池（Physical Block Pool）。
- 透過 **Block Table** 記錄邏輯塊到物理塊的動態映射（類似 OS 的 Page Table）：

### 2. 零拷貝分叉與共享（Copy-on-Write）

在平行採樣（Parallel Sampling，如一次生成 3 個回答）或 Beam Search 時，多個分支共享相同的 Prompt 前綴：

- 傳統做法：必須複製多份完整的 Prompt KV Cache。
- PagedAttention：多個邏輯序列直接指向**相同的物理 Block**，引用計數（Reference Count）加 1。
- 共用且尚未填滿的區塊若要寫入，會使用 Copy-on-Write；新的完整區塊可另行配置。節省量取決於共用前綴長度與分支數，沒有固定比例。

## 四、Continuous Batching（持續動態批處理）

傳統批處理（Static Batching）必須等待批次中最長的請求生成完畢才能結束，導致短請求結束後 GPU 計算單元大量空轉等待（Padding Waste）。

Continuous Batching 把排程邊界縮到每次迭代。

- 在每一次 Token 迭代（Iteration-Level）結束時，檢查是否有已完成的請求；
- 一旦請求完成，立即釋放其物理 Block，並在下一輪迭代中**無縫插入新的請求**。
- 原 vLLM 論文在其模型與工作負載上，報告相近延遲下相對 FasterTransformer、Orca 約 2～4 倍吞吐。這是整體系統結果，不能歸因於 Continuous Batching 單一功能，也不保證固定 GPU 利用率。

## 五、Speculative Decoding（推測解碼）：打破自迴歸速度極限

一般自迴歸解碼每個序列每輪產生一個 token。[Speculative Decoding 論文](https://arxiv.org/abs/2211.17192)用便宜的草稿模型提出候選，再由目標模型批次驗證。

1. 草稿模型依序提出 K 個候選 token，例如 K = 5。兩個模型需使用相容的 token 表示。
2. 目標模型在一次前向計算中評估候選前綴的條件分布。
3. 對候選 x，以 `min(1, p(x)/q(x))` 的機率接受，其中 p 是目標分布、q 是草稿分布。第一個拒絕位置改從正規化的 `max(0, p-q)` 抽樣，捨棄後續草稿。全數接受時還可從目標分布取得一個額外 token。
4. 在論文演算法及採樣前提下，可保持目標分布。這不表示每次輸出文字相同，也不涵蓋任意近似驗證或實作誤差。

實際收益取決於接受率、草稿模型成本、額外 KV 記憶體與驗證批次。接受率低或服務已高併發時可能變慢；量測每請求延遲與整體吞吐後再決定是否啟用。

## 六、生產環境落地最佳實踐

1. **量化加速（Quantization）**：採用 **AWQ（Activation-aware Weight Quantization）** 或 **FP8** 格式，將模型權重由 16 位元壓縮至 4/8 位元，大幅降低記憶體頻寬壓力。
2. **Chunked Prefill**：將超長 Prompt 切片與 Decode 請求混合批處理，限制單輪 prefill 工作量，平衡 TTFT 與 ITL；切片也會增加排程開銷。
3. **前綴快取（Prefix Caching）**：在 Agent 或 RAG 場景中開啟 `enable_prefix_caching=true`，自動複用多輪對話中相同的 System Prompt 與知識庫檢索上下文。

驗收時固定模型版本、GPU、量化格式、Prompt／輸出長度與到達率，同時記錄 TTFT、ITL、吞吐、接受率與峰值顯存。
