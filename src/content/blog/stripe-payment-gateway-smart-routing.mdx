支付系統是電商容錯空間最小的一環。扣款遺漏、重複請款或交易超時，都會直接變成財務損失，也會讓使用者不再信任這個平台。

先說明定位：這篇是通用支付網關的參考設計，不是 Stripe 的內部架構。Stripe 公開的部分有：

- [PaymentIntent 的狀態](https://docs.stripe.com/payments/paymentintents/lifecycle)（`requires_payment_method`、`requires_confirmation`、`requires_action`、`processing`、`requires_capture`、`succeeded`、`canceled`）；
- [`Idempotency-Key`](https://docs.stripe.com/api/idempotent_requests) 與其[錯誤處理行為](https://docs.stripe.com/error-low-level)；
- [Orchestration](https://docs.stripe.com/payments/orchestration/rules)（private preview），由商家自訂規則，在多家處理商之間分流；
- [BFCM 2023 期間](https://stripe.com/newsroom/news/bfcm2023)，Stripe API 可用性高於 99.999%，尖峰每秒 27,395 筆請求。這是黑色星期五到網路星期一期間的數字，不是全年 SLA。

以上連結都是我在 2026 年 10 月 22 日查閱的。Stripe 內部的資料模型、冪等鍵的儲存位置、超時對帳的參數都沒有公開，文中這些部分是我的設計，數字是假設值，會逐處標明。參考設計包含三塊：

- **交易有限狀態機（Finite State Machine, FSM）**：讓每筆交易的狀態單向、確定地流轉；
- **多收單機構（Multi-Acquirer）路由**：依費率、發卡國、通路成功率與延遲分流；
- **冪等性與超時對帳補償**：避免網路抖動造成重複扣款與掉單。

接下來從這三塊拆解一個支付網關的設計。

## 2. 交易兩階段模式：授權（Authorize）與請款（Capture）

在電商與訂閱業務中，支付通常分為兩大階段：

1. **授權（Authorization）**：
   - 凍結使用者信用卡上的指定額度，確保使用者帳戶有足夠資金，此時資金**尚未**真正轉移至商家。
   - 授權有時效。Stripe 文件寫線上刷卡的授權[一般為 7 天](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method)，不同卡組織與情境的期限不同。
2. **請款（Capture）**：
   - 商家確認履約（例如商品已實際打包出貨或數位憑據已交付）後，通知收單機構正式向發卡行請款轉移資金。
   - 支援**部分請款（Partial Capture）**或**撤銷授權（Void / Release）**。

### 狀態流轉約束

1. **不可逆性**：一旦進入終態（`SETTLED`、`FAILED`、`REFUNDED`），不可再轉移回中間態。
2. **中間態容災**：`PROCESSING` 與 `TIMEOUT` 必須設定 TTL，並由後台非同步對帳 Worker 負責推進。
3. **樂觀鎖版本控制**：資料庫交易紀錄必須包含 `version` 欄位，狀態變更時執行 `UPDATE transactions SET status = 'AUTHORIZED', version = version + 1 WHERE id = ? AND version = ?`，防止併發競態條件。

### 智慧路由決策演算法指標

1. **本幣本卡（Domestic vs. Cross-Border）**：例如持卡人是日本 JCB 卡時，可以設計成優先路由至日本境內收單行，減少跨國交易手續費（Cross-Border Fee）與發卡行風控攔截。這是設計舉例，Stripe 文件沒有描述自動依卡別導向境內收單行的機制。
2. **自適應重試與降級（Adaptive Retry）**：
   - 當收到收單機構的**軟性拒絕（Soft Decline）**（如網路超時、系統繁忙）時，路由層切換至備用收單行重試（Orchestration 也能設定在另一家處理商[重試一次](https://docs.stripe.com/payments/orchestration)）；
   - 當收到**硬性拒絕（Hard Decline）**（如卡號不存在、餘額不足、遭竊卡）時，直接標記失敗，不重試，以免被卡組織處以罰款。Stripe 自己判定不該再試而擋下的付款，[Declines 文件](https://docs.stripe.com/declines)會回傳 `advice_code: do_not_try_again`。

客戶端這時重試，可能造成重複扣款。支付系統要有兩道防線：

### 5.1 冪等鍵（Idempotency Key）防護

- 客戶端在發起扣款時必須攜帶唯一的 `Idempotency-Key`（例如 UUID。Stripe 建議用 [V4 UUID 或有足夠熵的隨機字串](https://docs.stripe.com/api/idempotent_requests)）。
- 網關在 Redis 中執行原子鎖：`SET payment:idemp:<key> <status> NX EX 86400`。Redis 與 86400 秒的 TTL 是我的假設，Stripe 沒有公開冪等鍵的儲存位置，只寫[至少保留 24 小時](https://docs.stripe.com/error-low-level)。
- 若相同的 Key 再次請求且上一筆交易正在處理中，直接回傳 `409 Conflict`；若已完成，直接回傳先前結果，不重複扣款。這兩個行為 [Stripe 都有公開](https://docs.stripe.com/error-low-level)。

### 5.2 延遲佇列與頻外主動對帳（Out-of-band Polling）

下面的秒數都是假設值，用來說明流程。Stripe 公開的做法不同：商家在 24 小時內用同一個 key 重試，之後靠查詢物件、Dashboard 與 webhook 對帳，事故復原時 Stripe 也會[嘗試對帳失敗的操作並發送 webhook](https://docs.stripe.com/error-low-level)。

- 若向收單行發起請求超過閾值（假設 5 秒未回傳），網關將交易狀態標記為 `TIMEOUT`，並將任務投遞至延遲訊息佇列（Delayed Queue）。
- 背景 Worker 在（假設）10 秒、30 秒、2 分鐘後向收單行主動發起「查詢訂單狀態」API，若收單行已扣款成功則自動補齊內部狀態並發送 Webhook 通知商家；若收單行確認未收到請求，則安全關閉交易。

## 6. 架構總結與設計檢查清單

1. **絕對不裸存卡號**：所有卡號、CVV 必須在前端通過 PCI-DSS Level 1 認證的 Tokenization SDK（Stripe 自身是 [PCI Service Provider Level 1](https://docs.stripe.com/security)）轉換為 Token，自家伺服器絕不接觸明文敏感資訊。
2. **狀態機是唯一的真理之源**：所有的業務異動必須以狀態機事件為準，禁止直接修改狀態欄位。
3. **全流程冪等覆蓋**：從商家端、網關層到收單行通訊，每個環節皆需具備明確的冪等保護與超時主動補償管線。
