這是一份受 TikTok 啟發的參考設計，不是 TikTok 的實際架構。TikTok 官方工程部落格公開的前端 MonoRepo 工具是 Rush 加 PNPM workspaces，外加三個周邊工具：Sparo（加速 Git）、Cobuilds（分散式建置）與 Subspaces（多份 lockfile）。官方提到的規模是超過 1,000 個專案、20 萬個原始碼檔案（見 [Sparo](https://developers.tiktok.com/blog/2024-sparo-faster-git-for-frontend-monorepos)，2024 年）。[Cobuilds](https://developers.tiktok.com/blog/cobuilds-distributed-builds-with-rush) 與 [Subspaces](https://developers.tiktok.com/blog/subspaces-divide-and-conquer-your-npm-upkeep) 兩篇我沒有取得發布日期。

下面的四道防線，除了標明來源的部分，都是我的設計示意，沒有來源顯示 TikTok 這樣做。文中的目錄結構、套件名稱、ESLint 邊界規則、AST 依賴圖都是假設的例子。Garfish 與 Rspack 是 ByteDance Web Infra 團隊的開源專案，我沒有找到來源說它們用在 TikTok 的這個 MonoRepo，所以只引用它們自己的文件，不歸給 TikTok。

## 挑戰：MonoRepo 膨脹到 20 萬個檔案時的瓶頸

多專案庫（Multi-Repo）的問題是依賴版本分歧、共用元件升級困難、跨專案重構步履蹣跚。全部合進單一 MonoRepo 之後，這些問題換成另一組。在 TikTok 公開的規模（超過 1,000 個專案、20 萬個檔案）下，至少會遇到這三個瓶頸：

1. **Git 很慢**：Sparo 那篇提到，網路慢的人回報 `git clone` 要花 40 分鐘以上。
2. **CI 耗時**：共用型別定義改一行，傳統 CI 可能重新建置大量專案。Cobuilds 那篇的壓測（模擬 700 個以上專案的 shadow monorepo）在關閉 Cobuild 時，建置要 1 小時 28 分鐘。這是模擬環境的數字，不是正式 CI 的佇列時間。
3. **依賴混亂與架構腐化**：不同團隊用相對路徑 `import ../../../shop/private/utils` 引入私有邏輯，模組之間高度耦合，無法獨立拆分與發布。這條是設計上的常見問題，不是 TikTok 公開的案例。

## 第一道防線：領域套件邊界隔離（設計示意）

為了處理耦合，在程式碼結構與工具鏈上建立**領域邊界（Bounded Contexts）**。下面的目錄是我假設的例子：

```
monorepo/
├── apps/                          # 獨立部署業務應用
│   ├── tiktok-web/
│   ├── tiktok-shop/
│   └── creator-studio/
├── packages/                      # 公共基礎庫 (Strictly Versioned)
│   ├── ui-components/
│   ├── api-client/
│   └── analytics-sdk/
└── domains/                       # 業務領域隔離套件
    ├── video-player/              # 僅暴露 index.ts 定義的公共 API
    │   ├── src/
    │   └── package.json
    └── checkout-flow/
```

### 1. 模組導出收斂（Public API Exports）

- 每個 Package 在 `package.json` 的 `exports` 欄位宣告公開介面。
- 禁止外部套件繞過 `index.ts` 直連內部私有檔案（如 `package/src/internal/*`）。

### 2. AST 靜態語法檢查與 ESLint 邊界攔截

在提交與 CI 階段執行自訂 ESLint / AST 規則：

- **層級依賴規則（Hierarchy Rules）**：基礎庫（`packages/*`）禁止依賴上層業務庫（`apps/*`）。
- **領域隔離規則（Domain Isolation）**：`domains/video-player` 禁止直接引入 `domains/checkout-flow`，跨領域通訊走事件匯流排（Event Bus）或明確的 API 介面。

## 第二道防線：依賴圖譜與受影響範圍分析（設計示意）

在這個規模的倉庫，每次提交都跑全量測試與打包並不實際。做法是找出受變更影響的最小子圖（Affected Graph）。

Cobuilds 那篇在估算要開幾台 VM 時舉了 `rush list --to git:origin/main` 這個專案選取器，那是估算機器數量的做法，不是受影響範圍分析的例證。TikTok 官方沒有公開受影響範圍分析的做法。以 AST 解析 `import`／`export` 建圖，是我的設計示意。

1. **靜態 AST 解析建構依賴 DAG**：每次分支提交時，分析專案內部的 `import` 與 `export` 關係，產生整個 MonoRepo 的依賴有向無環圖。
2. **Git Diff 比對與傳播（Propagation）**：假設開發者只改了 `domains/video-player/src/decoder.ts`：
   - 找出依賴 `video-player` 的上游應用，也就是 `apps/tiktok-web`。
   - 與它無關的 `apps/tiktok-shop` 與 `apps/creator-studio` 標記為 **Clean**。
3. **精準執行**：CI 只對受影響的套件執行 Lint、Test 與 Build。能剪掉多少無關任務，要看實際的依賴圖，我沒有可引用的數字。

## 第三道防線：內容雜湊雲端快取與分散式排程（設計示意與 Rush Cobuilds）

縮小到受影響套件之後，核心底層庫的修改仍可能波及很多子專案。這時可以用快取和多機平行。

### 1. 內容定址雲端快取（Content-Addressable Remote Caching）

- **輸入雜湊計算（Hash Key）**：針對每個 Task，綜合計算：
  ```text
  TaskHash = Hash(原始碼檔案) + Hash(依賴套件版本) + Hash(環境變數與 Node 版本)
  ```
- **快取命中即重用（Zero-Compute Replay）**：同一個 TaskHash 在別處建置過，就直接從雲端快取（S3 / Redis / Remote Cache）下載建置產物與日誌，不重新編譯。
- 誰可以寫入快取是設計取捨。[Cobuilds 那篇](https://developers.tiktok.com/blog/cobuilds-distributed-builds-with-rush)提到，Rush 的典型設定是任何工程師的電腦都能讀雲端快取，但只在 CI 對 main 分支的受控建置時寫入。

### 2. 分散式任務排程（Distributed Task Execution, DTE）

這一節有兩種做法，來源不同。

- **中央協調器（設計示意）**：把原本在單台 CI 機器上循序執行的 Task 拆成動態佇列，由中央協調器派發給多台平行的 CI Agent。這不是 TikTok 公開的做法。
- **Rush Cobuilds（TikTok 官方）**：沒有中央派發者。同一個 job 在多台 VM 上各啟動一個實例，各機器透過 Redis 類的 key/value 服務取得鎖，知道哪些專案已經有人在建置，自行跳過。壓測只用主 runner 加 2 條額外 pipeline（共 3 台），在模擬環境中把建置時間從 1 小時 28 分鐘降到 36 分鐘（含 log-only 模式的調整）。

以下三點對照 [Garfish 官方的沙盒文件](https://github.com/web-infra-dev/garfish/blob/main/website-new/docs/guide/concept/sandbox.md)：

- **JS 沙盒**：優先用 `Proxy` 代理全域 `window`，不支援 `Proxy` 的環境降級為快照沙盒。沙盒銷毀時統一清除計時器（`setInterval`、`setTimeout`）與全域事件監聽（`addEventListener`），避免記憶體洩漏與全域污染。
- **CSS 作用域隔離**：用 `scope` 隔離子應用的樣式，文件另有 Shadow DOM 的隔離方式。
- **多技術棧**：Garfish README 說明它支援任何框架與技術體系。

各子應用可獨立打包、發布到 CDN，由各團隊自行交付。這是微前端的一般做法，不是 TikTok 公開的部署方式。

## 治理工具鏈對照

下表是設計取向的對照，不是 TikTok 實際使用的工具清單。

| 治理維度               | 傳統無管理單體倉庫 (Raw Monorepo) | 有治理的 MonoRepo (Rush / Nx / Turbo 等) |
| :--------------------- | :-------------------------------- | :--------------------------------------- |
| **邊界控制**           | 無約束，隨意跨目錄 import         | 模組導出白名單 + AST ESLint 強制阻斷     |
| **CI 執行策略**        | 每次提交全量重跑（慢、易阻塞）    | 依賴分析，僅重跑受影響節點               |
| **建置快取**           | 無快取，重複編譯浪費算力          | Content-Hash 雲端快取                    |
| **任務平行化**         | 受限單台 CI 伺服器 CPU 核心       | 多台機器分散執行（如 Cobuilds、DTE）     |
| **打包與型別檢查速度** | 傳統 JS 工具（Webpack/tsc）較慢   | Rust 編譯鏈（Rspack/SWC/Oxc）            |

## 從這份參考設計帶走的 4 件事

1. **MonoRepo 是程式碼的組織形式，不是架構設計。** 所有程式碼放在同一個 Git 倉庫，模組之間仍要有清楚的領域邊界。
2. **倉庫大到一定程度，需要快取和受影響範圍分析。** TikTok 公開的數字是 1,000 多個專案、20 萬檔案，他們的對策是 Rush 的雲端快取、Cobuilds 與 Sparo。
3. **Rust 工具鏈值得評估。** Rspack 0.1 的[官方公告](https://rspack.rs/blog/announcing-0-1)（2023 年 3 月 6 日）說它能為應用的建置腳本帶來 5~10 倍的提升。這個數字只限 Rspack，SWC、Turbopack 我沒有查。
4. **開發期治理和執行期隔離各管一段。** MonoRepo 管建置效率，微前端沙盒管瀏覽器裡的互相干擾，兩者要一起看。
