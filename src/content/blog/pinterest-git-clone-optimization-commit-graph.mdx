Pinterest 的 Engineering Productivity 團隊在 2020-10-23 發表了〈[How a one line change decreased our clone times by 99%](https://medium.com/pinterest-engineering/how-a-one-line-change-decreased-our-build-times-by-99-b98453265370)〉。他們最大的 monorepo Pinboard 有超過 35 萬筆 commit，完整 clone 是 20GB。CI pipeline 的 Checkout 階段在 `git fetch` 加上 refspec、只抓 master 之後，clone Pinboard 的時間從 40 分鐘降到 30 秒，減少 99%。

那一行改的是「抓哪些分支」，和 Commit-Graph 無關，原文也沒有提到 Commit-Graph。這篇前半照原文整理 Pinterest 的案例。後半是通用的 Git 知識，不屬於 Pinterest 的案例：Git 的物件協商、Commit-Graph 與 generation number，以及 Blobless、Treeless、Shallow 三種 clone 的取捨。

## 1. Pinterest 的案例：Checkout 抓了 2,500 多個分支

### 1.1 Monorepo 與 CI pipeline

Pinterest 當時有六個主要的 repository：Pinboard、Optimus、Cosmos、Magnus、iOS、Android，每個都是 monorepo。Pinboard 和公司一樣老，也是最大的一個：超過 35 萬筆 commit，完整 clone 20GB。

CI pipeline 一天要 clone 很多次。原文說光是 Pinboard，每個工作日就有超過 6 萬次 git pull。Jenkins pipeline 設定腳本（Groovy）大多以一個「Checkout」階段開頭，先 clone repository，後面的階段再建置與測試。

### 1.2 根因：沒設 refspec，就會抓全部分支

Checkout 階段原本已經做了三件事：shallow clone、不抓 tags、只抓最近 50 筆 commit。原文指出，即使如此，因為沒有設定 refspec，Git 仍會抓所有 refspec，也就是 `+refs/heads/*:refs/remotes/origin/*`。在 Pinboard，這代表要抓 2,500 多個分支。

### 1.3 那一行：只抓 master

修正方式是在 pipeline 程式碼加上 refspec，指定只要 master。原文的程式碼是截圖。下面是我依原文描述寫的等效 Git CLI 示意，不是 Pinterest 的原始程式碼：

```bash
# 示意：shallow、不抓 tags、depth 50，再加上只抓 master 的 refspec
git fetch --no-tags --depth=50 origin +refs/heads/master:refs/remotes/origin/master
```

### 1.4 結果

原文寫的成效只有這些：

- clone Pinboard 從 40 分鐘降到 30 秒，clone 時間減少 99%。
- 建置時間因此「顯著縮短」（significantly reduced），原文沒有給百分比。

40 分鐘除以 30 秒約是 80 倍，這是我算的，原文沒寫。

沒有 Commit-Graph 時，走訪每個 Commit 都要：

- 從鬆散物件或解壓縮 Packfile 讀出 Commit 物件的文字 header。
- 解析出 `parent` 與 `tree` 的 SHA-1/SHA-256 雜湊值。
- 在記憶體裡排進走訪佇列。

提交越多，要解壓縮、解析的 Commit 物件就越多。

## 3. Commit-Graph 與 Generation Numbers

Git 2.18 加入了序列化的 **Commit-Graph（提交圖）** 檔案（[Derrick Stolee，2018-06-25](https://devblogs.microsoft.com/devops/supercharging-the-git-commit-graph/)）。依 Stolee 的第三篇（[2018-07-09](https://devblogs.microsoft.com/devops/supercharging-the-git-commit-graph-iii-generations/)），2.18 的版本只能讓 commit 走訪快上一個常數倍，計算 generation number 的演算法排在下一版 Git 2.19。

拓撲層級（generation number v1）沒有獨立的 chunk，它和 commit 時間一起存在 CDAT 每筆資料的最後 8 個位元組。選用的 GDA2 chunk 存的是 corrected commit date offset。

### 3.2 Generation Number

Commit-Graph 為每個 Commit 存一個整數，也就是 **generation number（生成序號，`G(C)`）**：

```text
G(C) = 1 + max(G(P) for P in Parents(C))
```

沒有 Parent 的初始提交，`G(C) = 1`。

> [!IMPORTANT]
> **可達性性質（Reachability Invariant）**：
> 如果 Commit `A` 可以到達 Commit `B`（即 `B` 是 `A` 的祖先），則必然滿足：
> `G(A) > G(B)`
> 反之，`A` 與 `B` 不同時，如果 `G(A) <= G(B)`，則 `A` 不可能到達 `B`。

Git 走訪 DAG、判斷某個 Commit 是否可達時，只要目前節點的生成序號已經小於目標節點，這條路徑就可以剪掉，不必再往下走。Stolee 的說法是，這讓 Git 能在好幾種情況下提早結束走訪。實際省下多少，要看圖的形狀。

### 3.3 fetch 時自動寫入

[`fetch.writeCommitGraph`](https://git-scm.com/docs/git-config) 設為 true 時，每次 `git fetch` 從遠端下載了 pack 檔，就會寫入 commit-graph。搭配 `--split`，多數時候只會在既有檔案上疊一個很小的新檔：

```bash
# git fetch 下載 pack 檔後，自動增量寫入 commit-graph
git config --global fetch.writeCommitGraph true
```

儲存庫歷史已經很長時，可以先手動產生一次完整的 commit-graph（[git-commit-graph](https://git-scm.com/docs/git-commit-graph)）：

```bash
# 從所有 refs 開始走訪，產生 commit-graph，並計算 changed-path Bloom filter
git commit-graph write --reachable --changed-paths
```

- `--reachable`：從所有 refs 開始走訪 commit。
- `--changed-paths`：計算每個 Commit 和第一個 parent 之間變更了哪些路徑，存成 Bloom filter，加速 `git log -- <path>`。

## 4. 大型 Monorepo 的 Clone 策略

除了 Commit-Graph，**Partial Clone** 與 Shallow Clone 可以減少下載的物件。下表的說明依 [GitHub Blog〈Get up to speed with partial clone and shallow clone〉（2020-12-21）](https://github.blog/open-source/git/get-up-to-speed-with-partial-clone-and-shallow-clone/)：

| Clone 策略         | 指令範例                              | 下載內容                                         | 適用情境                     | 缺點 / 代價                   |
| :----------------- | :------------------------------------ | :----------------------------------------------- | :--------------------------- | :---------------------------- |
| **Full Clone**     | `git clone <repo>`                    | 完整歷史所有 Commit、Tree、Blob                  | 離線開發、完整備份           | 體積最大、耗時最長            |
| **Blobless Clone** | `git clone --filter=blob:none <repo>` | 完整 Commit 與目錄結構 Tree，**不含檔案內容**    | **本機日常開發、多分支切換** | checkout 時才按需拉取檔案內容 |
| **Treeless Clone** | `git clone --filter=tree:0 <repo>`    | 僅最新 HEAD 的 Tree 與 Blob，**歷史僅有 Commit** | **CI/CD 自動化建置 Runner**  | 查看歷史版本檔案需要網路請求  |
| **Shallow Clone**  | `git clone --depth=1 <repo>`          | 僅拉取最新 1 筆 Commit 及目前工作目錄            | 單次測試、一次性容器         | 無法追蹤分支歷史、rebase 困難 |

同一篇 GitHub Blog 建議 shallow clone 最好搭配 `--single-branch --branch=<branch>`，只下載要用的那個分支。Pinterest 用 refspec 只抓 master，限制的也是分支數。

CI 工作如果需要完整的 commit 歷史（例如要算 merge-base），可以改用 blobless：

```bash
# 保留完整 commit 與 tree 歷史，檔案內容在 checkout 時才下載
git clone --filter=blob:none --no-checkout <repo_url>
cd <repo_name>
git config fetch.writeCommitGraph true
git checkout <target_branch_or_commit>
```

## 5. 整理

1. **先看抓了哪些 refs**：Pinterest 的 Checkout 已經是 shallow、depth 50、不抓 tags，慢在沒設 refspec。我會先檢查 CI 的 fetch 抓了幾個分支，再考慮動 Git 內部機制。
2. **用新版 Git 的 Commit-Graph**：開啟 `fetch.writeCommitGraph = true`，需要時用 `--changed-paths` 產生 Bloom filter。
3. **本機與 CI 分開選 clone 策略**：本機開發用 Blobless Clone，保留完整 log；用完即丟的 CI 容器用 Treeless Clone，或 Shallow 加 `--single-branch`。
