把同一個業務修改分散到多個服務後，團隊需要處理部署協調、網路失敗與資料一致性。若模組仍高度耦合，單純增加服務數量不會消除這些依賴。

模組化單體保留集中部署，同時限制模組間的依賴。下列設定是概念片段，尚未形成固定工具版本的完整驗收專案。採用時要跑同模組與跨模組的正反例，才能確認編譯器和 CI 實際攔下哪些引用。

## 限界上下文與部署單元分開決定

限界上下文描述模型與語言的適用範圍。不同上下文可以位於同一個應用程式，也可以分開部署。模組之間仍可透過約定的介面合作，沒有必要宣稱邊界之間零依賴。

[Shopify 2019 年的架構文章](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity)描述把既有單體演進為模組化單體，保留同一個程式庫並明確管理元件邊界。這個案例不能推論為大型公司都從微服務回遷。

同一行程內的模組呼叫不需要跨服務網路傳輸，但操作仍可能包含資料庫或外部 I/O。集中建置能減少部分協調成本，啟動與測試時間則取決於規模和依賴。日後拆分服務時，資料搬遷、交易一致性與部署仍需要設計，清楚的介面不等於固定天數內就能完成遷移。

## 分清編譯器檢查與公開入口規則

### TypeScript Project References 管理專案依賴

[TypeScript 官方文件](https://www.typescriptlang.org/docs/handbook/project-references.html)說明，Project References 使用被引用專案的 declaration 輸出，並由 `tsc --build` 管理建置順序。（來源查閱：2026-11-05。）以下 JSONC 片段展示建置依賴：

```jsonc
// packages/billing/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "rootDir": "src",
    "outDir": "dist",
  },
  "references": [{ "path": "../identity" }],
}
```

`references` 不會自動把 identity 專案限制成只能經由 `index.ts` 存取。公開入口還需要配合套件 `exports`、模組解析設定與依賴檢查。必須測試相對路徑、別名及建置輸出，確認沒有繞過原先規則。

### 公開入口是要驗證的設計規則

可以約定下列結構，再用工具檢查引用是否符合約定：

```text
src/contexts/billing/
├── index.ts                 # 對外入口
├── internal/
│   ├── Customer.ts
│   ├── BillingRepository.ts
│   └── TaxEngine.ts
└── tsconfig.json
```

同模組使用自己的 `internal` 應被允許，其他模組則透過公開入口。Go 的 `internal` 另有語言工具鏈的匯入限制：可匯入者須位於 `internal` 父目錄所涵蓋的目錄樹內，不能把它概括成所有跨模組引用都禁止。可參考 [Go command 的 Internal Directories 說明](https://pkg.go.dev/cmd/go#hdr-Internal_Directories)。

## BOUNDARY.md 提供指引，檔案權限另行控制

下面這種深層引用可能繞過團隊約定的公開入口，不論它由人或 Agent 寫出，都應納入測試：

```typescript
import { UserEntity } from "../../identity/internal/UserEntity";
```

模組文件可以說明可修改範圍與允許的依賴。以下為 Billing 的假設規則範例，資料庫與跨上下文溝通策略仍需依專案決定：

```markdown
# Billing Context 邊界

## 責任

管理帳務與發票資料，對外透過 BillingFacade 提供操作。

## 依賴約定

- 外部只能使用 billing/index.ts 提供的入口。
- 不直接匯入 identity/internal 的型別或儲存實作。
- 以 AccountId 識別帳號，所需資料經已約定介面取得。
- 新增跨模組依賴前，記錄理由並更新依賴測試。
```

團隊需要在實際使用的 Agent 設定中指定如何讀取這份文件，不能假設 `BOUNDARY.md` 會自動載入。文件能提供設計背景，阻止檔案讀寫則需要工具權限或沙箱；拒絕違規合併需要外部檢查。

## 用正反例驗證 CI 的攔截範圍

dependency-cruiser 可以依路徑與依賴關係設定規則，語法以[專案的 rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)及鎖定版本為準。不要讓尚未驗證的跨欄位正規表示式反向參照承擔核心限制。

先以單一目標模組寫出容易核對的規則概念：

```javascript
// 概念配置：正式採用前需在鎖定版本中跑 fixture。
module.exports = {
  forbidden: [
    {
      name: "no-external-billing-internals",
      severity: "error",
      from: { pathNot: "^src/contexts/billing/" },
      to: { path: "^src/contexts/billing/internal/" },
    },
  ],
};
```

這條規則只針對 billing 的內部路徑。若要保護其他上下文，需逐一新增規則或由已測試的配置生成流程建立。它也沒有檢查資料庫存取、執行期組合出的路徑或跨模組交易。

固定 dependency-cruiser 版本及 TypeScript 解析設定後，建立下列 fixture：

- billing 引用自己的 internal：應通過。
- identity 引用 billing/internal：應失敗。
- identity 引用 billing/index.ts：應通過。
- 同一越界引用改用別名或可解析的動態 import：依工具支援確認結果。
- 檢查範圍漏掉檔案、修改配置或跳過工作流：確認 repository 的保護設定能否攔下。

命令本身只是 CI 中的一個步驟：

```bash
pnpm depcruise --config .dependency-cruiser.cjs src
```

要限制合併，還需把工作流設定為 required check，並檢查允許繞過的人員與規則。Git pre-push hook 可提供早期回饋，但本機 hook 可以被略過。

## 先保護一組已知的模組邊界

挑 billing 與 identity 這組依賴，建立合法入口與非法深層引用的 fixture，保存工具版本、命令與輸出。只有當失敗案例確實讓必要檢查失敗，才把同一套規則擴展到其他模組。
