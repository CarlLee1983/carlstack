Microsoft 在 2026 年 11 月 10 日公開 Aspire CLI 資訊洩漏漏洞 CVE-2026-120792，GitHub Advisory Database 於 11 月 11 日更新紀錄。問題出在已棄用的 MCP 設定掃描器：診斷資料可能包含設定內容，並寫入共享暫存目錄中的固定路徑。具有本機存取權的攻擊者可能因此取得敏感設定。

這次查核以 [Microsoft 原始公告](https://github.com/dotnet/announcements/issues/518)、[Aspire 專案公告](https://github.com/microsoft/aspire/issues/22100)及 [GitHub 安全公告](https://github.com/advisories/GHSA-q6jf-24jf-m3cg)為據，日期為 11 月 12 日。沒有重現漏洞或執行 Aspire 更新，也沒有從這些來源取得實際攻擊事件的證據。以下資產盤點與驗收清單是工程建議。

## 哪些環境需要處理

公告列出 Linux、macOS，以及 x64、Arm64 架構。已報告的情境是在多位使用者共用暫存目錄的非 Windows 系統上，執行 Aspire CLI 的 agent 或 MCP 初始化指令。CVSS 3.1 分數為 7.3，向量中的 `AV:L`、`PR:L`、`UI:R` 分別表示本機攻擊、低權限與需要使用者互動。

因此，盤點應從「哪裡執行 Aspire CLI」開始。共享開發主機、會重複使用的 CI runner、團隊共用的遠端工作環境，都值得檢查。應用部署在 Linux，不代表部署主機一定安裝或執行過這個 CLI；反過來，正式服務完全沒有 Aspire，也可能在開發工具鏈裡使用它。

以一個假設情境說明：團隊的自架 runner 接收不同專案的工作，部分工作會執行 MCP 初始化。這時需要記錄執行帳號、CLI 來源、實際版本及暫存目錄是否跨工作共用。若只從正式服務的套件清單查找，這台 runner 可能整個漏掉。

單人筆電也應更新受影響版本，但是否有其他帳號或程序能讀取相關資料，要依實際環境判斷。公告沒有把 Windows 列為受影響平台，也沒有將這個問題描述成可直接從網際網路利用的服務漏洞。

## npm 與 NuGet 的版本範圍不同

修補版本統一為 **13.6.5 或更新版本**，但受影響範圍的起點依套件而異：

- NuGet 的 `Aspire.Cli`：大於或等於 `13.2.0`，且低於 `13.6.5`。
- NuGet 的 Linux、macOS 平台套件：大於或等於 `13.3.0`，且低於 `13.6.5`。例如 `Aspire.Cli.linux-x64`、`Aspire.Cli.osx-arm64`；完整清單見原始公告。
- npm 的 `@microsoft/aspire-cli` 及公告列出的 Linux、macOS 平台套件：大於或等於 `13.4.2`，且低於 `13.6.5`。

Aspire 與 .NET 分開發布。只安裝新的 .NET SDK 或 runtime，無法確認 Aspire CLI 已更新。使用 .NET tool 安裝者需更新 `Aspire.Cli`；使用 npm 安裝者則需更新 `@microsoft/aspire-cli`，並確認平台專用相依套件也解析到修補版本。

實務上，一台機器可能同時有全域安裝、專案鎖定版本和 CI 映像內的副本。建議按實際執行入口核對：開發者終端機叫到哪一份 CLI、專案腳本叫到哪一份、runner 啟動的映像又包含哪一份。套件管理器顯示某個位置已更新，不代表其他入口也會使用它。

對需要固定工具版本的專案，可先明確鎖定已修補版本，更新鎖定檔並重建使用它的映像。後續再依團隊維護策略升級。這樣能把安全修補與其他工具行為變更分開驗收，也避免新工作仍從舊映像啟動。

## 更新之外，確認是否留下敏感資料

公告指出風險來自診斷資料中的設定內容。更新 CLI 可以處理後續執行的漏洞，但先前是否已留下資料、是否有人讀取過，仍須另行調查。

建議由環境管理者確認曾使用受影響 CLI 的時間與工作範圍，再檢視相關診斷檔案的存在情況、擁有者、權限和保留位置。查核紀錄只需保留判斷所需的資訊，不要把完整設定或密鑰複製到 issue、聊天或 CI 日誌中。

若確認檔案含有仍有效的憑證，且可能被非預期對象讀取，應依既有事件應變流程評估撤銷與輪替。這是依暴露證據採取的處理，不是要求所有安裝 Aspire 的使用者無差別重設所有密鑰。清理暫存檔也應在保留必要證據後進行，避免先刪掉唯一能協助判斷影響的資料。

暫時無法完成更新的環境，可以先停止在共享環境執行受影響的初始化工作，改用已修補的獨立環境。這是減少暴露機會的操作建議，不能記成已完成版本修補。不要為了讓舊工具繼續執行而放寬暫存目錄權限。

## 修補完成的驗收紀錄

每個實際執行 CLI 的環境，至少留下以下結果：

1. 安裝方式、執行路徑與修補後版本。npm 安裝另核對平台相依套件。
2. 專案鎖定檔、映像或 runner 範本是否已更新，以及下一次工作實際採用的版本。
3. 以不含正式密鑰的測試設定執行必要初始化流程，確認功能仍可使用。
4. 先前可能留下的敏感診斷資料是否完成評估，必要的憑證處置是否有負責人與紀錄。

第三步是功能回歸，不能單憑初始化成功就認定沒有資料洩漏。版本證據、舊資料處置與功能驗收各自回答不同問題。

站內的 [GitHub Actions 日誌密鑰掃描](/blog/github-actions-log-secret-scanning/)處理上傳到平台的執行日誌；這次風險發生在執行機器的暫存檔。管理自架 runner 時，兩個位置都需要納入資料保存與存取管理。可以從一台會執行 Aspire 初始化的 runner 開始，確認它實際使用的 CLI 版本，以及診斷資料最後留在哪裡。
