設計事件驅動系統與分散式背景任務排程時，訊息佇列不只是一條「先進先出（FIFO）」的簡單管道。不同業務場景對訊息的處理時序與生命週期，要求各不相同：

- 金融交易與狀態機變更要求**嚴格順序（Strict Ordering）**。
- VIP 客戶與緊急警報需要**優先插隊處理（Priority Processing）**。
- 訂單超時 30 分鐘自動取消、定時推播需要**高精度延遲排程（Delay Scheduling）**。
- 格式錯誤、會讓消費者崩潰的「毒丸訊息（Poison Pill）」需要安全隔離到**死信佇列（Dead Letter Queue, DLQ）**。

下面依序拆解這四種佇列模式的底層資料結構、時間複雜度與正式環境的實作架構。

- **全域嚴格順序（Global FIFO）**：整個佇列只有 1 個分區與 1 個消費者實例。一旦出現慢任務，全站阻塞。
- **分區順序（Partitioned FIFO）**：實務上，跨使用者的事件順序往往無關緊要（User A 的付款不需要排在 User B 的前面）。以 `user_id` 作為 **Sharding Key / MessageGroupId**，單一業務實體內部維持嚴格時序，平行處理則靠增加分區往外擴展。

## 2. 優先權佇列（Priority Queue）與防飢餓機制

系統突然堆積時，付費 VIP 使用者的請求或系統 P0 級故障警報，必須比行銷郵件先被消費。

### 2.1 實作架構

1. **二元最大堆積（Binary Max-Heap）/ 跳躍串列**：在記憶體中維護優先權堆積，時間複雜度為 `O(log N)`。
2. **多優先權實體桶分流（Multi-bucket Routing - 推薦）**：建立 3 個獨立的實體佇列（`queue_high`, `queue_med`, `queue_low`），消費者用加權輪詢拉取任務（例如以 7:2:1 的比例從三個佇列拉）。

### 2.2 防飢餓機制（Starvation Prevention / Aging）

如果高優先權任務持續以 100% 頻率湧入，低優先權任務會**永遠輪不到執行（飢餓效應）**。

- **動態老化演算法（Aging Algorithm）**：低優先權任務在佇列中每多等 1 分鐘，優先權分數自動提高一階，所有任務最終都能在有限時間內被處理。

## 3. 延遲佇列（Delay Queue）：三種底層架構

延遲佇列用來「在未來某個時間點執行任務」，例如訂單 30 分鐘未付款自動關閉、使用者註冊 7 天後發送回訪通知。

| 實作方案                | 底層技術                | 時間精度            | 優缺點                 |
| :---------------------- | :---------------------- | :------------------ | :--------------------- |
| 1. 時間輪 (TimingWheel) | 環形陣列 + 雙向鏈結串列 | 毫秒級高精度        | 記憶體開銷低，O(1)     |
| 2. Redis Sorted Set     | SkipList + Dict         | 毫秒級              | 分散式原生，高可用性   |
| 3. RabbitMQ 死信 TTL    | Message TTL + DLX       | 粗粒度 (佇列頭阻塞) | 有佇列頭非均勻過期的坑 |

### 3.1 時間輪演算法（Hashed TimingWheel）

時間輪像鐘錶的秒針每秒前進一格，把時間劃分成一圈 Slot（例如 60 個格子的環形陣列，每個 Slot 代表 1 秒）：

- **新增任務**：算出目標 Slot 與輪數（`Round = delay / 60`），把任務掛進對應 Slot 的雙向鏈結串列，時間複雜度為 **`O(1)`**。
- **執行任務**：指標每走一格，檢查目前 Slot 的鏈結串列，取出 `Round == 0` 的任務執行，其餘任務 `Round -= 1`。

### 3.2 Redis Sorted Set（ZSet）延遲佇列實作

- 任務 Payload 當 Value，**觸發時間戳記（`unix_timestamp`）當 Score**，存進 ZSet：
  `ZADD delay_queue <target_timestamp> <task_payload>`
- 消費者定時輪詢（或透過 Redis Lua 腳本）：
  `ZRANGEBYSCORE delay_queue 0 <current_timestamp> LIMIT 0 10`
  再用 `ZREM` 原子地取出並刪除到期任務。

## 4. 毒丸防禦與死信佇列（Dead Letter Queue, DLQ）

消費訊息時，如果某則訊息因為 JSON 格式損壞、程式 NullPointer 例外或除以零，讓消費者每次處理它都**拋出例外並 Crash**，在重試機制下，這則訊息會一再被排回佇列頭，所有消費者接連崩潰，整個佇列完全卡死。這種訊息就叫**毒丸訊息（Poison Pill）**。

1. **重試計數器（Retry Counter）**：在 Message Header 中維護 `x-retry-count`。
2. **熔斷隔離至 DLQ**：重試次數超過門檻（如 3~5 次）時，停止重新排隊，直接把該訊息路由到死信佇列。
3. **主佇列持續消費**：主業務佇列繼續消費後面的正常訊息，不再被毒丸卡住。
4. **人工稽核與修復重播（Replay）**：工程師修好程式碼後，透過死信管理工具把 DLQ 中的歷史訊息重新注入主佇列，完成補償。
