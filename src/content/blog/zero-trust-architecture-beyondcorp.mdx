過去幾十年，企業安全大多採用 **「城堡與護城河模型（Castle-and-Moat Model）」**：

- 企業在外圍部署防火牆與 VPN。
- **員工一旦透過 VPN 進入公司內網，系統就預設這個使用者與裝置「完全可信」。**

遠距辦公、雲原生與多雲環境普及，加上進階持續性威脅（APT）攻擊，這種邊界模型撐不住了：**內網只要有一台伺服器或員工筆電被攻陷，攻擊者就能在內網橫向移動（Lateral Movement），竊取整個企業的資料庫。**

Google 在 2011 年啟動 **BeyondCorp** 計畫（見 [Google Cloud 的 BeyondCorp 介紹頁](https://cloud.google.com/beyondcorp)），2014 年 12 月在 USENIX ;login: 發表第一篇論文〈[BeyondCorp: A New Approach to Enterprise Security](https://research.google/pubs/beyondcorp-a-new-approach-to-enterprise-security/)〉。它是 **零信任架構（Zero Trust Architecture, ZTA）** 最早的大規模企業實踐之一，但不是這個概念的起點。依 [NIST SP 800-207](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-207.pdf) §1.1 的整理，Jericho Forum 在 2004 年就提出去邊界化（deperimeterization），「zero trust」一詞則由 Forrester 的 John Kindervag 提出。

下面依序整理零信任的核心原則、元件拓撲與實作方式。

- **位置不再等於信任**：請求不論來自辦公室內網的 Ethernet、家中 WiFi 或星巴克的公用網路，都要經過同樣嚴格的驗證。
- **動態持續評估**：驗證不是登入成功就一路放行，整個工作階段（session）期間都會持續評估使用者行為、裝置健康與網路環境。

### 各元件的職責

下面的元件名稱與做法出自 Google 在 USENIX ;login: 發表的三篇論文：2014 年的〈[A New Approach to Enterprise Security](https://research.google/pubs/beyondcorp-a-new-approach-to-enterprise-security/)〉、2016 年的〈[Design to Deployment at Google](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/44860.pdf)〉與〈[Part III: The Access Proxy](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/45728.pdf)〉。

1. **存取代理（Access Proxy）**：Google 的企業應用都透過面向網際網路的存取代理對外開放，應用在公開 DNS 用 CNAME 指向代理，員工不必連傳統 VPN。代理是擴充版的 GFE（Google Front End），負責終止 TLS，做完存取控制檢查才把請求轉給後端。代理到後端這段，Google 用內部的 LOAS 框架做雙向認證與加密。VPN 是逐步收斂的，只留給確實需要的使用者，非 HTTP 協定則另走 SSH proxy 等閘道。
2. **裝置清冊（Device Inventory Database）**：裝置必須在清冊裡登記且資料正確，才能拿到該裝置專屬的裝置憑證。憑證存在硬體或軟體 TPM，或合格的憑證儲存區。沒更新 OS 修補的裝置會被降低信任層級。未受管的裝置接上公司網路，只會被分到修復網路或訪客網路。
3. **單一登入（SSO）與使用者／群組資料庫**：集中驗證主要憑證與第二因子，比對 User Database 和 Group Database 後簽發短效 token。論文沒有指定第二因子的形式。（作者補充：現在對應的做法是 FIDO2／WebAuthn 硬體金鑰。）
4. **Trust Inferer 與 Access Control Engine**：Trust Inferer 用靜態規則加啟發式判斷，替每台裝置指派信任層級（trust tier），每個資源則設定存取所需的最低信任層級。代理內的 Access Control Engine 逐一請求判斷，依據使用者、所屬群組、裝置憑證與清冊資料。ACL 採 first-match 語意，類似傳統防火牆規則。論文沒有計算風險分數，也沒有用 ABAC、PDP 這些名稱。PDP／PEP 是 NIST SP 800-207 的通用術語，下一節的 ABAC 也是通用設計，不是 BeyondCorp 的原文。

BeyondCorp 處理的是使用者與裝置存取內部應用。服務對服務的零信任，Google 另外用 [BeyondProd](https://cloud.google.com/docs/security/beyondprod) 處理，服務之間的雙向認證與傳輸加密用的是 Google 自己的 ALTS。第 4 節的 mTLS 與微隔離是業界通用做法，不屬於 BeyondCorp。

## 3. 動態存取控制：RBAC vs. ABAC

傳統的角色存取控制（RBAC）在複雜環境裡很容易出現「角色爆炸（Role Explosion）」，零信任因此改採 **ABAC（Attribute-Based Access Control）**：

| 評估屬性                 | 檢查項目範例                                                            |
| :----------------------- | :---------------------------------------------------------------------- |
| **主體屬性（Subject）**  | 員工職級、所屬部門、安全認證等級、是否在出差核准名單中                  |
| **資源屬性（Resource）** | 目標資料庫的資料敏感等級（如 PII、金融核心、一般日誌）                  |
| **動作屬性（Action）**   | 唯讀查詢（Read）、批次下載（Export）、寫入修改（Write）                 |
| **環境屬性（Context）**  | 裝置防毒軟體版本、地理位置（是否異地異常登入）、時間（深夜 vs. 工作日） |

**決策範例**：

> _IF 主體屬性 =「財務部」AND 裝置屬性 =「企業受管且 EDR 正常」AND 動作 =「下載報表」AND 環境屬性 =「非異常 IP」➔ **ALLOW**；否則要求再用硬體金鑰驗證一次，或直接拒絕。_

## 4. 服務間通訊的零信任：mTLS 與微隔離（Micro-segmentation）

- **微隔離**：每個微服務都是獨立的安全邊界，預設禁止跨服務連線。
- **雙向 TLS（mTLS）與 SPIFFE / SPIRE**：
  - 每個 Pod / 容器啟動時自動取得短效的 X.509 數位身分憑證（SPIFFE ID：`spiffe://cluster.local/ns/prod/sa/order-service`）。
  - Service Mesh（如 Istio / Envoy）自動做雙向憑證驗證。即使底層在同一個 VPC 網路，未經授權的微服務也無法發起 TCP 連線。

## 5. 總結

- **身分與裝置取代網路邊界**：不再因為連上內網 VPN 就給予信任，改由存取代理統一接管流量。
- **持續動態評估**：用 ABAC 引擎綜合裝置健康、身分與環境，做即時的風險控管。
- **服務間微隔離**：用 Service Mesh 與 mTLS，把零信任延伸到服務之間的每一次 RPC 呼叫。
