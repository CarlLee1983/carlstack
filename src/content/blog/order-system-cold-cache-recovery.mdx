訂單清單每秒被查八十次，退款明細每秒二十次。平常清單有九成命中 Redis，主庫每秒只處理二十八次讀取。現在 Redis 換成空的實例，應用程式仍照原樣處理 cache miss，每次都回主庫，再把結果寫回快取。訪客沒有變多，主庫收到的讀取卻變成每秒一百次。

如果此時另外啟動暖機，逐筆把常用清單補回去，資料庫還要再接一批查詢。恢復速度開得太快，原本仍正常的下單與退款確認，也可能開始排隊。

這是系列第 22 篇的虛構訂單情境，接續[第 8 篇的讀取契約](/blog/order-system-cache-read-contract/)與[容量估算](/blog/order-system-capacity-budget/)。沿用 MySQL 單主庫與 Redis 清單摘要，這次把恢復方案限定在**單一應用實例**，暖機也在同一程序內執行。數量、延遲與額度都是待驗證的教學設定，沒有執行真實 MySQL／Redis 負載測試。官方資料查核於 2026 年 11 月 5 日。

## 清單可以暫時查不到，確認結果不能改讀舊摘要

清單用來找訂單，可以短暫落後，也可以在過載時回報暫時無法取得。退款明細仍從同一主庫的新快照確認目前結果。查詢失敗就明確回報無法確認，不把舊清單內容改裝成成功的明細回應。

這裡的「保住明細」，指保留它送出查詢的速率與在途名額，並把延遲列入驗收。保留額度無法替 MySQL 增加 CPU 或 I/O；資料庫整體過載時，明細依然可能失敗。下單也繼續使用原有交易與連線預算。

Redis 只保存可重建的清單摘要，沒有放尚未持久化的訂單、庫存異動或唯一一份 Session。故障演練使用隔離環境的空快取，不能在正式 Redis 清空所有資料來測試。[Redis 的 FLUSHALL 文件](https://redis.io/docs/latest/commands/flushall/)明確指出它會刪除所有資料庫的所有鍵。

AWS 在〈Caching challenges and strategies〉描述了同類問題：系統逐漸依賴快取後，冷快取或快取故障會突然增加下游負載。文件建議限制回源請求，並在停用快取的情況下測試保護措施。[AWS 原文](https://builder.aws.com/content/3K9TeXp6strMiJ4vhakpRD7BQWO/caching-challenges-and-strategies)

## 暖機每秒查十次，清單就少十次額度

先替這組固定形狀的讀取列一份候選預算。假設扣除下單、退款 worker 與其他既有工作後，留給清單、明細及暖機的總額是每秒六十次資料庫查詢。每次只執行一個已限制結果大小、使用適當索引的查詢。報表掃描、多次 SQL 的 API 與額外權限查詢另計，不能混進來仍當成一個單位。

正常狀況的粗估是 `80 × (1 − 0.9) + 20 = 28 次／秒`。快取全空、每個請求都需要不同資料時，變成 `80 + 20 = 100 次／秒`，比候選預算多四十次。若暖機再送十次，總需求就是一百一十次。

恢復期間先固定分配：明細每秒二十次、清單 miss 每秒三十次、暖機每秒十次。這三份加起來剛好六十次。額度以應用程式送出 SQL 的時刻計數，Redis 命中不扣這份額度。同鍵合併後真的執行一次，就記一次。

八十次清單都 miss、查不同鍵而無法合併時，至少五十次無法在這個速率內立即開始。首版直接回報暫時無法取得，不在應用程式建立無限等待佇列。前端保留已顯示的摘要及其取得時間，停止密集自動重新整理。重新嘗試也走相同額度，不准另外開一條重試通道。

停止新增暖機後，等最後一次暖機送出已超過一秒，才把它的十次額度重新分配給清單，清單上限提高到四十次。這是一次有紀錄的預算調整，保留最近一秒的歷史計數，且所有類別仍須通過全站每秒六十次的共同限制。剛送出的暖機仍占該窗口，不能重設計數立刻多放十次。首版不實作複雜的自動借用。明細空閒時，其額度也先保留，代價是某些時段沒有用滿資料庫。

這份分配適合先確認保護是否有效。真實查詢的成本若相差很大，就要按工作類別分開壓測，調低昂貴查詢的額度。每秒六十次只是算例，不能拿去當另一個系統的安全設定。

## 查詢慢四倍，同樣速率也會占更多名額

速率限制管每秒送出多少次，在途限制管尚未結束多少次。假設平均查詢占用時間是 50 ms，每秒六十次在穩態下約占 `60 × 0.05 = 3` 個名額；變成 200 ms，平均占用便接近十二個。尖峰、尾端延遲與連線等待還會增加壓力。

首版另給明細四個、清單四個、暖機兩個在途名額，合計十個。不同類別不互借。程序先取得該類別的在途名額，再以短期限借取可用連線。連線就緒後，送出 SQL 前還要同時通過分類與全站的速率檢查。沒有額度就歸還連線與名額並拒絕，不占著連線等待下一個速率窗口。借連線期間也算在途，借取逾時且未送出 SQL 時可直接釋放名額。

速率採用單調時鐘，記錄最近一秒的送出次數。分類與全站的檢查、登記和發起 SQL 呼叫必須在不可交錯的步驟內完成，避免兩個請求都看到最後一份額度。資料庫引擎真正開始執行的時刻可能更晚，應另外量測，不能由這份計數推算。重啟後至少等一秒，並確認前一程序的查詢已結束才重新放行，避免重設計數成為額外突發流量。

查詢期限到了，應用程式會發起取消。但名額要等驅動與資料庫已確認查詢結束，或完成可驗證的連線清理，才釋放。若 HTTP 已逾時而 SQL 還在跑，立刻回收名額就會讓下一批查詢疊上去。清理結果未知時，保留占用並告警，接受暫時降低服務能力。

暖機若因慢查詢用滿兩個在途名額，實際發送量會低於每秒十次。這是保護措施正常作用，不能為了追上暖機進度，把在途上限一起拉高。

## 保護邏輯要能在 Redis 不可用時運作

清單 miss 的執行順序是：驗證登入與查詢範圍，檢查快取，同鍵合併，取得回源名額，讀主庫，嘗試回填，再回應。快取鍵包含租戶、使用者與查詢條件，不能把別人的清單當成自己的命中結果。

一個程序內可以用記憶體表記住每個鍵正在執行的讀取。同一鍵後到的請求共用那個結果；每鍵最多十個等待者，超過或等逾 200 ms 就拒絕，不占資料庫連線。個別等待者逾時只退出等待，共享查詢按自己的期限收尾，確認結束後才移除同鍵記錄。這裡只合併授權範圍相同的清單讀取。不同顧客、不同頁碼或篩選條件仍各自查詢，所以不能預設合併會把全部八十次降成一次。

回源額度與在途計數也留在這個程序內，不依賴故障中的 Redis。快取連線設定短期限，連續失敗後暫時跳過快取呼叫，只用少量探測確認是否恢復。跳過快取之後，回源限制照常生效。若快取寫入失敗，可以交付剛從主庫讀到的合法結果，卻不應再為同一回應重新查一次資料庫。

這套程序內控制有明確的部署限制。增加第二個應用實例、啟動獨立暖機 worker，或滾動部署時讓新舊實例重疊，都會產生另一份計數器。**在所有活躍實例的額度總和沒有被限制以前，不得複製這組設定擴容。** 下一版可以分配固定且總和受控的實例額度，或使用可用性獨立的協調機制；協調失敗時要保守拒絕，不能全部放行。

## 只暖常用鍵，回填也要遵守新鮮度契約

暖機先取最近確實使用過、查詢範圍仍合法的一小批清單，不掃描所有使用者與任意篩選組合。工作清單有長度上限、每鍵只排一份，超過就留待後續自然請求載入。暖機和前景 miss 共用同鍵合併表，但送出的查詢仍按先啟動者所屬類別扣額度。

因此，前景請求若遇到已在暖機的同一鍵，可能要等暖機查詢完成。首版接受這個短暫等待，超過前述期限就拒絕。若希望前景可以搶先，就得另外設計優先順序，不能靠多送一次相同 SQL 達成。

Microsoft 的 Cache-Aside 文件把預先載入列為可選做法，同時提醒這種模式不保證資料庫與快取一致。[Microsoft 文件](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside) 暖機也可能讀到舊值後才回填，所以摘要要保留原本的資料取得時間，TTL 不因命中而延長。退款確認仍走主庫新快照，不因快取重新有資料就切換回清單摘要。

恢復速率分段提高，例如每秒二次、五次、十次，每段先觀察一個完整的五分鐘負載窗口。只有明細延遲、下單 SLO、資料庫在途量與錯誤率都符合事先約定的門檻，才進下一段。任何一項超標或監測資料過期，就停止新增暖機，已開始的查詢受控收尾。恢復不能只憑 Redis 已連線或命中率回升判定。

若低速暖機仍拖慢下單，先維持按需載入與清單限流。快取逐步恢復會慢一些，但可以少做許多沒有使用者需要的查詢。反過來說，若壓測證明主庫能長期承接全部讀取，直接繞過快取也可能更簡單，不必為一個沒有量測收益的快取維護恢復機制。

## 演練要同時送下單、明細與大量清單

在隔離環境建立與正式設定相近的資料、索引與查詢分布，保留既有下單和背景工作負載。下列驗收計畫尚待執行，數字可作為第一份測試規格。

1. 暖快取時送每秒八十次清單、二十次明細，記錄實際命中率與回源量。再改用空快取，維持相同入口流量，核對每一類放行與拒絕數，而非只看 API 成功率。
2. 讓清單全部查不同鍵，再改成同一個合法鍵。前者測回源限額，後者測合併是否只有一個執行者，以及等待者是否受到數量與期限限制。
3. 啟動每秒十次暖機。以應用程式送出 SQL 的時刻核對，每個滑動一秒窗口應滿足明細最多二十次、清單三十次、暖機十次，總量最多六十次。另測停止新增暖機、等最後一次送出退出一秒窗口後，才把清單提高到四十次的切換流程；明細二十次額度保持保留，全站總額仍不得超過六十。名額占滿時，實際速率可以更低。
4. 故意把讀取延遲拉長，令請求逾時。資料庫尚未確認結束前，在途名額不得提前回收。觀測最大在途數及取消中的數量，不能只查 HTTP 日誌。
5. 切斷 Redis，確認快取呼叫有期限、探測量有限，回源仍受控。之後恢復空 Redis，暖機只能依二、五、十次的階段推進。
6. 在暖機中途更新退款狀態，延遲舊清單的回填。等更新提交成功，再開始新的明細查詢，必須讀到該次更新或更晚版本。清單上的取得時間不能被重寫成回填時間。

固定測試負載下，首輪可把明細目標寫成「每個五分鐘窗口，合格請求至少 99% 在 300 ms 內得到正確結果」，拒絕與錯誤都計入未達標。下單沿用原有 SLO，不因這次演練降低標準。這些目標與六十次讀取額度必須一起測，達不到就調低清單或暖機，或重新評估容量。

監測至少分開記錄入口嘗試、快取命中、合併等待、SQL 送出與結束、資料庫實際執行的等待、各類拒絕、取消中數量，以及明細和下單的端到端延遲。把暖機關掉後再跑一次，才能知道變慢是恢復工作造成，還是原本的主庫就已經滿載。

## 練習：多開一台暖機 worker，會發生什麼事？

目前明細、清單、暖機的速率預算是二十、三十、十次，均以全站每秒送出的查詢數計算。團隊嫌暖機太慢，另開一個 worker，照抄每秒十次與兩個在途名額，並讓新 worker 使用自己的全站計數器與同鍵合併表。

請算出新的最大總速率與在途數，說明哪兩項保護已經失效。若主庫預算不增加，你會怎麼部署第二個 worker？

最大總速率變成 `20 + 30 + 10 + 10 = 70 次／秒`，在途上限變成 `4 + 4 + 2 + 2 = 12`。全站總額超過原設定，同鍵合併也只在各程序內生效，兩邊可能各查一次。

保守方案是先不增加 worker。若確實需要拆程序，讓兩個暖機程序合計最多十次／秒、兩個在途名額，例如各五次與一個名額，並確保滾動部署不再多出第三份。分配各自處理的鍵可減少重複工作，但程序失效與工作接手仍須測試。前景與暖機跨程序後不能再沿用原本的合併保證，應將額外查詢納入總額，或實作獨立驗證過的協調機制。
