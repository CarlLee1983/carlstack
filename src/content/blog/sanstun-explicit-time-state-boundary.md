重試流程的測試若要真的睡三十秒，測試成本很快就會反過來限制我們願意覆蓋的情境。逾時前一瞬間收到回應、時鐘跳過數個期限、連續兩次斷線，常被留到整合環境碰運氣。

Firezone 在 [2026 年 10 月 31 日介紹 sanstun](https://www.firezone.dev/blog/introducing-sanstun)，把 WireGuard 狀態機做成 sans-IO Rust 函式庫。這種分離不只把 socket 留在外面，也把時間與隨機性視為需要明確管理的輸入。它值得後端工程師研究的地方，是如何讓狀態改變可以被控制與觀察。

我讀了作者的設計說明與[公開儲存庫](https://github.com/firezone/sanstun)，沒有編譯、壓測或安全稽核這個實作。下面把設計借用到虛構的第三方 API 重試流程，屬於工程推演，不是 sanstun 提供的付款 SDK。

## 核心回傳意圖，外層決定怎麼送

傳統的 retry 函式常把四件事放在一起：發 HTTP、讀取現在時間、等待一段時間，再修改重試計數。測試若要走到最後一次重試，就得控制 HTTP client、timer 與內部狀態，測到一半還可能受真實排程影響。

可以改成由核心接收「發生了什麼」與明確時間，產出下一個動作。動作可能是送出請求、設定下一次期限、完成或交給人工處理。外層負責真正執行 HTTP 與 timer，再把結果送回核心。這是一種職責切法，不要求你更換語言或先拆微服務。

例如在測試資料中，時間使用同一個可控制的單調刻度。輸入 `t=0` 的開始事件，核心提出送出請求；輸入 `t=5` 的逾時事件，核心排定下一次重試；接著直接輸入下一個期限，不必讓測試程序真的等待。時間單位必須固定，不能把毫秒、秒與日期字串混用。

這種測試驗證決策。真實 HTTP adapter 是否正確送出、timer 是否被註冊、取消後是否仍有回呼，仍要另外驗證。若把外層整合全部拿掉，狀態機測試再完整也看不到資源洩漏。

## 必經檢查要在 API 上留下痕跡

sanstun 的設計說明有另一個具體例子：原始 datagram 經過 `Interface::receive` 後才取得相對應的訊息型別，再送進 tunnel。部分訊息型別的建構子限制在 crate 內，讓正常呼叫路徑必須先經過入口的解析與限制處理。

換到 webhook 系統，可以思考兩個函式的差別。一個接收任意 JSON，並在註解寫「呼叫前請驗證簽章」；另一個只接受由驗證器建立的事件物件。後者把前置條件放進 API 結構，程式審查時比較容易發現繞過路徑。

這只是設計類比，不表示 Rust 型別就能證明遠端來源可信。驗證器仍可能使用錯誤金鑰、漏掉時效或把不該信任的欄位納入判斷。在 TypeScript 裡，型別斷言也可能繞過編譯期限制；跨程序輸入更必須做執行期驗證。

實用的審查問題是：若有人直接呼叫最內層的處理函式，哪些檢查會消失？如果答案只有「大家知道不可以」，就值得把這個前置條件變成可檢查的介面。相關接收與重試問題可接著看[Webhook 系統設計](/blog/webhook-system-architecture-hmac-retry-dlq/)。

## 緩衝移到外面，容量責任也跟著移動

Firezone 說明 sanstun 不在函式庫內替使用者緩衝待送封包，呼叫者要自行決定沒有 session 時如何處理。這讓介面行為較明確，但應用程式也必須接下容量與丟棄策略。

對一般後端服務也是如此。把 retry queue 移出核心後，還要回答最大等待量、資料保存時間、取消與程序重啟後的恢復方式。不能只是換個類別存陣列，然後把記憶體無限成長留給上線後處理。

我會從最小的有界方案開始：核心只產出重試意圖，外層為每個工作保存目前狀態與下一次期限，同時限制總量。負載超過上限時，要拒絕新增、回覆可重試訊號，或依業務規則丟棄。每個選項都有代價，至少要選定一個，不讓預設行為替你做決定。

這與今天另一篇[匯出工作的接單與併發限制](/blog/order-system-export-admission/)互補。決策變得可測之後，仍要給執行器明確的資源預算。

## 先重播三個事件順序，再談平行化

作者也展示拆開狀態記帳與加解密工作的 API，並提供效能量測與理想化加速推估。我沒有重跑那些 benchmark，不把它換成我們服務的吞吐保證。執行緒交接、工作大小與同步成本都會影響實際收益。

對現有 Laravel 或 Node 專案，最小可行實驗反而是挑一個常因時間而不穩定的 retry 測試，讓時鐘由外部提供，重播三種順序：

1. 回應在逾時前到達，之後收到過期 timer，不能再送一次。
2. 逾時先發生，稍後原請求成功，不能同時把兩次結果都當成新交易。
3. 取消後仍收到回應，狀態應依明定規則處理，而非偷偷復活工作。

這些是待實作的驗收案例，尚未在專案執行。先確認同一組輸入能重現同一個決策，再測外層 adapter 的實際取消與資源釋放。當問題來自不可控時間，增加測試等待秒數通常只會讓失敗更晚出現。
