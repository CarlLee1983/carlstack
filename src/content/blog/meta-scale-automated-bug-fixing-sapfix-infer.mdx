2018 年 9 月 13 日，Meta（當時還叫 Facebook）在工程部落格發表〈[Finding and fixing software bugs automatically with SapFix and Sapienz](https://engineering.fb.com/2018/09/13/developer-tools/finding-and-fixing-software-bugs-automatically-with-sapfix-and-sapienz/)〉，介紹自動修復工具 SapFix。細節寫在隔年的論文〈[SapFix: Automated End-to-End Repair at Scale](https://discovery.ucl.ac.uk/id/eprint/10084761/1/SapFix-Automated-End-to-End-Repair-at-Scale-v2.pdf)〉（ICSE-SEIP 2019，[DOI 10.1109/ICSE-SEIP.2019.00039](https://doi.org/10.1109/ICSE-SEIP.2019.00039)）。

論文說 SapFix 是「the first deployment of automated end-to-end fault fixing, from test case design through to deployed repairs in production code」；部落格的說法保守一點，前面加了「To our knowledge」。論文中 SapFix 修過 6 個生產系統，每個都有數千萬行程式碼。另一篇 Meta 作者群的〈[Scaling Static Analyses at Facebook](https://cacm.acm.org/magazines/2019/8/238344-scaling-static-analyses-at-facebook/pdf)〉（CACM，2019 年 8 月）則提到，Facebook 的程式庫每天都有數千次程式碼變更。

先講時期。部落格寫的是「In its current, proof-of-concept state」，也說 SapFix 還在開發，使用規模比不上 Sapienz。部落格同時說 SapFix 設計成獨立工具，有沒有 Sapienz 都能執行（「SapFix is designed to operate as an independent tool, able to run either with or without Sapienz」），但當時的版本專注修 Sapienz 找到的 bug。論文的數字來自前三個月的部署，外加一次三天的實驗。我沒有找到 Meta 後來公開說 SapFix 仍在運作的資料，所以下面都是 2018 年前後的狀態，不是現役管線。

SapFix 的流程從動態測試工具 **Sapienz** 開始。Sapienz 找到當機、歸因到某個 Diff 後，把它交給 SapFix 產生補丁。靜態分析工具 **Infer** 是輔助：它幫忙定位可能為 null 的運算式，並在修補後重跑一次。

---

## 流程總覽

<MetaAutomatedBugFixingDiagram />

1. **Sapienz 觸發**：Sapienz 在 Android app 上跑自動化測試，找到當機並歸因到引入它的 Diff，再交給 SapFix。
2. **SapFix 產生補丁**：用範本修復、變異修復、整個 Diff revert、部分 revert 四種策略產生候選補丁。
3. **隔離環境驗證**：編譯補丁、用 Sapienz 確認當機消失且沒有新當機、跑既有測試，再重跑 Infer。
4. **人工審查與合入**：透過 Phabricator 把一個候選補丁送給原 Diff 的作者審查，接受後才合入。

## 1. 觸發端：Sapienz 找到當機

Sapienz 是 Meta 的動態測試工具，用搜尋式方法自動產生測試，部落格說它已經部署到生產環境，檢查 Facebook、Instagram、Workplace、Messenger 的 Android app。依[部落格](https://engineering.fb.com/2018/09/13/developer-tools/finding-and-fixing-software-bugs-automatically-with-sapfix-and-sapienz/)，Sapienz 的報告約有四分之三後來被開發者修掉（「Approximately three quarters of Sapienz reports resulted in fixes by developers」）。這個 75% 是 Sapienz 報告的人工修復率，不是 SapFix 補丁的採納率。

Sapienz 定位到造成當機的程式碼區段後，把資訊交給 SapFix。依[論文](https://discovery.ucl.ac.uk/id/eprint/10084761/1/SapFix-Automated-End-to-End-Repair-at-Scale-v2.pdf)的 Algorithm 1，SapFix 的輸入是 Sapienz 的當機資訊：被歸咎的 revision、檔案、行號、stack trace 和 crash id。Infer 提供的可疑運算式是選用的補充，沒有 Infer 資料時這個參數就是 null。

SapFix 只處理空指標例外（NPE）。論文寫「Algorithm 2 currently only supports fixing Null Pointer Exception (NPE) crashes」，評估裡的當機也全是 NPE。

### 2.1 範本修復

依部落格，範本是從人類工程師過去的修復中自動收集來的（「automatically harvested from those created by human engineers, based on a pool of past fixes」）。論文補充，這些範本來自另一個工具 Getafix。

### 2.2 變異修復

範本不適用時，SapFix 改用變異修復：在造成當機的敘述的 AST 上做小幅修改。論文說變異只有兩種：回傳 null，或用 null check 保護可能為 null 的運算式（「two simple mutations, which either return null or protect potentially null-valued expressions with a null check」）。實作上用 Eclipse JDT 解析出錯檔案的 AST，再把 null check 加在出錯敘述前面。

下面是我依這兩種變異寫的示意，不是論文裡的程式碼：

```java
// === 原始程式碼：Sapienz 回報的當機點 ===
User user = getUserProfile(userId);
String name = user.getName(); // user 為 null 時拋出 NPE

// === 變異一：在出錯敘述前加上 null check ===
User user = getUserProfile(userId);
if (user != null) {
    String name = user.getName();
}

// === 變異二：遇到 null 就回傳 null ===
User user = getUserProfile(userId);
if (user == null) {
    return null;
}
String name = user.getName();
```

### 2.3 Revert

論文也把撤回整個 Diff 和部分撤回列為策略，[部落格](https://engineering.fb.com/2018/09/13/developer-tools/finding-and-fixing-software-bugs-automatically-with-sapfix-and-sapienz/)則說 revert 用在觸發頻率高的 bug。實際結果是：前三個月 SapFix 嘗試 revert 18 個 Diff，這些建議全部被開發者拒絕（「These Diff revert recommendations were all declined by developers」）。

### 2.4 挑選要送審的補丁

論文的挑選順序是：先看策略優先序（範本優先），同一策略內選 Sapienz 最常執行到出錯敘述的那個，再選改動最小的。論文也說會參考 Infer 靜態分析和 linter 的結果（「favouring template-based fixes, where all else is equal, but taking account of results from Infer static analysis and also from linter reports」）。

## 3. Infer 在流程裡做什麼

**Infer** 是 Meta 開源的靜態分析工具，依它的 [GitHub README](https://github.com/facebook/infer)，支援 Java、C、C++、Objective-C。

### 3.1 Infer 本身：分離邏輯與 Bi-Abduction

Infer 的理論基礎是分離邏輯（Separation Logic）與 bi-abduction。依 [Infer 文件](https://fbinfer.com/docs/separation-logic-and-bi-abduction/)，bi-abduction 是 Infer 能擴展到大型程式庫、能增量分析程式碼變更的基礎：沒變的部分可以重用分析結果，只重新分析變更的部分。

```text
{P}  C  {Q}
```

Infer 會替每個函式推導出近似其行為的前置條件與後置條件，分析呼叫端時直接套用這份規格，不必重新分析函式內部（CACM 2019 文章的說法是「It deduces a precondition/postcondition specification … and then uses that specification when reasoning about its calls」）。

Infer 的主要部署方式是在 diff time 做增量分析：Diff 送進 code review 時，Meta 內部 CI 會跑一次 Infer。CACM 2019 文章說這一步平均在 15 分鐘內完成（「within 15 minutes on average」）。

依 [Infer 官網](https://fbinfer.com/)，它在 Java 上能找出 null pointer exception、資源洩漏、missing lock guard、並行 race condition 等問題；執行緒安全問題由 RacerD 回報。CACM 2019 文章提到，到 2018 年 3 月為止的一年內，RacerD 回報的資料競爭有超過 2,500 個被修掉。

bi-abduction 是 Infer 的歷史基礎。目前 Infer 的 [issue 類型清單](https://fbinfer.com/docs/all-issue-types)把 Null Dereference 和 Resource Leak 列在 `pulse` checker 下，所以我推測現行版本的主力 checker 已經換掉了。

### 3.2 Infer 在 SapFix 裡的兩個用途

部落格的說法是「SapFix uses Infer to assist with localisation and static analysis of fixes proposed」，論文裡對應兩件事：

- **輔助定位**：Infer 標出可能為 null 的運算式，當作 SapFix 的選用輸入。
- **修補後重跑**：論文說 Infer 會自動在補丁上重跑，當作 sanity check，確認靜態分析不再回報 SapFix 要修的那個問題（「as a sanity check that static analysis also no longer identifies the issue that SapFix seeks to fix」）。

1. **編譯**：無法編譯的補丁直接淘汰。
2. **重現當機與既有測試**：論文說 SapFix 用 Sapienz 重現原本的當機，並在候選補丁上多跑幾次 Sapienz，看有沒有新的當機。另外也檢查既有的 unit、integration 和 end-to-end 測試結果。
3. **Infer 重跑**：見 3.2 節，這是 sanity check。

論文前三個月的部署中，57 個 NPE 當機產生 165 個補丁，其中 131 個成功建構並通過所有測試，約 79%。通過測試不等於修對了，下一節的人工判定只有約一半。

---

## 5. 人工審查與合入

部落格說 SapFix 不會自己把修復部署到生產程式碼（「it is not designed to deploy fixes to production code on its own」），工程師一直在流程裡（「Engineers are always in the loop」）。論文描述的做法如下：

- **送審**：SapFix 從通過驗證的候選中挑一個，透過 Phabricator code review 系統請人審查。其他候選以 inline preview 的形式附在這個 Diff 上。
- **審查人**：指派給提交原 Diff（也就是 SapFix 想修的那個 Diff）的工程師。其他相關工程師依所有 Diff 共用的標準規則加入訂閱。
- **結果**：開發者拒絕，或 7 天內沒有審查，SapFix 就放棄這個候選。部落格說系統會追蹤審查回饋，合入被接受的補丁，再清掉其他候選。

### 5.1 論文報告的成效

- 約一半的 SapFix 補丁被開發者判定能正確修好當機。判定正確的補丁中，約一半照原樣合入；另一半是開發者自己改過，或開發者看到補丁前已經自行修好（「Of those that were modified, about half were edited by the developers, while half were simply reviewed by the developer only after they had already fixed the bug themselves」）。
- 換算下來，約四分之一的補丁合入生產程式碼，另有四分之一被判定正確但沒有合入，原因是開發者自己調整了修法，或在看到補丁前已經自行修好當機。
- 三天的既有當機實驗中，合入比例約 15%。
- 從當機首次被偵測到補丁送到開發者面前，時間中位數是 69 分鐘（四分位距 65～73 分鐘），最快 37 分鐘，最慢約 1.5 小時。

---

## 6. 我的看法

SapFix 的組合是：動態測試找當機、自動產生小補丁、測試與靜態分析驗證，最後一定交給人審。在 LLM 與 Agent 普及之後，我認為把 LLM 的程式碼生成能力和 Infer 這類符號邏輯驗證結合起來，會是軟體工程接下來的核心方向。SapFix 的數字也提醒一件事：165 個補丁有 131 個通過測試，但開發者判定正確的只有約一半。
