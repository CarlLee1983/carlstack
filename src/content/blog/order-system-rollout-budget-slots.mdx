訂單 API 查不到 Redis 快取時，會改查 MySQL，這個動作稱為「回源」。假設全站每秒最多允許六十次這類查詢，平常同時執行三份訂單 API，每份各限制二十次。每份獨立執行的 API 就是一個程序，也常稱為一個應用實例。它們不一定在不同機器上。

滾動部署會逐步用新版替換舊版，期間新舊程序可能同時執行。如果先啟動第四個程序，而它也有每秒二十次的配額，四個程序合計就能送出八十次查詢，超過原本的全站上限。

把每個程序的上限改成十五次，可以限制四個程序的總量，但還要處理配額交接。如果舊程序被標成離線，部署工具立即把它的額度交給新程序，稍後舊程序恢復執行，同一份額度仍會被用兩次。

[上一篇的冷快取恢復](/blog/order-system-cold-cache-recovery/)討論單一程序如何限制查詢。系列第 23 篇把範圍擴到多個程序，處理部署時如何分配與交接查詢配額。我會先固定分成四份，每份稱為一個「槽位」，同一時間只能交給一個程序使用。第一版接受部分配額暫時閒置，先不做動態借用或租約到期後自動接管。

情境仍是虛構的訂單 API、MySQL 主庫與 Redis 清單快取。以下容量、時間與驗收門檻都是教學假設；四槽方案是設計建議，不是 Kubernetes 內建功能。官方文件查核於 2026 年 11 月 6 日，尚未執行 Kubernetes／MySQL 的部署與故障整合演練。

## 限流範圍：訂單清單查詢

這次的配額只用於訂單清單。超過限制時，API 可以暫時回報無法取得清單。每次回源只送出一個限制結果大小、使用適當索引的 SQL。快取沒有資料時的查詢、相同查詢的重試，以及預先填入快取的暖機查詢，都算在內。退款確認明細、下單交易、匯出與部署控制資料各有另外預留且受限制的容量。

這是新的容量算例，不沿用上一篇明細二十、清單三十、暖機十次的分類設定。四槽總額只保護這組清單讀取，不會自動保留明細的份額，也不能證明下單的延遲目標已達成。

假設準備以壓測驗證的上限是任意連續一秒內最多送出六十次 SQL，同時最多十個尚未確認結束的操作。這裡把任意連續一秒稱為「滑動一秒窗口」，尚未確認結束的操作稱為「在途操作」。正常時每秒三十次回源，均勻分到三個程序約各十次。若工作量或查詢成本改變，必須重測這份預算。

限制點放在應用程式呼叫資料庫驅動、送出 SQL 的時刻。在途名額從準備借連線前開始占用，直到查詢或取消後的清理確實結束才釋放。資料庫真正開始執行可能更晚，不能把送出數當成資料庫執行時間的量測。

## 四個固定槽位，平常只啟用三個

把查詢配額固定分成四個槽位，持久保存每個槽位的分配紀錄。每槽的限制是：

- 每個滑動一秒窗口最多十五次 SQL 送出。
- 最多兩個在途操作，包含借連線、執行與取消清理。
- 同一時間只能由一個明確的程序啟動實例持有。

四個槽位合計 `4 × 15 = 60 次／秒`，在途上限 `4 × 2 = 8`。十個候選名額中的另外兩個刻意不分配，不能遇到逾時就偷偷借用。平常 A、B、C 各占一槽，每秒最多送四十五次，同時最多六個在途操作。第四槽留給部署中的新程序 D。

這個選擇付出了四分之一速率容量的代價。假設中的每秒三十次仍有空間，但若正常需求已是五十五次，三個程序各十五次就不合格。應先調整部署方式、重新驗證容量或選擇另一種協調方案，不能拿部署安全當成吞吐不足的理由。

每個槽位都守住任意一秒窗口的十五次，且同一槽位交接時，前後程序的送出紀錄不會落在同一個一秒窗口內，四份相加才得到六十次。整秒歸零的計數器可能在邊界前後各放十五次；一般 token bucket 也可能允許額外突發。若契約寫的是滑動一秒，就要用相符的演算法與測試，不能只看參數也叫「每秒十五」。

## 用啟動 ID 記錄配額歸屬

讓每個 Pod 都帶著 `SLOT_ID=1`，不會產生互斥。首版需要一份持久化登記，記錄槽位、持有者、設定版本與交接狀態。持有者識別必須包含每次程序啟動的新 ID；Pod 名稱、甚至仍沿用的 Pod UID，都不足以區分容器內的重新啟動。

指派由序列化的部署程序完成，登記更新使用具備條件檢查的原子操作。這裡假設只有一份具權威性的登記，不能由各地可獨立寫入的副本分別發放。同時有兩個程序申請同一個空槽時，最多只能指派給其中一個。指派結果不明時，重新讀取登記確認，不替另一個程序再發一份。這個登記服務的可用性與管理成本，是固定槽方案需要承擔的代價。

程序啟動時預設禁止回源，取得綁定自身啟動 ID 的指派後才開啟。程序重啟、複製容器或再開一個子程序，不能沿用先前的指派與清空後的計數器。沒有槽位的程序可以啟動，卻不能接需要回源的工作。背景暖機與重試也必須通過同一個入口，不因沒有 HTTP 請求就例外。

已取得槽位的程序，在登記服務暫時不可讀時仍可依原配額工作，前提是槽位不會因逾時被重新指派。所有新增指派與交接此時停止。恢復登記資料也不能直接載入過期備份後恢復發放；先核對現存持有者，無法確認的槽位保持占用。

這裡的安全來自不重複指派與確實停用舊持有者。單純把登記上的版本加一，不會阻止一個已暫停、稍後恢復的程序向 MySQL 送 SQL。若要以 fencing 取代停用證據，就必須有實際拒絕舊版本請求的執行點，不能只在紀錄裡多放一個數字。

## 配額交接的三個條件

A、B、C 正常服務時，先讓新版 D 取得第四槽。D 可用後，讓 A 停止接受新工作並準備結束。下文稱這個過程為「退休」：A 這次啟動之後不能再送出新 SQL，只能完成已開始的工作並退出。

### 先關閉所有新查詢入口

A 原子地把自己的送出入口切成不可逆的退休狀態。切換與每次 SQL 送出必須經過同一套同步機制，避免請求先看見「可以送出」，卻在退休確認之後才送出。

已接到但尚未送 SQL 的 HTTP 請求、排隊中的工作、重試計時器與暖機都要停止發起新查詢。readiness 改成 false 只處理後續流量導向，不能代替這個程序內的停用動作。退休程序不能因設定重新載入或網路恢復再次開啟入口。

所有回源 SQL 經過同一個本地派送器，檢查本次啟動的有效指派、退休狀態、滑動窗口與在途名額，再登記並發起驅動呼叫。退休確認只在入口永久關閉後回傳，帶上槽位與程序啟動 ID。控制端也要比對目前持有者與狀態，過期確認不能釋放已經換人的槽位。

若拿不到可信的退休確認，也沒有證據證明舊程序已終止，就保留整個槽位。單憑「目前沒有 SQL」不夠，暫停中的程序還可能恢復送出。

### 再確認舊 SQL 與清理都結束

A 已送出的查詢繼續占用它的兩個名額。HTTP 逾時、送出取消請求、程序退出，都不能單獨證明遠端資料庫已停止工作。驗收需要把程序啟動 ID 對應到資料庫連線及查詢，確認所有相關操作已結束；證據不足便停在收尾狀態。若需取消連線，先重新核對歸屬，不能只憑保存過的數字 ID 操作。

MySQL 8.4 的文件指出，`KILL QUERY` 只終止目前 statement，連線仍保留；`KILL` 回傳也不等待終止確認，後續還有中止與清理時間。因此，收到取消指令成功回應時就歸還名額，會過早增加可執行的工作。[MySQL KILL 文件](https://dev.mysql.com/doc/refman/8.4/en/kill.html)

### 最後留下完整的一秒空窗

確認 A 不可能再送新 SQL，且舊操作全部結束後，由交接控制程序以單調時鐘再等完整一秒。期間槽位保持不可指派，時間到才記錄退休完成並交給下一個啟動實例 E。

這樣不用把 A 的單調時鐘值搬到 E 的機器上比較，也不會把 A 在上一秒用掉的十五次額度清掉後立刻再送十五次。若交接控制程序在等待期間重啟，保守地重新等待完整一秒，不能靠一份不明確的倒數紀錄直接放行。

槽位空窗是保守交接的一部分。它不保證資料庫已恢復效能，也不取代前兩個條件。只睡一秒、但舊程序仍可執行，仍然不安全。

## `maxSurge: 1` 不能保證只有四個執行者

團隊可能認為設定三個 replicas、最多多開一個，就已經保證只有四個程序。Kubernetes Deployment 文件明確提醒，終止中的 Pod 仍可能消耗資源，部署過程的總資源使用可能超過 `replicas + maxSurge`。[Deployment 文件](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

所以槽位限制應獨立於 Pod 數量。即使排程器又建立 E、F，沒有安全釋出的槽位就不准回源。首版一次只推進一段交接，不同時展開多輪版本更新。rollout 卡住時，先檢查哪個槽位仍在收尾，不靠提高副本數解除限制。

Pod 從 API 消失也不足以作為交接證據。官方文件指出，強制刪除不等待 kubelet 確認程序已終止。這是控制面的可見狀態與實際執行可能不同的情況。[Pod 強制終止文件](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#forced-pod-termination)

若 A 失聯卻仍持有第一槽，B、C、D 可以繼續各用自己的配額。第一槽整份保留，連目前看似沒用到的速率也不借出去。要重新使用第一槽，就先證明 A 已安全退休，否則接受這一槽無法交接。其他槽位仍可各自完成安全退休與換版，但不能因此清掉 A 的占用紀錄。租約到期本身不能代替這份證據。

## 三種部署與配額分配方式

### 停舊再開新，適合能接受短暫降級的服務

如果清單暫時不可用的成本低，先讓單一舊程序完整退休，再啟動新程序，會比四槽登記簡單。仍要確認遠端查詢結束及速率窗口退出，但不必維護多份同時有效的配額。

對還沒證明需要多副本的系統，我會先保留這條路。如果不需要多副本，仍可沿用上一篇的單程序方案。

### 固定槽位，適合副本少且部署可受控的服務

固定分配不必在每次 SQL 前呼叫跨網路配額服務，但會浪費空閒槽位。流量不均時，A 可能超過十五次而拒絕，B 卻只有三次。負載平衡可以改善分布，不能保證每次都均勻。上層也不應收到拒絕就輪流重試其他程序，否則只是增加額外嘗試。

先量測每槽送出、拒絕、在途、退休時間，以及清單端到端延遲。如果正常負載的拒絕持續來自分配不均，而資料庫實際有餘裕，才值得改善分配。

### 集中協調，適合已量到固定分配浪費的服務

集中式回源執行服務，或可驗證的全域配額協調，可以更靈活分配名額，代價是新增依賴、網路延遲及故障處理。集中服務自身擴容或換版，也要回答同一個交接問題。

升級條件應寫成具體需求，例如需要自動擴到十個以上程序、三個程序合計每秒四十五次的上限不夠，或偏斜流量已讓清單 SLO 持續失敗。不要只因為有 Redis，就把配額放進同一個正在故障恢復的 Redis；協調失效時的拒絕策略要先設計。

## 部署與故障的驗收情境

下面是待執行的整合驗收計畫。使用隔離環境，固定查詢形狀與資料量，並同時保留既有下單和明細流量。

1. **正常部署。** A、B、C 各占一槽，D 使用第四槽。在 A 完成停用、資料庫收尾及一秒空窗前，E 不得取得第一槽。三個正常槽位的候選上限是四十五次，四槽重疊時才是六十次。
2. **重複指派。** 同時讓兩個新啟動 ID 申請同一空槽，最多一個成功。模擬指派回應遺失，再重送申請，仍不得多出第二個持有者。
3. **舊程序暫停後恢復。** 暫停 A，讓健康檢查失敗並建立替代程序，再恢復 A。替代程序不能取得第一槽；A 仍只能使用原配額。若 A 已完成不可逆退休，恢復後任何待送工作都必須被拒絕。
4. **重啟清空計數器。** A 在不到一秒內已送滿十五次，隨即重啟。新的啟動 ID 預設禁止回源，不能用同一個槽位名稱直接再送十五次。
5. **取消延遲。** 讓 A 的兩個查詢遲遲無法確認結束，HTTP 先逾時。名額仍占用，槽位不能退休。第五個 Pod 即使已啟動，也不得繞過登記。
6. **控制程序重啟與流量偏斜。** 在空窗中斷交接程序，確認它恢復後重新等待。再把大部分流量送到同一槽，分開計算拒絕率與其他槽位的閒置量，不能只看全站平均值就判定達標。

記錄每次送出的槽位 ID、程序啟動 ID、查詢 ID、送出與確認結束事件，以及指派和退休事件。跨機器的單調時間不能直接相減；壓測應使用可校準的共同觀測時間軸，或在受控模型中使用同一時鐘，並寫出量測誤差。資料庫端另量實際執行與等待情況。

驗收同時檢查每個滑動一秒窗口最多六十次、在途最多八個，以及下單和明細既有 SLO。任何未知持有者或未知清理結果，都應使該槽交接停止推進，不能為了讓發布顯示綠燈就釋放槽位。

## 練習：第一槽看起來空了，可以交給 E 嗎？

A、B、C、D 各占一槽，每槽十五次／秒與兩個在途名額。A 在 `t = 0.0` 到 `0.2 秒` 間分批送出並完成十五次短查詢，同時在途不超過兩個。A 隨後失去管理連線，但程序是否停止未知。E 正在等第一槽。

團隊提議在 `t = 0.3 秒` 把槽位交給 E。請指出兩個獨立風險。如果 `t = 2.0 秒` 才取得 A 不可能再送 SQL、且所有舊操作已結束的可靠證據，保守方案最早何時讓 E 開始？若 E 已被錯誤放行而 A 又恢復，五個持有者的候選總速率與在途上限各是多少？

<details>
  <summary>參考思路</summary>

第一個風險是速率窗口重疊。即使 A 永久停止，E 從 0.3 秒起陸續送完十五次，仍可能讓同一槽在一秒內送出三十次。第二個風險是 A 尚未退休，恢復後能繼續送出；等到一秒結束也不能消除這個風險。

可靠證據到 2.0 秒才齊備，之後再等完整一秒，最早在 3.0 秒完成空窗並指派。等待中若控制程序重啟或證據失效，就保守延後。

若 A 和 E 同時使用第一槽，實際變成五份本地限制，候選總速率 `5 × 15 = 75 次／秒`，在途上限 `5 × 2 = 10`。十個雖沒超過最初的候選容量，仍違反已選定的八個在途合約，並讓每秒六十次的限制失效。未分配的兩個名額不能拿來掩飾重複指派。

</details>

部署檢查表要記錄由誰確認舊程序已停止送出 SQL、資料庫操作已結束，以及一秒等待已完成。這三項都有證據後，才能把原配額指派給新程序。
