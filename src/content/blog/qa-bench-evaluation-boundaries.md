AI 測試工具回報了十個問題，八個已確認、一個已排除、一個還沒人看。你要拿哪個數字估算工程師明天的工作量？如果只寫「準確率 88.9%」，那個等待複核的問題就從分母消失了。

[Momentic 的 QA-bench](https://github.com/momentic-ai/qa-bench)提供了一個適合拆開檢查的實例。它以 Gitea、Metabase、Twenty、Saleor 的 20 個功能區域，以及 1,396 個經人工審閱的錯誤標籤，評估 AI agent 能找出多少問題。[11 月 2 日的結果](https://github.com/momentic-ai/qa-bench/blob/a4dc8987edab813482e5f849c9a85eb7780f6979/results/2026-11-02.csv)值得讀，尤其是計分規則與執行環境。

> [!NOTE]
> 查核日期為 2026 年 11 月 3 日。Momentic 同時開發 Mo 並維護這套評測，結果是廠商公布，並非獨立第三方驗證。我讀取了固定版本 README 與結果 CSV，重算 Mo 的彙總比率，沒有執行 agent 或重做錯誤標註。下面的訂單案例與驗收流程是工程建議，未實測。

## 19.3% recall 與 84.2% precision 回答不同問題

[固定版本 README](https://github.com/momentic-ai/qa-bench/blob/a4dc8987edab813482e5f849c9a85eb7780f6979/README.md#results)列出，Mo 在每個功能區域 60 分鐘預算下，跨區域合計平均找到 269.3 個符合標籤的問題，recall 為 19.3%，precision 為 84.2%。269.3 是多次執行的平均結果，沒有「半個 bug」這種單次發現。

這兩個百分比分別回答：

- Recall：1,396 個已標註問題中，這組設定找到了多少。
- Precision：已歸入 Correct 或 Incorrect 的回報中，有多少屬於 Correct。

依[計分定義](https://github.com/momentic-ai/qa-bench/blob/a4dc8987edab813482e5f849c9a85eb7780f6979/README.md#scoring)，Correct 必須對應已確認標籤，Incorrect 對應已排除的主張。兩邊都對不上的 Unmatched 另列，可能是新問題，尚不能判定對錯。重複回報也另外計數。

因此 `precision = Correct / (Correct + Incorrect)` 的分母沒有 Unmatched 與重複回報。開頭的虛構例子就是 `8 / (8 + 1) ≈ 88.9%`，而十份回報中已確認有效的比例是 80%。後者是另一項工作量指標，不能直接替換官方 precision 的名稱。

Mo 這一批 60 分鐘 CSV 的 Unmatched 合計為零，所以這個排除規則沒有因未判定項目而拉高 Mo 當批結果。我把各區域已四捨五入的平均值加總，得到 Correct 269.32、Incorrect 50.67，重算 precision 約 84.17%、recall 約 19.29%，與 README 顯示值相符。這只核對了算術，沒有證明每個標籤都判得正確。

導入自己的測試流程時，我會同時保留未判定數量與複核耗時。否則工具可以讓 precision 看起來很乾淨，團隊卻仍不知道還有多少報告必須讀完。

## 一小時的比較，必須固定工具與重跑次數

這份榜單比較的是 agent、模型、瀏覽器工具與執行設定的組合。相同模型搭配 Playwright MCP 或 agent-browser，會落在不同列。拿兩列差異直接歸因於模型能力，會漏掉工具可見資訊、瀏覽器操作方式與子代理行為。

README 也明列，Devin 每個區域、每種時間預算執行一次，其餘設定執行三次。CSV 每列先取該區域的平均，總分再加總並重算比率。這個彙總方式不等於把每個區域的百分比直接平均，也沒有提供足夠依據讓讀者宣稱任何微小差距都穩定可重現。

費用與時間也各有邊界。評測時間不含環境建立與評分，公布費用不含 E2B 與評分成本。若要決定是否替一個訂單後台購買工具，預算應另外包含啟動測試環境、模型裁判、人工重現與整理缺陷單的成本。只用榜上的每個 Correct 成本乘以預期 bug 數，會少算導入工作。

## 應用程式進沙箱，不代表評測代理已被隔離

[執行方法](https://github.com/momentic-ai/qa-bench/blob/a4dc8987edab813482e5f849c9a85eb7780f6979/README.md#methodology)讓每次測試取得固定 commit 的應用程式、種子資料與獨立 E2B 環境。這有利於讓不同 agent 面對相同應用狀態，但 agent 自己還有哪些檔案與網路權限，需要另外檢查。

QA-bench 的公開標籤與專案歷史可以在網路上查到。代理若搜尋已知問題再寫成測試報告，測到的就混入了答案檢索能力。README 因而建議對 Codex、Claude Code 啟用 `--prevent-cheating`，但預設仍是關閉，以維持和既存結果的可比性。啟用後的執行會被另行標示，不能把新設定的分數直接當成舊榜單的同條件重跑。

更容易忽略的是 `codex-agent-browser`。文件明說它不使用 Codex sandbox，shell 能寫入目前使用者可寫的路徑。即使接受 `--prevent-cheating`，這個旗標也不會變成 shell 的網路防火牆。Browserbase 導覽限制無法阻擋 shell 另外連向資料集，使用本機瀏覽器時還有不同限制。測試應用本身的伺服器端外連，例如 Gitea 從 GitHub 匯入專案，也是另一條路徑。

**沒有驗證代理程序與測試應用的外連限制，就把結果標成「未驗證答案隔離」，不要列入隔離評測組。** 這是結果分類的停止規則，不代表要把公開榜單全部作廢。

## 用一個訂單後台功能，做可追溯的小規模試用

假設團隊要測試折扣碼管理頁，最小方案可以只選這個功能，不必複製完整四套應用評測。建議先把產品預期行為、已知有效錯誤、已排除主張分開保存，鎖定應用 commit 與種子資料。正式環境憑證和客戶資料不進測試機。

接著以獨立、可拋棄的執行環境跑 agent。測試案例、裁判標籤與其他 agent 的輸出，不掛載到它可讀的位置。網路限制由環境執行，而非只寫在提示詞裡。開始計分前，驗證允許的測試入口能讀取，未允許的資料集站點不能由瀏覽器或 shell 取得，同時確認測試應用的伺服器端外連符合試驗需求。若某個功能必須外連才能測試，就明確列為例外，或把該功能另分一組。

每份回報至少留下重現步驟、預期與實際結果、畫面或請求證據，以及對應的應用版本。彙總保留 Correct、Incorrect、Unmatched、重複回報四類，Unmatched 進人工複核清單。發現新的有效問題後，更新標籤版本，再讓所有候選設定對同一版本重新評分。只替其中一個工具補分，會改變比較條件。

另一種合理方案是允許代理查公開文件與 issue，測試它能否協助維護者整理既有問題。這對實際工作可能更有用，但衡量的是有資料可查時的協作成效，和受限探索的分數要分開。團隊可以同時保留「受限探索」與「允許檢索」兩組，分別記錄網路範圍和人工處理時間。

## 下一次試用，交付原始回報而不只一個百分比

先選一個低風險功能，保存固定環境、agent 設定與每次原始回報。評估者拿到四類計數後，抽查 Correct 是否能重現，再處理 Unmatched。這樣才能知道工具找到的是哪些問題，以及節省的探索時間是否被複核工作抵消。

若團隊目前只能取得廠商總分，下一步就要求一份可重算的明細，至少列出標籤版本、執行次數、未判定回報與隔離設定。這些資料缺席時，適合安排試用，還不適合據此取消既有測試或讓 agent 自動決定是否發布。
