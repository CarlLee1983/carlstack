顧客的訂單列表多了一欄「品項數」。畫面仍然每頁 50 張訂單，程式卻開始對每張訂單查一次明細，再數陣列長度。一次列表請求因此多出 50 次資料庫往返。

這次沿用虛構的模組化單體與 MySQL，決定列表的品項數怎麼取得。選擇先查這一頁的訂單，再針對這批 ID 一次彙總品項數。列表不需要商品名稱與規格，就不載入完整明細。

以下流量、數量與延遲目標均為教學假設，官方來源查核於 2026 年 11 月 16 日。SQL 是設計片段，尚未在 MySQL 或 Laravel 專案中執行，沒有實測延遲或壓測結果。

## 「兩個品項」與「五件商品」

一張訂單有兩列明細：一列是兩件杯子，另一列是三件盤子。畫面上的品項數是 2，商品件數是 5。若同一 SKU 因折扣或客製內容分成兩列，這個設計仍算兩個品項。

因此欄位命名為 `line_count`，計算明細列數，不用 `SUM(quantity)`，也不使用不同 SKU 的數量。取消與退款不刪除原始明細，品項數代表成立時的訂購內容。若之後要顯示「尚未出貨件數」，需要另外定義計算範圍。

功能需求限於已成立訂單列表：每頁最多 50 張、保留既有排序、只查目前顧客有權閱讀的訂單。訂單與明細一起提交，成立後不新增或刪除明細。這個前提讓兩次查詢之間的品項數保持穩定；可修改的購物車不在這個入口。

驗收目標先訂為列表 p95 小於 300 ms，範圍從應用收到請求到組好回應。查詢次數也要能直接測試。**這個用例的訂單與品項查詢最多兩次，不隨頁面筆數增加。** 此頁不提供訂單總筆數，沒有額外的總筆數查詢。登入查詢與監控寫入另外記錄，避免混淆計數。

## 每張訂單查一次的成本

假設列表流量是每秒 80 次請求，每頁 50 張訂單。先查訂單，再逐張讀明細，需要 `1 + 50 = 51` 次查詢，每秒便有 `80 × 51 = 4,080` 次 SQL 執行。改成兩次後是每秒 160 次。

這只比較查詢次數，不能據此宣稱快了 25.5 倍。第二次查詢仍要讀取明細索引，資料分布、連線等待與資料庫負載都會影響時間。它省掉的主要是逐張往返與重複執行成本。

若每張訂單平均有 8 列明細，50 張共有約 400 列。假設完整明細平均 600 bytes，全部搬到應用約需 240,000 bytes；若每張只回傳 ID 與數量，假設每組 40 bytes，50 組約 2,000 bytes。這是未計協定與物件額外成本的量級估算。批次彙總減少傳出的資料，資料庫仍須找出符合條件的明細。

## 只彙總這一頁的 ID

第一步沿用[訂單列表的排序欄位](/blog/order-system-list-sort/)，先取得已授權的訂單頁。下面以第一頁為例，省略分頁游標與完整 schema：

```sql
SELECT id, created_at, status, total_minor
FROM orders
WHERE tenant_id = :tenant_id
  AND customer_id = :customer_id
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

第二步使用剛取得的 ID，而不是接受客戶端另外提供一串 ID：

```sql
SELECT order_id, COUNT(*) AS line_count
FROM order_items
WHERE tenant_id = :tenant_id
  AND order_id IN (:id_1, :id_2, :id_3)
GROUP BY order_id;
```

每個 ID 都各自綁定參數，三個 placeholder 只示意有三張訂單的情況。空頁直接回傳空列表，不產生 `IN ()`。服務端的 `tenant_id` 來自驗證後的範圍，沿用[訂單明細的授權檢查](/blog/order-system-detail-authorization/)。

`order_items` 的候選索引是 `(tenant_id, order_id)`，讓資料庫能依租戶與訂單找到明細。實際採用前仍要確認現有主鍵、外鍵與索引，避免新增等價索引。查詢結果整理成以 `order_id` 為鍵的 map，再依第一步的訂單順序組回 DTO。不要拿 `GROUP BY` 結果的位置對應第幾張訂單。

[MySQL 的 COUNT 文件](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html#function_count)區分 `COUNT(*)` 與 `COUNT(column)`：前者計算列數，後者忽略指定欄位的 `NULL`。數明細不必依賴某個可空欄位。沒有明細的訂單也不會憑空得到一列分組結果，組裝時要依業務契約處理缺項。

在這個「成立訂單至少有一列明細」的假設下，缺項應視為資料不完整，記錄訂單 ID 並回傳通用服務錯誤，不能悄悄顯示 0。資料庫逾時同樣不能當作零品項。若產品允許零品項訂單，才把成功查詢後缺少的分組補成 0。

## 什麼時候改用 ORM 或 JOIN

若列表還需要顯示每個品項名稱，批次載入明細是合理選擇。Laravel 的 eager loading 可以避免逐張存取關聯造成的 N+1 查詢；但只有數量需求時，[`withCount`](https://laravel.com/framework/docs/13.x/eloquent-relationships#counting-related-models)能取得關聯數量，不需要載入關聯模型。採用 ORM 時應檢視實際 SQL、作用域與執行計畫，而非要求它一定長得像上面的兩次查詢。

單一 SQL 加上相關子查詢也是合理替代方案。它少一次往返，並讓查詢使用同一個讀取快照。是否比批次彙總快，取決於執行計畫及每張訂單的明細量，不能只看 SQL 數目。這裡選兩次查詢，是因為訂單頁的選取與品項統計可以分開驗收，且明細在成立後固定。

若把兩張表直接 JOIN，再對展開後的明細列套 `LIMIT 50`，得到的可能是 50 列明細，不是 50 張訂單。要使用 JOIN，就得確認限制套在訂單頁，而不是讓第一張大訂單占滿結果。

之後若允許成立後增刪明細，兩次查詢的一致性假設就失效。可評估單一查詢，或在同一個短交易中以 REPEATABLE READ 執行一致性讀取。[MySQL 官方說明](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)指出，同一交易的 REPEATABLE READ 一致性讀取共用第一個此類讀取建立的快照；READ COMMITTED 則每次建立新快照。單純包進交易，沒有確認隔離級別，仍可能讀到不同時點。

## 驗證查詢數與資料量

測試資料至少準備一張訂單、滿頁 50 張、空頁，以及單張含大量明細的訂單。對照回傳的 `line_count`，並在測試中記錄這個用例實際發出的 SQL。從 1 張增加到 50 張時，查詢數不應變成 51 次；完整序列化回應後再結束計數，才能抓到 DTO 或 accessor 裡偷偷讀取關聯的情況。

接著加入同租戶其他顧客、其他租戶的資料，確認它們既不出現在列表，也不影響數量。另測第二次查詢失敗、缺少明細，以及兩張訂單品項數不同的情況，避免 map 組回時拿錯資料。

在受控測試資料庫對候選 SQL 執行 [`EXPLAIN ANALYZE`](https://dev.mysql.com/doc/refman/8.4/en/explain.html#explain-analyze)，檢查實際列數、迴圈與耗時。這個指令會執行查詢。壓測時同時記錄 p95、資料庫掃描量、應用記憶體與連線池等待，避免查詢次數減少了，卻在某張大訂單上讀取過量資料。

只有在這些量測仍超出預算時，才評估把 `line_count` 存在訂單列。固定明細的系統可在建立訂單的同一交易寫入數量，但新增了一項需要回填與核對的衍生資料。若允許修改明細，每一條修改路徑也要同步更新數量。列表尚未證明有這個成本需求時，維持即時計算較容易查錯。

## 練習

現在列表新增「商品總件數」，同一張訂單有兩列明細，數量分別為 2 與 3。你會改動哪一段查詢？原本的 `line_count` 是否保留？請寫出回應欄位與一個能抓到混用列數、件數的測試。

## 參考思路

保留 `line_count = 2`，另加語意明確的 `unit_count = 5`。同一批彙總可加入 `SUM(quantity)`，不必逐張再查一次。測試要同時斷言兩個欄位，並涵蓋單列多件商品。數量欄位的合法範圍、空值與退款後是否扣減，須由契約決定，不能靠函式名稱推定。

實作時可以先挑一個既有列表，在完整回應序列化期間記下查詢次數與取得列數，再決定需要明細還是只需要彙總值。
