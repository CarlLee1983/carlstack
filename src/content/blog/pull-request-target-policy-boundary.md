外部貢獻者送來一個 PR，CI 需要跑測試，也想替它加標籤。兩件事都由同一個事件觸發，很容易讓人順手放進同一條工作流程。但測試需要執行對方的程式，標籤機器人需要修改自己的儲存庫；把這兩種需求綁在一起，就容易把外部程式帶進高權限環境。

GitHub 在 [2026 年 11 月 2 日公告](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/)，將公開儲存庫的 `pull_request_target` 預設封鎖從原訂 11 月 2 日延到 **12 月 2 日**。有適用且明確允許此事件的 Actions event policy 可形成例外。私人、internal 儲存庫與 GitHub Enterprise Server 不在這次變更範圍。

多出的一個月，應拿來決定哪些工作真的需要高權限，而不是提前替所有工作流程加上允許。

> [!NOTE]
> 查核時間為 2026 年 11 月 3 日。時程與平台行為依 GitHub 官方公告和文件；下列盤點與驗收方式是工程建議，未在讀者的儲存庫或實際封鎖時段執行，也沒有修改本站 Actions 設定。

## 兩次演練會留下失敗紀錄，不只是警告

正式生效前，GitHub 安排兩次 brownout，暫時執行預設封鎖：

- 11 月 9 日 16:00–18:00 UTC，即臺灣時間 **11 月 10 日 00:00–02:00**。
- 11 月 16 日 16:00–18:00 UTC，即臺灣時間 **11 月 17 日 00:00–02:00**。

依公告，被預設規則擋住的嘗試會產生帶錯誤註記的失敗 run，工作流程不會執行。時段結束回到 evaluate 模式，執行可繼續但會有警告。團隊若只盯「CI 紅了」，容易把政策阻擋當成測試壞掉，值班時直接放寬權限。

我會先把演練時間換成團隊時區，記在維運交接裡。每個受影響工作流程要有負責人，能說明失敗 run 是預期阻擋、真的測試失敗，還是應保留的例外尚未設定。這樣演練產生的訊號才有用途。

## 檢查的是誰的程式，使用的是誰的權限

GitHub 的[事件文件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target)說明，`pull_request_target` 使用基底儲存庫預設分支的執行脈絡；一般 fork PR 的 `pull_request` 則有較受限的 token 與 secrets 存取。前者適合標籤、分類或回覆，不適合直接拿來執行未信任 PR 的建置與測試。

最值得查的組合，是工作流程雖然來自自己的預設分支，卻另外取得 PR head，再執行其中的指令。只看 YAML 是誰提交的，會漏掉實際執行來源。

[官方安全指南](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)進一步區分：checkout 本身不等於執行，後面的建置、測試、依賴安裝與設定載入，才可能讓 PR 控制的內容在高權限環境運作。把事件改名成 `workflow_run`，再下載前一個 run 的產物執行，也沒有消除這個問題。

用一個虛構的 TypeScript 套件專案來看。維護者希望 fork PR 能驗證型別，同時由機器人加上待審標籤。我會拆成兩件可分別失敗的工作：

1. PR 驗證讀取待測程式，在不含正式部署憑證的隔離環境跑檢查。若測試需要公司私有服務，先改成替身或有限測試環境，不能因為測試不方便就借用正式權限。
2. 標籤工作只處理必要的 PR 識別值與狀態，使用有限的寫入權限。它不安裝 PR 的依賴、不執行 PR 附帶腳本，也不把標題直接拼成 shell 指令。

代價是多一條工作流程，以及結果與 PR 的對應邏輯。好處是測試失敗不會逼標籤機器人取得更多權限，機器人故障也不會阻止基本驗證。小型專案若暫時做不到安全拆分，先停用自動標籤、由維護者手動分類，通常比整批開放更容易控制。

## 盤點要追到執行輸入，不只搜尋事件名稱

先列出所有使用 `pull_request_target` 的工作流程。每一筆至少回答四個問題：它要完成什麼、取得哪些外部輸入、會執行哪些內容，以及執行時有哪些權限。

接著沿著工作內容往下查：

- 是否 checkout PR head、merge ref 或 fork repository？是否另用下載指令取得程式？
- 依賴安裝、測試工具與建置設定，是否由 PR 改動？「只跑測試」仍然是執行程式。
- 高權限工作是否讀入低信任工作的產物？若只需要測試結果，能否限制成固定結構、限制大小，並核對 repo、PR 與 commit，而不載入可執行內容？
- 寫入 token、部署憑證與 runner 的內網可見範圍，是否超過這份工作的需要？

最後一題不能被事件政策取代。即使某個 run 已被允許，仍需獨立檢查它能觸及的資源。我會先從不需要 secrets 的工作移除權限，再處理少數真正依賴驗證身分的流程，避免一次改太多後無法定位行為差異。

## 必須保留的例外，應縮到特定工作流程

GitHub 的[政策管理文件](https://docs.github.com/en/actions/how-tos/administer/control-workflow-execution)支援對特定工作流程路徑設定範圍，也提醒政策可能來自 repository、organization 與 enterprise 多層。實際變更前，要先看目前適用的政策與 Insights，不能假設只有儲存庫層的一個開關。

對於確實需要保留的工作，我會要求一張簡短紀錄：允許哪個 workflow、業務用途、輸入來源、必要權限，以及誰負責重新檢查。若只是補標籤，就不要把同一條例外擴張到建置、發版與部署。

可行的替代方案是完全保留預設封鎖，將需要寫入的動作移到可信任的合併後流程。這會讓 PR 階段少一些即時回饋，卻減少例外維護成本。選擇取決於功能是否真的需要在合併前完成，而不是哪種設定最容易讓紅燈變綠。

## 驗收要同時證明該跑的有跑，不該跑的沒跑

我會先在可拋棄的測試儲存庫使用無害固定資料，驗收以下條件，避免拿正式 secrets 來證明隔離：

- 一個普通 fork PR 能得到預期的低權限測試結果；更新 commit 後，結果能對回新 commit。
- 只需中介資料的工作，執行紀錄中沒有讀取或執行 PR 的腳本、依賴或產物。
- 不在允許範圍內的工作確實被政策擋下，而不是跑到一半才失敗。
- 被允許的工作只保留必要動作；若輸入缺欄位、來源不符或產物格式錯誤，會停止而非猜測後繼續。
- 暫時封鎖與正式生效時，負責人能從錯誤註記區分政策拒絕和程式失敗，並知道應停用功能還是修正設定。

這份清單的通過標準，不是所有 workflow 都恢復綠燈。驗收要確認外部 PR 的程式碼驗證與高權限操作已能各自運作，例外沒有把兩者重新接在一起。12 月 2 日到來時，團隊應該只需要核對既定決策，而不是臨時為每一個失敗 run 放行。
