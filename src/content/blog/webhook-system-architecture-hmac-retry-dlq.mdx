在現代 B2B SaaS、金融支付與開放平台生態中，**Webhook** 是實現系統間即時事件驅動整合的事實標準。

然而，構建一個生產級的 Webhook 系統遠比表面上「發送一個 HTTP POST 請求」複雜得多：

- **對端伺服器隨時可能宕機或響應緩慢**，同步發送會讓對端延遲拖住核心交易；
- **惡意中間人可能偽造或篡改請求**，引發嚴重的安全性漏洞；
- **某個租戶的端點崩潰引發海量重試風暴**，可能擠佔資源導致其他正常租戶的 Webhook 嚴重積壓延遲。

下列設計以持久化事件、非同步投遞、驗簽與重試為主。供應商特有的簽名規格另行區分。

## 2. 密碼學安全防禦：HMAC-SHA256 簽名與防重放攻擊

接收方如何確保這個 HTTP POST 請求真的是由你的官方伺服器發出，而非黑客偽造？

### 2.1 簽名生成演算法標準

簽名格式依供應商而異。Stripe 使用 `Stripe-Signature`，其 v1 簽名涵蓋時間戳、句點與原始 body；GitHub 的 `X-Hub-Signature-256` 則是 `sha256=<hex digest>`，以原始 body 計算 HMAC，沒有相同的內建時間戳格式。接收端應使用供應商 SDK 或對應驗證規格，不能混用兩者。

若設計自己的協定，可以定義 `X-Webhook-Signature: t=<unix_seconds>,v1=<hex_digest>`，簽署 `t + "." + RawRequestBody`。時間戳也必須受簽名保護。

1. 驗證原始 body 的 HMAC，使用經審查的 constant-time 比較函式，並處理長度不符。
2. 檢查已驗簽的時間戳是否落在允許範圍，例如前後 300 秒。這限制舊請求的重放時間，仍允許時間窗內的重放。
3. 以已驗證 payload 中的事件 ID 做冪等處理，將處理紀錄與業務更新原子提交。保留期限至少涵蓋供應商的自動重試與允許的人工重送期限。每次合法重試可使用新簽名時間，但同一事件 ID 必須不變。

參考 [Stripe 簽名與重放防護](https://docs.stripe.com/webhooks#preventing-replay-attacks) 與 [GitHub Webhook 驗證](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)。

## 3. 彈性重試機制：帶抖動的指數退避（Exponential Backoff with Full Jitter）

如果對端伺服器因大促銷流量過載而返回 `503 Service Unavailable`，若所有 Worker 同時在固定間隔（如每 5 秒）重新發起請求，可能形成重試尖峰，進一步加重對端負載。

```python
import random

def calculate_backoff(attempt: int, base_delay: int = 10, max_delay: int = 86400) -> float:
    # attempt 從 1 開始，表示第幾次重試
    if attempt < 1:
        raise ValueError("attempt must be >= 1")
    temp_delay = min(max_delay, base_delay * (2 ** (attempt - 1)))
    # 2. 加入 Full Jitter 隨機抖動 (0 到 temp_delay 之間隨機均勻分佈)
    sleep_seconds = random.uniform(0, temp_delay)
    return sleep_seconds
```

- 第 1、2、3、5、10 次重試的等待區間分別為 0–10、0–20、0–40、0–160、0–5,120 秒；這是每次等待時間，並非累積耗時。第 15 次起才達到 86,400 秒（24 小時）的上限。
- 若策略最多重試 10 次，便不會用到 24 小時上限。第 10 次重試仍失敗後，轉入 DLQ 並告警。

## 4. 租戶級隔離與公平性調度（Tenant Rate Limiting & Fair Queuing）

在大規模多租戶環境中，必須防範「吵鬧鄰居（Noisy Neighbor）」問題：

- 某個客戶系統當機，導致累積了 100 萬筆失敗重試；
- **防禦架構**：採用 **公平排隊（Fair Queueing）** 或 Redis 令牌桶。每個租戶分配獨立的發送配額（如每秒最多 100 個請求，另設同時在途請求數上限），超額部分排隊等待，避免單一租戶耗盡 Worker，並量測各租戶的排隊延遲。

## 5. 總結與最佳實踐清單

1. **永遠維持非同步解耦**：核心業務只寫入 Outbox 表或 Kafka，由獨立 Worker 叢集負責網路 I/O。
2. **強制簽名與防重放**：依供應商驗簽，配合可用的重放防護與事件冪等處理。
3. **提供開發者自助工作台**：記錄每筆 Webhook 的 Request Header、Payload、Response Code 與耗時，並提供「手動一鍵重發（Manual Redeliver）」功能，極大降低技術支援成本。
