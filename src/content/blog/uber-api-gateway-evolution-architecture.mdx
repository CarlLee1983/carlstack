Uber 在 2020 年的 [Domain-Oriented Microservice Architecture 專文](https://www.uber.com/blog/microservice-architecture/)（2020-07-23）提到，公司當時約有 2,200 個關鍵微服務。手機 App 要怎麼存取這些服務，是 API 閘道要回答的問題。

Uber 自己把閘道的演進分成三代，寫在 [Designing Edge Gateway, Uber's API Lifecycle Management Platform](https://www.uber.com/blog/gatewayuberapi/)（2020-08-18，以下稱 Edge Gateway 專文）。閘道的內部構造則另外寫在 [The Architecture of Uber's API gateway](https://www.uber.com/blog/architecture-api-gateway/)（2021-05-19，以下稱閘道架構文）。下面依這兩篇整理，引用其他文章時會另外標明。

## 第 1 代（2014）：dispatch 與 api 自然長出來的架構

Edge Gateway 專文說，如果在 2014 年盤點 Uber 的架構，會看到兩個關鍵服務：`dispatch` 負責媒合乘客與司機，`api` 負責使用者與行程的長期儲存。此外還有個位數的微服務，支撐消費者 App 的關鍵流程。乘客端和司機端 App 都透過單一端點連到 dispatch，需要 api 的請求再用一種特殊的 `ApiCommand` 訊息代理過去。

專文說，從 API 閘道的角度看，`ApiCommand` 看起來就像進入 Uber 的閘道。這一代被稱為 “the organic evolution”：單一的單體服務開始服務真實使用者，再靠增加微服務找到擴展的方式。

---

## 第 2 代（2015 年初起）：集中式 Node.js RTAPI

第二代的閘道叫 **RTAPI**（Real Time-API），2015 年初從單一 RESTful API 起步，專文稱它 “arguably the first true gateway”（可說是第一個真正的閘道）。它後來成為 Uber 最大的 Node.js 應用程式之一。專文列出它的目標：解耦、協定轉換、橫切面能力、串流酬載、減少來回次數，以及替前端提供 BFF（Backend for the Frontend）。

橫切面能力包括身分驗證、監控（延遲、錯誤、酬載大小）、資料驗證、資安稽核紀錄、資料中心黏著（datacenter stickiness）、CORS、在地化、快取、限流、負載卸除與欄位遮蔽。

專文給的規模數字：

- 尖峰流量約每秒 800,000 個請求。
- 約 1,600 支複雜 API，單一 binary 跑不下，因此部署成 40 多個獨立服務。
- 呼叫約 400 多個下游服務，分屬 100 多個團隊。
- 約 1,500 名工程師在這個 monorepo 裡寫程式。
- 手機 build 裡約 20% 的程式碼，是從 RTAPI 這一層定義的 schema 生成的。

### RTAPI 遇到的問題

專文自己列出的問題有這幾類：

1. **動態語言**：隨著時間，動態語言帶來的困難愈來愈多。重複出現的 NPE（null pointer exception）曾讓關鍵的閘道部署卡住好幾天，直到修好為止。
2. **monorepo 與相依套件**：1,500 名工程師共用一塊自由寫程式的空間。把 2,500 個 npm 套件升級到新版 Node.js，花的力氣愈來愈大。
3. **業務邏輯滲進閘道**：「減少來回次數」和「BFF」這兩個目標，讓大量業務邏輯流進閘道。閘道程式碼的複雜度也不再只是 I/O bound，少數幾支 API 的效能退化就可能拖慢整個閘道。
4. **閘道團隊成為瓶頸**：閘道團隊變成 Uber 產品開發的瓶頸。當時的緩解作法是依 API 分片部署（sharded deployments），以及把程式碼審查分散出去。

## 第 3 代（2018 年起）：自助、去中心化、分層的 Edge Gateway

專文說，到了 2018 年初，Uber 已經有全新的業務線和許多新的 App，其他部門也轉向以 Go 和 Java 為主要支援語言。第三代的方向是 “self-service, decentralized, and layered”。從第二代開發與遷移到第三代，前後花了兩年；各團隊在 2019 年指派了帶領遷移的工程與專案負責人。

第三代把原本塞在閘道裡的職責拆成四層：

- **Edge layer**：閘道本體。負責第二代目標裡除了 BFF 和「減少來回次數」以外的所有功能，不再放客製的業務或畫面程式碼。
- **Presentation layer**：專門標記為替前端提供 BFF 的微服務，各 App 的畫面產生與資料聚合放在這裡。
- **Product layer**：描述產品或功能、可重用的 API。
- **Domain layer**：位在最末端、各自提供單一功能的微服務。

閘道本身成為一個獨立的 Go 服務，搭配一個 UI。Uber 的工程師都能在 UI 上設定、建立和修改對外的 API。專文說，改用 Go 之後，資源使用率和每核心處理的請求數都明顯改善。

presentation layer 的聚合程式仍然是工程師寫的。專文也提到 Uber 內部用 Go 做了 Control Flow Framework（CFF），讓工程師編排服務之間的呼叫流程。

### 閘道怎麼設定：Thrift IDL、YAML 與 Zanzibar

閘道架構文（2021）說明了第三代閘道的內部。開發閘道時，Uber 可選的語言是 Go 和 Java，最後採用程式碼生成的方式產出可執行的 build artifact，生成機制包成開源函式庫 [Zanzibar](https://github.com/uber/zanzibar)。

API 的合約寫在 Thrift IDL 裡，HTTP 協定的細節用 Thrift 的 annotation 標註。各元件的設定放在 Thrift 和／或 YAML 檔，YAML 負責把元件串起來。下面是 Zanzibar repo 範例裡的一段 endpoint 定義（取自 `examples/example-gateway/idl/endpoints-idl/endpoints/multi/multi.thrift`）：

```thrift
service ServiceAFront {
    string hello (
    ) (
        zanzibar.http.method = "GET"
        zanzibar.http.path = "/multi/serviceA_f/hello"
        zanzibar.http.status = "200"
    )
}
```

工程師平常不直接改這些檔案。閘道架構文說，所有和閘道系統的互動都透過 UI：工程師在 UI 上設定 API 參數、發布 API，UI 也會對 API 的各個面向做檢查。

閘道架構文提到的幾項能力：

- **驗證與授權**：每個外部 API 請求都會經過 AuthN 和／或 AuthZ。
- **限流**：endpoint 的擁有者可以選擇替 API 限流，每個 endpoint 的配額能動態調整，不必重新部署。
- **協定轉換**：protocol manager 能接收 JSON、Thrift 或 Protobuf 酬載，例如收 JSON 請求、回 Protobuf 編碼的回應。文中也承認這項功能帶來了複雜的相容性問題。
- **手機端程式碼生成**：一個 CI job 從閘道取得所有 endpoint 的 IDL，再用自訂的程式碼生成產出各種 model。

第三代也有代價。Edge Gateway 專文說，UI 適合對既有 API 做小幅修改，新建 API 就比較吃力；對工程師來說，UI 有時候比直接改 checkout 下來的程式碼慢。

### Envoy 與 gRPC：2021 年還在開發中

Envoy 在閘道架構文裡出現兩次。一次是拿 Kong、Tyk 與 Envoy、Nginx 這類反向代理和自家閘道做比較；另一次是展望：2021 年時，Uber 正在開發一種處理 App 到後端 gRPC 請求的閘道執行期，以 Envoy 為基礎，而且自助 UI 的使用體驗不會有明顯改變。這篇文章沒有說這個 gRPC 版本後來是否上線。

## 延遲感知的自適應併發限制：做在服務端的 Cinnamon

Uber 確實有依延遲調整併發上限的機制，但它在服務端。[Cinnamon Auto-tuner 專文](https://www.uber.com/blog/cinnamon-auto-tuner-adaptive-concurrency-in-the-wild/)（2023-12-07）介紹的是 Cinnamon load shedder 裡的 Auto-tuner：它把觀測到的請求處理延遲和參考延遲比較，持續估算 inflight 上限，作法改自 TCP-Vegas 演算法。文中說目標是部署到數千個微服務。上面兩篇閘道文章都沒有把這套機制寫成閘道的功能。

## 我讀完的幾個心得

以下是我的解讀，不是 Uber 的說法。

1. **閘道收斂成一個服務，業務邏輯則往外推**：第三代保留了第二代幾乎所有的橫切面能力，只把 BFF 和「減少來回次數」移出閘道。集中與去中心化在同一代裡並存，分界線是「通用能力」和「業務邏輯」。
2. **IDL 是閘道和手機端共用的合約**：同一份 Thrift IDL 既用來生成閘道的 Go 程式碼，也用來生成手機端的 model。合約只寫一次，兩端從同一個來源產生。
3. **程式碼生成省下的是轉發和 model，聚合邏輯還是要人寫**：Zanzibar 生成閘道程式碼，presentation layer 的聚合則靠工程師用 CFF 編排。
4. **限流分兩層**：閘道上有依 endpoint 設定的限流與負載卸除，服務端另有 Cinnamon 依延遲調整併發上限。
