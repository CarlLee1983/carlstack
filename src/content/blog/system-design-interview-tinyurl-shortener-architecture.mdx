短網址服務將長 URL 映射為較短的識別碼，讀取時再回傳重新導向。

這個題目看似簡單（將一個長 URL `https://example.com/very/long/path?id=123` 縮短為 `https://tiny.url/aB3x9Z`），但背後卻涵蓋了：

- **容量估算與數學建模**；
- **字串編碼（Base62）與哈希碰撞（Hash Collisions）解法**；
- **HTTP 重新導向狀態碼（301 vs. 302）的業務權衡**；
- **高併發讀取快取與防穿透防禦**。

以下以每月新增 1 億筆為容量假設，分別評估編碼空間、唯一性與重新導向快取。

---

## 1. 需求分析與容量估算（Math Modeling）

### 1.1 功能與非功能性需求

- **核心功能**：
  1. 輸入原始長網址，生成一個全域唯一的 7 字元短網址。
  2. 點擊短網址，毫秒級重新導向至原始長網址。
  3. 支援自定義短網址別名（Custom Alias）與到期時間（TTL）。
- **非功能性需求**：
  - 目標示例：可用性 99.99%、服務端讀取延遲 `< 10ms`；需另定量測區域與分位數。
  - 短網址不能被輕易猜測遍歷（安全防爬蟲）。

### 1.2 容量估算

- **寫入 QPS**：假設每月新增 1 億（100M）個短網址：
  `寫入 QPS = 100,000,000 / (30 * 24 * 3600) ≈ 40 QPS`
- **讀取 QPS（讀寫比 100:1）**：
  `讀取 QPS = 40 * 100 = 4,000 QPS (峰值 10,000+ QPS)`
- **10 年總資料量與字元長度計算**：
  - 10 年累積短網址數：`100M * 12 * 10 = 120 億 (12 Billion)`。
  - 短網址字元集採用 `[0-9], [a-z], [A-Z]` 共 62 個字元（Base62）。
  - 設短網址長度為 `L`：
    - `62^6 ≈ 568 億`（6 位數已足夠，但 7 位數可提供 `62^7 ≈ 3.5 兆` 種不重複組合，增加容量餘裕；安全性仍取決於生成方式與存取控制）。
    - 6 字元已能容納這個數量；以下選 7 字元（例如 `aB3x9Z1`）作為容量餘裕，並將發號範圍限制為 `0 ≤ ID < 62^7`。

### 2.1 兩種方案的唯一性與容量限制

- **雜湊或隨機短碼**：將輸出映射至 Base62 空間，靠資料庫唯一約束原子插入，衝突時重試。不能把十六進位雜湊的前 7 個字元當成 7 字元 Base62；兩者容量不同。
- **唯一 ID + Base62**：進位轉換是一對一映射，但前提是 ID 本身唯一且未截斷。固定 7 字元只容納 `0` 到 `62^7 - 1 = 3,521,614,606,207`；任意 unsigned 64-bit ID 最多要 11 字元。Snowflake 類 ID 的跨節點順序不等於嚴格全域單調，還要處理時鐘回退與 worker ID 衝突。
- 遞增 ID 轉成 Base62 後仍可枚舉。增加一個字元不能代替授權；私人資源需獨立存取控制，公開短網址則要評估隨機生成、限速與濫用偵測。

## 3. HTTP 重新導向狀態碼深度抉擇：301 vs. 302 / 307

當使用者訪問 `https://tiny.url/aB3x9Z1` 時，伺服器應返回哪種 HTTP 狀態碼？

- **301** 表示永久重新導向，允許啟發式快取；不代表永久存於每個瀏覽器。`Cache-Control` 等標頭仍影響快取行為。
- **302 / 307** 表示暫時重新導向，設定明確的快取期限時仍可被快取。307 保留原始方法與 body；302 在部分情況可將 POST 改為 GET。
- 若每次點擊都要進入服務端計數，可對重新導向回應使用 `Cache-Control: no-store`，並確認 CDN 不覆寫策略。若允許 CDN 快取，就要從邊緣收集點擊紀錄，不能只算回源請求；阻擋器、機器人與重試也會影響統計。

以下圖解採可快取的 302 路徑：CDN 命中時在邊緣記錄事件，未命中才回源。快取期限須配合短網址到期、撤銷與失效機制。HTTP 語義與快取規則可查 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) 與 [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html)。

### 4.1 資料庫選型（NoSQL vs. SQL）

短網址資料模型非常單純（只需儲存 `short_key -> long_url, user_id, created_at, expire_at`），且不需要複雜的跨表 `JOIN`。

- 首選 **分散式 NoSQL KV 資料庫（如 AWS DynamoDB 或 MongoDB）**，以 `short_key` 作為 Partition Key，天然具備水平擴展與自動分片能力。
