「AI 已經能自己寫 Code、修 Bug、跑測試，工程師還需要學系統架構嗎？」

這次讀到的一張迷因把兩條曲線畫得很直白：普通開發者的知識慢慢增加，Vibe Developer 的自信先衝高，進入 production 和 debug 後又急速跌落。這張圖適合當提醒，不適合當數據。它沒有定義「普通」或「自信」，也沒有證明每個使用 AI 的人都會走同一條曲線。

但它抓到一個值得工程師處理的問題：程式碼產出變快，不代表系統理解、驗證與營運也變快。

## 速度感和證據是兩件事

GitKraken 在 2026 年 8 月 20 日發布的 [調查文章](https://gitkraken.com/blog/everyone-feels-faster-almost-nobody-can-prove-it) 訪問 554 位開發者與工程主管。84% 的受訪者認為 AI 讓自己更有生產力，但 39% 的組織沒有方法衡量 AI 的影響，另有 33% 主要依賴開發者自述。這是工具廠商發布的調查樣本，不能推論所有團隊，也不能把「感覺更快」解讀成因果證明。

我的做法是先替一種重複任務記錄從開始到通過驗收的時間，包含人工審查與返工。不要只計算 Agent 產生 diff 的時間；上線後若需回退，也要算進交付成本。這是本文的衡量建議，不是調查已證明的改善方案。

## 除錯前，先對齊 Agent 缺少的脈絡

2026 年 8 月 19 日線上發表的 [Reliable Vibe Coding](https://journals.sagepub.com/doi/10.3233/FAIA260505) 研究，分析一名開發者使用 Claude Code 建置與除錯系統時的 163 個互動片段。作者提出 human-AI context gap、非同步學習、信任侵蝕與錯誤擴張四個主題，並在這個案例中描述一個迴圈：背景脈絡沒有補齊，Agent 產生局部合理但整體錯置的修改；錯誤增加後，人類得花更多時間解釋、監控與除錯，脈絡差距又變大。

這篇是單一開發者、單一系統的質性研究，互動紀錄來自 2025 年至 2026 年初，並非 8 月才進行的實驗。因此它不能估算失敗率，卻能幫我們看見失敗怎麼累積。把「需求、架構決策、不可變條件、驗收方式」寫進 repository 的文件與測試，目的不是讓 Agent 變聰明，而是縮小每一輪對話中必須猜測的範圍。

## 生成程式與理解語意，要分開驗證

Nature 旗下 Communications AI & Computing 在 2026 年 8 月 13 日刊出的 [SemBench 研究](https://www.nature.com/articles/s44488-026-00014-y) 評估 LLM 對程式靜態語意的理解。研究報告指出，模型在程式碼生成上的表現，可能比對基礎語意屬性的理解進步更快；其中一項弱點是判斷變數的值在後續程式中是否仍可能被使用。研究使用 1,000 個 C 程式檔案建立題目，這是受限的 benchmark，不等於真實 repository 或所有模型。

我據此調整驗收方式：`build`、單元測試與 lint 都綠，不足以證明 Agent 理解了資料生命週期、跨模組不變條件或故障時序。例如修改 CSV 匯入器，成功讀入一個正常檔案只驗證了一條路徑。空檔案、缺欄位，以及處理到一半失敗時是否留下半成品，都要由需求決定預期行為，再用對應案例驗證。SemBench 本身沒有測試這個匯入情境；這是本文的應用示例。

本文最初從 [Andrew Ng 的 Software Engineering Fundamentals 貼文](https://x.com/andrewyng/status/2093388974194872781) 出發；[作者官網](https://www.andrewng.org/writing) 將同題文章列於 2026 年 8 月 28 日。本次更新以以上三份可讀取的一手資料補充，將「基本功很重要」落到具體驗收。

## 把 Agent 放進一個可驗證的工作流

我會用下面四個問題審查一次 Agent 產生的變更：

| 審查問題                     | 可留下的證據                       |
| ---------------------------- | ---------------------------------- |
| 哪些行為必須維持、哪些要改？ | 變更前後的規格或測試               |
| 它依賴了哪些脈絡？           | ADR、資料流、錯誤處理說明          |
| 測試沒有覆蓋什麼？           | 明列未測的外部服務、併發與資料案例 |
| 出錯時怎麼知道該停？         | log、metric、trace、告警與回退程序 |

**說不清預期行為或驗收方式，就先停止擴大修改。** 四題有一題答不出來，先縮小範圍或補齊條件，再讓 Agent 繼續；不適用的項目則寫明原因。這是本文建議的停止規則，讓下一步取決於可檢查的證據。

## 下一步：量測一個小變更

挑一個低風險、可回退的 issue，先記錄人工完成它需要的時間、審查輪數、測試結果與回退方式，再讓 Agent 完成同一類工作。比較交付結果與維運成本，而不是只比較產生 diff 的速度。

先拿下一個 issue 寫下這四題的答案，再開始產生程式碼。
