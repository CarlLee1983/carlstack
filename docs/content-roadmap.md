# CarlStack 內容擴充規劃

本文件記錄內容方向與交付順序；實際待寫文章只列在 [`article-queue.md`](article-queue.md)，文章規格依 [`content-guide.md`](content-guide.md)。開始撰寫前，仍須重新查重並確認專案現況。本規劃不代表任何文章或網站功能已完成。

## 現況與判斷依據

2026-10-05 盤點時，`src/content/blog` 有 243 篇正式文章、4 篇草稿，`src/content/projects` 有 8 個專案；正式文章已形成 13 個系列。網站已有文章、系列、標籤、搜尋與專案入口。專案目前集中在 `/projects/` 的卡片詳情，介紹多為一段文字，沒有各自可分享的本站詳情網址。

內容優勢是系統設計與 AI 工程的廣度，以及作者自己的開源工具。接下來優先補讀者能核對與使用的材料：專案的實際取捨、可重現的輸入與結果、跨文章的閱讀順序。選題不以增加篇數為目標，而以讀者讀完能做出什麼判斷為準。

去重結果：dbcli 已有〈[把資料庫接給 AI Agent 之前](/blog/agent-database-authorization-boundary/)〉，涵蓋授權詞彙、執行路徑、黑名單實測與限制；不再安排同論點的新文章。AgentPort 也已有[架構實戰文](/blog/agentport-remote-coding-runtime-gateway/)。Feature Store 已寫成[可重現案例](/blog/feature-store-point-in-time-training-serving/)；全球多活及 Raft／Multi-Paxos 仍列在文章佇列，不在此另建待辦清單。

## 優先交付順序

### 1. 補強專案介紹與既有文章的連結

先更新 `dbcli` 與 `loop-apidoc` 的專案內容。每份介紹應讓讀者快速找到：適用情境、最短可操作例子、主要設計邊界、驗證依據、目前限制、原始 repository 與相關本站文章。內容必須以各專案目前可查的文件或成果為準，不填寫未驗證的效能或使用數字。

- dbcli：連到既有授權與實測文章，補一個能安全展示工作流程的範例；不重寫同一篇案例。
- loop-apidoc：展示一份輸入來源如何對應到 OpenAPI、provenance 與驗證報告；若真實材料不可公開，使用明確標示的示例資料。
- 驗收：讀者能判斷工具是否適合自己的情境、從哪裡開始，以及哪些結果仍須自行驗證。

先以現有專案卡詳情承載精簡內容。若完整範例使詳情難以閱讀，再單獨評估專案詳情網址與頁面設計；新增路由時依 [`architecture.md`](architecture.md) 檢查 URL 與內容存取邊界。

### 2. 撰寫 loop-apidoc 專案實戰文

以「來源沒有提供的 API 事實，文件產生器應如何保留未知」為主問題。用一份可公開的輸入，展示來源片段、結構化輸出、查核報告，以及一個必須交還人工判斷的缺口。與專案介紹分工：介紹負責用途與入口，文章負責決策、失敗情境和證據鏈。

驗收：讀者可以沿範例追到每個關鍵欄位的來源，並分辨已驗證、推論與未知內容。正式選題與排程見 [`article-queue.md`](article-queue.md)。

### 3. 完成 Feature Store 可重現案例

把既有候選題聚焦在訓練資料與線上推理的一致性：以小型資料集展示時間點錯誤如何讓訓練看見未來資料，再說明離線取值、線上取值與延遲的取捨。避免只列平台元件或工具功能。

驗收：讀者可依資料與步驟重現錯誤及修正後的差異；外部系統能力與版本須以一手文件查核。這是佇列既有題目的具體切角，不新增重複項目。

### 4. 做一次備份還原演練並記錄結果

以一個明確的工作負載，記錄備份、還原、資料完整性檢查、服務恢復與回切。先定義目標 RTO／RPO，再記錄實際耗時與可確認的資料狀態；若只能做隔離環境演練，不把結果稱為正式環境保證。

驗收：讀者能照步驟檢查「備份存在」之外，資料是否可讀、服務是否可用、恢復是否達到預先設定的目標。須與既有故障診斷、資料庫複製及部署文章互連，避免重述原理。

### 5. 編排一條跨系列閱讀路徑

先用已發布文章試做「從一筆支付請求走到對帳」：每一步寫一個要回答的問題、對應文章、讀完可做的決策，以及尚未覆蓋的缺口。確認內容順序有幫助後，再考慮「Agent 工作流上線前」與「資料庫擴容與復原」。

驗收：讀者不需理解站內標籤和系列分類，也能沿路徑走完一個工作情境。先以現有內容形式試做；只有在閱讀路徑確實需要獨立入口時才增加網站功能。

## 後續可試的內容形式

- **可重用材料**：從已完成的文章提取測試資料、設定範例、驗收清單或決策紀錄範本。可執行材料保存在對應專案 repository，由文章連回，避免兩份內容分叉。
- **專案演進紀錄**：選一次有來源可查的設計修正，交代原決定、失敗訊號、修正和仍存在的限制；不要手動複製 release notes。
- **作者方法**：在 `/about/` 補上實際選題、查證與更新舊文的做法。只描述現行可佐證的工作方式，不新增無憑據的經歷或成效。

以上內容先以一份代表作試行，再決定是否擴張成系列或新 collection。

## 執行與驗收原則

1. 撰寫前搜尋 `src/content/blog`、`src/content/projects`、`docs/research` 與文章佇列；同一來源或同一讀者收穫優先更新舊文。
2. 每項交付先寫明讀者問題、可公開的證據與具體完成條件；缺少實測材料時保留未驗證狀態，不補造數字。
3. 文章、專案與範例互相連結，但各自只有一個維護來源。文章發布遵循內容指南與 repository gate；新頁面或 schema 變更另按架構邊界評估。
4. 每完成一項，檢查讀者是否能依材料重做關鍵步驟，或解釋方案何時適用、何時應停下。若做不到，先補證據與說明，再擴大題目。
