## 可辨識的中心主張

分享卡標題為「70GB 模型跑在 48GB Mac 上：Qwen3.8-Flash-Next 部署實錄」，並列出作者的配置：MacBook Pro／Apple M4 Pro／48GB 統一記憶體、`Qwen3.8-Flash-Next REAP-288 MLX 4-bit`、oMLX 0.6.4，以及 PLE 表以 mmap/NVMe 串流讀取。能安全寫成：**這是一個特定量化、裁剪與磁碟 offload 配置的個人部署主張，不是原始 Qwen 模型可直接完整載入 48GB 的主張。**

## 一手資料核對

- **Qwen3.8-Flash-Next 確有大型外部 N-gram embedding 表可搬移。** Qwen 團隊說明模型含 125B 主模型與額外 51B N-gram embeddings，且該表可 offload 到 host memory 並以非同步 prefetch 與運算重疊；官方亦列出 Apple Silicon 的 MLX 支援。這支持「記憶體需求可因表的放置而變動」，不代表任意 Mac 都能流暢執行。[Qwen 官方 repository](https://github.com/QwenLM/Qwen3.8-Flash-Next)
- **此處的「70GB」主要是特定 REAP-288 4-bit build 的磁碟大小，不是常駐 RAM。** 該 build 的發布者記錄磁碟 68GB、NVMe N-gram 模式下約 39GB resident memory；它是將每層專家由 512 裁到 288 的衍生 checkpoint，而非原始權重。[REAP-288 model card](https://huggingface.co/sh0wie/Qwen3.8-Flash-Next-REAP-288-MLX-4bit)
- **SSD mmap 是 runtime 支援的方向，但不能等同完整 48GB 實測的獨立驗證。** oMLX 0.6.3 release 說明其可讓大型 N-gram PLE 表保持常駐或採 SSD mmap；REAP-288 作者另稱其 39GB 模式使用的 row-granular disk-read patch 已合併至 mlx-vlm `main`，但尚待正式 release。兩者支持機制存在，卻不證明貼文的 oMLX 0.6.4、M4 Pro、context length 或長時間穩定性。[oMLX 0.6.3 release notes](https://sourceforge.net/projects/omlx.mirror/files/v0.6.3/)、[REAP-288 model card](https://huggingface.co/sh0wie/Qwen3.8-Flash-Next-REAP-288-MLX-4bit)
- **48GB 不是可忽略的安全餘裕。** 以 model card 自報的約 39GB resident 值推算，只剩約 9GB 給 macOS、KV cache、prompt prefill、其他程式與記憶體波動；這是依來源數字所作的推論，不能寫成長 context、多併發或無 swap 的保證。
- **品質／速度僅有 build 作者的有限證據。** model card 報告同機器 164 題 HumanEval、單次每 build 的比較，並明說多模態權重雖保留、但只有文字品質被評估；其列出的約 28 tok/s 是 128GB M4 Max，不是本貼文的 48GB M4 Pro。不可移植成 M4 Pro 的速度、品質或 agent 成效數字。[REAP-288 model card](https://huggingface.co/sh0wie/Qwen3.8-Flash-Next-REAP-288-MLX-4bit)
