## 原文主張與採用邊界

Thariq 將 effort 描述為模型可投入多少計算工作的近似控制，並以不同 effort 下的 build 任務和 Terminal-Bench 3.0 執行說明：較高 effort 可能帶來更多自行判斷、驗證與邊界測試；一般功能開發可先用低或中等 effort 快速迭代，再提高 effort 做測試與驗證。

可作為作者本人觀察引用的例子：

- Fable 5.1 在 html-js-filter 從 low 的 1/5 次通過，升到 xhigh 的 5/5。
- Opus 5.5 在 mvcc-lsm-compaction 從 low 的 0/5 次通過，升到 xhigh 的 4/5。
- 追蹤到的高 effort sanitizer 執行包括對抗式 review、閱讀 parser 原始碼、重複性測試、既有 XSS 測試集與隨機文件 fuzzing。
- 作者指出較高 effort 有助減少漏掉邊界案例的失敗，但無法修正模型採錯方法或誤解 domain rule。

作者註明每項任務各跑五次；Fable 5.1 的生產安全介入在該組內部測試中關閉，安全任務不連網，錯誤分類部分由 model judge 判定。原始文章沒有公開每次執行資料或完整 verifier，研究時無法獨立重跑。因此數字只用來說明可能出現的行為，不推論為一般成功率或因果效果。

Terminal-Bench 的官方 release 頁已列出 v4.0.0；本文來源分析的是較早的 v3.0。若要比較模型或 effort，應固定資料集版本、模型、工具、網路及 verifier，不能把不同版本或內部 runs 當成同一 leaderboard。來源：[Terminal-Bench v3.0.0](https://github.com/harbor-framework/terminal-bench/releases/tag/v3.0.0)、[release history](https://github.com/harbor-framework/terminal-bench/releases)、[v4.0.0](https://github.com/harbor-framework/terminal-bench/releases/tag/v4.0.0)。

## Claude 官方文件核對

- [Claude Code model configuration：effort](https://code.claude.com/docs/en/model-config#adjust-effort-level)說明 effort 控制 adaptive reasoning；較低層級較快、較省 token，較高層級提供較深推理。可用層級依模型而異，且各模型分別校準；官方提醒 max 可能有遞減收益並造成 overthinking。
- [Claude Code 命令參考：/effort](https://code.claude.com/docs/en/commands#all-commands)說明可用 /effort LEVEL、/effort auto 或互動選擇層級；模型、CLI 版本與組織限制會影響可用選項。max 通常只限當前 session。
- [Anthropic API effort 文件](https://platform.claude.com/docs/en/build-with-claude/effort#change-effort-mid-conversation)說明部分模型可用 per-message effort 設定在對話中切換並維持 prompt cache；一般 top-level effort 在不同 request 間改動可能改變快取前綴。此行為有模型與 API 功能限制，不應概括為每一種 Claude Code/API 工作方式都不影響快取。
- [Claude Code prompt caching 文件](https://code.claude.com/docs/en/model-config#prompt-caching-configuration)說明 Claude Code 會使用 prompt caching，並列出停用設定。它不單獨證明任意 effort 切換都會保留 cache。

## 寫作判斷

文章把 effort 定位為「驗證預算」與人類參與程度的選擇，不是答案正確率保證。規格模糊時先追問並固定 acceptance criteria；人會快速 review 的例行實作可從 low/medium 開始；隱藏邊界多、漏測代價高時才升到 high；max 只用在更高自治確實節省交接成本、而且已有預算與停止條件的任務。

成本回歸需固定任務輸入、工具版本與驗收條件，重複執行並同看通過率、失敗類型、thinking/input/output token、wall-clock time、工具次數與人工 review 時間。不可只以單次成功或 token 下降判定最佳設定。
