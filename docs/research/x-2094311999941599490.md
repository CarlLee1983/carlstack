## 原文主張

貼文把 AI agent 說明為由 harness 驅動的迴圈：`Context → Reason → Act → Observe → Update → Repeat`。模型是推理核心；context、state 與 memory 提供資訊；tools 讓模型能產生外部效果；harness 負責組裝 context、執行工具、回填結果、更新 state 與控制迴圈。

這些是作者的教學性框架，不應延伸為下列強宣稱：

- context、state、memory 的命名與邊界不是跨框架的唯一標準；不同 SDK 對 state、memory 與 conversation history 的切分不同。
- 「三個 levels」是 Oracle 的架構分類，不是所有 production agents 必經的成熟度模型。
- 模型停止發出 tool call 不足以證明任務完成；是否完成仍是由系統的終止與驗證條件判定。

## 一手資料核對

- **Agent loop 是 harness 在單次 run 內反覆組裝 context、推理、行動並檢查停止條件的執行模式（高確定性）。** Oracle 將此描述為 agent loop，並列出目標完成檢查、最大迭代、timeout、不可恢復錯誤與重複動作偵測等停止條件。[Oracle：The Agent Loop Decoded](https://blogs.oracle.com/developers/the-agent-loop-decoded-three-levels-every-agent-engineer-must-know)
- **模型與 harness 是可區分的層次（高確定性）。** Oracle 將 model 定義為推理引擎，harness 則負責準備 context、執行工具、施加操作限制與持久化 state；這支持「模型不是完整 agent」的解釋，但不是性能比較。[同上](https://blogs.oracle.com/developers/the-agent-loop-decoded-three-levels-every-agent-engineer-must-know)
- **記憶需要選取與生命週期管理（高確定性）。** Oracle 將 memory-aware agent 描述為主動 encode、store、retrieve、inject 與 forget；資訊被保存不代表應無條件注入下一輪 context。[同上](https://blogs.oracle.com/developers/the-agent-loop-decoded-three-levels-every-agent-engineer-must-know)
- **停止工具呼叫不是完成驗收（高確定性）。** Oracle 明確區分 terminal message 與使用者目標滿足，指出 harness 必須另行檢查目標是否完成。[同上](https://blogs.oracle.com/developers/the-agent-loop-decoded-three-levels-every-agent-engineer-must-know)
