## 原文主張與範圍

作者以自己的產品經理工作為例，將流程拆成調研與競品、網站／圖片轉原型、PRD、跨角色預審、埋點規格與問卷，最後把產出做成可分享站點。文中使用的開源專案是 [SpaceZephyr/pm-skills](https://github.com/SpaceZephyr/pm-skills)，並把它描述為「21 個 Skill」的產品工作流工具箱；它包含 `pm-master`、`pm-url2proto`、`pm-image2proto`、`pm-prd-writer`、`pm-review-board` 與 `pm-tracking-spec-writer` 等項目。

這是作者的操作展示，不是任何產品的效能測試或品質保證。下列數字只屬這一次 demo，不能外推為所有需求：預審找出 3 個阻斷項與 7 個問題；產出 15 個埋點事件、欄位字典、QA 清單與驗收 SQL。

## 一手資料核對

- **工具包確實列出 21 個 Skill（高確定性）。** 專案 README 將 14 個執行型工具與 7 個顧問型 Skill 列為 21 個，並定義各 Skill 的輸入／輸出用途。[SpaceZephyr/pm-skills README](https://github.com/SpaceZephyr/pm-skills)
- **Skill 不是模型能力或品質證明（高確定性）。** OpenAI 的官方文件將 Skill 描述為一組可重用工作流指令與資源，需由宿主依適用性載入；它能提供程序，不會取代可執行的驗收。[OpenAI：Build skills](https://learn.chatgpt.com/docs/build-skills)
- **Codex 的可驗證證據仍由檢查與人工 review 提供（高確定性）。** OpenAI 說 Codex 可運行測試、輸出 terminal logs 與 test results，並明確要求使用者在整合／執行前人工 review 與驗證產物。[OpenAI：Introducing Codex](https://openai.com/index/introducing-codex/)
- **原型與網頁發布是不同 gate（高確定性）。** OpenAI 的 Sites 文件區分本地 preview、production build 與 hosting；可看見的原型不是部署成功、權限正確或需求已批准的證據。[OpenAI：Sites](https://learn.chatgpt.com/docs/sites)

## 寫作角度與限制

站內已有〈[25 個 AI Skills 真的能跨 Claude、ChatGPT 與 Gemini 使用嗎？](../../src/content/blog/ai-productivity-skills-portability.md)〉，所以新文不重述 Skill 規格或跨平台性。角度應窄化為：把「調研 → 原型 → PRD → 預審 → 埋點 → 發布」看成 artifact pipeline；每一段輸入、輸出與 gate 都要清楚，AI 產生的跨角色 review 只能做提早找問題的候選清單，不能替代決策、實際資料、隱私／安全 review 或正式批准。

最小工作流：先只以一項需求和一組可檢驗的產出跑完整鏈路；每個 artifact 都保留來源、責任人、驗收條件及停止原因。只有在 handoff 已重複而且品質穩定時，再把步驟拆成更多 Skill 或 Agent。
