## 原貼文與可讀討論

原貼文主張：若團隊多數成員無法維持工程判斷與責任感，AI 在短時間內把大量品質不佳的程式寫進共用程式庫，會擴大所有人的風險；微服務切分可提供業務隔離。[原貼文](https://x.com/d3ad13eef/status/2103137019291717887)

討論中主要有以下幾組看法：

- **流程與審查派：** 認為應以 code review、pipeline、程式碼 owner、PR 範圍限制和文件補足 AI 工具缺少的脈絡；結構調整無法取代責任歸屬。
- **作者的反例：** 作者表示團隊已使用 pipeline 和較便宜的 AI 程式碼掃描，但約千行 MR 可能在局部看似合理，整體架構仍有問題。[作者後續貼文](https://x.com/d3ad13eef/status/2103332439611605065)
- **大型 PR 討論：** 有人分享超過 300 行 MR 預設退回、經理可例外的本地規則，也指出微服務並不能阻止低品質的人類或 AI 審查被核准。[相關回覆](https://x.com/Super530F/status/2103483027284525549)
- **架構切分派：** 有人認為 AI 讓跨模組串接成本降低，因此單體的整體變更更難審查；也有人指出單體可以靠模組邊界治理，不必把每個模組部署成服務。另有回覆提出單一 monorepo 配合子專案拆分、由核心維護者負責關鍵模組、以及關鍵和非關鍵模組採不同 ownership。
- **風險外擴提醒：** 部分回覆指出 AI 和微服務都可能放大原先的流程缺陷，應把故障隔離與程式碼可讀性／可維護性分開討論；另有回覆反映 AI 降低跨模組接線的成本，但缺少領域知識仍可能造成效率下降。

**討論可見性限制：** 原文頁面讀取時顯示 29 則回覆。我查看了 Recent 排序中可讀的回覆、展開可見分支，也查看了 X 顯示的 probable-spam 項目；頁面有一則貼文標示為 unavailable，另有可能被排序或折疊的內容，無法保證已看到所有帳號可見性之外或已刪除的回覆。此紀錄不推測不可讀貼文的內容，也不以留言數推定討論完整性。

## 一手資料與可支持的結論

- [DORA 2025 Report](https://dora.dev/research/2025/dora-report/) 將 AI 描述為會放大組織既有優勢與弱點的力量。它沒有比較微服務和單體對 AI 生成程式碼的審查效果；文章只把「AI 會放大工作系統既有能力」用作解讀討論的背景。
- [DORA：Loosely Coupled Teams](https://dora.dev/capabilities/loosely-coupled-teams/) 將鬆耦合結果描述為可獨立設計、測試、部署變更，並說明此能力可存在於單體／大型主機系統；名義上的微服務也可能因相依而無法獨立測試、部署。這支持以實際自治而非服務數量評價邊界。
- [Google Code Review：What to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html) 要求審查設計、功能、複雜度、測試與程式碼健康，且應將改動放在更大的系統脈絡下理解。
- [Google Code Review：Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html) 建議每個 CL 聚焦自洽改動，並把約 100 行描述為常見合理大小、約 1000 行通常太大；這是審查經驗指引，不是跨團隊強制上限。故文章將討論串的 300 行政策定位為團隊案例，而不視為普遍準則。
- [GitHub：About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) 說明 `CODEOWNERS` 可請求指定負責人審查；只有另以 branch protection 要求 code owner 核准，才會把該要求設成合併門檻。
- [Martin Fowler：Microservices](https://martinfowler.com/articles/microservices.html) 描述微服務的獨立部署、擴縮與模組邊界特性，同時說明其分散式系統成本。
- [AWS Prescriptive Guidance：Decompose by subdomain](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-decomposing-monoliths/decompose-subdomain.html) 建議沿著定義清晰的業務子域拆解，並提醒服務過多會增加服務探索與系統整合複雜度。
- [Shopify：Deconstructing the Monolith](https://shopify.engineering/shopify-monolith) 記錄其 Rails 單體元件化、Packwerk 依賴與封裝檢查的實務演進。這是公司工程個案，不是微服務／模組化單體的受控比較。

## 分析與文章決策

可直接支持的區分是：微服務可以成為部署、資源與執行期故障邊界，但不能代替合併前的設計審查、測試及架構約束。若要用 AI 生成速度作為拆分理由，必須另外證明服務邊界能帶來獨立部署、測試、擴縮、資料治理或故障隔離，並納入網路、資料一致性、監控與值班成本。

這是綜合 DORA、Google、GitHub、AWS、Fowler 與 Shopify 等來源而得的工程推論；目前這批來源沒有直接研究「微服務是否更能控制 AI 生成變更品質」。因此文章避免宣稱一種架構普遍勝出，改以兩份檢核清單區分合併前品質控制與上線後故障控制，並連回系列第四篇的模組化單體護欄。
