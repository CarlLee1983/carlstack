## 原文在說什麼

這是作者 2,000+ 小時 AI coding 經驗的個人工作台，而不是產品評測或可重現的效能研究。他把「agentic engineering」拆為：

1. 用 `bb`、cmux、Ghostty、Herdr 與自製 Corral 看見並排序多個 agent 的狀態；
2. 以訂閱而非 API 價格取得更多模型額度；
3. 把長時間 agent 放進自架 VPS，透過 SSH 接續；
4. 依任務選 Pi、Cursor CLI、Claude Code、Codex 等 harness；
5. 將重複流程變成 skills，並加上 guardrails、worktree、ADR、測試與 production 資料讀取權限；
6. 以 commits、agent sessions 與 prompts 的長期趨勢觀察自己的產出。

### 可作為「作者自述」引用的項目

- 他偏好以完成／阻塞／執行中等狀態，及 P1–P4 優先級處理多 agent 的回覆順序。
- 他主張自架 VPS + SSH 可降低本機斷線與睡眠造成的中斷。
- 他建議把重複操作做成 preset／skill，並將重要架構決策寫成 ADR。
- 他主張 production DB 應給 agent 讀取、不可給寫入。

寫法必須是「Ondrej 的工作方式／判斷」，不可轉成普遍事實或成效保證。

### 不可直接採信或不應寫成事實的項目

- 「2,000+ 小時」、「3–4 倍更快」、「雲端 agent 是未來」、「管理 agent 將成為常態」：個人經驗、預測或未提供方法的數字。
- Cursor 內部 merged PR 中 cloud agent 比例、各模型能力／速度／價格、OpenCode Go 與 ChatGPT／Claude／Cursor 的訂閱組合與美元金額：**價格、可用模型、額度、併購／供應商關係皆高度時間敏感**；本研究不驗證，不應入文作比較或推薦。
- 「API pricing 一定最差」、「VPS 十分鐘即可安全完成」：忽略任務量、資安、維運、網路、備援與資料治理成本；不可採用。
- `Corral` 是作者尚未開源的自製工具，沒有可核對的第一方產品文件；不可描述其實作或能力，只能轉述作者說它做 P1–P4 排序。
- `bb`、cmux、Herdr 與其他工具的功能仍在快速演進；所有產品能力都要附來源與研究日期，避免寫成永久規格。
- 「YOLO mode」、「跳過權限」、「VPS 上給 root」不應當作效率技巧推薦；這與最小權限、sandbox、核准與可稽核性相衝突。

## 建議文章主論點：介面不是控制平面

不要寫「我的 2026 agent 工具清單」。可寫成：**當一人同時跑多個 coding agent，真正需要先設計的不是更多終端分頁，而是可觀測的工作狀態、可中斷的優先級、隔離的執行環境，以及模型外強制的驗收與權限。**

建議用一個最小控制迴路收束工具選型：

```text
任務契約 → 排程／優先級 → 隔離工作區 → agent 執行 → 測試與 review 證據 → 人類或平台 gate → 可接續的狀態／決策紀錄
```

文章可先讓讀者回答四個問題：

1. 同時完成的多項工作，哪一項應先由人處理？（狀態與 priority）
2. 兩個 agent 能否互相覆寫檔案或污染本機環境？（worktree／sandbox）
3. session 中斷後，下一個人或 agent 能否從 repository 找回決策與證據？（ADR、repo instructions、trace）
4. 哪些動作由模型建議，哪些必須由 DB、CI、branch protection、approval policy 強制？（權限與驗收）

只有這些答案出現明確瓶頸，才挑選 bb／cmux／Herdr／VPS 等介面；小型、單一工作線先用既有 terminal、branch、CI 即可。這也避免把「可同時開 20–30 個 agent」誤當成導入門檻。

## 需要刻意保留的邊界

### 狀態與優先級

Herdr／cmux／bb 能改善可見性，但「done」最多表示 agent 或介面回報的狀態。真正的完成應由 task contract、CI、review 與 production gate 共同定義。優先級也不能只按 agent 完成時間；至少需納入使用者影響、阻塞關係、風險與人工處理成本。

### 雲端、自架 VPS 與供應商鎖定

遠端主機能讓 session 在筆電離線後持續，不等於雲端 agent 的隔離、秘密管理、權限撤銷、備份、觀測與 incident response 都已完成。文章可以把 VPS 定位成「自行承擔操作責任的持久 worker」，列出 SSH key、最小權限 service account、network allowlist、secrets、更新與 audit 的成本；不要使用「幾分鐘就取代 cloud agent」的敘述。

### Skills、guardrails 與 aliases

skill 適合封裝已重複且可驗證的流程；guardrail 適合限制不該發生的動作。兩者都不是 access control 的替代品。將 `--dangerously-skip-permissions` 或等價的 YOLO alias 寫進文章，會鼓勵移除必要的安全邊界，應明確排除。

### ADR、測試與 review

ADR 的價值是記錄「程式碼無法表達的決策背景」，但只為核心且仍有效的決策寫短紀錄，並連到實作與淘汰狀態；不要把每個選擇變成文件負債。測試依風險與穩定 test surface 選擇，反對測試膨脹不等於鼓勵「不要測」；單一 agent 也不應是唯一 reviewer。

## 建議最小文章結構

1. 從「多個 agent 完成時，誰先拿走你的注意力？」開場，而非列出軟體名稱。
2. 定義狀態面：working／blocked／needs-review 與 P1–P4；說清楚狀態不等於驗收。
3. 定義隔離面：少量工作用單 checkout；衝突開始出現才使用 Git worktree；遠端 worker 要算入營運與權限成本。
4. 定義治理面：skills 是可重複流程，DB／branch／sandbox／approval 才是強制邊界。
5. 以一個單 repository、低風險、兩條並行工作線的導入檢查表收尾，量測 review wait、返工、CI failure 與人工介入，而非 token、session 或 pane 數量。

## 發布前核對清單

- 保留原始 X URL；若 X 仍不可讀，將其內容清楚標為作者自述，勿以轉載頁支撐外部事實。
- 每個產品能力只寫已列出的官方文件；更新模型／價格相關句子時，當日重新查官方 pricing／changelog，並註明日期。
- 不推薦權限 bypass、root agent、共享 production credentials 或不受限制的自架 VPS。
- 對「read-only production DB」補上 schema/table 範圍、RLS／敏感資料、secret rotation、查詢資源限制與 audit 的限制，而不是提供通用 production SQL。
